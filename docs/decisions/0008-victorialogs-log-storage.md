# ADR-0008: VictoriaLogs for HSM server log storage in the docker-compose deployment

**Status:** Accepted
**Date:** 2026-09-28
**Supersedes:** —

---

## Context

Operators and AI agents need to search HSMServer logs: by time, level, logger, and message text. Today the logs are pipe-separated text files under `Logs/`, which means downloading files and grepping by hand. The supported Docker Compose deployment (ADR-0007) is the environment to improve; Windows bare-metal deployments are out of scope for v1. The server logs through NLog with a sink-level credential redaction wrapper (`${hsm-redacted}`, `hsm_pat_` tokens) that must survive any new pipeline unchanged.

A design session (#1470) walked the full decision space: store, shipper, format, read path, auth, retention, and enablement.

## Decision

Add an infra-only `logs` profile to docker-compose.yml (issue #1470), with no .NET code changes (the one nlog.config target ships inside the app image):

- **Store: VictoriaLogs** (upstream `victoriametrics/victoria-logs`, version-pinned, single container). Chosen over alternatives below. Retention via `-retentionPeriod` (`VL_RETENTION_PERIOD`, default 30d, minimum 1d), 512 MB cgroup memory limit, data in a named volume. Disk usage is capped by `-retention.maxDiskSpaceUsageBytes` (`VL_RETENTION_MAX_DISK`, default 10GiB): past the cap VictoriaLogs drops the oldest whole per-day partitions automatically and always keeps the last two days; the percent-based variant of the flag is not used because the named volume shares the host filesystem (a `du` one-liner for checking usage is documented in `aicontext/architecture/docker.md`).
- **Format at source: an additive single-line JSON NLog target** in `src/server/HSMServer/nlog.config` (fields: `_time`, level, logger, thread, traceId, `_msg` incl. exception; `${hsm-redacted}` preserved inside the JSON attributes). The rule is gated on `HSM_STRUCTURED_LOGS=true`, set only by the compose `app` service, so other deployments are unaffected. `JsonLayout` escapes newlines: one event = one line. The field names are VictoriaLogs' reserved ones (`_time`, `_msg`), so the file collector maps them directly. `_time` is UTC round-trip ISO 8601 (`${date:universalTime=true:format=o}`): an explicit `Z` designator keeps it correct even if the app container's `TZ` is later changed.
- **Shipping: vlagent (VictoriaLogs' vendor-native agent), file-collector mode.** The file under `Logs/` is the source of truth and the single shipping source; the app never talks to VictoriaLogs. vlagent (upstream `victoriametrics/vlagent`, version-pinned to the same v1.52.0 as the store, 128 MB cgroup memory limit) mounts `./Logs` read-only, tails `HSM-structured-log-*.json` (`-fileCollector.glob`; `-fileCollector.msgField=_msg -fileCollector.timeField=_time` pin the mapping; every other attribute becomes an individual log field, and the default `hostname`/`file` stream fields are kept), and ships to `http://victorialogs:9428/insert/native` on the compose network — ingest is never exposed outside it. **Durable delivery is vlagent's, not the app's:** reading-position checkpoints and the unsent-data buffer live on disk in the named volume `vlagent-data` (`-remoteWrite.maxDiskUsagePerURL=1024MB`, oldest data dropped when full), so vlagent restarts resume exactly where they stopped and a VictoriaLogs outage is absorbed by the buffer and replayed automatically when the store returns — no manual backfill. No ports are published; like the store's image, vlagent's has no shell, so there is no in-container healthcheck (`/health` and metrics answer on :9429 inside the compose network).
- **Read path: through the existing Caddy** on the web ports, same origin and TLS as the UI. `/select/vmui` (built-in web UI) and `/select/logsql/*` (query API) route to VictoriaLogs behind Caddy `basic_auth`; credentials (`VL_UI_USER`/`VL_UI_PASSWORD`) live in `.env`, and the existing caddy entrypoint bcrypt-hashes the password so the plaintext never reaches the Caddyfile or the adapted configuration. In the pinned VictoriaLogs version the built-in UI is served under `/select/vmui` (the `/vlui` path of older releases does not exist). Nothing else is proxied: `/insert/...` is compose-network-only. The routes disappear entirely when the credentials are unset. **Default-off:** `.env.example` ships the `VL_UI_*` pair commented out, so a fresh install stores logs but exposes nothing until the operator opts in; the entrypoint additionally refuses the published `change-me` placeholder (case-insensitive) and passwords shorter than 12 characters. The Caddyfile/entrypoint change ships as a new pinned hsm-caddy image tag (2.11.4-2) per ADR-0007.
- **Enablement:** VictoriaLogs and vlagent run under `profile: logs`; `.env.example` ships `COMPOSE_PROFILES=logs` so storage is on by default for fresh installs and disabled by removing one line. The app-side gate `HSM_STRUCTURED_LOGS` defaults to `false` in docker-compose.yml (`.env.example` sets `true` alongside the profile): a deployment that upgrades only docker-compose.yml, with an `.env` predating log storage, gets neither the containers nor the JSON log file — no silent second copy of every Info+ event on disk. The public read routes are a separate, deliberate opt-in via the `VL_UI_*` pair.

## Consequences

- Operators and agents get time-, level-, logger-, and message-scoped search over server logs with no new external dependencies beyond two upstream images (store + agent) from the same vendor and release train.
- Log flow starts only when an app image containing the new nlog.config target is released; until then vlagent sees no matching file. The compose, vlagent, and Caddy pieces deploy independently.
- **Delivery is durable, not best-effort:** checkpoints and the on-disk buffer (named volume `vlagent-data`, keep it across upgrades) survive vlagent restarts and VictoriaLogs outages, and replay is automatic. **Rotation edge case residual (accepted):** NLog archives yesterday's file into `Logs/Archives/` at the daily rotation (the files are named `.zip` but stored uncompressed NDJSON since NLog 6) and vlagent does not read the archives, so a vlagent outage spanning the rotation moment can leave that day's tail absent from the store (it stays in the archive file; the archive files on disk remain the ultimate backstop). Wiping `victorialogs-data` while keeping `vlagent-data` also leaves a gap, because the checkpoints already mark everything as shipped; recovery means replaying archive files by hand through VictoriaLogs' generic HTTP insert API — an archive is already the exact NDJSON `/insert/jsonline` ingests, so it can be POSTed as-is (no unzip; unzipping would fail).
- The basic-auth credential is **separate from HSM users/roles**: access equals knowledge of the password. Rotating it means editing `.env` and `docker compose up -d` (the hash is regenerated per start).
- **bcrypt cost 10 residual (accepted):** the entrypoint hashes at cost 10 instead of Caddy's default 14. This Caddy also terminates TLS for sensor ingestion, and every *failed* basic-auth attempt pays the full bcrypt cost (only successful checks are cached), so cost 14 would let unauthenticated traffic with random `Authorization` headers burn Caddy CPU and degrade ingestion — a denial-of-service lever on the public listeners. Cost 10 is tens of milliseconds per verification; the compensating control is the enforced 12+ character random password. Unauthenticated traffic still burns *some* CPU per request — accepted; revisit with rate limiting or an IP allowlist only if it is seen in practice.
- Same-origin residual: the VictoriaLogs UI is served from the same origin as the HSM web UI, so an XSS in the VictoriaLogs UI could ride an HSM session cookie (HttpOnly prevents reading it, not reusing it). If this ever matters, moving the UI to a subdomain is a one-line Caddyfile change.
- Disk usage on the log volume is capped at `VL_RETENTION_MAX_DISK` (default 10GiB): past the cap VictoriaLogs drops the oldest whole per-day partitions and always keeps the last two days, so growth beyond the cap is possible only when those two days alone exceed it (raise the cap or lower retention then).
- **Archive-file disk cost:** `VL_RETENTION_MAX_DISK` caps only the store's named volume. The app's `jsonfile` target keeps up to 60 daily archive files (`maxArchiveFiles="60"`) of uncompressed NDJSON under `Logs/Archives/` (named `.zip` because NLog 6 removed `enableArchiveFileCompression` from FileTarget), so budget roughly 60× the daily Info+ JSON volume on the `Logs/` disk. Adding `archiveAboveSize` to bound a single day's archive sooner was considered and declined: it mixes size-based rotation with `archiveNumbering="Date"`, whose interaction is untested; the 60-file cap already bounds the total.
- Redaction is inherited, not duplicated: the JSON target wraps message and exception in the same `${hsm-redacted}` wrapper as the text targets, so `hsm_pat_` tokens are redacted before the line ever reaches disk.
- The `jsonfile` rule sits **below** the `Microsoft.AspNetCore*` final rule in `nlog.config`, so the JSON file — and through it vlagent and VictoriaLogs — receives the same Info+ stream the text targets keep: per-request ASP.NET framework noise (5–8 Info lines per HTTP request, dominated by sensor ingestion) stays out in Debug and Release alike, and the JSON volume tracks application events, not request rate. `NlogConfigTests` pins the rule order.

## Alternatives Considered

- **Loki + LogCLI:** rejected because a usable UI needs Grafana, and Grafana integration is deprecated in HSM (2026-09-14); shipping a deprecated stack for log search was not acceptable.
- **ELK / OpenSearch:** rejected as overweight for a single-node compose deployment (multi-service JVM stack, memory footprint, operational surface).
- **Quickwit:** rejected on UI grounds — its search UI story did not meet the operator-facing goal.
- **Seq:** rejected on licensing — the free tier's limits and license terms do not fit an open-source server product's bundled deployment.
- **Shipper: three rounds.** The v1 implementation landed a **Vector** sidecar (file tail → remap → HTTP sink); the round-1 review surfaced two problems: the documented two-file install never fetched `vector/vector.toml` (Docker turned the missing bind source into a root-owned directory and the shipper restart-looped), and the wiring depended on four upstream mechanics found only by trial (no native `victoria_logs` sink in Vector 0.58, `/insert/jsonl` renamed to `/insert/jsonline`, framing defaults sending JSON arrays, no default CMD). v2 dropped the sidecar for **direct posting from NLog** (WebService target from the `NLog.Targets.WebService` package, JsonPost with a single nameless JsonLayout parameter, exactly the NDJSON line `/insert/jsonline` expects) — zero extra containers, but delivery was best-effort by design: NLog has no durable remote buffer, so a prolonged store outage left a gap whose documented closure was a manual curl. The final round replaced it with **vlagent**: the vendor-native agent gives the same no-touch wiring (one image, no config file, reserved field names parsed natively) *and* durable delivery — checkpoints plus an on-disk buffer with automatic replay — which NLog could not provide. The on-disk files remain the source of truth; the store is a searchable derivative.

## Phase 2

Agent access without the shared basic-auth credential is planned as MCP log-query tools on the #1391 track (HsmApiToken auth, no second credential). The query API exposed here is the same one those tools will call.
