# Скиллы Мэтта Покока в HSM — как начать

Документ для разработчиков команды. Читается за 10 минут, после чего можно работать.

## Что произошло

В репозиторий вендорен набор инженерных скиллов [mattpocock/skills](https://github.com/mattpocock/skills) — 21 штука, снимок версии 1.2.0. Это **трайал**: мы проверяем, лучше ли этот способ работы того, что у нас сложилось. По итогам решим — оставить, оставить частично или откатить.

Скиллы лежат в репозитории (`.claude/plugins/matt/`), а не устанавливаются каждым по отдельности. Версия у всех одна — коммит `master`. Обновление приезжает обычным `git pull`.

## Первый запуск

1. `git pull` на `master`.
2. Claude Code при первом открытии проекта предложит подключить маркетплейс `hsm` и включить плагин `matt@hsm` — согласиться. Ставить руками ничего не нужно.
3. Перезапустить Claude Code.
4. Проверить: набрать `/matt:` — должен выпасть список из 21 скилла.

## Что изменилось в привычках

| Было | Стало |
|---|---|
| `/create-issue` | заморожена на время трайала (лежит в `.claude/commands-parked/`). Вместо неё — `/matt:to-spec` или `/matt:to-tickets` |
| `/work-issue` — от issue до draft PR целиком | осталась, но только про **git-механику**: свежий `master`, имя ветки, draft PR, `Closes #N`. Думание отдаёт скиллам. Прежняя версия целиком лежит в `.claude/commands-parked/work-issue-full.md` |
| `/release-collector`, `/release-server` | не изменились, работают как раньше |
| Правила проекта в `AGENTS.md` | переехали в `CLAUDE.md`; `AGENTS.md` остался двухстрочной заглушкой |
| `@claude` в комментариях к issue и PR | **удалён**. Агент по запросу из комментария больше не запускается ни у кого |
| Ревью PR роботом | без изменений: `claude-review.yml`. Срабатывает на **каждый push в non-draft PR**, а также при открытии и в момент перевода draft → ready. Каждый прогон — платный вызов API |

Плюс в репозитории появились метки триажа: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`. Пятая из канонического набора — `wontfix` — была у нас и раньше, её создавать не пришлось. Они описывают **стадию** issue и живут рядом с нашими тематическими (`bug`, `collector`, `cpp-port`).

## Главное: как работать

Полная карта потоков — в самом наборе: **`/matt:ask-matt`**. Это роутер: описываешь ситуацию, он говорит, какой скилл применить. Не запоминай 21 имя, запомни одно это.

Основной маршрут оттуда, коротко:

```
идея → /matt:grill-with-docs → /matt:to-spec → /matt:to-tickets → /matt:implement
                                                                    └─ внутри: /matt:tdd, /matt:code-review
```

- **`/matt:grill-with-docs`** — допрос по одному вопросу за раз, чтобы идея стала конкретной. Ведёт `CONTEXT.md` и ADR по ходу.
- **`/matt:to-spec`** — превращает разговор в спеку и публикует issue.
- **`/matt:to-tickets`** — режет план на тикеты со связями блокировки.
- **`/matt:implement`** — строит по тикету.

Спека и тикеты — это ветка для работы, которая не влезает в одну сессию. Небольшая правка идёт сразу в `/matt:implement`, в том же окне контекста, без спеки и тикетов.

Он-рампы (ситуации, с которых работа начинается):

- **входящие баги и запросы** → `/matt:triage`
- **что-то сломалось** → `/matt:diagnosing-bugs`
- **огромный туманный кусок** → `/matt:wayfinder`

**Контекстная гигиена.** Шаги от грилинга до тикетов держать в одном окне контекста, не компактить. Каждый `/matt:implement` — с чистого листа, от тикета. Если окно подходит к пределу раньше времени — `/matt:handoff` и продолжить в свежей сессии.

### Где в это встраивается `/work-issue`

Скиллы Мэтта не трогают ветки, draft PR и `Closes #N` — `/matt:implement` берёт спеку как данность и заканчивается коммитом. Поэтому у нас:

```
/work-issue 1234     ← ветка от свежего master + draft PR
   └─ внутри: /matt:implement, при необходимости /matt:tdd, /matt:diagnosing-bugs
```

Правило про синхронизацию `master` перед веткой оплачено кровью на #1297 — фикс уехал против UI, который днём раньше заменили сквош-мержем. Не пропускайте этот шаг.

## Что у нас намеренно расходится с апстримом

1. **Документы задвоятся.** Скиллы ожидают `CONTEXT.md` в корне и `docs/adr/`. У нас канон — `aicontext/` и `docs/decisions/`. Мы сознательно не стали подгонять скиллы под себя: иначе трайал мерил бы нашу раскладку, а не их подход. Когда `/matt:domain-modeling` создаст `CONTEXT.md` — это ожидаемо, а не поломка. Что с этим делать, решим в конце.
2. **Два процесса ревью.** `/matt:code-review` (стандарты по смеллам Фаулера + сверка со спекой) конкурирует с нашим `aicontext/architecture/development_lifecycle/technical_review_orchestration.md`. Сравнить их — одна из целей трайала.
3. **Правила репозитория никто не отменял.** Всё из `CLAUDE.md` действует как раньше: правило #9 про конформанс-покрытие, обратная совместимость публичного API коллектора, net6.0 + net472, никаких русских комментариев в коде. Скилл, который предложит их нарушить, — неправ.

## Грабли

- **Скиллы есть только на ветках от `master`** после мержа. Если работаешь на старой ветке, отведённой раньше, — `/matt:*` там не найдётся. Перебазируйся.
- **Правки в самих скиллах доезжают только после коммита.** Версия плагина — это коммит `master`; в грязном дереве работает старая копия из кэша. Проверить правку до коммита: `claude plugins uninstall matt@hsm --scope project && claude plugins install matt@hsm --scope project`.
- **Выключить отдельный скилл** = перенести его папку: всё в `.claude/plugins/matt/skills/` грузится, всё в `skills-off/` — нет. Даже если добавить в манифест поле `skills`, фильтром оно не станет — папка сканируется независимо от него.
- **`.claude/plugins/**` — это код, а не документация.** Скиллы — инструкции, которые агент исполняет, а формат плагина допускает ещё и хуки с MCP-серверами. Ревьюить соответственно.

## Что мы меряем

Трайал имеет смысл, только если в конце будет ответ. Полезнее всего сравнения на одной и той же задаче:

- `/matt:grilling` против обычного обсуждения — ловит ли дыры в плане, которые вы бы пропустили;
- `/matt:code-review` против нашего role-based ревью — чьи находки полезнее на одном и том же PR;
- `/matt:to-spec` против нашего старого `/create-issue` — какой issue лучше читается через неделю.

Наблюдения складывайте в issue с меткой `needs-triage` и словом «skills-trial» в заголовке — по ним и будем решать.
