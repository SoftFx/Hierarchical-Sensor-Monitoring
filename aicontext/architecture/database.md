# Database Architecture

> Owner: shared | Last reviewed: 2026-11-20 | Canonical: yes

## Overview

HSM stores application data in an embedded **LevelDB** database through `HSMDatabase.LevelDB` / `SoftFX.LevelDB.Standard`. No external database service is required.

## Projects

| Project | Purpose |
|---|---|
| `HSMDatabase` | Abstract interfaces (`IDatabaseCore`, `ISnapshotDatabase`) and settings |
| `HSMDatabase.LevelDB` | LevelDB implementation of database interfaces |
| `HSMDatabase.AccessManager` | Data access layer with entity formatting and typed read/write operations |

## Data Stored

- Sensor history values (all types: bool, int, double, string, timespan, version, bar, file)
- Product metadata and access keys
- User accounts and roles
- Sensor configurations and policies (TTL, alerts)
- Journal entries (audit log)
- Tree snapshots

## Key Design Points

- Database is embedded in the server process — no network overhead
- Data path is configured via volume mount (`/app/Databases`)
- Backup via SFTP to `DatabasesBackups` volume: the environment and server layout databases only; the weekly history databases (rows and sealed chunks) are not backed up
- `ConcurrentStorage<T>` pattern: in-memory cache synced with LevelDB on writes
- Serialization uses MemoryPack for high performance
- **A failed write of a sensor or product row is logged, not thrown.** `EnvironmentDatabaseWorker` catches the exception of the LevelDB `Put`, writes an `Error` line and returns, and `IDatabaseCore.AddSensor` / `UpdateSensor` are void: their callers are not told. One caller has to know, the registration of a sensor by a collector (#1756: a registration answered as applied is not sent again). It uses the checked variants, `IDatabaseCore.AddSensorChecked` / `UpdateSensorChecked` (over `IEnvironmentDatabase.WriteSensorIdToList` / `WriteSensor`), which do the same writes and return the failure, or null when the row was written; nothing is thrown there either. In the worker the void methods are the checked ones with the outcome dropped, so the two cannot drift apart; `AddSensorChecked` differs from `AddSensor` only in what it does after a failure (it does not write the row when the id list could not be written, and takes the id off the list again when the row could not). Do not move another caller to the checked variants without deciding what it does with a failure: today a failed write leaves the object in memory and the next save writes it.

## Weekly Shards and Their Compaction

Sensor history and the presentation journal are split into one LevelDB database per week (`SensorValuesV2_<from>_<to>` under the database folder, `JournalValues_<from>_<to>` under `Journals/`; Monday 00:00 to the next Monday). `ValuesDatabaseDictionary<T>` discovers the shard directories at startup and opens each one lazily, on first use; `GetShards()` lists them without opening any.

A closed history week can be **sealed** (ADR-0020): its rows encoded into chunks in a sibling LevelDB database `SensorValuesSealedV1_<from>_<to>`, complete only when it holds the file `hsm-sealed`. When the week is opened, `LevelDBManager` then serves it with `SealedSensorValuesDatabase` instead of `SensorValuesDatabaseWorker`: the row database stays as the overlay, reads merge it with the chunks, writes go to it, range deletes rewrite the chunks they touch. A week whose chunk directory exists without the marker is served from its rows alone. `SensorHistoryDbSize` counts both directories of a week. Layout, merge rule, range-delete crash states and error reporting: `aicontext/features/storage/sealed-history/feature.md`, section "Sealed week store".

Weeks are sealed by the **sealing job** (#1804, `HistorySealingService` → `IDatabaseCore.RunHistorySealingPass`, off by default: `HistorySealing.Enabled`). Every history week sits behind a `SensorValuesWeek` handle in the shard dictionary, which lets the job swap a week from rows to sealed (and back, for an unseal) while the server runs. A pass takes one action on one week, chosen by `HistorySealingPlanner` (pure, unit-tested): finish an interrupted unseal, remove the source rows of a sealed week whose keep period ended, seal a closed week, or fold a sealed week's overlay. A pass enters the same compaction state as the two compaction paths below, so sealing, folding, unsealing, the background compaction and the manual Compact never run at the same time, and shutdown waits for a running pass (which also stops at its next safe point once disposal has begun). Its stages live in marker files next to `hsm-sealed`, in the week's own directories. Design, markers, crash states and configuration: the feature doc, section "Sealing job".

Rewritten and deleted rows stay in a shard's files until a LevelDB compaction merges them, and a week nobody writes to any more is not compacted on its own (a production week measured 65 MB before and 23 MB after `Compact()`). Two paths compact:

- **Manual:** the Compact button (`HomeController.Compact` → `IDatabaseCore.Compact`) compacts the environment database and every shard, the current week included, in one go. It writes the compaction marker into every closed shard it compacted (not into the current week's: it is still being written, and the background step compacts it once it has closed), so the background step does not compact those shards again.
- **Background (#1801):** `HistoryCompactionService` calls `IDatabaseCore.CompactNextDueHistoryShard` every 10 minutes (first pass 10 minutes after start). Each call compacts **at most one** shard, so the backlog of the first run after an upgrade (every closed week, sensor and journal) drains one shard per pass instead of in one burst. The newest due week goes first; on the same week the sensor shard before the journal shard.

  It is **off by default** and confined to a daily window: section `HistoryCompaction` of `Config/appsettings.json` (`HistoryCompactionConfig`, read once at startup, written back with its defaults, validated with an error that names the key):

  | Key | Default | Meaning |
  |---|---|---|
  | `Enabled` | `false` | Off: a pass does nothing and opens nothing. Off by default so that an upgrade changes nothing on disk until the operator says so: the first run after it finds every closed week due, and on a large deployment (more than a hundred weekly shards of up to several GB) that is about a day of continuous rewriting (`HistoryCompactionConfig.DefaultEnabled`). |
  | `WorkingHoursStartUtc`, `WorkingHoursEndUtc` | `"00:00"`, `"00:00"` | Daily UTC window, `HH:mm`; equal values mean all day, a window may wrap past midnight. Same parsing and semantics as `HistorySealing` (`DailyUtcWindow`). Outside it a pass does nothing. |

  The check lives in the service; `IDatabaseCore.CompactNextDueHistoryShard` itself compacts whenever it is called. A compaction that is running when the window ends is not interrupted (a LevelDB compaction cannot be), so the work may overrun the window by one shard. At construction the service logs `History compaction is off (HistoryCompaction.Enabled)`, and a Warn when `HistorySealing.Enabled` is true at the same time (sealed weeks do not get smaller on disk after their source rows are removed until this step runs, see below); when on, a start line names the window and the first pass (`History compaction is on: one closed history shard per pass[, working HH:mm-HH:mm UTC]; first pass at <UTC>, then every 10 minutes`). The switch does not affect the manual Compact below nor the compaction a seal does of its own chunk database; neither goes through this service.

A shard is due (`HistoryShardCompactionPlanner`, pure and unit-tested) when all of these hold:

- its week began before the current week did: the current week and any later one are never compacted by the service;
- it carries no compaction marker: it was never compacted, or it had a reclaimable change since;
- it has had no reclaimable change for the quiet period (3 hours, longer than the hourly retention pass): a shard still being trimmed waits until that stops instead of being compacted after every trim. A shard with no reclaimable change since the server started counts the quiet period from the start (`DatabaseCore.StartedUtc`, the time the database core was created), opened or not: what changed before the start is not known, so a shard trimmed just before a restart is not compacted minutes after it and again after the next trim;
- no failed attempt holds it back: a failed compaction is logged with the shard name and the shard is retried a day later (in memory; a restart retries at once). Other shards go on meanwhile.

**Reclaimable changes.** Only a change that leaves a compaction something to reclaim counts for the due rule: a delete, or a change made of deletes. That is a clear-history, retention or sensor-removal range delete that finds rows (on a sealed week also one that only deletes or rewrites chunks, its delete watermark included), the sensor-move merge's delete of the source rows, and the sealing job's removal of source rows, fold and unseal (`IntervalDataseBase.OnBeforeDelete`; the job through `MarkChanged`). A plain put does not count (`OnBeforePut`): a value, a journal record, the copy step of a sensor-move merge. A put of a new key leaves no garbage, and the one stale version an overwrite leaves is dropped by LevelDB's own compaction; what piles up in the bottom levels of a closed week comes from deletes. Puts do keep reaching closed weeks: an out-of-order value is written to its own week, an operator's change of the last value (`ChangeLast`) saves that value again under its key, a bar's in-progress bar is saved under its own time at shutdown and before a sensor-move merge, and the merge copies rows under their keys. Until a run of aggregated values (`AggregateValues`) ended at the week boundary, such a sensor also wrote its stored row again under the key of its first value on every equal value, in whatever week the run began, possibly months ago; now a run is folded only within one storage week (see `features/server/overview.md`), and a run an upgraded server finds in an earlier week stops being rewritten with the first value after the upgrade. Were those puts changes, a closed week that keeps receiving them would never be quiet for 3 hours and the space its deletes left (the sealing job's removal of source rows above all) would never be reclaimed. Each shard keeps the count and the time (by `DatabaseCore.Clock`) of its last reclaimable change since it was opened (`ReclaimableChangeCount`, `LastReclaimableChangeUtc`); a separate `WriteCount` counts every put and delete for the sealing job's fold count.

**The compaction marker** is a file named `hsm-compacted` inside the shard directory (`CompactedShardMarker`). It is written after a compaction (background or manual) and removed by the shard worker before any reclaimable change; a put leaves it in place. A range delete that finds no row leaves it in place too. Because it is removed before the data changes, a crash in between costs at most one extra compaction. A reclaimable change that lands while the compaction runs keeps the marker off (`TryMarkCompacted` compares the reclaimable change counter read before the compaction); a put that lands meanwhile does not. If the marker cannot be deleted, the shard still counts as changed in memory and the failure is logged once (not on every later delete); the stale file on disk can make the shard miss one compaction after a restart, which costs space, not data. If the background step cannot write a marker, the step counts as failed and the shard waits for the failure backoff. The marker lives in the shard rather than in the environment database so that it is read without opening the shard, survives a restart, and travels with the shard when the directory is copied, backed up or restored. LevelDB claims only `CURRENT`, `LOCK`, `LOG*`, `MANIFEST-*` and numbered files of its directory and ignores this one.

Each background compaction logs the shard path and its size before and after. The two paths share `IsCompactRunning`, taken with a compare-and-swap (the sealing job takes it too): the service skips its pass while the manual compaction or a sealing pass runs, and the button answers "already running" while a background step runs. A sealing pass that finds the state taken is skipped and logs what held it (#1805). A seal changes no row, so the week keeps its compaction marker and this step does not visit it; the seal compacts the new chunk database itself, outside the week's gate, before it marks the week sealed (#1805). After the sealing job removes a week's source rows, the deletes have already cleared its compaction marker, so this background step compacts the week (rows and chunks) once it has had no reclaimable change for 3 hours, puts into it (an aggregated sensor's row rewritten every minute) notwithstanding, and only when `HistoryCompaction.Enabled` is true and inside its window; the job does not compact it then. A week that the hourly retention pass is trimming is never quiet for 3 hours. On a sealed week retention costs almost nothing since #1805: a delete of a prefix of one sensor's history (retention, clear history, sensor removal) deletes the chunks wholly below its cutoff and records a per-sensor delete watermark in the chunk database instead of re-encoding the chunk the cutoff falls into; other range deletes still rewrite their border chunks (feature doc, "Writes and range deletes"). In the manual path a shard that fails to open or to compact is logged with its name and the next shard goes on.

**Shutdown and compaction exclude each other.** Once `DatabaseCore.Dispose` has begun, no compaction starts (the background step answers `ShuttingDown`, the button is refused), and `Dispose` waits for a running one to finish before it closes any database: a LevelDB compaction cannot be cancelled, and closing a shard under it would free the native database it still uses. A manual run that is going over all databases stops after the shard it is compacting, so the shutdown waits for one shard, not for the rest. The wait is logged with the name of the database being compacted, every 30 s. The server disposes the database after the host has stopped its hosted services, when the DI container is disposed (and once more from `TreeValuesCache.DisposeAsync`; the second call returns at once). The host's shutdown timeout (`HostOptions.ShutdownTimeout`, 30 s by default, not set by HSM) bounds only how long the host waits for the hosted services to stop, so it does not cut this wait short. What can is the process manager: `docker stop` kills the container 10 s after SIGTERM unless `stop_grace_period` says otherwise, and HSM's compose files do not set it. A kill during a compaction is what a crash is to LevelDB: the shard reopens from its last consistent state, keeps no marker, and is compacted again later.

## Table Blocks (#1844)

The blocks of table sensors (ADR-0021) live in `Tables/` under the database folder: `Tables/Blocks` (key `arrival hour | sequence`, both big-endian, value = envelope + the block as received, no compression, synced puts) and `Tables/BlockIndex` (the same key, a derived 84-byte summary per block), plus the durable sequence mark `Tables/hsm-sequence-mark`. Both keys only grow, so LevelDB never compacts during ingest. Nothing is created until the first table sensor or block. Neither the manual Compact nor the background history compaction touch these databases (they compact the environment database and the weekly shards only); freeing the space of deleted hours is the merge step's job (#1850). They are not backed up, like sensor history. Details: `aicontext/features/storage/table-blocks/feature.md`.

## Table Batches (#1850)

The hourly merge packs the blocks of a closed arrival hour into batches per table sensor and keeps them in `Tables/BatchesV1/<productId>/` (the version is part of the folder name): one LevelDB database per Monday-aligned week of the merge hour and per retention period class, `<yyyyMMdd>_P<weeks>` (`P0` = kept forever), and `Hours`, the product's merged hours (one record per hour: the commit point of the merge, and what the read selects hours by). In a week database every key starts with the merge hour (index records, batches, the hour's mark), except a region of moved batches that starts with `0xFF` and lies after every hour key; all of them only grow. Only the databases of the week being written stay open; a closed week is flushed when its week ends and is opened again only for a read or retention, at most `TableSensors.MaxOpenBatchDatabases` at a time (32 by default). Retention drops a week database as a folder. Not backed up, like sensor history. Details: `aicontext/features/storage/table-batches/feature.md`.

## Large Files (#1883)

The content of large file values (ADR-0022) lives in files, not in LevelDB: the folder `LargeFiles.Folder` (`LargeFiles` next to `Databases` by default, `/app/LargeFiles` in the container; it may be another volume), with `uploads/<productId>/<fileId>.part|.idx|.rec` and `archives/<productId>/<archiveId>.zip`. It is not under the database folder, not part of `TotalDbSize` and not backed up, like sensor history. The value row is a `LargeFileValue` (a `FileValue` under MemoryPack union tag 12, so ordinary file rows keep their bytes) holding the description and the file id; the file's state is in its record. Nothing is created until the first upload. A pass of the store's own removes the files of values that are gone, because history removal deletes key ranges and never looks at values. Details: `aicontext/features/storage/large-files/feature.md`.

## Native Libraries

The LevelDB native libraries come inside the NuGet package `SoftFX.LevelDB.Standard` (repository `SoftFx/leveldb.net`), embedded in its managed DLL and extracted at run time: Windows x64, Windows x86 and Linux x64. There is no Linux ARM or macOS library. (`src/lib/runtimes/` holds LMDB binaries, not LevelDB, and nothing in the build uses them.)

## Block Compression (#1815)

Every database is opened through `LevelDBDatabaseAdapter`, which sets the compression of the blocks it writes in one place, `LevelDBDatabaseAdapter.WriteCompression`. LevelDB records the compression of each block, so reading never depends on that setting, only on whether the native library knows the codec.

- **Up to package 1.2.1** the Linux library had no Snappy. Every database a Linux server wrote is uncompressed (sensor rows about 137 B/row against 54 B/row on Windows), and a database written on Windows could not be opened on Linux (`Corruption: corrupted compressed block contents`).
- **Package 1.2.2** has Snappy on Linux, so the server reads Snappy blocks on every platform.
- **Writing, step 1 (the first release on 1.2.2):** Windows writes Snappy, as it always did. Everything else writes uncompressed, so a rollback to a release on 1.2.1 can still read all the data this release wrote. `LevelDBCompressionTests` pins both halves.
- **Writing, step 2 (the next release):** Linux writes Snappy. After it, a rollback past the step-1 release cannot read the new blocks. Old uncompressed blocks shrink only when a compaction rewrites them; `Compact()` does not rewrite an already compacted database. The background history compaction (#1801) marks a compacted closed week (`hsm-compacted`) and skips it afterwards, so step 2 must also make a week compacted under the old write setting due again (for example, record the write compression in the marker).
