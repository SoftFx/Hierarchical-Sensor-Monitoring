# HSM Glossary

> Owner: shared | Last reviewed: 2026-11-27 | Canonical: yes

Canonical terms for Hierarchical-Sensor-Monitoring. Prefer these names in code,
docs, PR descriptions, review comments, and user-facing documentation.

## Core Product Terms

| Term | Meaning | Notes |
|---|---|---|
| HSM | Hierarchical-Sensor-Monitoring product and repository. | Use `HSM` after first expansion when useful. |
| Sensor | A monitored value source identified by a hierarchical path. | Avoid using "metric" when the code/API uses sensor semantics. |
| Bar sensor | Aggregating sensor that collects min/max/mean/count over a time window. | Keep bar period and post period semantics explicit. |
| StdDev (σ) | A bar's population standard deviation, `sqrt(Σ(x − mean)² / Count)`, posted as `StdDev` (#1509) by the native collector only (#1529). | Always population, never sample (n − 1). `null`/absent = unknown, never 0. See `features/server/bar-stddev/feature.md`. |
| Rate sensor | Sensor that accumulates values and reports a rate over a configured period. | Check zero/NaN handling when changing accumulation. |
| Function sensor | Sensor that periodically calls user-provided code and sends the result. | User exceptions must be isolated. |
| Instant sensor | Sensor where the integrator explicitly calls `AddValue()` / `SendValue()`. | Public methods can be called from any thread. |
| Default sensors | Built-in sensors for CPU, RAM, disk, threads, GC, service status, and related metrics. | Platform-specific behavior belongs in collector/default-sensor docs. |
| Sensor path | Full logical path of a sensor in the hierarchy. | Use for identity and navigation. |
| Sensor value | A concrete value sent by a sensor at a point in time. | Includes status and optional comment depending on DTO. |
| Sensor status | Health/status marker attached to a sensor or value. | Examples include OK/error-like states from `SensorStatus`. |
| Product | Server-side logical group of sensors, usually identified by an access key. | Keep distinct from product/application code naming. |
| Node | Hierarchical folder in the sensor tree. | Path example: `Computer/Module/SensorPath`. |
| Module | Logical group under a collector/client that owns sensors. | Do not confuse with .NET project/module. |
| Environment | Server-side scope/grouping used to organize monitored systems. | Confirm exact behavior in server docs before changing. |
| Dashboard | Operator-facing view for monitoring selected HSM data. | Use for UI dashboards, not arbitrary charts. |

## Collector Terms

| Term | Meaning | Notes |
|---|---|---|
| DataCollector | .NET library entry point used by applications to register sensors and send values. | Public API compatibility matters. |
| DataProcessor | Internal collector component that owns queues, sensor storage, deduplication, and sending flow. | Internal term; avoid in user docs unless troubleshooting internals. |
| Sensor storage | Collector-owned registry of sensors. | Prefer `SensorsStorage` only when referring to the class. |
| Collector scheduler | Per-collector scheduler used for periodic sensor work. | Avoid "global timer" for new docs. |
| Sync queue | Collector queue that buffers values before send. | Document lifecycle and backpressure when changed. |
| Message deduplicator | Collector helper that groups repeated error/log messages within a time window. | Use when describing error-noise reduction. |
| Package sending info | Result metadata for sending a batch, including content size and optional error. | Code term: `PackageSendingInfo`. |
| Polly pipeline | Retry pipeline wrapping HTTP requests. | Watch `ShouldHandle` behavior for HTTP status codes. |

## Server And Storage Terms

| Term | Meaning | Notes |
|---|---|---|
| HSM Server | ASP.NET server application hosting API, site, background services, and storage access. | Use instead of just "backend" in public docs. |
| HSM Server Core | Shared server domain/core project. | Code/project term. |
| Self-monitoring | The server watching itself: a dedicated product ("HSM Server Monitoring") where the server reports its own health and traffic the same way collectors report customer products. | The operator's surface for server-side performance questions; home of the token usage sensors. The server finds the product by its name at every start, so the name is fixed: the product cannot be renamed. Say "self-monitoring", not "telemetry" (too generic) or "internal metrics". |
| LevelDB storage | On-disk database implementation used by HSM. | Mention LMDB/native dependencies only when relevant. |
| Weekly shard | One LevelDB database holding one week (Monday to Monday) of data. The general term for both kinds: sensor history shards (`SensorValuesV2_<from>_<to>`) and journal shards (`Journals/JournalValues_<from>_<to>`). | A shard is closed once its week has ended; only the current week takes ordinary writes. |
| Compaction marker | The `hsm-compacted` file inside a weekly shard: the shard was compacted and has had no reclaimable change since (#1801). | Removed before any reclaimable change (a delete, or a change made of deletes); a put leaves it. See `architecture/database.md`. |
| Reclaimable change | A change to a weekly shard that leaves a LevelDB compaction something to reclaim: a delete, or a change made of deletes (a range delete that finds rows, a chunk rewrite, the sealing job's removal, fold and unseal). A put is not one (#1801). | Drives the compaction marker and the background compaction's quiet period; see `architecture/database.md`. |
| Snapshot | Persisted or cached representation of current tree/state. | Be explicit: tree snapshot, sensor snapshot, or database snapshot. |
| Aggregated row | One history row standing for a run of equal values of a sensor with Aggregate values on (`AggregateValues`): key = the first value's time, `LastReceivingTime` = the last one's, `AggregatedValuesCount` = the run length. A run ends at a different value, a timeout, or the storage-week boundary (Monday 00:00 UTC), so it never spans two history shards; rows written before that rule can. | Folding a value into it is not the sealing job's Fold. See `features/server/overview.md`. |
| History shard | The weekly shard that holds sensor history, one row per value (`SensorValuesV2_<from>_<to>`). | See Weekly shard. |
| Sealed week | A closed week whose sensor history has been encoded into chunks (ADR-0020), in `SensorValuesSealedV1_<from>_<to>` next to its row database; it counts as sealed only once that directory holds the `hsm-sealed` marker. Read and changed by `SealedSensorValuesDatabase` (#1803); sealed by the sealing job (#1804). | The opposite is a week still held as rows. Do not call it "archived": the data stays online and readable. |
| Chunk | A bounded run of one sensor's history rows encoded as one stored value in a sealed week. | Not a LevelDB block and not a Parquet row group. |
| Overlay | The row database of a sealed week, holding what was written to that week after sealing. | On an equal key the overlay row wins over the chunk. During the keep period it also still holds the source rows. |
| Sealing job | The background job that seals closed weeks, removes their source rows after the keep period, folds overlay rows into chunks and finishes unseals (#1804). Off by default (`HistorySealing.Enabled`). | One action on one week per pass; shares the compaction state, so it never runs with a compaction. |
| Source rows | The rows of a week as they were when it was sealed; after the seal they stay in the overlay for the keep period. | Removed only where they still equal their chunk row. |
| Keep period | How long the source rows of a sealed week stay after a verified seal (`HistorySealing.KeepSourceRowsWeeks`); the end time is written into the week's `hsm-keep-source-rows-until` file. | ADR-0020, decision 8. |
| Fold | Re-encoding a sealed week's overlay rows (late values, edits) into its chunks, then removing the overlay rows that equal the new chunk rows. | Not "merge": the sensor-move merge is a different operation. |
| Unseal | Turning a sealed week back into rows (an operator's action on the Configuration page); the week is then never sealed again until its `hsm-unsealed` file is deleted. | Rows come back with the fidelity of the codec (`ReceivingTime` to the millisecond). |
| Week needing attention | A history week the sealing job will not touch until an operator acts: a chunk directory that lost `hsm-sealed` (it may hold the only copy of the week), an unreadable keep time, or an unreadable chunk during source-row removal or an unseal (#1804). | Reported by the self-monitoring sensor `Weeks needing attention`; the feature doc lists what to do for each cause. |
| Table sensor | A sensor whose data is a table: rows ordered by time with a fixed set of typed columns (ADR-0021). It has no per-row statuses, alerts or comments. | Not a File sensor (opaque bytes) and not a set of ordinary sensors, one per column. |
| Table schema | The ordered list of named, typed columns of a table sensor, the first being the time; fixed when the sensor is registered. | A different shape is a different sensor. |
| Schema id | The CRC-32 of a table schema's canonical bytes (column types and names); carried by every block entry, computed by collector and server alike, never exchanged. | Not an index into a list of schemas; the server also compares the column types. |
| Block | What a collector sends for table sensors: the rows of all its table sensors for one tick, grouped by table, as raw columns under one zstd frame (ADR-0021). The server stores a block as it arrived until its hour is merged. | The only table format outside the server. Not a package of values and not a LevelDB block. |
| Null map | Which rows of one column of a table hold no value: one bit per row, least significant first, set = null (#1859). Every column but the time may have one. A block carries a column's map only when that column has a null in the block; the cells it marks hold zero. | Not a column of the schema and not a schema property: the schema says nothing about nulls, all but the time are nullable. A null is not 0 and not NaN: the 0 in the cell is filler, the map is the truth. |
| Batch | The stored form of table rows after the merge: up to 4,096 rows of one table sensor, coded with the column coders of sealed history and zstd. Internal to the server. | Not a chunk: a chunk holds the history rows of an ordinary sensor in a sealed week. Not a block: a block holds many tables and is what travels. |
| Batch exception | A value of a double column of a batch that is not a decimal of the column's exponent, stored aside with its index and its 8 raw bytes so that the rest of the column keeps the decimal mode: at most max(1, n / 256) of the column's n present values (#1850, `aicontext/features/storage/table-batches/feature.md`). | Not a .NET exception, and not a null: an exception is a value. |
| Feed sensor | An ordinary sensor the server keeps under `.tables` in a table sensor's product, posted per period from the blocks it stores and the hours it merges (rows, stored MB, delivery lag, refused tables, blocks the merge could not read; rows per table sensor). Users set alerts and TTLs on it (#1847, `aicontext/features/server/table-feed-sensors/feature.md`). | Not a table sensor and not self-monitoring: it lives in the user's product, not in the server's own. A table sensor has no alerts; its feed sensors do. |
| Arrival hour | The hour in which the server received a block; the first part of the block key. | Not the time of the rows: a late block has a later arrival hour. |
| Block store | The two LevelDB databases under `Tables/` that hold blocks as they arrived (`Blocks`) and a derived summary of each (`BlockIndex`), with an in-memory index of every stored block (#1844). | Not the sensor history shards and not the batch databases of the merge (#1850). |
| Block envelope | The bytes the server stores in front of a block: arrival time, product, producer, producer sequence and the refused tables. | Not part of the block format: the block after it is byte for byte what the collector sent. |
| Table connection | The second WebSocket of a collector that has table sensors (#1845, ADR-0021 point 7): subprotocol `hsm.tables.v1` on the session route, tied to the collector's live session by `X-Hsm-Session`. It carries blocks as binary frames, one in flight at a time, each answered with a text acknowledgement. | Not a second session: it takes no slot, lives only as long as its session, and a new one replaces the old. The session itself stays text-only. |
| Table tick | The collector-wide period (`CollectorOptions.TableTickPeriod`; native `hsm_table_options_t.tick_period_ms`; 10 s by default) at which a collector takes the rows of all its table sensors into one block (#1846, ADR-0021 point 6). | Not a timer per sensor and not the send period of value queues (`PackageCollectPeriod`). |
| Table backlog | The packed blocks a collector holds until the server gives each a final answer, sent one at a time in producer-sequence order; bounded by `CollectorOptions.MaxTableBacklogBytes`, the oldest dropped and counted past it (#1846). | Not the row buffer, which holds the rows added since the last tick (`MaxTableBufferBytes`). |
| Producer | Who sends a stream of blocks: a 128-bit id a collector installation makes once and keeps across restarts, next to its file of undelivered blocks (#1845). | One per installation. Two collectors with one producer id (a copied data folder) make each other's blocks duplicates; the server warns. Not the client name and not the access key. |
| Producer sequence | The producer's own number of a block, rising by one per block and never going back; with the product and the producer id it recognises a block sent twice (#1845). | Not the block sequence of the store. A block that got a final refusal is dropped and its number is not reused; a collector that cannot read its producer state takes a new producer id. |
| Producer, producer sequence | Who sent a block (an id a collector keeps across restarts, #1845) and its own number for the block; a stored pair is not stored again. | Not the block sequence, which is the server's number and part of the key. |
| Refused table | A table of a block the server did not take (unknown or blocked sensor, another kind, another schema, an invalid identifier, a sensor newer than the block); recorded in the envelope, never served. | Not a refused block: the rest of the block is stored. A block with every table refused is not stored at all. |
| First sequence | The block sequence a table sensor was created at; blocks numbered before it are never read for the sensor. | Not the time of its first row. |
| Batch merge | The background job that packs the blocks of a closed arrival hour into batches per table sensor, once, verifies them and removes the blocks (ADR-0021, point 9). | Not the sensor-move merge and not a fold. |
| Chart reduction | What the server sends for the chart of a table sensor: the rows of a range reduced to a minimum and a maximum per bucket of time and column, with counts of rows, nulls and non-finite values; a range of at most twice as many rows as buckets also carries its rows (#1847, ADR-0021 point 14, `aicontext/features/server/table-sensors-ui/feature.md`). | Not a sampling of rows (no row is skipped: every row of the range is in its bucket) and not the aggregation of ordinary sensor values. |
| Merged hour (committed hour) | An arrival hour of a product whose batches are committed by its record in the product's `Hours` database (#1850). A read takes it from its batches only and ignores its blocks, which stay for the deletion delay after the commit. | Per product: an arrival hour is merged for the merge job only when every product with blocks in it is committed. |
| Producer watermark | The highest producer sequence merged for a product and a producer, kept in the records of merged hours; a block sent again at or below it is a duplicate after its blocks are gone (#1850). | Not the delete watermark of sealed history. Relies on in-order delivery per producer. |
| Period class | A table sensor's history setting in whole weeks, rounded up (at least 1; 0 for kept for ever); its batches of an hour go to the week database of the class its placement gives that hour (#1850, `TablePeriodClass`). | Not the history setting itself: a month counts as 5 weeks. |
| Placement | Where a table sensor's batches are (#1850 part 4b, `TablePlacement`): a target class, the one its hours are merged into now, segments of earlier hours still in another class after a change of its period, and the sensor's first hour, before which it has no rows and no segment reaches. The merge and every read take the class of an hour from it. | Not the history setting: it follows the setting from a cut-off hour on. |
| Move (of a table sensor's rows) | Copying a sensor's batches of the hours of a segment of its placement into the target class's databases, then switching the placement and deleting the source (#1850 part 4c), a step at a time (one sensor, hours of one week); when the target class has passed for the week, deleting them instead and switching (an expired step). | Not a sensor move (another path) and not the batch merge. |
| Large file value | A value of a File sensor whose content is not part of the value: the value holds the description of the file (name, size, the SHA-256 of the original bytes, the modification time of the source file, the id of the file in the store) and the content lies in the large file store (ADR-0022); the state of the file (uploading, verified, packed) is in the store's record, not in the value. Its time is the time the server accepted it. It is secure or not (Secure file). On a session an ordinary send whose content is larger than a quarter of the session frame limit becomes a large file value that is not secure (Routed send). | Not an ordinary file value, which is one row with the bytes inside and stays limited to megabytes. One File sensor may hold both. No preview. |
| Dump | A file with a snapshot of a process (written by the application as it crashes, on request, or by a person), delivered to HSM as a large file value. To HSM it is bytes. | Not a database dump of HSM and not the conformance `dump_payloads_to`. HSM does not create dumps. |
| Piece | A fixed-size part of the source file of a large file value (the last may be shorter), compressed by itself with zstd; its number names its place in the file, so an upload continues from a piece number. | Not a block (table rows) and not a chunk (sealed history). |
| File connection | The WebSocket of a collector session that carries the pieces of a large file: its own subprotocol on the session route, tied to the live session by `X-Hsm-Session`, opened when a file is to be sent and kept while files are waiting; it carries them one after another (ADR-0022). | Not the table connection: a piece never waits ahead of a block, nor a block ahead of a piece. |
| Upload | One large file on its way to the large file store, known by its sensor, name, size, modification time, source identity and secure mark across restarts of either side; named on the wire by an upload id (32 hex digits). A file connection holds at most one, as a lease of the store; the number held on the server is bounded (#1884). | Not a value yet: the value exists only after the end check. |
| End check | The server's check of an upload after `end`: every stored piece is decompressed within its bounds and compared with its SHA-256, and the hash of the piece digests with the collector's; only then is the file verified and the value written (#1884). A check done within 2 seconds is answered with its outcome; a longer one (minutes for a large file) is answered `202` and asked again. | Not the checksum of a piece (CRC-32 at arrival), which catches a damaged frame and refuses only that piece. |
| Large file store | The folder of the server that holds large file values as files: a part while a file is uploaded and checked (uploading, then verified), then one zip with Zip64 (packed), whatever the kind: encrypted under the product's dump password for a secure file, without encryption for a file that is not secure. A secure file of a product without a password stays verified. | Not a LevelDB database, by decision (ADR-0022); not part of the databases' backups. Only the finished archives are shown to Caddy. |
| Waiting for the collector | The state of an upload on the File sensor page whose collector stopped sending: every piece is in but no end check runs (the collector left before `end`, or a check failed), or no piece came for longer than the store's lease. Shown with the time of the last piece and when the store removes the part (#1886). | Not "being checked", which is the end check running now; not a failure: the collector continues the upload from the server's piece number. |
| Download log | The record of every allowed download of a large file value: who (the user, or the token and its owner), when, which file. A download that cannot be recorded is refused. | Not the Journal, which holds changes of configuration and never refuses an action. |
| Dump password | The password of a product under which its secure large file values are given out: the download of a secure file is an AES zip with it. Set and seen by a Manager of the product and by an admin, on a page of the web UI only. | Not a credential of HSM: it does not sign anyone in, and HSM still checks who may download. Never returned by an API, never written to the Journal as a value. A file that is not secure does not use it. |
| Secure file | A large file value whose zip is encrypted (AES-256) under the product's dump password. A file that is not secure is packed into the same zip without encryption and without a password, and is downloaded by everyone who may see the product whether or not the product has a dump password. The application decides at the send, per file: a file handed over or taken from a watched folder is secure unless it says otherwise; a file of an ordinary send above the threshold is never secure. The mark travels in `begin` (absent = secure) and is never changed afterwards (ADR-0022). | Not a setting of the sensor. The password protects a downloaded copy, not the server, which holds a secure file without it while the file is uploaded and checked. HSM checks who may download either kind. |
| Routed send | An ordinary file send of a collector on a session (managed `SendFile`, `SendFileAsync`, a string content; native `hsm_sensor_add_file`, `hsm_sensor_add_file_from_path`, `FileSensor::SendFile`) whose content is larger than a quarter of the session hello's `maxFrameBytes` (1 MiB by default; no setting): it goes from memory in pieces on the file connection and becomes a large file value of the same File sensor that is not secure (ADR-0022 point 20). | Not a file of the large-file API: no watched folder, no state file, nothing deleted, nothing kept across a restart; a final refusal is a dropped file value. At or below the threshold, with the HTTP transport, or where the route is not available, the send takes the ordinary path (a `list` frame when it fits). |
| Password version | The number of one value of a product's dump password: each change makes the next version. Every secure archive records the version it opens with, and a download names it in `X-Hsm-Password-Version`. | A replaced version stays readable to Managers and admins until 30 days (a setting) after its last archive was re-encrypted, then it is removed. See `features/server/dump-password/feature.md`. |
| Archive build | The server's packing of a large file value into its zip: the first pack of a verified file, or the re-encryption of an archive under a newer password version. One at a time for the whole server; every archive is read back and checked against the SHA-256 of the original bytes before it counts. | A re-encrypted archive is a new file with a new id. Not the collector's compression of pieces. See `features/server/large-file-download/feature.md`. |
| Archive hand-over | HSM's answer to a checked download that came through the bundled Caddy: an instruction (`X-Hsm-Archive`) naming the archive, which Caddy serves from its read-only view of the archives instead of HSM sending the bytes. | Honoured only from a trusted proxy; without one HSM serves the file itself. Not a redirect and not a signed link. |
| Watched folder | A folder, a name mask and a sensor path an application gives its collector: a file there is sent as a large file value once its size and modification time have not changed for the configured time (on Windows it must also open with no writer). | The collector deletes the file it sent after the server confirmed it, unless told to keep it. |
| Week handle | `SensorValuesWeek`: what the shard dictionary holds for a history week; it can swap the instance serving the week (rows or sealed) while the server runs. | Swapped only by the sealing job. |
| Journal | The single journal of every configuration change: the monitoring tree's (#1588) and, since #1828, the chats' and the Telegram bot settings'. Global page + per-node tabs + `/api/v1/journal` + MCP tools, with entity kinds, products and undo-group links. | The undo mechanics are internal; say "journal record", not "change set", on user-facing surfaces. |
| Journal record | One journaled change with kind (`sensorDataPolicies`, `sensorTtlPolicies`, `productTtlPolicies`, `alertTemplate`, `alertSchedule`, `nodeSettings`, `treeCrud`, `folder`, `chat`, `serverSettings`), root product and, for rollbackable kinds, the undo-group link. | Legacy/non-config rows have null kind ("other"); sensor value history is not part of this surface. A `chat` or `serverSettings` record never carries a secret — a webhook, the bot token and the Telegram chat id are named by their state only (#1828). |
| Undo group | The server-minted per-request grouping of journaled writes (#1588): one HTTP request / MCP call / form post = one group; one rollback undoes the whole request. | Ids are never client-supplied or echoed (the #1570 `changeSetId` and fork rule are gone, ADR-0013). |
| Update queue | Server-side queue for propagating sensor/tree changes. | Treat ordering and idempotency as important. |
| Sensor move | Moving one sensor to another path, in its product or into another, keeping its id and therefore its history, settings, policies, journal and dashboard references (#1718, ADR-0018). | Sensors only — nodes are never moved, and a node below the root is never renamed (a root product is). Say "move", not "rename" (a move may also rename) or "relocate". |
| Sensor alias | An old path of a moved sensor that keeps routing values and registrations to it; expires by the sensor's SelfDestroy interval, removable, displaced by a real sensor at that path. | Say "alias", not "redirect" or "tombstone" (a tombstone would reject values). |
| SSO sign-in | Signing in to the web UI through an external OpenID Connect provider (#1782; Authentik first). The provider's username is the HSM login; the result is the same HSM auth cookie a password sign-in issues. | Optional, off by default; password login always stays. Say "SSO sign-in", not "SSO user" — an HSM user is the same whichever way it signed in. See `features/server/sso-login/feature.md`. |
| Data Protection key ring | The ASP.NET Core key ring protecting the auth cookie and antiforgery tokens, persisted at `Config/DataProtection-Keys/` (#1633) so sessions and forms survive a container recreate. | Never delete or "clean up" the folder — each past key file decrypts payloads minted under it; keys are unencrypted at rest (see `features/server/authentication/feature.md`). |
| Before-image / After-image | Structured snapshot of an entity's configuration taken immediately before / after a journaled write. | Stored as entity rows (`PolicyEntity`, `AlertTemplateEntity`, `AlertScheduleEntity`), never secrets; internal to the Journal's rollback machinery. |
| Rollback (journal record) | Replay of compensating full-list writes in reverse order through the record's undo group, restoring before-images. | Admin-only everywhere (the token owner must be `IsAdmin`); refuses on after-image mismatch (content comparison) unless forced; configuration only — notifications/alerts/history untouched. |
| Rollback conflict | State where an entity's current content differs from the recorded after-image at rollback time. | Detected by content comparison, not timestamps (editors re-assert full lists on every save). |

## Alerts And Notifications

| Term | Meaning | Notes |
|---|---|---|
| Alert | Rule-driven notification condition for monitored sensors. | Use "alert" for rule/notification concept. |
| Global alert | Alert defined via an `AlertTemplate` (wildcard path + folder + sensor type) that auto-applies to matching sensors. | Canonical mechanism for non-leaf alerting since #1142. |
| Per-sensor alert | Alert attached to a single sensor via the `_Alerts.cshtml` editor. | Supported path; templates materialize onto sensors as per-sensor policies tagged with `TemplateId`. |
| Node-level alert (removed) | Legacy alert attached directly to a Folder/Product via the per-node editor. | Removed in #1142; replaced by global alerts. Storage cleanup migration prunes dangling rows. |
| Alert template | Reusable alert configuration/template. | Keep distinct from a concrete alert instance if code does. |
| Alert variable | `$name` placeholder substituted in an alert message template (e.g. `$product`, `$value`, `$emaMean`). | The registry is `AlertState`'s `[AlertVariable]`s; substitution matches substrings and the message renders with string.Format — braces are not allowed (they throw at evaluation time or silently substitute another variable) and the template splits on spaces, dropping whitespace that touches a space (whitespace with no space in it is kept); only other plain text ships as-is. The full table travels in the MCP tool schemas (`AlertVariablesDocs`). |
| Condition-property availability matrix | Which condition properties each sensor type offers (e.g. no `Value` on bar types, `Length` String-only). | Source of truth: `AlertPolicyConditionRules` (drives the 422 validation; the template write enforces the same matrix through the domain reconstruction of its policies — a non-offered pair fails the whole template write with a parse error, and an AnyType template accepts only the common set, #1609); documented exhaustively in the MCP tool schemas via `AlertPropertyMatrixDocs`. |
| Alert schedule | Time window or schedule controlling alert activity. | Time zone and boundary behavior need tests. |
| Path pattern | A template's `paths` entry, compiled by `PathTemplateConverter` to a regex anchored `^...$` and matched against the sensor's full product-prefixed path. | `*` matches any run of characters within ONE segment (cannot cross `/`, may cover part of one); there is no any-depth wildcard (`**` is two single-segment classes) and the depth is fixed by the segment count — a pattern of LITERALS without `/` can never match. The guarantee is for literal characters only: constant parts reach the regex unescaped, so metacharacters in them stay live — `.` matches any character including `/` (`Product.cpu` matches `Product/cpu`). Semantics stated in the `AlertTemplateDto.Paths` field docs (#1565). |
| Zero-match / dead pattern | A path pattern that matched no sensors in the template's folder at apply time. | A legal save (sensors may come later); since #1565 it is reported through the #1401 `warnings` channel of the create/update/restore result — one entry per dead pattern, the `sensor` slot carrying the pattern itself — instead of clean success. The reason text says "matched no sensors"; matching includes the template's sensor-type and folder filters. |
| Notification | Delivered message via Telegram/email or other channel. | Use when discussing delivery, retries, and failures. |
| Chat | The destination an alert's notification is routed to: ONE record carrying up to three delivery channels at once — a Telegram binding, a Slack webhook and a Mattermost webhook. A chat bound to no access-grouping folder is global (offered from every node's alert editor); a chat bound to folders is offered only from those folders. | The name is required, at most 100 characters and unique per server ignoring case (#1829). Created, changed and deleted in the web UI (Configuration → Chats) and since #1829 through `POST`/`PATCH`/`DELETE /api/v1/chats` and the `create_chat`/`update_chat`/`delete_chat` tools; every write leaves a `chat` journal record that never carries a webhook value. Not a chat of a messenger: a Telegram group or direct chat reaches HSM only through a Telegram binding. |
| Bot credential | The Telegram bot's three settings — its username (`BotName`), the token from BotFather (`BotToken`) and the delivery switch — kept in the settings file. Administrators change them on the Configuration page's Telegram tab and, since #1830, through `GET`/`PATCH /api/v1/telegram-bot` and the `get_telegram_bot`/`update_telegram_bot` tools. | The token is a secret and write-only on the management surface: a read answers `hasBotToken`, a journal record names the state of the setting, a log line says that it changed (#1824, #1828). |
| Server settings | Settings that belong to the server itself rather than to the monitoring tree; `serverSettings` is their journal kind. | Since #1830 the bot credential is the only one with a management surface. |
| Telegram binding | The link between a Chat record and one Telegram chat — a direct chat with the bot or a group. It is created only by a person's `/start` against an invitation, never by the chat's numeric id. | Stored on the chat (`telegramChatId` with its type and title) and shown by `get_chat` once the `/start` has happened; no request creates one. A bound chat is not rebound in place and a Telegram chat bound to another chat is not taken over: the old binding is cleared first (`clearTelegramBinding`). |
| Invitation | The one-shot, short-lived token a person uses to bind a Telegram chat: in a direct chat the link `https://t.me/<botName>?start=<token>` and the Start button, in a group the command `/start@<botName> <token>`. The consent is the person's action in Telegram; nothing is bound by a record on the server. | The web UI issues it at the moment of use and it lives 2 minutes; the management surface (`POST /api/v1/chats/{id}/telegram-invitations`, `create_chat_telegram_invitation`) answers it with its `expiresAt` and it lives 10 minutes — the longer road server → orchestrator → person. The first `/start` consumes it; the tokens live in memory, so a restart forgets the outstanding ones and instances do not share them. |
| Chat setup guide | The steps of setting up a notification chat — creating the bot in BotFather, creating a Slack or a Mattermost incoming webhook, binding a Telegram group or direct chat — held once in code (`ChatSetupGuide`), each marked as the messenger's (a person does it inside Telegram, Slack or Mattermost) or HSM's (the person acts in HSM's own form). | The web UI's three help modals print it (#1827; the BotFather guide has no modal). The management API's guide (`GET /api/v1/chats/setup-guide`, `get_chat_setup_guide`, #1831) answers the messenger's steps as text and HSM's part as the calls that do it — never as a person's instructions. |
| Next steps | The `nextSteps` lines an answer of a chat-setup write carries (#1831): what the orchestrator does next, each line naming its tool call. | They ride answers and never tool descriptions: a description is static and travels in every tool listing. On reads the member is absent. The invitation's next steps are the person's — the guide's words of its kind with the invitation in place. |
| TTL | Time-to-live policy on a sensor. | Expiration and status transitions should be tested. |

## API And Integration Terms

| Term | Meaning | Notes |
|---|---|---|
| DTO | Public data transfer object, often in `HSMSensorDataObjects`. | Serialization compatibility matters. |
| Access key | Product-scoped credential used by collectors and data clients (e.g. the Grafana JSON datasource) to send and/or read sensor data, per its permissions (`CanSendSensorData`/`CanReadSensorData`); managed on the Access keys page. | A different concept from an API token (management clients) — don't shorten either to "API key". Treat as sensitive. |
| API token | Personal opaque bearer credential (`hsm_pat_v1_<token-id>.<secret>`) for non-interactive management clients; only a SHA-256 verifier is persisted. An eternal full mirror of its owner's rights, optionally read-only (#1384). | Distinct from collector access keys; creation/lifecycle is cookie-only. See `aicontext/features/server/api-tokens/`. |
| Sensor API | The data-ingestion surface under `/api/sensors` (values, history, files, the collector session), authenticated by an access key in the `Key` header. | Public name used in README/AGENT-SETUP; distinct from the management API. |
| Management API | The administration surface under `/api/v1` (products, access keys, alerts, chats, the Telegram bot, journal), authenticated by an API token; the MCP server at `/mcp` renders the same operations. | Public name used in README/AGENT-SETUP. |
| Read-only token | API token whose only restriction is that every write operation of the management API is denied; reads follow the owner's sight exactly. | The flag is fixed at creation; changing a token's power means revoking and minting a new one. |
| Profile | The per-user page reached from the header user menu item "Personal tokens" (route `/Profile`): a read-only card about the signed-in user plus the API tokens section where the user manages their own tokens. | Editing user data is not part of the Profile; it is a view + personal-token surface. |
| TokenId / EntityId | API-token identity: TokenId is the public 128-bit authentication lookup key (opaque, not a secret, but never disclosed by management responses); EntityId is the stable GUID used by lifecycle routes. | Lifecycle and list responses expose EntityId only — the TokenId matters solely inside the presented credential. |
| Token verifier | Domain-separated `SHA-256("HSM-API-TOKEN" ‖ 0x00 ‖ version ‖ tokenId ‖ secret)` stored instead of the secret. | Compared constant-time against stored-or-dummy on every authentication. |
| Revocation generation | Monotonic global/per-owner counter; a token authenticates only while its at-issue generations equal current values. | Emergency revoke-all/revoke-user advances it; missing-as-zero is the fresh baseline, corrupt/regressed fails closed. |
| HsmApiToken scheme | The dedicated ASP.NET authentication scheme for API-token bearers; never the default scheme, runs only from the management policy. | Cookie stays default and is pinned into the `DefaultPolicy`; a cookie-only principal never satisfies a management endpoint. |
| Management area (`/api/v1`) | The versioned management-API route family, SitePort-only and fail-closed: endpoints need `[ManagementApi]` plus their policy, everything else in the area is 404 by default. | `/api/v1/api-tokens` is the sole cookie-only family inside the area. |
| Authorization boundary | The anchor a management-API target resolves to at evaluation time: Global, a product, or a folder (a sensor inherits its product's CURRENT folder). | Resolved from the live hierarchy per request; deleted ids fail closed. A token mirrors its owner's rights at whatever boundary the target resolves to (ADR-0005). |
| Sensor-tree folder (wire) | In the management-API sensor-tree surface (#1386), `"type": "folder"` on a node — a NESTED `ProductModel` under a root product; `"type": "product"` is a root. | Distinct from the access-grouping Folder entity (`FolderModel`, `IsFolderAvailable`): those are NOT addressable through the sensor-tree surface. The wire pair mirrors the web UI's product/folder vocabulary. |
| MCP surface (`/mcp`) | The Model Context Protocol endpoint hosted by HSMServer (#1391, phase-2 writes): Streamable HTTP, snake_case tools rendering the management-API surface (reads of the sensor tree and its sensor policies, alert templates and schedules, chats, access-grouping folders, access keys, the agent installer link, large files, the journal, the Telegram bot status and the chat setup guide; writes of sensor policies, alert templates, schedules, products, access keys, chats and the bot credential; the chat test message and the Telegram invitation; sensor muting, deletion, move and alias removal; journal rollback) through the SAME HsmApiToken credential and owner sight — read-write tokens only (every MCP message is a POST). | Outside the `/api/v1` area guard (JSON-RPC errors, SDK-owned handler) but inside the bearer credential family; SitePort-only. See `aicontext/features/server/mcp/`. |
| Token usage sensors | The per-token view of management-API usage inside self-monitoring: how often the token authenticates `/api/v1`/`/mcp` requests and how long they run. Keyed by owner login + token EntityId — never the name (collides, moves) or the TokenId (never disclosed). | The Profile token card displays the EntityId as the join key. See `aicontext/features/server/token-usage-monitoring/`; rationale in ADR-0006 (`docs/decisions/`). |
| Collector session | The long-lived WebSocket connection a collector holds to `GET /api/sensors/session` (ADR-0017): data frames up, acknowledgements and directives down. | Designed, not shipped: `docs/initiatives/collector-session-websocket.md`. One of the two transports a collector can be set to; the HTTP Sensor API stays beside it (script clients use it), and a collector never falls back from one to the other. Distinct from a kept HTTP connection (#1653), which is transport reuse without a session. |
| Transport setting | The collector setting that chooses how it talks to the server: `session` or `http`. | The default is `session` (ADR-0019: managed collector 4.0.0, agent 0.6.0, probe 0.13.0); `http` stays selectable. A collector uses one or the other and never changes it on its own: there is no fallback from a session to HTTP. |
| Session frame | One JSON message on a collector session. Request (collector to server): `id`, `op`, `body`. Acknowledgement: `ack`, `status`, then `body` on success or `error` on failure. Push (server to collector): `op`, `body`. Heartbeat (either direction): `op` = `ping` / `pong`, no `id`, not acknowledged. The body of a `list`/`commands` request is byte for byte the HTTP body of the matching Sensor API route. | The envelope is new wire; the body is the existing wire contract. |
| Session registry | The server-side record of live collector sessions (product, access key, client name, collector kind/version, address, connected-at, last-frame-at). | Answers "which sessions are open"; push goes through it. Not the disconnect alert: that stays the `Service alive` inactivity alert. |
| C++ wrapper | Native wrapper surface under `src/wrapper`. | Keep parity with collector public APIs. |
| Ping module | External module under `src/module/HSMPingModule`. | Integration surface and deployment assumptions matter. |

## HSM Agent Terms

| Term | Meaning | Notes |
|---|---|---|
| HSM Agent | Standalone Windows-service product (`src/agent`) that hosts the native collector and streams a machine's metrics to an HSM Server. | Distinct from the collector library it hosts; epic #1167. |
| Agent bundle | Per-product zip an admin downloads from the server (signed `hsm-agent.exe` + generated `config.json` + install scripts). | The exe is byte-identical across downloads; only `config.json` differs. |
| Agent config | `config.json` read by the agent (server address + access key + sensor groups). | Schema lives in `src/agent` + `docs/hsm-agent.md`; the server generates it per product. |
| Agent connection URL | Admin server setting (`AgentConfig.ExternalConnectionUrl`) — the externally-reachable Sensor-API base baked into bundles. | Behind Docker/NAT the server can't infer it; blank falls back to the request host. |
| Linux probe | The systemd-hosted Linux host/Docker monitoring process (`hsm-linux-probe`, epic #1413), the Linux counterpart of the HSM Agent. | Say "Linux probe", not "Linux agent": it is a separate product built on the native collector. |
| Probe bundle | The per-product `.tar.gz` an admin downloads for a Linux host: the released `.deb`, a generated `config.json`, the access key in its own file, optionally `server-ca.pem`, and `install.sh`/`uninstall.sh`. | Built by `LinuxProbeInstallerBundle` (#1424); the Linux sibling of the agent zip. |
| Probe release pin | `src/server/HSMServer/probe-release.txt` — the one tracked line naming the `probe-v*` release the server stages and serves. | Empty = nothing staged: staging skips and the download answers 503. Mirrors `agent-release.txt`. The release is published by `probe-release.yml` from a `probe-v<X.Y.Z>` tag (#1418). |

## Deprecated / Avoid

| Avoid | Prefer | Why |
|---|---|---|
| Global scheduler | Collector scheduler | Scheduler ownership is per collector in current architecture. |
| Metric | Sensor or sensor value | HSM domain model is sensor-based. |
| Backend | HSM Server | Public docs should name the product component. |
| Timer task | Scheduled task | Matches collector scheduler terminology. |
| Telemetry (for the server's own health/traffic product) | Self-monitoring | Only when referring to the server-watching-itself product; collector diagnostic sensors ("overflow telemetry") and access-key/request telemetry (`TelemetryCollector`, "key telemetry") keep their names. |
| Internal metrics (for the server's own health/traffic product) | Self-monitoring | Same scope as the "telemetry" row. |
| API key | Access key (product data: collectors, Grafana) or API token (management) | Ambiguous blend of two distinct credentials; name the one meant. |
