# Feature: HTTP Client

> Owner: collector | Last reviewed: 2026-11-10 | Canonical: yes
> Scope: Collector - HTTPS transport with Polly retry for sending sensor data

---

## Description

`HsmHttpsClient` wraps `System.Net.Http.HttpClient` for sending sensor data to HSMServer. Each value type (data, priority, file, command) has its own request handler; the data, priority and file handlers repeat a failed request inside the send through a Polly retry pipeline, the command handler does not. Wire shapes and endpoint payloads: `../../api/wire-contract/feature.md`.

---

## Business Rules / Invariants

- Default scheme is HTTPS; an explicit `http://` in `ServerAddress` requires `AllowPlaintextTransport=true`, otherwise upgraded to HTTPS.
- `AllowUntrustedServerCertificate` must be explicitly set to `true` to bypass TLS validation. Default is `false` (secure by default).
- Auth headers on every request: `Key: <AccessKey>`, `ClientName: <ClientName>`.
- `RequestTimeout` (default 30s) is set on `HttpClient.Timeout`.
- **Connection reuse (both collectors).** Sends ride a kept connection, not a new TCP+TLS handshake per request. Managed: one pooled `HttpClient` connection, retired after 5 minutes (`PooledConnectionLifetime`; `ServicePoint.ConnectionLeaseTimeout` on net472) so DNS is resolved again (#1102-E4). Native: `HttpTransport` keeps one libcurl easy handle and resets it between requests (a concurrent caller gets its own handle, closed afterwards); the kept handle is retired 5 minutes after its creation, a connection idle for more than 60 s is not reused (`CURLOPT_MAXAGE_CONN`, the managed handler's idle timeout), TCP keep-alive is on, and a handle whose transfer failed is destroyed, never kept (#1653). Delivery stays at-least-once in both collectors: a batch the server stored but whose response was lost is sent again. On a kept connection the same can happen at stop: the request is on the wire almost at once, so a cancel that arrives while the collector waits for the response aborts a send the server has already taken, and the stop drain sends that batch again. There is still no application-level session: the server cannot push to a collector and learns that one went away only from TTL.
- `HttpResponseMessage` is always disposed after use (`using` blocks).
- `HttpContent` is disposed after sending (in `ExecutePipelineAsync`).
- Polly retry per handler: data/priority/file — 10 retries, exponential backoff 1 s → 2 min. **Commands: none, one attempt per send (#1659 A3, 3.6.3).** Before 3.6.3 the command pipeline retried a failed connection `int.MaxValue` times with a linear pause of up to 2 minutes, all inside one send: against an unreachable server the send never returned, so the command queue could not take newer registrations into the package and retried on Polly's growing pause, not on `PackageCollectPeriod`. Now a failed command send returns, the queue re-enqueues the package and sends it again after `PackageCollectPeriod` (`../data-pipeline/feature.md`), which is what the native collector does. Pinned on both TFMs by `Transport/CommandSendAttemptTests` (one source, compiled into the unit project for net472 and into the integration project for net6.0).
- `ShouldHandle` (`BaseHandlers.ShouldRetry`, #1096) of the data/priority/file pipelines: transport-level exceptions are always retried, and so is a returned **5xx**. **4xx** are permanent and never retried. A 5xx that exhausts the budget still falls through to queue re-enqueue, so no data is lost.
- `CancelPendingRequests()` (`ICancelableDataSender`, called by collector Stop) cancels the shared in-flight token and installs a fresh one. It must **NOT** dispose the HttpClient — disposal during a graceful stop converted remaining flush sends into `ObjectDisposedException` data loss (PR #1080 finding #7; regression-tested in `HsmHttpsClientCancellationTests`).
- `PackageSendingInfo` captures content size (chars), success flag, the answered status (`StatusCode`, `null` when no answer arrived; 3.6.2, with a constructor that takes a bare status for a sender that is not HTTP) and error string for self-diagnostics: the exception message, or for a refused request `Code: 406 (Not Acceptable). <server message>` (#1659 A1, 3.6.4). Before 3.6.4 the text interpolated the `HttpContent` object and so printed its type name (`System.Net.Http.StreamContent`), never what the server said. The server message is included by the built-in handlers only, only for an answer below 500 (a refusal; the body of a 5xx is as often a proxy's page that differs from answer to answer), only when the answer is `text/plain`, and cut at 256 characters: a JSON answer is the request batch itself (`/list` 400) or the per-path dictionary (`/commands`), and sensor values do not belong in a log line or in `Collector errors`. The public constructor that takes an `HttpResponseMessage` (custom senders) cannot read the content and reports the status and reason phrase. The command queue reads the status to tell a rejection (4xx, final) from a failure worth repeating (`../data-pipeline/feature.md`).
- JSON: System.Text.Json, `AllowNamedFloatingPointLiterals`, runtime-polymorphic write via `JsonRequestConverter`.
- A failed send is reported once per cause and window (#1659 A4, `../error-handling/feature.md`): the final failure by the queue, an attempt the pipeline repeats by the sender through the collector's deduplicated error channel. Never with the payload content; the payload byte count and the attempt number are in the Debug log. The queue's report is keyed without the item counts (`PackageSendFailedException.Report`; the counts are at Debug), because a failing package grows from cycle to cycle. The cause of a send that got no answer keeps the innermost exception's message (`PackageSendingInfo.DescribeException`), which is where the reason is (name not resolved, connection refused, certificate not trusted). A server message is taken only from a `text/plain` body of at most 16 KiB, and never from a 5xx: the failure text is the key of the report, and a body that names the request would make every cycle of an outage a new report. An attempt the pipeline repeats is spelled like the final failure (`Failed to send data. Code: 503 (Service Unavailable).`), with the innermost exception's message for an attempt that got no answer.
- `Dispose()` is idempotent (guarded by `_disposed` flag). Disposes all handlers, token source, and HttpClient.
- `InnerException?.Message` uses null-conditional to avoid NRE when InnerException is null.

## Native port (C++) — #1096

The native collector (`src/native/collector`) emits the **byte-identical** wire stream (see `../../api/wire-contract/feature.md`) and ships a real HTTP transport that mirrors this client:

- `hsm_http_transport.{hpp,cpp}` — a libcurl easy-handle wrapper (`Post`/`Get`) that keeps its handle between requests (#1653: before 0.11.3 every request created and destroyed its own handle, i.e. its own connection), confined to one TU so the rest of the core never sees `<curl/curl.h>` and the `-Werror`/`/WX` gate stays green. `CURLOPT_TIMEOUT_MS` ↔ `RequestTimeout`, `CURLOPT_SSL_VERIFYPEER` ↔ `AllowUntrustedServerCertificate`, `CURLOPT_XFERINFOFUNCTION`-abort ↔ `CancelPendingRequests`. Built only when `HSM_COLLECTOR_HTTP=ON` (curl via vcpkg manifest); the default build is curl-free.
- `hsm_http_endpoints.hpp` — pure route table + scheme defaulting (bare host → https; explicit `http` kept only with `AllowPlaintextTransport`), and per-kind / batch / command routing identical to `DataHandlers`/`CommandHandler.GetUri`.
- `hsm_http_retry.hpp` — the retry policy with the `ShouldRetry` semantics of the managed pipelines as they were at #1096 (bounded 5xx retry, unbounded commands exceptions-only, 4xx never). Unit-tested, not used by the send path; its `Commands()` shape no longer exists in managed since 3.6.3 (#1659 A3).

Routing + retry are pure headers compiled into the always-on core, so they are unit-tested in the default `/WX` lane (`native_http_endpoint_routing_matches_net`, `native_http_retry_policy_matches_net`); the transport is exercised by an in-proc capture-server E2E (`native_http_transport_posts_to_capture_server`) in the `HSM_COLLECTOR_HTTP` CI lane. The .NET side of the 5xx fix is pinned by `Retry5xxParityTests` against the fake server.

### Live send-path wiring (#1097)

`TrySendBatch` delegates to a **sender seam** (`sender_`, a `std::function<bool(std::vector<std::string>&)>`). The default records each batch into `sent_values_` so the behavior corpus and the `sent_count`/`get_sent_json` accessors keep working in both build lanes. In the `HSM_COLLECTOR_HTTP` build, `TestInstallHttpSender()` swaps in a real libcurl POST: the batch is joined into a JSON array and sent to the `/list` route with `Key`/`ClientName` headers, exercising the full `add → queue → worker → POST` pipeline. Installed before `Start` (same one-way contract as the clock seam — the worker only reads `sender_` after `Start`, so the swap needs no lock). `StopWorker` calls `HttpTransport::Cancel()` (aborting an in-flight POST so the join stays bounded) and `StartWorker` calls `ResetCancel()` to re-arm after a restart.

Send semantics: **one POST attempt per batch**. A non-2xx or transport failure returns `false`, so the dispatcher re-enqueues the batch at the tail — the same durable-retry contract the C# queue uses (re-enqueue on `PackageSendingInfo.Error != null`, including 5xx and 4xx). The Polly-equivalent in-send exponential/linear backoff (`hsm_http_retry.hpp`, unit-tested separately) is a non-blocking refinement layered on later; doing it inline would block the single worker thread for up to the policy max-delay per batch. The end-to-end live path is pinned by `native_http_live_send_posts_to_capture_server` (drives a real int value through the collector and asserts the captured POST route/headers/body).

**Public live transport (#1165):** `hsm_collector_use_http_transport` (C ABI) / `Collector::UseHttpTransport()` (C++) makes the libcurl transport reachable from application code. Installed before Start, it (a) POSTs the wire `AddOrUpdate` registration batch to `/commands` at Start (the `Type:0` Command discriminator), and (b) switches values/bars to the **server wire format** (`Time` ISO-8601, bar `OpenTime`/`CloseTime`) via `OutgoingValueJson`/`OutgoingBarJson` — the conformance corpus keeps the canonical/in-memory recorder (`send_wire_` is false there). Pinned by `native_http_registers_sensors_on_start` + the wire assertions in `native_http_live_send_posts_to_capture_server`, and proven end-to-end against a Dockerized HSM server by `examples/server-monitor` (registration + live int/double values readable via `/api/sensors/history`). Before #1165 the transport was test-only and posted canonical JSON, so nothing reached a real server. Still open: per-command error-dictionary parse, in-send Polly backoff, and registering sensors created *while running* (today only the Start-batch registers over HTTP).

### WebSocket client connection (#1662, collector session step 1)

The connection under the collector session (ADR-0017, `docs/initiatives/collector-session-websocket.md`). Used by the session transport below (since collector 0.12.0); a collector on the HTTP transport never opens one.

- `WebSocketConnection` (`hsm_ws_connection.{hpp,cpp}`): `Open(url, headers, subprotocol, timeout)`, `SendText`, `Receive`, `Close`, `Cancel`. One owner thread; `Cancel()` is the only cross-thread member and unblocks a waiting `Open`/`SendText`/`Receive`.
- **The protocol is libcurl's, not ours.** The upgrade exchange, masking, frame encoding and frame parsing happen inside libcurl (`CURLOPT_CONNECT_ONLY = 2`, then `curl_ws_send` / `curl_ws_recv`). The collector carries no RFC 6455 code (owner decision, 2026-11-10: no self-written protocol code). The class adds policy only: timeouts, cancellation, whole-message assembly, the size limit, text only, the subprotocol check.
- **A session exists only where libcurl can carry one.** `WebSocketConnection::Supported()` is true when the libcurl in the process is at least 8.14.0 and lists the `ws` protocol. Before 8.13 libcurl does not say which fragment of a message is the last; 8.14 is the first release that lets the caller answer pings (`CURLWS_NOAUTOPONG`), and libcurl's automatic pong is not relied on (8.21 keeps it queued until the next send or data frame). Against headers older than 8.14.0 the class compiles as a stub that reports "unsupported", so the capability is also fixed at build time: a binary built on a host with older libcurl headers has no session even where the runtime libcurl is new enough (the probe's `.deb` is built in `debian:13`, which has 8.14.1). Unsupported means the collector stays on the HTTP transport.
- Where the libcurl comes from: the vcpkg manifests (`src/native/collector/vcpkg.json`, `src/agent/vcpkg.json`, `vcpkg-port/vcpkg.json`) ask for `curl[ssl,websockets]`, pinned at 8.21.0 by the baseline; the Linux probe links the distribution's libcurl, which has WebSocket on Debian 13 (8.14.1) and not on Ubuntu 24.04 (8.5.0). The Conan recipe still pins libcurl 8.10.1, so a Conan build has no session. The registry port under `ports/` gains the feature when the first session-capable version is published.
- `Open` reports the HTTP status of a refused upgrade (404, 503, ...) and the subprotocol the server selected, which must be exactly the offered one (none when none was offered). Refused before anything is sent: a request header name that is not a plain token, a value with a line break (header injection), a name that would replace one of the upgrade's own headers (`Upgrade`, `Connection`, `Sec-WebSocket-*`); and after the response, more than one `Sec-WebSocket-Protocol` line. Only `ws`/`wss` may come out of the handle (`CURLOPT_PROTOCOLS_STR`). The timeout bounds the open only and is cleared on the handle afterwards.
- What libcurl does **not** verify in the upgrade response (checked against 8.21.0): the `Sec-WebSocket-Accept` digest and the `Connection: Upgrade` header. Neither authenticates the server; TLS does, with the same `verify_peer` rule as the HTTP transport. What the digest would have caught is an intermediary that answers `101` without speaking WebSocket: that now surfaces as a frame error on the first `Receive`, not as a failed `Open`.
- `Close(linger_ms)`: `0` (default, and the destructor) writes the close frame once without waiting; a positive linger is the orderly close for a planned stop, waiting for the peer's close so the server sees a normal closure and not a reset.
- Every terminal outcome (failed `Open`, failed `SendText`, `Receive` returning `Closed` or `Error`) releases the connection; `IsOpen()` is the truth and nothing is written to a finished WebSocket. No member throws. Errors carry libcurl's own description when it gives one.
- Waiting is a poll in 100 ms slices (`poll` on POSIX, so descriptors above `FD_SETSIZE` are fine). The session transport calls `Receive` with a short timeout between looks at its outgoing queue (50 ms when idle, 5 ms while requests wait for acks); libcurl gives a `CONNECT_ONLY` handle no way to be woken for outgoing data.
- `Receive` returns `Text`, `Timeout` (connection still usable, nothing lost), `Closed` (close frame or TCP close) or `Error`. After `Closed`, `LastClosure()` says which: a close frame (`close_frame`, with the status `code` and `reason` of its payload, RFC 6455 5.5.1) or the end of the TCP stream without one (libcurl's `curl_ws_recv` returns `CURLE_GOT_NOTHING` when the socket read returns 0; a reset is `CURLE_RECV_ERROR`, which is an `Error` with libcurl's text). `Open` also reports the address it connected to (`peer`, from `CURLINFO_PRIMARY_IP`/`PRIMARY_PORT`; behind a CDN or proxy it is theirs). It assembles fragmented messages and partial reads, answers pings, ignores pongs, and refuses binary messages and anything over 8 MiB (from the frame header, before the payload is read). Frame-level violations (a masked server frame, reserved bits, a stray continuation) are detected by libcurl and surface as `Error`.
- Tests: `native_ws_*` in the HTTP lane against `tests/ws_test_server.hpp`, an in-process RFC 6455 server. That fixture is the only RFC 6455 code in the repository and never ships; `native_ws_fixture_accept_key_matches_rfc` pins its handshake digest. Where libcurl has no WebSocket the connection tests skip and say so; where `HSM_REQUIRE_WEBSOCKET=1` is set (the CI HTTP lane, both platforms) that is a failure instead. `native_ws_reports_libcurl_support` runs everywhere and checks the unsupported path. The fixture is plaintext; `native_ws_live_probe` is a manual, env-gated check of the TLS path against a real endpoint.

### Session transport (#1668, collector session step 4)

`hsm_collector_use_session_transport` (C ABI, since 0.12.0) / `Collector::UseSessionTransport()` selects the collector session instead of HTTP requests. Installed before Start, one transport per collector; the agent (`server.transport`) and the Linux probe (`hsm.transport`) expose it as a setting with the values `http` (default) and `session`.

- **No HTTP beside it.** A collector on the session sends nothing over `/list`, `/commands` or any other HTTP route, and never falls back to them (owner decision 2026-11-10: a collector uses one transport, with no fallback; the HTTP routes themselves stay on the server for good, owner decision 2026-11-11, so `http` remains a transport a collector can be set to). While no session is up a send fails at once, the batch goes back to the queue and registrations stay queued for retry: the same recovery as an unreachable server over HTTP.
- `SessionTransport` (`hsm_session_transport.{hpp,cpp}`) owns one thread and one `WebSocketConnection` at a time. `Request(op, body, timeout)` writes `{"id":N,"op":op,"body":body}` and waits for the ack with that id; any number of threads may wait at once (the data worker, registration posts from host threads). Frames from the server are parsed with nlohmann/json; the collector carries no parser of its own for bytes that come off the network.
- **Start does not wait.** The session opens in the background: URL `ws[s]://host[:port]/api/sensors/session` from the same address rule as HTTP, subprotocol `hsm.sensors.v1`, upgrade headers `Key`, `ClientName`, `X-Collector-Kind: native`, `X-Collector-Version`, plus the host's extra request headers. The first frame must be the server's `hello`; its `maxFrameBytes` and `heartbeatSeconds` are the session's limits (a hello with unusable limits ends the attempt). Connect, TLS, upgrade and hello share one 15 s budget. While no session is up, registrations are not even serialized: the post returns "retry" at once.
- **Reconnect.** A refused upgrade (any status, including 401, 429 and 503), a dropped connection or an ended session is followed by a new attempt after a jittered exponential backoff, 1 s to 60 s. The backoff starts over only after a session that lasted a minute: a server that takes the upgrade and then closes on the first frame is not reopened every second. A server that stays away is logged once per distinct reason, not once per attempt.
- **Heartbeat.** When nothing was sent for a heartbeat interval the transport sends `{"op":"ping"}`; when the server sent nothing for two and a half intervals the session is given up and reopened.
- **Ack timeout.** A request that gets no ack within the collector's request timeout fails, and the session is reopened, so a late ack can never be matched to another request. The batch is sent again on the next session: an ack lost in transit can therefore deliver a batch twice, as a lost HTTP response can.
- **Frame limit.** A batch is split into `list` frames that fit `maxFrameBytes`. Each frame is acknowledged on its own; when a later frame fails, only the values not yet acknowledged go back to the queue. A single value larger than a frame cannot be delivered: it is dropped, logged and counted in `Queue overflow`, once, whatever happens to the frame around it. A registration batch that does not fit is posted in halves (recursively), each acknowledged and recorded on its own; one registration larger than a frame is answered as a final 413, like an HTTP 4xx.
- **Statuses.** An ack carries the status the same HTTP request would have got. 2xx is delivered; anything else sends the batch back to the queue, and for registrations follows the HTTP rule (5xx retried, 4xx final).
- **File values** are refused before they are queued: `hsm_sensor_add_file` / `hsm_sensor_add_file_from_path` return `HSM_RESULT_INVALID_STATE` and the refusal is logged. The session has no op for them yet (step 2b), and there is no HTTP to carry them instead. They are not counted in `Queue overflow`: the value never was in the queue, and the caller is told.
- **Stop.** The stop drain uses the session while it is up, inside the same stop budget as over HTTP. Then the session is closed: a graceful stop gives the close handshake up to 1 s so the server sees a normal closure (1000); a terminal one does not wait. A session thread stuck in a write is cancelled a second after the linger, so Stop stays bounded.
- **Without WebSocket in libcurl** (`WebSocketConnection::Supported()` false) Start logs one error saying the transport is unavailable, and nothing is delivered. It does not use HTTP instead.
- Pushed frames (directives, step 5) and unknown ops are ignored.
- **Logging.** The collector is a library inside someone else's process, so the session logs only on a change of state, and the facts go into those lines: no line per frame, request, ping or poll, and nothing on a stop (the host asked for it; its stop may hold the collector's locks while the session thread finishes). The log callback is never called while the transport holds its lock. Text from the network or libcurl (a close reason, an ack's `error`, libcurl's error text) has control characters and line breaks replaced by `?` and is cut (300 bytes; a close reason to 123); the access key, header values, URL query and frame bodies are never logged.
  - `INFO The collector session is up: connected to 203.0.113.7:443 in 412 ms (connect, TLS, upgrade and hello); frame limit 4194304 bytes, heartbeat 30 s.` After an outage: `... is up after 3 failed attempt(s) and 1m 12s without a session: ...`; after a session that ended: `... is up again, 1.2 s after the previous one ended: ...`.
  - `INFO The collector session ended after 5h 12m 03s: <how>. Peer 203.0.113.7:443; requests sent 1234, acks received 1233, still waiting for an ack 1; pings sent 12, pongs received 12; last frame from the server 0.4 s before the end. Reconnecting.` `<how>` is one of: `the server sent a close frame (code 1001, reason "...")` (or `without a status code`); `the connection ended without a close frame (TCP closed by the server or an intermediary)`; `the connection failed: <libcurl's text>`; or the collector's own decision: `the server sent nothing for two and a half heartbeats (1m 15s)`, `a request got no ack in time`, `sending a frame failed: ...`, `sending a heartbeat failed: ...`. The close frame may come from an intermediary that speaks for the server. A session that ended is INFO, not ERROR: behind a CDN or proxy long-lived connections are rotated, and the reconnect follows.
  - `Cannot open a collector session (attempt 3, 12.0 s without a session, peer ...): the upgrade failed with HTTP 503. Values stay queued; retrying.` Once per distinct reason until a session opens (two failures are the same reason when the HTTP status and the text without its digits match, so a timeout worded with a changing number is logged once); after any session, however short, a failure that comes back is logged again. ERROR when a retry will not cure it (the upgrade refused with 400, 401, 403, 404, 405, 406, 410 or 426; a 101 without the subprotocol; a first frame that is not a usable `hello`); INFO otherwise.
  - `ERROR No collector session for 5m 00s (N failed attempt(s); the last: ...). Values stay queued; retrying.` Once per outage, when it reaches 5 minutes: that is where the server starts alerting on the collector's missing beat, and a server restart or a CDN reshuffle is over well before it.
  - A session that keeps ending early (lived less than a minute) is flapping: the up lines of sessions that follow one another are suppressed (never the up line that follows failed attempts: it is what says the outage is over), an end line is logged when its reason differs from the last one logged and suppressed when it repeats (a close frame is compared with its code; other reasons without their digits), the next end line that is logged says `(N line(s) about earlier short-lived sessions suppressed)`, and once a session holds for a minute one `INFO The collector session has held for 1m 00s after N short-lived session(s); M line(s) about them were suppressed.` With the backoff, a flapping connection logs a bounded number of lines.
  - ERROR `The collector session transport is selected, but it is unavailable here: ...` (no WebSocket in libcurl) as before.
- Tests: `native_session_*` in the HTTP lane against the session mode of `tests/ws_test_server.hpp` (hello, acks, refused upgrades, silence, drops): delivery of registrations and values with the upgrade headers, queueing while the upgrade is refused, reconnect after a drop, ack timeout, the frame split of values and of registrations, a partly delivered batch, an oversized value, and the transport's request contract. `native_session_logs_how_a_session_ended` pins the log lines through `SessionOptions.log` (a close frame's code and printable reason, a TCP close reported as such, counters and lifetime, INFO level, suppression of a flapping session, no key); `native_session_logs_open_failures_by_kind` pins INFO for a 503 and ERROR for a 401; `native_ws_tells_a_close_frame_from_a_tcp_close` pins `LastClosure()` and `peer`. The 5-minute outage ERROR has no test (it needs a clock seam the transport does not have). The fixture is plaintext; over TLS the session is checked by hand against a real server.
- Not covered by the conformance corpus: the corpus drives both collectors through the in-memory sender and cannot observe a transport. The session scenarios for both drivers arrive with the managed session sender (initiative step 3).

## Known Issues / Limitations

- No circuit breaker pattern. If the server is down for extended periods, each batch attempt will exhaust all retry attempts before failing.
