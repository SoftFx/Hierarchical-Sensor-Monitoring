# Feature: HTTP Client

> Owner: collector | Last reviewed: 2026-11-10 | Canonical: yes
> Scope: Collector - HTTPS transport with Polly retry for sending sensor data

---

## Description

`HsmHttpsClient` wraps `System.Net.Http.HttpClient` for sending sensor data to HSMServer. Each value type (data, priority, file, command) has its own request handler; the data, priority and file handlers repeat a failed request inside the send through a Polly retry pipeline, the command handler does not. Wire shapes and endpoint payloads: `../../api/wire-contract/feature.md`.

---

## Business Rules / Invariants

- Default scheme is HTTPS; an explicit `http://` in `ServerAddress` requires `AllowPlaintextTransport=true`, otherwise upgraded to HTTPS.
- `AllowUntrustedServerCertificate` must be explicitly set to `true` to bypass TLS validation. Default is `false` (secure by default).
- Auth headers on every request: `Key: <AccessKey>`, `ClientName: <ClientName>`.
- **Server directive channel (#1198; managed since 3.7.0, #1659 B1).** A request that carries sensor values (the data, priority and file handlers) also carries the host's `CollectorOptions.ExtraRequestHeaders`, and the `X-Hsm-Directive` headers of its **accepted** answer are handed to `ServerDirectives` (`Client/ServerDirectives.cs`). A registration (`/commands`) carries the access headers only and its answer is not read for directives, as in the native collector (`HttpSendBatch` vs `PostRegistrationsWire`). The server sends directives only to a client that states `X-Agent-Version`, so a collector that does not set that header receives none. **Directives are handled inside the collector; there is no public event** (owner decision, 2026-11-10). The managed library acts on none of today's directives (`update-available`, `sensor-disable`, `sensor-enable` are agent matters), so `ServerDirectives` counts each one, notes each name once at Debug (at most 32 names of at most 64 characters, they come from the network) and drops it; a directive the library should act on later is dispatched from `ServerDirectives.Receive`. The native counterpart is `hsm_collector_set_extra_request_header` plus the host callback of `hsm_collector_set_server_directive_handler`. Directives pushed over a collector session (#1660 step 5) are to arrive at the same `ServerDirectives`. Tests: `Transport/DirectiveChannelTests` (both TFMs).
- `RequestTimeout` (default 30s) is set on `HttpClient.Timeout`.
- **Connection reuse (both collectors).** Sends ride a kept connection, not a new TCP+TLS handshake per request. Managed: one pooled `HttpClient` connection, retired after 5 minutes (`PooledConnectionLifetime`; `ServicePoint.ConnectionLeaseTimeout` on net472) so DNS is resolved again (#1102-E4). Native: `HttpTransport` keeps one libcurl easy handle and resets it between requests (a concurrent caller gets its own handle, closed afterwards); the kept handle is retired 5 minutes after its creation, a connection idle for more than 60 s is not reused (`CURLOPT_MAXAGE_CONN`, the managed handler's idle timeout), TCP keep-alive is on, and a handle whose transfer failed is destroyed, never kept (#1653). Delivery stays at-least-once in both collectors: a batch the server stored but whose response was lost is sent again. On a kept connection the same can happen at stop: the request is on the wire almost at once, so a cancel that arrives while the collector waits for the response aborts a send the server has already taken, and the stop drain sends that batch again. There is still no application-level session: the server cannot push to a collector and learns that one went away only from TTL.
- `HttpResponseMessage` is always disposed after use (`using` blocks).
- `HttpContent` is disposed after sending (in `ExecutePipelineAsync`).
- Polly retry per handler: data/priority/file — 10 retries, exponential backoff 1 s → 2 min. **Commands: none, one attempt per send (#1659 A3, 3.6.3).** Before 3.6.3 the command pipeline retried a failed connection `int.MaxValue` times with a linear pause of up to 2 minutes, all inside one send: against an unreachable server the send never returned, so the command queue could not take newer registrations into the package and retried on Polly's growing pause, not on `PackageCollectPeriod`. Now a failed command send returns, the queue re-enqueues the package and sends it again after `PackageCollectPeriod` (`../data-pipeline/feature.md`), which is what the native collector does. Pinned on both TFMs by `Transport/CommandSendAttemptTests` (one source, compiled into the unit project for net472 and into the integration project for net6.0).
- `ShouldHandle` (`BaseHandlers.ShouldRetry`, #1096) of the data/priority/file pipelines: transport-level exceptions are always retried, and so is a returned **5xx**. **4xx** are permanent and never retried. A 5xx that exhausts the budget still falls through to queue re-enqueue, so no data is lost.
- `CancelPendingRequests()` (`ICancelableDataSender`, called by collector Stop) cancels the shared in-flight token and installs a fresh one. It must **NOT** dispose the HttpClient — disposal during a graceful stop converted remaining flush sends into `ObjectDisposedException` data loss (PR #1080 finding #7; regression-tested in `HsmHttpsClientCancellationTests`).
- `PackageSendingInfo` captures content size (chars), success flag, the answered status (`StatusCode`, `null` when no answer arrived; 3.6.2, with a constructor that takes a bare status for a sender that is not HTTP) and error string for self-diagnostics: the exception message, or for a refused request `Code: 406 (Not Acceptable). <server message>` (#1659 A1, 3.6.4). Before 3.6.4 the text interpolated the `HttpContent` object and so printed its type name (`System.Net.Http.StreamContent`), never what the server said. The server message is included by the built-in handlers only, only when the answer is `text/plain`, and cut at 256 characters: a JSON answer is the request batch itself (`/list` 400) or the per-path dictionary (`/commands`), and sensor values do not belong in a log line or in `Collector errors`. The public constructor that takes an `HttpResponseMessage` (custom senders) cannot read the content and reports the status and reason phrase. The command queue reads the status to tell a rejection (4xx, final) from a failure worth repeating (`../data-pipeline/feature.md`).
- JSON: System.Text.Json, `AllowNamedFloatingPointLiterals`, runtime-polymorphic write via `JsonRequestConverter`.
- A failed send is reported once per cause and window (#1659 A4, `../error-handling/feature.md`): the final failure by the queue, an attempt the pipeline repeats by the sender through the collector's deduplicated error channel. Never with the payload content; the payload byte count and the attempt number are in the Debug log. The queue's report is keyed without the item counts (`PackageSendFailedException.Report`; the counts are at Debug), because a failing package grows from cycle to cycle. The cause of a send that got no answer keeps the innermost exception's message (`PackageSendingInfo.DescribeException`), which is where the reason is (name not resolved, connection refused, certificate not trusted). A server message is taken only from a `text/plain` body of at most 16 KiB.
- `Dispose()` is idempotent (guarded by `_disposed` flag). Disposes all handlers, token source, and HttpClient.
- `InnerException?.Message` uses null-conditional to avoid NRE when InnerException is null.

## Collector session transport (managed, 3.9.0; epic #1660 step 3)

`CollectorOptions.Transport = CollectorTransport.Session` replaces `HsmHttpsClient` with `SessionDataSender` (`Client/Session/`): one WebSocket to `GET {base}/session` (`wss` by default, `ws` only where the HTTP client would use `http`), subprotocol `hsm.sensors.v1`, every package a frame the server acknowledges. Protocol: `../../api/wire-contract/feature.md`, design: ADR-0017 and `docs/initiatives/collector-session-websocket.md`. **`http` is the default; a session is opt-in.**

- **No HTTP beside the session and no fallback.** A collector on a session has no HTTP client at all. While no session is up a send fails and the queue keeps the package, as it does when the server is unreachable over HTTP; the queues fill and overflow is reported as usual. Pinned by `expect_no_http_requests` in every session scenario.
- **Who starts and stops the session.** The collector that created the `SessionDataSender` (the first one built from a `CollectorOptions` instance) starts it on every start path, the obsolete `Initialize()` included, and stops it after its drain. A second collector built from the same options shares the sender and neither starts nor stops it (it says so at Start); a sender that was disposed says at Start that nothing will be delivered.
- **A close from the server is answered.** `ClientWebSocket` sends no close by itself, so on a server close (`1001` at a server shutdown) the receive loop answers with close `1000` (one second at most) before the session is given up and reopened; a dropped connection instead would read on the server as a session that broke after its close. Scenario `close_from_the_server_is_answered_and_the_session_reopened`.
- **`SendFile` on a session returns `false`** and the file is not read: the refusal of a file value (`DataProcessor.RefusesFiles`) is reported once per sensor and window and counted as overflow, whether the value came through `SendFile` or `AddValue`.
- **net472 limits.** `AllowUntrustedServerCertificate` makes a `wss` session unavailable (a plaintext `ws` session has no certificate to check and is not affected). An extra request header that `HttpWebRequest` reserves for its own properties (`User-Agent`, `Accept`, `Referer`, `Date`, `Range`, `If-Modified-Since`) is accepted over HTTP but refused by `ClientWebSocket` at connect: every attempt to open the session then fails with that error, reported once per window.
- **The WebSocket is `System.Net.WebSockets.ClientWebSocket`.** The collector frames, masks and parses nothing (owner rule: no self-written protocol code); the JSON envelope is read with System.Text.Json.
- **A frame body is the HTTP body byte for byte.** Every element is written by the serializer of the HTTP client (`HttpRequest<T>.SerializeElement`) and the elements are joined into the array (`SessionTransportTests.Frame_body_is_the_http_body_byte_for_byte`).
- **Upgrade headers**: `Key`, `ClientName`, `X-Collector-Kind: managed`, `X-Collector-Version`, then `CollectorOptions.ExtraRequestHeaders`.
- **Lifecycle** (`SessionConnection`): Start begins connecting in the background and never waits. The first frame must be a `hello` with `maxFrameBytes` >= 1024 and `heartbeatSeconds` in 1..3600. An attempt (connect, upgrade, hello) has 15 s. After a failed attempt or an ended session it tries again on an exponential backoff with jitter, from 1 s to 1 min (each pause between half and the whole step); a session that held for a minute starts the backoff over. A refused upgrade is reported through the deduplicated error channel (`Cannot open a collector session to <url>: <cause>. Values stay queued; retrying.`); `ClientWebSocket` gives no handshake status as a value on these TFMs, but its exception text names it and is passed on. A session that comes up or ends is one Info line each. **A session that ends before it has held for a minute is also reported as an error**, deduplicated (`The collector session to <url> ended early: <cause>`): a server that takes the upgrade and never acknowledges, or closes right after its hello, would otherwise deliver nothing and look healthy at Info level.
- **Heartbeat at the application level**: `{"op":"ping"}` when nothing was sent for `heartbeatSeconds`; the session is given up after two and a half heartbeats without any frame from the server. `ClientWebSocket`'s own keep-alive stays on, for NAT and proxy timers.
- **Requests**: `{"id","op","body"}`, one in flight per queue; the ack is awaited for `RequestTimeout`. **A request without an ack in time closes the session** (a late ack is then impossible) and the package goes back to the queue. A session that drops with a request outstanding is the same failed send. A caller that gives up (a stop cancelling a queue) ends its own wait and nothing else: a frame whose write has begun is finished under the send timeout alone, because cancelling a WebSocket write aborts the connection, and the stop's drain is about to use it.
- **The status of an ack means what the HTTP status means**: 2xx delivered; a registration answered 4xx is final (#1659 A2); anything else is re-sent.
- **Frame limit**: a package is split so that every frame fits `maxFrameBytes` less 64 bytes for the envelope, and each frame is acknowledged on its own. When a later frame fails, the sender tells the queue which items are settled (`PackageSendingInfo.Settled`: delivered in an earlier frame, or dropped) and only the others are re-enqueued, so nothing delivered is sent twice and nothing dropped is counted twice. The same holds for a send cancelled part of the way through a package: it is reported as a failed send with what is settled, not as a cancellation, which would send the whole package back. **A value that cannot fit a frame on its own is dropped**, reported (`Dropped a value of <path>: its N bytes are larger than a collector session frame`) and counted as overflow; sent, it would close the session and come back for ever. A registration that cannot fit is reported and not sent.
- **File values are refused before the queue** (`DataProcessor.AddFile`, `ICollectorTransport.CanCarryFiles`), where a running collector would have queued them: the session has no op for them (step 2b) and there is no HTTP to send them over. One deduplicated error per sensor, counted as overflow. A collector with file sensors stays on `http`.
- **Frames from the server are bounded at 8 MiB** (the native bound); a larger one ends the session. The server states no limit for its own frames (#1667); a success ack is the per-path error dictionary of one package.
- **The queues wake when the session comes up** (`ICollectorTransport.WaitForConnectionAsync`): a package that only lacked a connection leaves when there is one, not a collect period later. Without this every Start registered its sensors one `PackageCollectPeriod` late, because Start does not wait for the session. A package waiting for a connection is not an error of the queue and is logged at Debug; the session reports its own state.
- **Stop**: the drain uses the session if it is up and never waits for a reconnect; then the collector sends close 1000 and gives the server a second to answer (a terminal stop does not wait).
- **`TestConnection()`** on a session answers "yes" when one is up, otherwise opens a session, reads its hello and closes it. It does not use the HTTP test route.
- **When a session cannot exist on the host**, Start completes and does not throw, one error names the cause and nothing is delivered: on `net472` together with `AllowUntrustedServerCertificate` (`ClientWebSocket` has no per-connection certificate callback there, and the process-wide one is not the collector's to change), and on an operating system without a WebSocket client (before Windows 8).
- **Start says** when `Transport = Session` sits next to a custom `DataSender` (the setting has no effect) and when a session is enabled without the `Service alive` sensor (its inactivity alert is the collector's disconnect alert).
- **Directives pushed on the session** (`{"op":"directive"}`, step 5, not sent by the server yet) are handed to the same `ServerDirectives` receiver as the HTTP headers.
- Tests: `HSMDataCollector.Tests/Transport/SessionTransportTests.cs` against `ScriptedSessionServer` (both TFMs), the conformance scenarios `tests/conformance/collector/session_transport_contract.hsmtest`, and a manual run against a real local server over TLS (session up on `wss`, int, string and bar values and `Service alive` stored and read back over the history route, the file value refused).

## Native port (C++) — #1096

The native collector (`src/native/collector`) emits the **byte-identical** wire stream (see `../../api/wire-contract/feature.md`) and ships a real HTTP transport that mirrors this client:

- `hsm_http_transport.{hpp,cpp}` — a libcurl easy-handle wrapper (`Post`/`Get`) that keeps its handle between requests (#1653: before 0.11.3 every request created and destroyed its own handle, i.e. its own connection), confined to one TU so the rest of the core never sees `<curl/curl.h>` and the `-Werror`/`/WX` gate stays green. `CURLOPT_TIMEOUT_MS` ↔ `RequestTimeout`, `CURLOPT_SSL_VERIFYPEER` ↔ `AllowUntrustedServerCertificate`, `CURLOPT_XFERINFOFUNCTION`-abort ↔ `CancelPendingRequests`. Built only when `HSM_COLLECTOR_HTTP=ON` (curl via vcpkg manifest); the default build is curl-free.
- `hsm_http_endpoints.hpp` — pure route table + scheme defaulting (bare host → https; explicit `http` kept only with `AllowPlaintextTransport`), and per-kind / batch / command routing identical to `DataHandlers`/`CommandHandler.GetUri`.
- `hsm_http_retry.hpp` — the retry policy with the `ShouldRetry` semantics of the managed pipelines as they were at #1096 (bounded 5xx retry, unbounded commands exceptions-only, 4xx never). Unit-tested, not used by the send path; its `Commands()` shape no longer exists in managed since 3.6.3 (#1659 A3).

Routing + retry are pure headers compiled into the always-on core, so they are unit-tested in the default `/WX` lane (`native_http_endpoint_routing_matches_net`, `native_http_retry_policy_matches_net`); the transport is exercised by an in-proc capture-server E2E (`native_http_transport_posts_to_capture_server`) in the `HSM_COLLECTOR_HTTP` CI lane. The .NET side of the 5xx fix is pinned by `Retry5xxParityTests` against the fake server.

### Live send-path wiring (#1097)

`TrySendBatch` delegates to a **sender seam** (`sender_`, a `std::function<bool(std::vector<std::string>&)>`). The default records each batch into `sent_values_` so the behavior corpus and the `sent_count`/`get_sent_json` accessors keep working in both build lanes. In the `HSM_COLLECTOR_HTTP` build, `TestInstallHttpSender()` swaps in a real libcurl POST: the batch is joined into a JSON array and sent to the `/list` route with `Key`/`ClientName` headers, exercising the full `add → queue → worker → POST` pipeline. Installed before `Start` (same one-way contract as the clock seam — the worker only reads `sender_` after `Start`, so the swap needs no lock). `StopWorker` calls `HttpTransport::Cancel()` (aborting an in-flight POST so the join stays bounded) and `StartWorker` calls `ResetCancel()` to re-arm after a restart.

Send semantics: **one POST attempt per batch**. A non-2xx or transport failure returns `false`, so the dispatcher re-enqueues the batch at the tail — the same durable-retry contract the C# queue uses (re-enqueue on `PackageSendingInfo.Error != null`, including 5xx and 4xx). The Polly-equivalent in-send exponential/linear backoff (`hsm_http_retry.hpp`, unit-tested separately) is a non-blocking refinement layered on later; doing it inline would block the single worker thread for up to the policy max-delay per batch. The end-to-end live path is pinned by `native_http_live_send_posts_to_capture_server` (drives a real int value through the collector and asserts the captured POST route/headers/body).

**Public live transport (#1165):** `hsm_collector_use_http_transport` (C ABI) / `Collector::UseHttpTransport()` (C++) makes the libcurl transport reachable from application code. Installed before Start, it (a) POSTs the wire `AddOrUpdate` registration batch to `/commands` at Start (the `Type:0` Command discriminator), and (b) switches values/bars to the **server wire format** (`Time` ISO-8601, bar `OpenTime`/`CloseTime`) via `OutgoingValueJson`/`OutgoingBarJson` — the conformance corpus keeps the canonical/in-memory recorder (`send_wire_` is false there). Pinned by `native_http_registers_sensors_on_start` + the wire assertions in `native_http_live_send_posts_to_capture_server`, and proven end-to-end against a Dockerized HSM server by `examples/server-monitor` (registration + live int/double values readable via `/api/sensors/history`). Before #1165 the transport was test-only and posted canonical JSON, so nothing reached a real server. Still open: per-command error-dictionary parse, in-send Polly backoff, and registering sensors created *while running* (today only the Start-batch registers over HTTP).

### WebSocket client connection (#1662, collector session step 1)

A building block for the collector session (ADR-0017, `docs/initiatives/collector-session-websocket.md`), **not used by the send path yet**.

- `WebSocketConnection` (`hsm_ws_connection.{hpp,cpp}`): `Open(url, headers, subprotocol, timeout)`, `SendText`, `Receive`, `Close`, `Cancel`. One owner thread; `Cancel()` is the only cross-thread member and unblocks a waiting `Open`/`SendText`/`Receive`.
- **The protocol is libcurl's, not ours.** The upgrade exchange, masking, frame encoding and frame parsing happen inside libcurl (`CURLOPT_CONNECT_ONLY = 2`, then `curl_ws_send` / `curl_ws_recv`). The collector carries no RFC 6455 code (owner decision, 2026-11-10: no self-written protocol code). The class adds policy only: timeouts, cancellation, whole-message assembly, the size limit, text only, the subprotocol check.
- **A session exists only where libcurl can carry one.** `WebSocketConnection::Supported()` is true when the libcurl in the process is at least 8.14.0 and lists the `ws` protocol. Before 8.13 libcurl does not say which fragment of a message is the last; 8.14 is the first release that lets the caller answer pings (`CURLWS_NOAUTOPONG`), and libcurl's automatic pong is not relied on (8.21 keeps it queued until the next send or data frame). Against headers older than 8.14.0 the class compiles as a stub that reports "unsupported", so the capability is also fixed at build time: a binary built on a host with older libcurl headers has no session even where the runtime libcurl is new enough (the probe's `.deb` is built in `debian:13`, which has 8.14.1). Unsupported means the collector stays on the HTTP transport.
- Where the libcurl comes from: the vcpkg manifests (`src/native/collector/vcpkg.json`, `src/agent/vcpkg.json`, `vcpkg-port/vcpkg.json`) ask for `curl[ssl,websockets]`, pinned at 8.21.0 by the baseline; the Linux probe links the distribution's libcurl, which has WebSocket on Debian 13 (8.14.1) and not on Ubuntu 24.04 (8.5.0). The Conan recipe still pins libcurl 8.10.1, so a Conan build has no session. The registry port under `ports/` gains the feature when the first session-capable version is published.
- `Open` reports the HTTP status of a refused upgrade (404, 503, ...) and the subprotocol the server selected, which must be exactly the offered one (none when none was offered). Refused before anything is sent: a request header name that is not a plain token, a value with a line break (header injection), a name that would replace one of the upgrade's own headers (`Upgrade`, `Connection`, `Sec-WebSocket-*`); and after the response, more than one `Sec-WebSocket-Protocol` line. Only `ws`/`wss` may come out of the handle (`CURLOPT_PROTOCOLS_STR`). The timeout bounds the open only and is cleared on the handle afterwards.
- What libcurl does **not** verify in the upgrade response (checked against 8.21.0): the `Sec-WebSocket-Accept` digest and the `Connection: Upgrade` header. Neither authenticates the server; TLS does, with the same `verify_peer` rule as the HTTP transport. What the digest would have caught is an intermediary that answers `101` without speaking WebSocket: that now surfaces as a frame error on the first `Receive`, not as a failed `Open`.
- `Close(linger_ms)`: `0` (default, and the destructor) writes the close frame once without waiting; a positive linger is the orderly close for a planned stop, waiting for the peer's close so the server sees a normal closure and not a reset.
- Every terminal outcome (failed `Open`, failed `SendText`, `Receive` returning `Closed` or `Error`) releases the connection; `IsOpen()` is the truth and nothing is written to a finished WebSocket. No member throws. Errors carry libcurl's own description when it gives one.
- Waiting is a poll in 100 ms slices (`poll` on POSIX, so descriptors above `FD_SETSIZE` are fine). An idle `Receive` therefore wakes ten times a second; the session transport (step 4) needs its own wake-up primitive for outgoing data anyway and replaces this.
- `Receive` returns `Text`, `Timeout` (connection still usable, nothing lost), `Closed` (close frame or TCP close) or `Error`. It assembles fragmented messages and partial reads, answers pings, ignores pongs, and refuses binary messages and anything over 8 MiB (from the frame header, before the payload is read). Frame-level violations (a masked server frame, reserved bits, a stray continuation) are detected by libcurl and surface as `Error`.
- Tests: `native_ws_*` in the HTTP lane against `tests/ws_test_server.hpp`, an in-process RFC 6455 server. That fixture is the only RFC 6455 code in the repository and never ships; `native_ws_fixture_accept_key_matches_rfc` pins its handshake digest. Where libcurl has no WebSocket the connection tests skip and say so; where `HSM_REQUIRE_WEBSOCKET=1` is set (the CI HTTP lane, both platforms) that is a failure instead. `native_ws_reports_libcurl_support` runs everywhere and checks the unsupported path. The fixture is plaintext; `native_ws_live_probe` is a manual, env-gated check of the TLS path against a real endpoint.

## Known Issues / Limitations

- No circuit breaker pattern. If the server is down for extended periods, each batch attempt will exhaust all retry attempts before failing.
