## Overview

A **batch** (glossary) holds 1 to 4,096 rows of one table sensor after the hourly merge: its columns, coded with the integer and double coders of sealed history (ADR-0020) and compressed with zstd 15. It is internal to the server: nothing outside it reads or writes a batch, so its format can change with a server release under the versioning rules below.

`TableBatchCodec` (`src/database/HSMDatabase.SealedHistory/TableBatchCodec.cs`) is a pure codec next to `ChunkCodec`: no storage, no shared state, safe from any thread. It takes a `TableBatch` (a schema id and columns, the first the time) and returns bytes; it decodes bytes back into a `TableBatch` bit for bit, or throws `TableBatchFormatException` with a `TableBatchFormatError`.

## Invariants

- **Fidelity.** Every value reads back bit for bit: time ticks and 64-bit integers, doubles by their IEEE 754 bits (NaN payloads, ±0.0, ±Infinity). Every null reads back as null; a null cell decodes as 0.
- **Order as given.** Rows decode in the order they were encoded; the codec neither sorts nor requires time order (the merge sorts, stably, before it encodes). The header holds the minimum and the maximum time.
- **Nulls cost the coders nothing.** A null cell is left out of its column's stream (the stream holds the present values only); which rows are null is the column's presence map.
- **An outlier does not cost a double column its decimal mode.** Up to `max(1, n / 256)` values of the column's n present values that are not decimals of the column's exponent are set aside as exceptions.
- **Never larger than raw by much.** Each column is written as the rule's coded stream or as raw 8-byte values, whichever is smaller after zstd at level 1; the whole payload is one zstd 15 frame, or stored as it is when that is not smaller.
- **Fail loudly, never partially.** A damaged batch is refused with a named error; the reader never returns an empty or partial batch. Every size the reader allocates is bounded by the header's row and column counts (at most 4,096 × 255), and a header that declares more payload than those counts allow is refused before anything is allocated.
- **The sealed coders' output for sealed chunks does not change.** The batch codec uses two additive helpers (`IntColumn.WriteVarint`, `DoubleColumn.WriteDecimal`) and an overload of `DoubleColumn.TryFindDecimalExponent` with exceptions; `IntColumn.Write`, `DoubleColumn.Write` and every sealed golden chunk are unchanged.

## Byte layout (format version 1)

All integers are little-endian.

### Header (48 bytes)

| Offset | Size | Field | Rule |
|---|---|---|---|
| 0 | 2 | magic | ASCII `HT` |
| 2 | 1 | format version | `1`; the same position in every version |
| 3 | 1 | encoder revision | any value; readers ignore it |
| 4 | 1 | flags | bit 0: the payload is one zstd frame; the other bits zero |
| 5 | 3 | reserved | zero |
| 8 | 4 | schema id (u32) | the table sensor's schema id (`TableSchema.Id`); opaque to the codec |
| 12 | 4 | row count (i32) | 1..4,096 |
| 16 | 1 | column count | 1..255 |
| 17 | 3 | reserved | zero |
| 20 | 4 | payload length (i32) | the decompressed payload; `columns ≤ length ≤ columns × (rows × 16 + 1,024)`; equal to the stored length when not compressed |
| 24 | 4 | stored length (i32) | ≥ 1; the batch is exactly `48 + stored length` bytes |
| 28 | 8 | first time | the minimum of the time column; equal to the last time for one row |
| 36 | 8 | last time | the maximum of the time column |
| 44 | 4 | checksum | CRC-32C (Castagnoli), as in sealed chunks: over bytes 0..43, then the stored bytes |

CRC-32C and not the CRC-32 of blocks: a batch never leaves the server, so the constraint that chose CRC-32 for blocks (the collector's target frameworks) does not apply, and the hardware CRC-32C of `ChunkCodec` is reused.

When flag bit 0 is set, the stored bytes are exactly one zstd frame (not skippable) that declares a content size equal to the payload length; it is checked before decompression. The encoder compresses at level 15 and stores the payload as it is when the frame is not smaller.

### Payload

```
types        column count bytes: 1 time, 2 int64, 3 double; the first is 1
column 0     an integer stream of row count values (the time; never null)
column c ≥ 1:
  presence   the sealed Presence: 0 every row present, 1 no row present,
             2 then ceil(rows / 8) bytes, bit i (byte i / 8, bit i % 8) set = row i present; padding bits zero
  if at least one row is present (n present values):
    time or int64 column: an integer stream of n values
    double column:
      exceptions  varint count k, 0 ≤ k ≤ max(1, n / 256), k < n;
                  then k times: varint delta of the value's index among the n present values
                  (the first absolute, then strictly ascending: every later delta ≥ 1), 8 bytes of the value's bits
      a double stream of the n − k values that are not exceptions, in order
```

The payload ends right after the last column. Presence is the inverse of a null map: a bit set means a value.

### Streams

Every stream starts with an encoding byte:

| Byte | Encoding | Allowed for | Body |
|---|---|---|---|
| 0 | raw | every column | the values, 8 bytes each (a double by its bits); a double column's exception count must be 0 |
| 1 | integer coder | time and int64 columns | an `IntColumn` stream (sealed format: mode 0 constant, 1 varints of residuals of order 0..2, 2 bit buckets) |
| 2 | double coder | double columns | a `DoubleColumn` stream (sealed format: mode 0 constant, 1 XOR bytes, 2 decimal with an `IntColumn` stream of mantissas, 3 Gorilla) |

The integer and double streams are byte for byte the layouts of `aicontext/features/storage/sealed-history/feature.md`, read by the same `IntColumn.Read` and `DoubleColumn.Read`.

## The rule (encoder revision 1)

How the encoder chooses, per column. A reader does not depend on any of it: any stream the table above allows decodes.

- **Time and int64:** the coded stream is mode 0 (one constant) when every value is equal, otherwise mode 1 with order 1 (varints of the first difference).
- **Double:**
  1. Every value equal: the double coder's own choice (mode 0, one constant).
  2. Every value a decimal of 0..15 digits (`DoubleColumn.TryFindDecimalExponent`): mode 2 with the smallest such exponent, the mantissas as one constant or varints of their first difference. No exception.
  3. Otherwise, the smallest exponent for which at most `max(1, n / 256)` values do not fit, and fewer than n: those values are exceptions, and the rest are coded as in 2 with the smallest exponent they all fit.
  4. Otherwise (the decimal mode is given up): no exception, the double coder's own choice among XOR bytes and Gorilla.
- **Raw or coded:** the column's coded form (the exception list and the coded stream) and its raw form (exception count 0 and the raw stream) are each compressed alone with zstd level 1; raw is written only when it is strictly smaller.

Why a fixed rule and not a choice among every candidate after zstd (measured, #1850 phase A, synthetic quotes hour): the coders as they are choose their mode by size before zstd and give 2.75 bytes per row; compressing every candidate at zstd 15 and keeping the smallest gives 2.195, but costs 4.5 µs per row; making the same choice at zstd 1 or 3 costs 0.8–0.9 µs per row and gives only 2.35, because at those levels the XOR and Gorilla streams look smaller than decimal mantissas as varints while at level 15 the varints win. The fixed rule gives 2.193, as good as the exhaustive choice, and with the comparison against raw it costs 0.45–0.58 µs per row (`TableBatchBenchmark`). The time column goes from 2.18 to 1.78 bytes per row (varints of differences instead of bit buckets), as on the real hour (17–32%). One zstd frame for the whole payload is smaller than one frame per column (2.193 against 2.303). A once-a-day exhaustive check per sensor was considered and not built; it would be a new encoder revision.

Measured with outliers (0.05% of ask values outside any decimal): the coders as they are 3.25 bytes per row, the rule with exceptions 2.21 (the clean hour: 2.20). Nulls: 0.05% of cells +0.4%, 5% of cells +13%, mostly the presence maps themselves.

## Errors

| `TableBatchFormatError` | When |
|---|---|
| `NotABatch` | the first two bytes are not `HT` |
| `UnknownVersion` | the format version is not 1 |
| `Truncated` | shorter than the magic, the version, the header, or the declared stored length |
| `ChecksumMismatch` | the CRC-32C does not match |
| `LengthMismatch` | a stored length below 1; bytes after the stored payload; a payload length outside its bound or, uncompressed, not the stored length; a decompressed payload of another length; bytes after the last column |
| `CorruptHeader` | unknown flags, reserved bytes not zero, a row count outside 1..4,096, no column, first time after last time (or not equal for one row) |
| `CorruptFrame` | the stored payload is not exactly one zstd frame of the declared content size, or it does not decompress |
| `CorruptStream` | an unknown column type, a first column that is not the time, an unknown encoding or one not allowed for the column, a stream cut short, a bad mode, varint or presence map (any refusal of the sealed coders) |
| `CountMismatch` | an exception list longer than allowed or than the column, out of order or beyond the column, or beside a raw stream |
| `HeaderMismatch` | the decoded time column does not have the header's first and last time |

## Versioning

As ADR-0020 point 12 for sealed chunks:

- **A new format version** for any change a reader of the current version would decode differently or refuse: a new encoding or column type, a header of another layout, another meaning of a field, another checksum or compressor, a change of a limit (4,096 rows, 255 columns, the exception bound, the payload bound). A reader refuses an unknown version and decodes every older one forever.
- **A new encoder revision** for different bytes of the same rows that a current reader decodes: another rule, other zstd levels (15 for the frame and 1 for the choice are pinned by a test), a zstd library whose output changes. The revision records which encoder wrote a batch; readers ignore it.
- **Golden batches** (`src/tests/HSMDatabase.SealedHistory.Tests/GoldenTableBatches/format{F}-encoder{R}/*.htbatch`) stay forever as decode tests; the set of the current revision also pins the bytes the encoder writes. `HSM_WRITE_GOLDEN_TABLE_BATCHES=1` writes a missing set and never overwrites one.

## The batch store (#1850, part 2)

`TableBatchDatabase` (`src/database/HSMDatabase.LevelDB/TableBatches/`, behind `ITableBatchStore` in `HSMDatabase.AccessManager/TableBatches/`) keeps the batches of merged hours. `IDatabaseCore.TableBatches` holds the one instance; `DatabaseCore.Dispose` closes it. Nothing is opened or created before the first call that needs a product.

### On disk

| Path | Holds |
|---|---|
| `<Tables>/BatchesV1/` | The store. The version is in the name: an incompatible layout is a new folder, and a server that does not know it ignores it. |
| `<Tables>/BatchesV1/<productId:N>/Hours` | LevelDB, the product's merged hours. Key: the merge hour, ticks, big-endian (8 bytes); value: the hour's record (below). A merged hour is committed by this record. And the **complete key** (two bytes, `0xFF 'C'`, value `1`): the database is trusted only with it ("What is in memory"). |
| `<Tables>/BatchesV1/<productId:N>/Placements` | LevelDB, the product's placements ("Placements", below), with the same complete key. |
| `<Tables>/BatchesV1/<productId:N>/Dropped` | A text file, the product's record of dropped week databases: one name `<yyyyMMdd>_P<weeks>` per line. Written atomically and durably (`DurableFile.WriteAtomic`, strict: a temporary file flushed, renamed with write-through on Windows, the folder synced on Linux) before a dropped database's folder is deleted. On Windows a rename another process holds for a moment is retried for up to 940 ms (`DurableFile.RenameRetryPauses`, #1883), for this file and every other `DurableFile` file of the store; the wait runs under the lock the write holds (`Dropped`, `Move` and `Compact` under the product's lock, `Removed` under the removals lock), so their other users wait with it. Outside `Hours`, so it survives the loss of `Hours`. Absent until the first drop. |
| `<Tables>/BatchesV1/<productId:N>/Move` | A text file, the product's step of the move between period classes in flight (#1850 part 4c): one line, `1 <sensor:N> <yyyyMMdd>_P<from> <from> <to> <first hour ticks> <end hour ticks>`. Written with `DurableFile.WriteAtomic` (strict) and deleted when the step is done (`SetMoveInFlight`). A file and not a key in `Placements`: a rebuild of the placements deletes every key there, and `LoadPlacements` refuses any key that is not 16 bytes. A file that does not read (damaged, of another format, or that cannot be opened: a sharing violation, an access right) is logged as an Error and taken as none, and the product opens (the placement, not the record, says where the rows are). Absent while nothing is in flight. |
| `<Tables>/BatchesV1/<productId:N>/Compact` | A text file, the product's week databases due for a compaction (#1850 part 4c): one name `<yyyyMMdd>_P<weeks>` per line, written as `Dropped` is, so a compaction decided before a crash is not forgotten (`AddToCompactList`, `RemoveFromCompactList`). A file that cannot be read at the open is logged as an Error and taken as empty: it is a hint, a database's counter says again whether it is due. Absent while empty. |
| `<Tables>/BatchesV1/Removed` | A text file, store-wide, the removals the tree recorded (#1850 part 4d, "The removal"): one mark per line, `S <sensor:N> <product:N>` for a table sensor (the product of 32 zeros when the tree did not know it) and `P <product:N>` for a root product. Written with `DurableFile.WriteAtomic` (strict) and deleted when empty. A file that cannot be read is a fault at every call until it reads, and is never written over. Absent while nothing is removed. |
| `<Tables>/BatchesV1/<productId:N>.removed-<ticks>` | The folder of a removed product between its rename and its delete (`RemoveProduct`): never listed as a product (its name is not an id), deleted by the store's first listing of its products in a later run when a crash or a failed delete left it. |
| `<Tables>/BatchesV1/<productId:N>/<yyyyMMdd>_P<weeks>` | LevelDB, one per Monday-aligned week (`StorageWeek`) of the merge hour and per retention period class: `weeks` whole weeks, `P0` kept forever. No LevelDB compression (batches are zstd already), every write synced. |

The open of a product and `GetProducts` look at folders only (`GetProducts` at folders whose name is a product id): the files above, their temporary `<name>.tmp` left by a write that stopped, and any other file are ignored, by this build and by the builds before it (`The_move_in_flight_and_the_compaction_list_are_durable_files_that_the_open_the_product_list_and_a_rebuild_of_the_placements_leave_alone`).

The database of a batch is (product, week of its merge hour, the sensor's period class at the merge). Outside a move between classes (part 4), the rows of a sensor for a week are in one database, the one of its current class, so a read looks in one database per week.

### Keys of a week database

| Region | Key | Value |
|---|---|---|
| Index | `hour (i64 BE) \| 0x00 \| sensor id (16, big-endian Guid bytes) \| first time (i64 BE) \| ordinal (i32 BE)` | u8 version (1), i64 last time, i32 rows, i32 stored length (17 bytes, little-endian) |
| Batches | `hour \| 0x01 \| ordinal` | the batch (the format above) |
| Mark | `hour \| 0x02` | the hour's record, the same bytes as in `Hours` |
| Moved batches, index | `0xFF \| hour \| sensor \| 0x00 \| first time \| ordinal` | as the index |
| Moved batches | `0xFF \| hour \| sensor \| 0x01 \| ordinal` | the batch |
| Deleted-bytes counter | `0xFE 'D'` (two bytes) | i64 little-endian: the stored bytes of the batches `DeleteSensorHours` and `CopySensorHours` deleted from this database since its last `CompactWeek` (#1850 part 4c); absent: 0 |

The counter key lies above every hour key (they start with `0x00`..`0x2B`) and below the region of moved batches; no scan of a week database meets it, in this build and in the one before it (5bb5933e5): every scan seeks a prefix of an hour (eight bytes, nine with a tag, 25 with a sensor: `DeleteHourKeys` and so `RemoveStaleParts` and the rewrite of an uncommitted hour, `ReadSensor`, `RebuildPlacements`, and the new `DeleteSensorHours`, `CopySensorHours`, `GetSensorHourBytes`) or of `0xFF | hour`, and the rest are exact `Get`s of an hour's mark (`Rebuild` of `Hours`, `ReadMark`, the copy); `Hours` and `Placements`, whose loads and rebuilds read every key, never hold it. **The flush** (`CompactRange(FlushKey, FlushKey)`, when a week stops being the newest and when a dirty database is closed) compacts at the point `0xFF 0xFF`, above every key a week database holds, so no table file contains it and the call only writes the memtable out as one new table file: measured with the native library (`A_flush_writes_the_memtable_out_and_rewrites_no_table_file`: three table files of 50,543, 186 and 12,607 bytes stay as they are and one of 4,247 bytes is added). The earlier point, `0xFE`, lay between the hour keys and the region of moved batches: a table file written from a delete (hour-key tombstones and the counter) or a copy (the hour's mark and moved keys) contains it, and every flush then compacted such files with the next level's files they overlap (in the same test the 186- and 12,607-byte files were rewritten into one of 12,689), while `Close` flushes under the store-wide cache lock and `PinWeek` under the product's lock. Only week databases are flushed: `Hours` and `Placements` (whose 16-byte sensor keys can start with `0xFF 0xFF`) never are.

The region of moved batches is ordered by hour first (#1850 part 4b): every key of an hour there is one prefix, `0xFF | hour`, so writing an hour again deletes it with the hour's region in one seek (see "Moved batches and an hour merged again"). A read seeks `0xFF | hour | sensor | 0x00` once per hour, as it seeks the hour region.

The ordinal numbers the batches of one hour in one database in the order the merge gives them; a sensor's batches of an hour are in their row order. Every hour key is below `0x2C…` (the ticks of `DateTime.MaxValue` start with `0x2B`), so the region of moved batches, written by a move to another period class (part 4), lies after every hour key: ingest only appends at the end of the hour region and a move only writes into its own region, and neither makes LevelDB rewrite the other. The merge writes hours in order, so the keys of a database only grow.

### The record of a merged hour

Little-endian: u8 version (1), i64 hour, i64 first block sequence, i64 last block sequence, i32 blocks merged, u16 class count, per class (u16 period weeks, i64 minimum row time, i64 maximum row time, i32 batches, i64 rows), i32 count and the i64 sequences of the blocks the merge could not read, i32 count and per producer (16 bytes producer id, i64 sequence) the product's watermarks after the hour (cumulative), i64 the commit time (UTC ticks, the store's clock when `WriteHour` wrote the hour; last in the record). A record that does not decode is a `FormatException` at the open. The commit time is what the deletion delay of the hour's blocks runs from, also across a restart (`TableBatchHour.CommitTicks`). The field was added before the store was released, without a version step. A mark holds the time its part was written; an `Hours` database rebuilt from the marks takes the time of the rebuild as the commit time of every hour it rebuilds (the safe side: their blocks live a little longer).

### Writing an hour

**An hour of a product is merged atomically by its commit.** Its batches may span several databases (one per period class of its sensors), so there is no single write for all of them: each class's part is written with its mark in one synced write of its own, and the hour's record in the product's `Hours` database, written last, is the commit point. Before the record the hour is not merged, whatever parts are on disk; after it the hour is merged. `Hours` is rebuilt from the marks when it is missing or damaged. This also lets a product's merged hours be known at its first use without opening a single week database.

`WriteHour(product, commit, parts)`, one part per period class:

1. If the hour is committed, nothing (a repeat changes nothing). `WriteHour` checks this under the product's lock against the hours in memory, loaded from `Hours` at the open, so a committed hour is never written again.
2. The record is encoded once: every mark this run writes is the same bytes, the commit time included (two runs differ at least in it).
3. Per part, in class order, in the week database of the class: one synced write of the index records, the batches and the mark. Every key the database already holds of the hour, in both regions (the hour's own keys and its moved batches, `0xFF | hour`), is deleted in the same write first, **whether or not a mark of the hour is there** (#1850 part 4b, after the review of 139327ef1; before, only a database with a mark was cleared): the part is **always** written again. Its metadata cannot tell which sensors' rows it holds: two sensors that swapped classes between the runs, one row each at the same time, give parts with the same counts and ranges.
4. Then every other week database of the product's week (a class the record does not name) that holds any key of the hour, with or without its mark (a part of a run that did not commit, before a sensor's period changed; a moved copy of the hour): the hour's keys in both regions deleted, one synced write each. After the parts, not before: see the table.
5. The record into `Hours`, synced: the hour is merged from here on.

Each part written over keys of the hour (3) or deleted (4) is counted in `PartsRewritten` once its write succeeded (not posted to self-monitoring, like `HoursRebuilt`) and logged as a warning. Of the region of moved batches only the hour's own keys are touched. A database a part is deleted from is pinned as a written one is, so the newest week's databases are all flushed when the next week starts.

So at the commit every mark of the hour is its record, byte for byte, and `Rebuild` takes an hour only when its marks are the same bytes. A crash of a repeat (record R2) over the parts of a run that did not commit (R1):

| Crash | On disk | `Hours` lost: the rebuild | and a class database dropped first |
|---|---|---|---|
| before the first part of R2 is durable | R1 parts as they were | as for the crash of R1 | as for the crash of R1 |
| inside the first synced write, after it became durable, or after some parts of R2 | R2 and R1 marks, or R2 marks with a part of R2 missing | not committed (marks differ, or a part missing) | a dropped class counts as found. R2 marks only, every other class of R2 present or dropped: committed with R2. R1 and R2 marks: not committed. A lone mark of an earlier run (R2's parts all in classes dropped since) is taken as committed once every other class it names is dropped (see Known Issues: with a period change between the runs this loses rows) |
| after every part of R2, during the removals | R2 marks, R1 marks in classes R2 does not name | not committed | dropping every remaining R1 class leaves R2 marks only: committed with R2 |
| after the removals, before `Hours` | R2 marks only, complete | committed with R2 | committed with R2's classes left, if at least one R2 mark survives |
| after `Hours` | committed | | |

"Committed with R2" needs at least one R2 mark on disk: an hour whose record has no parts, or whose classes were all dropped before the rebuild, is not restored and stays not merged. That loses nothing a read could still serve, but its blocks are in general **not** still there: the readable blocks of a committed hour are deleted after the delay (`DeleteMergedBlocksAfterHours`), and only those its record lists as unreadable stay until they expire. An hour whose every class was dropped had expired by then (a class is dropped only once the rule of expiry lets it), so its rows are gone by retention, not by the rebuild; an hour without parts held no batch (every row refused, dropped or expired). While its blocks are still kept (within the delay, or unreadable ones), the merge takes it as not merged and writes it again from them, as for any uncommitted hour.

Without the loss of `Hours` the hour is simply not merged until the merge repeats it, and the repeat writes every part again. The old order (removals first) lost rows: R1 in P0 and P1, R2 names P0 only (B moved to P0); the repeat removed P1's part and crashed before P0; P0 kept R1's mark, which names P1; with P1 dropped and `Hours` lost, the rebuild committed R1 with P0's rows of A only, and the deletion of the hour took B's blocks. Residual: two runs whose clocks gave the same tick have equal marks if their metadata is equal too (not seen with the system clock between a crash and a repeat).

Pinned by `TableBatchDatabaseTests`: `Two_sensors_that_swapped_classes_between_the_runs_...`, `A_repeat_with_another_batch_split_...`, `..._another_list_of_unreadable_blocks_...`, `A_sensor_moved_to_another_class_between_the_runs_...`, `A_repeat_equal_to_the_crashed_run_writes_its_parts_again_...`, `A_repeat_that_moved_a_sensor_and_crashed_leaves_no_rebuilt_hour_without_its_rows` (crash after the part, after the removal; the old class dropped, `Hours` lost), `A_repeat_that_crashed_before_removing_the_old_class_part_is_not_rebuilt_...`, `The_database_a_repeat_removed_a_part_from_is_flushed_...`, and for the rebuild `A_rebuild_does_not_commit_an_hour_whose_marks_disagree` and `A_rebuild_does_not_commit_parts_of_two_runs_with_the_same_metadata_and_another_commit_time`. A database closed without a flush replays its log at the next open: `A_crash_at_any_point_of_the_hour_write_...` (after the first of two parts, before the commit, after it) and `A_store_that_stopped_without_closing_its_databases_...`.

### What is in memory

Per product opened: the merged hours with, per class, the minimum and maximum row time (a read selects hours by them: a late block makes an hour reach back), the watermarks (per producer the highest over every commit of the product, whatever order the hours were committed in: an hour merged after a later one may name a producer the later one does not), the week databases on disk. Loaded from `Hours` at the product's first use, without opening a week database. `GetHours` lists the hours that hold batches and whose week still has a database of any class, each with every class its record names, dropped ones included (#1850 part 4b): a sensor's rows of an hour may be in a class the record does not name (moved there), and their times are then within the record's ranges, so a read takes the sensor's class from its placement and selects the hour by the union of the record's class ranges ("The read", step 3; #1850 part 4c, before it the class's own range when the record named it). **`Hours` is trusted only with its complete key** (#1850 part 4b, after the review of 139327ef1). If `Hours` is missing, or exists without the key (new, or left by an open that stopped), it is rebuilt from the marks of the week databases, visited by week start then class (an hour whose marks are the same bytes, commit time included, and whose mark is in every database its record names; marks that differ are parts of two runs, an hour not committed, left on its blocks; a class the record of dropped databases names for the hour's week counting as found: the hour is restored with the classes left); if its open fails with LevelDB's corruption or a record does not decode, it is moved aside to `Hours.damaged-<ticks>` and rebuilt the same way. A rebuild writes nothing before its scan has ended: its result and the complete key go in **one synced write**, which also deletes whatever the database held (without the key nothing of it was trusted). So no state is trusted without a positive mark: a crash right after `Hours` is created (a valid, empty database), a crash or a week database that does not open during the scan, and an orderly shutdown during the open (the dispose marks the store closed, the scan's next week database is refused) all leave an `Hours` without the key, and the next open rebuilds again. For a product that never had batches the rebuild is an empty scan and the write only marks the new `Hours` complete (one more synced write at a product's creation; not counted in `HoursRebuilt`, not logged). An `Hours` with its key is the truth, also when it is empty: a first hour whose commit was not written is not merged. The earlier rule (an `Hours` whose folder exists is trusted, unless it holds the key `[0xFF]` a rebuild wrote before its scan) left a hole between the creation of the folder and that first write. **A database written before the complete key has none, and is rebuilt at its next open** (accepted: the branch is not released). Its cost, once per product: every week database of the product opened once (about 14 ms each) with 168 reads of marks, for `Hours`, and one seek per committed hour and week database for `Placements` (measured for five years of hourly commits of one class, 43,800 hours in 261 week databases: 8.8 s for `Hours`, 4.6 s for `Placements`, see "Measured" under "Retention"); every hour's commit time becomes the time of the rebuild (the blocks of hours merged within the deletion delay live up to that delay longer); an hour committed without any batch, or whose week has no database left, is not restored (Known Issues); and a rebuilt placement has the class of the sensor's newest hour as its target, a change of period recorded but not yet in any merged hour being recorded again, from a new cut-off, by the next pass. Pinned by `A_crash_right_after_the_hours_database_is_created_leaves_nothing_trusted_and_the_next_open_rebuilds`, `A_crash_during_the_scan_of_a_rebuild_is_not_trusted_and_the_next_open_rebuilds_again`, `A_dispose_during_a_rebuild_of_the_hours_leaves_nothing_trusted_and_the_hours_are_back_after_a_reopen`, `A_new_product_is_marked_complete_at_its_creation_and_its_empty_hours_are_the_truth`.

**The generation** (#1847, #1850 parts 4b and 4c), in memory only, per product: the product's term and, per sensor, the sensor's term (`ITableBatchStore.GetGeneration(product, sensor)` = product term + sensor term; `GetGeneration(product)` = product term + the product's sensor counter, "anything changed in the product"). The product's term changes with every write that any sensor's read plan can see: a commit (one without any class too), a week database created by the write of an hour (also one that does not reach its commit), `DropWeek`, `ForgetHours` that removes an hour, a rebuild of `Hours` or of `Placements`. A write that only one sensor's plan can see sets that sensor's term to the next value of the product's sensor counter: `SetPlacement` of the sensor (a plan reads only its own sensor's placement) `CopySensorHours` and `DeleteSensorHours` of the sensor (every key they write or delete carries the sensor's id, or for a batch of the hour region the ordinal of one of the sensor's own index records, and a week database the copy creates holds no row of another sensor, whose rows of the week could only have gone into a database that existed then: the copy's source is a database of the same week). A copy that finds nothing of the sensor in the source, whatever the target holds, creates no database, writes nothing and changes no generation (`A_copy_with_nothing_of_the_sensor_in_the_source_writes_nothing_creates_no_database_and_changes_no_generation`; the `WriteMoved` it replaces changed the product's term for an empty list). All of it under the product's lock, which every such write holds too: each term only grows, so no reading goes back, and two equal readings of a sensor's generation mean that neither term changed between them. A sensor's entry is never removed (removed, it would read 0 again and could equal a value an older plan took): about 40 to 50 bytes per sensor written in this process, 50 KB for 1,000 sensors. The per-sensor entries are kept on purpose, not leaked: nothing removes one (a removed entry would read 0 again and could equal an old plan's reading), so they are bounded by the sensors ever placed in the product while the process lives. Nothing of it is on disk; a plan never spans two processes. Effect: a placement write or a move of one sensor never makes a chart or a read of another sensor of the product plan again (`TableChartReadTests.A_move_step_of_one_sensor_plans_no_chart_of_another_again_...`), and a folder-level period change (a placement written per sensor in one `Reconcile`) no longer makes every chart of the product plan again once per sensor. Pinned for the store by `TableBatchDatabaseTests.A_sensors_generation_changes_with_its_own_placement_and_moved_batches_and_with_every_write_of_its_product`.

**Opening a product** (#1850 part 4, after the review of #1867): the store-wide `_productsLock` only finds or adds the product's slot; the open itself (`Hours`, and a rebuild that opens every week database of the product) runs under the slot's own gate, outside that lock. So two calls for the same product get one open (the second waits on the gate and takes the first one's state), and a slow open never holds up a call on another product, `IsOpened` or `WeekDatabases` of the self-monitoring tick (`WeekDatabases` copies the opened products under the lock and takes each product's lock outside it). An open that fails leaves the slot empty: the next call opens again (a `Lazy` would have kept the exception until a restart), and nothing it opened stays open: its `Hours` and `Placements`, and every week database a rebuild had opened through the cache and let go (a first week scanned, a second that failed to open; `An_open_whose_rebuild_fails_at_a_later_week_leaves_no_week_database_open`). A dispose that starts during an open waits on the slot's gate; the open sees the store closed, closes its `Hours` and fails with the "closed" fault. Pinned by `TableBatchDatabaseTests.Two_calls_for_the_same_product_get_one_open_and_another_product_is_not_held_up_meanwhile`, `An_open_that_failed_is_retried_by_the_next_call`, `A_dispose_during_an_open_waits_for_it_and_leaves_nothing_of_it_open`. The two concurrency tests force their order of events by the store's checkpoints: `"product-opening"` holds the opener under its gate until the test releases it (a wait without a bound), and a caller that finds a slot held says so right before it waits for it (`"product-busy"` for a call, `"dispose-open-busy"` for a dispose); the only bounded waits are assertions, whose expiry fails the test.

### Week databases: the bound, the flush

- The databases of a product's newest week written are pinned. When a later week is written, the databases of the earlier ones are flushed (a `CompactRange` at a point above every key, `0xFF 0xFF`, writes the memtable out and merges no file; see "Keys of a week database") and unpinned: a closed week has no log to replay when it is opened again.
- Every other database is opened on demand (a read, retention, a rebuild) through one cache for the whole store, at most `MaxOpenDatabases` open (`TableSensors.MaxOpenBatchDatabases`, 32 by default), least recently used closed first. A database is held only while a read or a write uses it; a read of many weeks holds one week at a time. Pinned and held databases are never closed, so the count can be above the bound while they are more than it.
- A database is opened with `MaxOpenFiles` 100.
- Opens go through `LevelDbOpen.Open` (`src/database/HSMDatabase.LevelDB/LevelDbOpen.cs`), the block store's retry made shared: an IO error that names the temporary `.dbtmp` file (in practice the replace of `CURRENT`) is retried four times with pauses of 10, 30, 60 and 120 ms, any other error fails at once; a Warn line per retry.

### Reading

`ReadSensor(product, sensor, period class, hours)`: per week of the hours, the database of that week and class (none: nothing, nothing created); per hour one seek to `hour | 0x00 | sensor`, then one seek into the region of moved batches of the sensor; each index record with its batch. In hour order, then the hour region before the moved region, then by ordinal. An index record that does not decode or whose batch is missing is counted (`ReadFailures`) and skipped. `ReadSensor(..., fromTicks, toTicks, out failed)` (#1850 part 4c, what the read of `TableBlockService` calls) skips an index record whose rows (its first time in the key, its last time in the value) cannot meet `[from, to)` before it fetches the batch: such a record is neither returned nor counted, also when its batch is missing (it would add no row to the answer). A record that does not decode is counted: its range is not known. Pinned by `TableBatchDatabaseTests.A_read_with_a_range_skips_a_record_out_of_it_before_its_batch_so_only_a_missing_batch_in_the_range_fails`.

### Dropping a week

`DropWeek(product, week)`, under the product's lock:

1. Marks the database as being dropped in the cache: from then on a read finds nothing there and does not open it again, and a write into it is a fault. Waits for the reads that hold it (looking the handle up again after every wait: a read's release may have closed it over the bound) and closes it.
2. Adds the database to the record of dropped databases (`Dropped`), durably, before anything is deleted. Then deletes its folder.
3. The mark of step 1 is cleared. **The hours of the week keep their records** (#1850 part 4b): an hour leaves `Hours` only through `ForgetHours`, which retention calls once no database of its week is left and the block store holds none of its blocks. Until then the hour stays merged, so the merge never takes an hour whose blocks are still held (unreadable ones, kept until they expire) as not merged and merges it again; it is not listed by `GetHours` once its week has no database, and a read finds nothing for it. `GetHoursWithoutDatabases` lists such hours. Pinned by `A_dropped_week_is_gone_from_disk_and_its_hours_stay_committed_until_they_are_forgotten` and `Forgetting_hours_that_fails_is_a_counted_store_fault_and_the_hours_stay_committed`.

Why the record: the mark of an hour in the databases of its other classes still names the dropped class. Without the record a rebuild of `Hours` could not tell a class retention dropped after the commit from a part a crash left unwritten, and an hour of a forever class would be lost once a shorter class of its week was dropped. With it, a rebuild counts a recorded class as found; a part never written (no record) still keeps its hour out.

- **A write into a dropped database is refused** (`TableBatchStoreException`, counted in `Batch write failures`), by `WriteHour` before anything is written and by `CopySensorHours`: its period has passed, and a database created again would make the record wrong. The merge leaves out the rows that would go into a dropped database (`IsWeekDropped`, see "The one rule of expiry").
- **A delete that fails** (a file held open, a permission) throws `TableBatchStoreException` with the week dropped all the same: gone from `GetWeeks` and from the hours' classes, absent to reads, the folder left on disk. The next open of the product deletes a folder the record names (also one a crash left between the record and the delete); if that fails too, the folder stays absent until the open after. A record that cannot be written fails the drop before anything is deleted: the week stays listed and readable.
- **Forgetting hours that fails** (the write into `Hours`) throws `TableBatchStoreException`, counted in `Batch write failures`: the hours stay merged, and retention tries again an hour later.
- **Bounded:** an entry stays while a database of its week is left (a mark there may name it) or its own folder is still on disk; the others go when the record is next written. It holds at most the dropped classes of the weeks still on disk: a few lines a week for a product with a forever class, nothing once a week's last database is dropped and the record written again.

### Closing the store

`Dispose` refuses every operation that starts after it (`TableBatchStoreException`, "closed"), then closes each week database once the reads and writes that hold it let it go, and each product's `Hours` under the product's lock, so after a write in flight. Closing a LevelDB database under a live iterator or a running write would free it under native code. No timer bounds the wait: an operation in flight ends. A write in flight that needs another week database after the close began fails with the "closed" fault and leaves its hour not committed.

### The block store's part

- `CloseHour(hour)`: no block is appended to that hour or an earlier one afterwards, also with the clock behind (held in memory: the merge closes its newest hour again after a restart).
- `DeleteMergedHour(hour, keep, watermarks)`: under the append lock, raises the watermarks, deletes the hour's blocks except `keep` (a set of sequences: blocks the merge could not read, and the blocks of the hour's other products when one product's blocks are deleted) from `Blocks` (synced) and then `BlockIndex` (a repeat removes index entries left by a crash between the two), and drops them from the in-memory index and the duplicate map; then compacts the range outside the append lock.
- Watermarks per product and producer, in memory (`RaiseWatermarks`, `GetWatermark`): an append at or below its producer's watermark is a duplicate with `Merged`, which the block service answers as `Duplicate` with `RefusalsKnown` false, no sequence and no refusals (`RefusalsKnown` is true by default and false also for a duplicate whose stored envelope cannot be read; the same shape as the wire step's). The durable watermarks are in the records of the merged hours (`GetWatermarks`); the merge raises them before the first put after a start (part 3).
- `TableSensors.DeleteMergedBlocksAfterHours` (24 by default, 0..8,760): how long the blocks of a merged hour stay after its commit; reads of a merged hour take the batches and ignore them (part 3).

### Self-monitoring

Under `Database/Tables`, once a product of the batch store was opened in this process: `Batch databases open`, `Batch week databases`, `Merged hours` (product hours committed), `Batch write failures` and `Batch read failures` (Error in the sample in which they grew), and the merge's sensors (section "Self-monitoring of the merge").

## The merge (#1850, part 3)

`TableMergeJob` (`src/server/HSMServer.Core/TableSensors/TableMergeJob.cs`), owned by `TableBlockService` (`Merge`) and run by `TableMergeService` (`src/server/HSMServer/BackgroundServices/DatabaseServices/`): one pass a minute after a start delay of a minute, one pass at a time, at below normal priority. A pass does nothing and opens nothing on a server without a `Tables` folder. The pass takes its clock as a parameter (`RunPass(utcNow, token)`); it never throws: a fault is logged, counted and reported in its `TableMergePassReport`.

### A pass

1. **The state after a start, per product** (`TableBlockService.EnsureMergeState(product)`, once per product, before its first put and before the merge of its first hour): the product's watermarks are raised in the block store (`GetWatermarks` → `RaiseWatermarks`), and its newest committed hour (`GetNewestHour`) is closed (`CloseHour`, so no block of the product lands in an hour committed for it). A product whose batches cannot be opened (a held `LOCK`, permissions) faults its own puts and merges only (`TableBlockStoreException`) and is tried again on its next use; the other products go on.
2. **Due hours**: the arrival hours with blocks of a product not committed for them, whose end plus `MergeGrace` (2 minutes) has passed, oldest first, every one of them (a pass catches up after a downtime).
3. **One hour H**: `CloseHour(H)`; the blocks of H are listed after it (an append in flight is published under the store's lock, so the listing is the whole hour). Per product with blocks in H that is not committed (in the order of the products' ids):
   - **The memory budget** (`TableSensors.MergeMemoryBudgetMb`, 256 MB by default) bounds the rows held at once, each weighed by its table's columns: `TableMergeJob.RowBytes(columns)` = 8 bytes a cell (the block reader gives every column, the time column included, its own `long[]` or `double[]`) + 1 bit a cell for null maps, rounded up to a byte per 8 columns + 20 bytes a row (the arrays the cut of a sensor builds over its rows: table, row, time, order). So 45 bytes a row for 3 columns, 61 for 5, 280 for 32, 540 for 64. To the rows each table of a block adds what the reader allocates for it whatever its rows, `TableMergeJob.TableBytes` (64-bit runtime: object header 16, array header 24, reference 8): 104 + the id's length per table (the `BlockTable`, its id array, its column array, its slot in the sensor's list), 80 per column (the value array's header, the `BlockColumn`, its slot) and 32 per column with a null map (the map's header and padding). Blocks hold about six rows of a table, so for a wide schema this is more than the rows: a one-row table of 64 columns weighs about 5.8 KB, not 540 bytes. With the default budget about 6 M rows of 3 columns in one pass in tables of thousands of rows, 0.96 M of 32. Not weighed: the copy of the one batch being encoded (at most 4,096 rows), the tables of the block being read that are not kept, and the encoded batches, held until the hour is written (5.4 bytes a row in the benchmark's hour).
   - The index gives an hour's rows (the sum of `RowCount`) but not their width. When the rows fit the budget at the narrowest weight (`RowBytes(1)`, 29 bytes), one pass reads every block and adds up the weight of each table it keeps; once that passes the budget it gives up, before anything is encoded, and the hour is split as below (the blocks it found unreadable stay noted, the rows it counted as dropped or expired are counted again by the shares). Otherwise, or after such a try, a pass reads only the directories, weighs each table (by path, `TableBytes` of its directory entry: rows, columns, null maps, id; tables dropped later weigh too) and gives the tables to shares that fit the budget, heaviest first (a table heavier than the budget gets a share of its own); then one pass per share reads the blocks again and keeps the share's tables. The try and the split weigh by the same `TableBytes`, so a wide schema, or many short tables, is split where a narrow one with as many rows in few tables is merged in one pass. A table's rows are never split across shares, and the batches written are byte for byte those of one pass.
   - A block that is missing from `Blocks`, whose envelope is damaged, or whose bytes do not read (`TableBlockFormatException`) is unreadable: kept in the block store, listed in the hour's record, counted. An error of LevelDB's `Get` is told by the status its message starts with (`TableBlockDatabase.IsTransientReadError`, next to `ReadBlock`): an `IO error` is transient, a fault, not damage: the merge reads with `ReadBlock(entry, readErrorIsFault: true)`, which throws `TableBlockStoreException`, and the product's hour is merged again by a later pass. Any other status (`Corruption`, `Not found`, `Not implemented`, `Invalid argument`) or an error without one is permanent: damage, so the block is listed as unreadable, counted and reported with an Error, and the hour is committed without it; retrying it would hold its hour and every later hour of its product back for ever. The reads of users count either as a failed block. A block read in the first pass and not in a later one is a fault.
   - Refused tables (the envelope) are skipped. A table is resolved to the table sensor on its path in the product (strict UTF-8, `TryGetSensorByPath`); rows without one, of a block below the sensor's `FirstSequence`, or whose column types are not the sensor's are dropped and counted. Rows of a sensor that have expired for the week of the hour by the one rule of expiry (`TableBatchRetention.IsExpired(placement, hour, now, setting)`, see "Retention": the class that holds the hour, the stored target and the sensor's setting as read at the merge have all passed), or whose week database of the class that holds the hour was dropped by retention (`ITableBatchStore.IsWeekDropped`), are left out and counted as expired (`Rows expired before the merge`): a catch-up merge after a long downtime must not write into a week database retention has dropped (`WriteHour` refuses a dropped week, which would fault the product's hour for ever), and the hour commits with the other sensors' rows, without a fault.
   - Per sensor: its rows (the block tables kept as they are, not copied) are ordered stably by (time, block sequence, row) — no sort when they are in order already — and cut evenly into batches of at most 4,096 rows. Each batch is encoded, decoded and compared value by value (doubles by their bits) and null by null with its rows. A mismatch, a decode failure or an encode refusal stops the product: nothing is written for it, `Verification mismatches` grows (Error), its blocks stay, and the product hour is not tried again in this process (a codec defect is deterministic; it is tried after the next start).
   - The parts: one per period class, the sensors by id, each sensor's batches in row order. The commit: first and last block sequence, the blocks merged, the unreadable ones, and the watermarks (the product's watermarks from `GetWatermarks`, per producer the highest over every committed hour, raised by every block of the hour, unreadable ones included).
   - The free disk of the `Tables` folder is checked against `TableSensors.MinFreeDiskMb` (a fault below it), the stop token is checked, and `WriteHour` writes and commits the product's hour.
   Once every product with blocks in H is committed, the block store's watermarks are raised for those products.
4. **Deletions** run first in every pass, before any merge, each hour in its own guard: a fault of the merge (too little disk above all) never holds off the deletion that gives the disk back, and an hour that cannot be deleted now does not hold off the others. **Per product** (after the review of 30933652f): the blocks of an arrival hour of a product that committed it, except those its record lists as unreadable, are deleted once `DeleteMergedBlocksAfterHours` have passed since that product's commit time (the record's, so the delay holds across a restart), with `DeleteMergedHour(H, keep: every other block of the hour, watermarks: those products' newest)`, under the write side of the read gate (`TableHourGate`). The blocks of a product that has not committed the hour (or whose batches cannot be read now: a counted fault, the next pass tries again) stay, and so do those of a product within its delay. The block store deletes by sequence (sequences are unique across products, `keep` names the ones that stay), so this needs no change of the block store. Before, an hour was deleted only once **every** product with blocks in it had committed it: a product that never merges (a batch that does not verify after every start, placements that cannot be written) held every other product's blocks of the hours it shared with it for ever (`A_product_that_never_merges_holds_no_blocks_of_another_product_of_the_same_hour`).
5. **Faults** are per product: any exception while a product's hour is merged (a store, the free disk, a block read error, its batches that cannot be opened) leaves that product's hour untouched or committed, is logged and counted (`Faults`), and the product's later hours wait for the next pass, so a product's hours are committed in order. The other products of the hour and of later hours go on, and the next pass tries the faulted product again from its oldest unmerged hour. What this keeps: a product's blocks of an hour are deleted only once that product has committed the hour, so a product's hour left on its blocks keeps them whatever later hours and other products do; the read decides hour by hour and assumes no order; the watermark is the highest producer sequence merged for a product, and while a product's earlier hour is not committed its blocks are still in the block store (no later hour of that product is committed meanwhile, except after a verification mismatch, whose hour's blocks are never deleted) and its resends are answered by the duplicate map first. A fault outside any product (the block store cannot list its blocks) ends the merge part of the pass; the deletions have run by then.
6. **Shutdown**: the token is checked between hours, products and shares and before a product's `WriteHour`; a product's hour is committed or untouched. A call that started after the stores were disposed ends with their "closed" fault; with the token cancelled the job takes it as the stop, not as a fault.

### Crash points

Each pinned by `TableMergeJobTests.A_crash_at_any_point_of_the_merge_...` (a theory over the points): the hook throws, the batch store stops without flushing its databases, the server restarts over the same folders, and then a read returns the same rows in the same order as before the merge, the hour is committed exactly when the crash came after its commit, a rerun completes the hour (or its deletion), and a second rerun merges, writes and deletes nothing.

| Point | Hook | Left on disk | After the restart |
|---|---|---|---|
| After encode | `TableMergeJob.Checkpoint("encoded")` | nothing of the hour | served from blocks; the rerun merges |
| After one class's part | `TableBatchDatabase.Checkpoint("part-written")` | one part with its mark | served from blocks; the rerun writes every part again and commits |
| Before the `Hours` commit | `"before-commit"` | every part | the same |
| After the commit | `"committed"` | the commit | served from batches; the rerun raises the watermarks only |
| After the watermarks | `TableMergeJob.Checkpoint("watermarks-raised")` | the commit (watermarks are in memory) | the start state raises them again |
| Between the two deletes | `TableBlockDatabase.FaultHook("after-hour-blocks-deleted")` | blocks gone, index entries left | the hour is committed, its listed blocks are ignored; the rerun removes the entries |
| Before the compaction | `"before-hour-compaction"` | the deletes | the rerun deletes nothing more and compacts |

### The read (`TableBlockService.Read`)

Under the read side of `TableHourGate` (shared; a deletion takes it alone, so no hour's blocks are deleted while a read uses them, also with a delay of 0). The steps 1 to 3 are the plan; it is taken at one generation of the sensor (`GetGeneration(product, sensor)`, read before the merged hours and again after step 2, #1847; the sensor's and not the product's since #1850 part 4c, "What is in memory"): when the two readings differ, something the plan sees changed during it (a commit, one without any class included, a week database created or dropped, hours forgotten, a rebuild of `Hours` or of `Placements`, the sensor's own placement or moved batches written; the generation is the only test of staleness, no list is compared, #1850 part 4b; a placement or moved batches of another sensor do not count), the plan is stale and is taken again, and after three stale plans the read throws `TableReadChangedException` (the read route answers 503 with `Retry-After: 1`). The merged hours are in fact listed before step 1, in the same plan; the order below is the one of the reasoning.

1. The sensor's product's blocks are listed (`GetBlocks`); the candidates are those at or above the sensor's `FirstSequence` whose header range meets `[from, to)`.
2. For each arrival hour of a candidate, `IsHourMerged(product, hour)` is asked once: a committed hour's blocks are ignored (kept ones and those within the delay included); the others are read from blocks.
3. The committed hours are listed afterwards (`GetHours`, with their classes' row ranges). The sensor's placement gives the class of each hour (`ClassOf`, #1850 part 4b; a sensor without a placement has no batch). An hour is read from its batches when the row times it can hold for the sensor meet `[from, to)` (`RowTimes`: the union of the record's class ranges, dropped classes included, whatever class holds the sensor's rows, #1850 part 4c: rows moved into a class the record names keep their times, which are within the range of the class they came from and not of the one they are in; before part 4c, the class's own range when the record named it), the database of its week and of the sensor's class for it exists, its last block sequence is at or above the sensor's first sequence, and it was not found uncommitted in step 2 (a commit between the two steps: its blocks are still there, the gate holds their deletion off). So an hour is read from batches or from blocks, never both and never neither, at any moment of a merge and at any crash point. Late blocks are found by the row-time ranges of the hours that merged them.
4. **Sources** — the blocks of one arrival hour, or one merged hour and its class — are visited in the order of their earliest row in the range (then by hour). A merged hour's batches are read with one `ReadSensor` per hour (bounded memory for long reads) with the range of the read: an index record whose rows cannot meet it is skipped by the store before its batch is fetched (#1850 part 4c); the others are decoded and added. A batch that does not decode, whose columns are not the sensor's, or whose index record in the range survives without its bytes (`ReadSensor`'s `failed`), is counted (`BatchesFailed`, the store's `Batch read failures`) and skipped. So an hour selected through the gap between two classes' ranges (rows of P1 only at 10:00 and of P5 only at 12:00, a read of the P1 sensor for 11:00) reports no row and no failure, but it is not free: it is a source whose earliest row is taken as the read's `from` (so the early stop never stops before it), and it costs the read side of the gate, two readings of the generation (a chart's `ChangedSincePlan` before and under the gate), the acquire of the week database of its class (a LevelDB open when the handle is not cached, against `MaxOpenBatchDatabases`), an iterator and two seeks (the hour region and the moved region), all answering nothing (Known Issues: one sensor with wide row times makes the others pay it over its hours) (`TableChartReadTests.An_hour_selected_through_the_gap_between_two_classes_returns_no_row_and_reports_no_failed_batch`; it fails with the union and without the store's range test).
4a. **Blocks kept unreadable** (#1850 part 4b): a block of a committed hour that the hour's record lists as unreadable, in the range and at or above the sensor's first sequence (the test for the blocks of an unmerged hour), is counted in `BlocksFailed`, once per read, as it was before the merge. Whether it held rows of this sensor is not known, so it counts. Both readers (`Read` and the chart) take it from the same plan.
5. **Order**: time, then arrival hour, then rank within the hour — `(block sequence << 24) | row` for a block, `(moved << 62) | (ordinal << 12) | row` for a batch. Within a merged hour the ordinals follow the merge's (time, block sequence, row) order, so the order is the same before, during and after a merge.
6. **The limit stops early**: past the limit the collected rows are sorted and the latest dropped (as before); before each source, once rows have been dropped past the limit, the read stops when the source's earliest row is after the latest row kept. `Truncated` stays exact (a row was dropped); the result equals the unlimited result cut at the limit.
7. A fault of the batch store is thrown as a `TableBlockStoreException`: one fault type for the caller (5xx).

`TableRows` gains `BatchesRead` and `BatchesFailed`.

### The period class (`TablePeriodClass`)

`Weeks(policy, utcNow)`: the presets by their nominal length (`TimeInterval.Month` 31 days → 5, three months → 14, six months → 27, a year → 53), custom ticks rounded up to weeks (at least 1), 0 for kept for ever. It applies the rule of the ordinary history cleanup: what never expires there is 0 here — `None`, `FromFolder` with 0 or fewer ticks, ticks at or past `utcNow.Ticks`, and a class above 65,535 weeks. A calendar preset inherited from a folder (#1864, PR #1955) reaches the sensor as `FromFolder` with `TimeIntervalModel.FolderPreset`, and the class is that of the preset (`AppliedInterval`): 5, 14, 27 or 53 weeks, the same as a preset set on the product. Only an inherited setting stored by an earlier build without its preset (`FromFolder` with 0 ticks) is still kept for ever, until the start of the server resolves it from the folder (`FolderManager.ResolveInheritedCalendarPresets`); the move job then brings the sensor's rows to its class. Pinned by `TableMergeJobTests.The_period_class_is_...` and `FolderCalendarPresetTests`.

The class is the sensor's placement's (part 4b): the merge and the reads both take `ClassOf(hour)`, so a sensor whose period was changed reads its hours merged under the old class from there until the move brings them over. For storage the setting is read in two places only, both through `TablePeriodClass.Of`: `TableMergeJob.PlaceSensor`, which records a change in the placement, and every expiry decision, which takes it as the third term of the rule of expiry ("Retention").

### A block with every table refused

Such a block is not stored and answered `AllRefused`, a final answer: the collector drops it, its rows are lost and counted, and its producer sequence is never sent again (the wire contract). The reason is the watermark: it answers every sequence of the producer at or below the highest merged one as a duplicate, so a refused block sent again after a later block of its producer was merged would be acknowledged and not stored. After its sensors are registered, the rows of later blocks are taken.

## Retention (#1850, part 4a)

`TableMergeJob.RunRetention` (`src/server/HSMServer.Core/TableSensors/TableMergeJob.Retention.cs`), run by the merge pass after the merge (so a catch-up merges what it can before retention judges what is left), at most once per hour of the pass's clock (`RunPass(utcNow)`: the job never reads the system clock, and tests drive it). It never throws.

**The rule of a class.** A period class P has passed for a week when `TableBatchRetention.IsExpired(week start, P, utcNow)`, that is `utcNow >= week start + (P + 1) weeks`: rows are kept for P whole weeks after their week has ended. A row may outlive its period by up to a week, never by less than zero. `P0` (kept for ever) never passes. P is a sensor's history setting in whole weeks, rounded up (`TablePeriodClass`).

**The one rule of expiry** (#1850 part 4b, after the review of 139327ef1; three terms after the review of 30933652f): `TableBatchRetention.IsExpired(placement, hour, utcNow, setting)`, one function asked by every decision that discards or deletes rows: the merge leaving out expired rows (`TableMergeJob.IsLeftOut`), the deletion of expired blocks (`IsBlockExpired`), the retention guard and so the drop of a week database (`HoldsUnexpiredRows`). It takes **three terms**, and a row is kept while any of them keeps it, **expired only when all three have passed for the hour's week**:

1. **the class that holds the hour** (`ClassOf(hour)`): **where** the rows are stored;
2. **the stored target** (the placement's `Target`): the period recorded by the last change written;
3. **the class of the sensor's setting as read at the decision** (`TablePeriodClass.Of`, the function `Reconcile` compares with the target). A sensor that is no longer in the tree has no setting: its stored target alone decides (as before this term existed).

The third term makes every expiry decision independent of whether a placement write succeeded and of whether `Reconcile` has seen a change: the review of 30933652f found two sequences in which a lengthened period lost rows because the protection depended on the write. (1) S in P1, the P1 database of its week W due in clock hour 10; the pass of 10:21 reconciles S unchanged, the user keeps S for ever half a second later, the merge of a due hour resolves S and the write of its changed placement fails: the product's merge faults (it was reconciled), and retention, deciding by the stored placement (P1, no segment), dropped W's P1 database. (2) The same without any failure for a sensor with no rows in the hours merged after the change: nothing resolved it again before retention, and in a catch-up that window is the whole merge loop. With the setting read at the decision both keep the database (`TableMergeJobTests.A_period_lengthened_after_the_reconciliation_whose_write_fails_in_the_merge_keeps_its_week_database`, `..._of_an_inactive_sensor_keeps_its_week_database`; both fail with the rule reduced to the two stored terms). So a stale or unwritable placement never causes a deletion the current setting forbids, and retention needs no placement write: it reads the stored placements (`StoredPlacement`) and writes none.

So a period lengthened before a week expired protects every row of that week, merged or still to be merged, and the blocks kept unreadable, from the moment the setting changes (`A_period_lengthened_before_its_week_expired_protects_an_hour_still_to_be_merged_and_a_block_kept_unreadable`: the first version decided by the class that holds the rows alone, and lost both). **A shortening never frees disk early**: the stored terms and the setting must all have passed, so until the shortening is written the stored target (the longer class) keeps the rows, and after it is written the class that holds the hours merged before the cut-off (the longer class) does; only rows merged from the cut-off on, in the new class, expire by the new period. The move (the next pull request) is what deletes rows of a shortened period earlier. Pinned by `A_shortened_period_frees_nothing_until_the_class_that_holds_the_rows_has_passed` (written and not written) and `A_period_shortened_deletes_nothing_before_the_class_that_holds_the_rows_has_passed`; they fail when the class that holds the hour is left out of the rule, not when the setting is (a shortened setting never keeps anything). The first version decided by the class that holds the rows alone in the merge and for blocks: a P1 sensor lengthened to P52 before its week expired lost the readable rows of an hour that waited for its merge past P1's time (left out as expired, the hour committed without them) and its blocks kept unreadable (deleted), although its period protected both (`TableMergeJobTests.A_period_lengthened_before_its_week_expired_protects_an_hour_still_to_be_merged_and_a_block_kept_unreadable`; the other way: `A_period_shortened_deletes_nothing_before_the_class_that_holds_the_rows_has_passed`).

**Not expiry, but left out all the same: a dropped week database.** A sensor whose class P passed for a week while P was still its period lost that week's database to retention, rightly. If its period is lengthened only afterwards and an hour of that week is still to be merged (its blocks held by another sensor's longer period), the rule says the rows have not expired, but the database of the class that holds the hour is gone and a write into it is refused. The merge leaves those rows out and counts them as expired (`IsWeekDropped`): they went with their week when the period they had then passed. Pinned by `Rows_whose_week_database_was_dropped_before_the_period_was_lengthened_are_left_out_and_the_hour_commits`.

1. **Expired blocks first.** An arrival hour whose blocks the ordinary deletion holds back (a product that did not commit the hour: a batch that did not verify, a merge that keeps faulting; or blocks a commit lists as unreadable) is deleted once every one of those blocks has expired: for each, the rows of the hour have expired by the one rule for every table sensor with rows in it, by the block's directory (the class that holds the hour for the sensor, its stored target and its setting as read now have all passed for the hour's week; never for a sensor any of them keeps for ever). A table with no sensor on its path, or in a block below its sensor's first sequence, is never served and counts as the shortest class (1). A block whose directory cannot be read, or that its product's commit lists as unreadable, is judged by every table sensor of its product (its whole tree; the shortest class when it has none). **A late hour is never taken for expired:** an hour whose week ended less than a week ago is not looked at (the shortest class is one week), and after that the test is the rule of each sensor against the hour's week, never the hour's age alone. A committed product whose deletion delay (`DeleteMergedBlocksAfterHours`) has not passed holds its own unreadable blocks back, as the ordinary deletion does. **Per product** (after the review of 30933652f): a product's held blocks of the hour go once every one of them has expired, whatever the other products' blocks of the hour are; a fault while one product is judged (its batches cannot be read, a read error on one of its blocks) keeps that product's blocks, is counted in `Retention faults` and logged (once an hour, as retention runs), and the others go on (`A_fault_judging_one_products_expired_blocks_does_not_hold_another_products_of_the_same_hour`) (`DeleteMergedHour(hour, keep: every other block of the hour, those products' watermarks)`), under the write side of the read gate, logged as an **Error** with its blocks and rows (from the block index: every table of a block, no decompression), and counted. Before, the hour went whole or not at all, so a product with a sensor kept for ever held another product's expired blocks of the same hour for ever. Retention decides by the stored placements and the settings as they are, and writes no placement, so it runs for a product whose placements could not be reconciled in the pass.
2. **Week databases.** For every product of the batch store, every week database that is due by its own class (the rule for the sensors whose period is that class) and that the guard does not hold is dropped (`DropWeek`, under the write side of the read gate, so a read in flight ends first and one read sees every hour of a week or none): the folder deleted, the drop recorded (see "Dropping a week"). Logged at Info per database. **The guard** (#1850 part 4b; three terms after the review of 30933652f): a due database is kept while it may hold rows that have not expired by the one rule: rows of a sensor whose placement puts hours of that week in that class (a segment of that class, or the target itself outside the segments, from the sensor's first hour on) and whose stored target or setting as read now has not passed for the week. Rows of a sensor whose period changed since they were merged are owed to their new class, and the move (the next pull request) brings them there; rows of a sensor whose change is not written yet (its write failed, or it came after this pass's `Reconcile`) are held by its setting. `Move weeks pending` shows how many databases the guard holds. Rows whose every term has passed go with the database.
2a. **Hours with nothing left.** The committed hours of a product no database of whose week is left and of which the block store holds no block are forgotten (`ForgetHours`).
3. **Faults.** A drop or a deletion that fails (a held folder, a store fault, a block read error) is logged as an Error, counted in `Retention faults`, and tried again an hour later; the other weeks, hours and products go on. A product whose placements were not reconciled in the pass gets its retention all the same: it decides by the setting as well as by the stored placement ("Placements", fail closed). A drop whose folder could not be deleted is dropped all the same (the next open of the product deletes the folder).

The record of an hour stays in `Hours` while its blocks do (a drop does not remove it, part 4b), so an hour with blocks kept unreadable is never merged a second time when the last database of its week is dropped before those blocks expire.

## Placements (#1850, part 4b)

Where each table sensor's batches are, kept by the batch store per product (`<product>/Placements`, LevelDB: key the sensor id, 16 bytes big-endian; value u8 version 2, u16 target, i64 the sensor's first hour, i32 count, per segment i64 first hour, i64 end hour, u16 class, little-endian; version 1, without the first hour, does not decode and is rebuilt). A `TablePlacement` (`HSMDatabase.AccessManager/TableBatches/TablePlacement.cs`) is a **target** class, the one the sensor's hours are merged into now, **segments**, runs of earlier merge hours `[first, end)` whose rows are still in another class: merged there before a change of the sensor's period and not moved yet, and the sensor's **first hour**, before which it has no rows and no segment reaches. `ClassOf(hour)` is the segment's class, or the target. **The merge writes a sensor's rows of an hour into `ClassOf(hour)`, and every read looks there**, so the two never disagree, before, during and after a change.

- **The only writer of a change.** `TableMergeJob.PlaceSensor` compares `TablePeriodClass.Of(sensor)` (the history setting in whole weeks, inherited from folder and product) with the placement's target. It runs in the merge (`Resolve`, for every table of an hour, creating the placement of a sensor that has none before its first batch is written) and at the start of every pass for every sensor with a placement (`Reconcile`), so a change on a folder or a product, which raises no event per sensor, is recorded within a pass whether or not the sensor has new rows. Reads and retention never write a placement. The setting is also read, as it is at the moment, by every expiry decision (the third term of the rule of expiry, "Retention").
- **Fail closed, only where a placement says where to write** (#1850 part 4b; narrowed after the review of 30933652f). A product whose `Reconcile` did not complete in a pass (the synced write of a placement failed, its placements could not be read) is **not merged in that pass**: the merge needs a placement to know where an hour's rows go, and a change must be on disk before any hour from its cut-off on. When the batch store cannot list its products, that is every product. **Retention and the deletion of expired blocks run for it**: every expiry decision reads the sensor's setting as well as the stored placement, so a placement on record that a lengthened period has made stale (P1 changed to for ever, the write failing) cannot cause a drop the setting forbids. The first version left such a product out of retention too, which the review of 30933652f showed to be a stall that sustains itself: the disk fills, the user changes a period, every pass the placement write fails with "no space", no hour is merged, no expired block deleted, no expired week dropped, nothing frees space, and the write keeps failing, with an Error per product a minute. Now an expired database of an unchanged sensor is dropped and expired blocks are deleted while every placement write fails, and a lengthened sensor's database is kept (`With_every_placement_write_failing_retention_still_frees_what_has_expired_and_keeps_a_lengthened_period`; it fails with the rule reduced to the stored terms). The ordinary deletion of the blocks of merged hours past their delay was never held back: it decides nothing by a placement. Counted (`TableMergeStatistics.ProductsNotReconciled`, not posted to self-monitoring, and `Faults`, which is) and logged as an Error **once per product and hour of the pass's clock** (as retention is rate-limited, by the pass's clock), not once a pass; every pass's report names it (`TableMergePassReport.ProductsNotReconciled`, `Fault`); the next pass, a minute later, tries again. Pinned by `TableMergeJobTests.A_placement_write_that_fails_does_not_let_retention_drop_rows_the_setting_now_keeps` (the sequence of the review of 139327ef1), `A_product_whose_placements_were_not_reconciled_is_not_merged_and_its_blocks_are_judged_by_the_setting_now`.
- **A change takes effect from the cut-off hour C** (`Cutoff`): `C = max(the current hour of the pass's clock, the newest arrival hour with blocks of the product + 1 h, the newest committed hour + 1 h, the end of the last segment)`. The hour after the newest hour with blocks, **the open hour included**: at 10:05 with a block in the 10:00 hour, C is 11:00 and the whole 10:00 hour stays in the old class (decided after the review of 139327ef1, which read the doc as `max(current hour, newest arrival hour, ...)`: the code was right, the later cut-off is the safe one, and this text, the code's comment and ADR-0021 now say the same). The merge writes only closed hours with blocks, so no hour from C on has a part on disk; and an hour that holds blocks is never at or after C whatever the clocks say (the merge takes an hour for closed by its pass's clock, the block store files a block under the hour of its own clock, and a clock set back can make an hour look open that a run has already written parts of). The price: a change made while the current hour already holds blocks applies to rows that arrive from the next hour on. Every hour before C keeps the class it has, including hours not merged yet, and a merge that repeats an hour after a crash gives every sensor the class the crashed run gave it. This closes the Known Issue of a lone mark of an earlier run taken as committed (it needed a period change between two runs that did not commit). `Retarget(new, C)`: the hours from the sensor's first hour to C in the old target become a segment of the old target; a segment whose class is the new target goes (its rows are where the sensor's hours belong again); hours from C on are in the new target. Pinned by `A_change_of_period_takes_effect_from_the_hour_after_every_hour_with_blocks_and_earlier_hours_keep_their_class`, `A_change_of_period_while_the_open_hour_already_holds_blocks_takes_effect_from_the_hour_after_it` (the pass runs while that hour is still open), `A_repeat_of_an_hour_that_did_not_commit_gives_every_sensor_the_class_of_the_run_before_a_change_of_period`, `A_change_on_the_product_is_recorded_for_every_sensor_that_inherits_it_within_a_pass`, `A_change_of_period_keeps_every_earlier_hour_in_its_class_and_a_change_back_drops_the_segment`.
- **The first hour** (`TablePlacement.FirstHour`, #1850 part 4b, after the review of 139327ef1). A segment is what makes retention keep a week database (the guard), so it must not cover hours the sensor never had rows in. The first version started the first segment at the start of time: a sensor created this week in P1 and then kept for ever had a segment over all of the past and held last week's P1 database, with rows of other sensors only, for ever. The first hour is recorded in the placement when the merge first writes it (durable with it): **the oldest arrival hour with blocks of the product that is not committed at that moment** (`TableMergeJob.FirstUncommittedHour`). That is the hour being merged, except when an earlier hour was left behind (a batch that did not verify: merged after the next start, and it may hold the sensor's rows), in which case it is that earlier hour. Chosen over the sensor's first merged hour, which is not known without a scan of the indexes and can be later than an hour merged afterwards. A placement rebuilt from the indexes takes the sensor's first hour with a batch (the batch store cannot see blocks), so **the merge job lowers the first hour** (never raises it, `TablePlacement.WithFirstHour`) to the oldest arrival hour with blocks of the product that is not committed, the same rule as at creation, wherever it is about to depend on it (after the review of 30933652f): when the merge resolves the sensor for an hour (to `FirstUncommittedHour` of that hour, before it writes the sensor's rows there) and when it records a change of period (before `Retarget`). Lowering changes the class of no hour (hours before the first hour are in no segment, so in the target); it only moves where the next change's segment starts. No flag "first hour not confirmed" is kept: the rule applies to every placement, and for one the merge created it changes nothing unless a block lands in an older hour (a clock set back). Without it (the review's sequence): hour H3 holds S's first rows and does not verify, H4 is committed with S's first batch, the placements are rebuilt (S: P1, first hour H4), after the restart H3 is merged into P1, S is then kept for ever, and the change's segment [H4, C) left `ClassOf(H3)` = P0: the read looked for H3 in P0, and the P1 database with S's rows of H3 would have been dropped with P1's time. Pinned by `A_rebuilt_placement_covers_an_older_hour_merged_after_the_rebuild_and_a_later_change_keeps_it_where_it_was_merged` (without the lowering the read returns one row of two). Pinned by `TableMergeJobTests.A_segment_starts_at_the_sensors_first_hour_so_a_sensor_keeps_no_week_from_before_it_existed`, `The_first_hour_of_a_placement_is_the_oldest_hour_with_blocks_not_committed_when_it_was_created`.
- **Durable before it is used.** `SetPlacement` is one synced write, then memory; a placement is written before the merge writes a batch by it, and a change before any hour from C on is merged.
- **Lost, incomplete or damaged: rebuilt from the indexes.** A `Placements` that is missing (a store from before placements, or lost) or has no complete key (new, or left by an open that stopped) is rebuilt at the product's open; a damaged one (LevelDB's corruption, a value that does not decode) is set aside to `Placements.damaged-<ticks>` and rebuilt. The rebuild reads, for every committed hour, the index records of every database of its week: one seek to `hour | 0x00` per hour and database (index records only, not the batches) and the hour's keys in the moved region. A sensor's rows of an hour are in one database; should two hold them (a move stopped between its copy and the delete of its source), the hour region is taken: the source, complete until it is deleted, which happens only after the switch. A sensor's target is the class of its newest hour, its earlier runs in other classes its segments (each from its own first hour up to the start of the next run), its first hour its first hour with a batch (lowered by the merge job to an older hour not committed yet, see "The first hour"). The next `Reconcile` then brings the target to the setting from a new cut-off. As `Hours`, it is trusted only with its complete key, written in the one synced write of a rebuild's result (which deletes whatever the database held), so a rebuild that stopped, or a crash right after the folder was created, leaves nothing trusted; for a product without a week database the rebuild is an empty scan. Counted (`PlacementsRebuilt`) and logged as a warning when there were week databases to rebuild from. Residual: an hour not committed when the placements were lost is merged into the rebuilt placement's class for that hour, which may not be the class a crashed run of it used (it needs the loss of `Placements`, a period change and a crashed run of the same hour). Pinned by `Lost_placements_are_rebuilt_from_the_indexes_of_the_week_databases`, `Damaged_placements_are_set_aside_and_rebuilt_and_so_is_a_rebuild_that_stopped_in_its_scan`, `A_crash_right_after_the_placements_database_is_created_leaves_nothing_trusted_and_the_next_open_rebuilds`.
- **Removed sensors** (#1850 part 4d): the placement goes with the sensor's keys, after them ("The removal"). A placement whose sensor is not in the tree and has no record of its removal is kept and reported, never deleted by itself (an orphan placement).

### Moved batches and an hour merged again (design note for the move)

The move (the next pull request) copies a sensor's batches of an hour from the database of its old class into the region of moved batches of the target class, then switches the placement, then deletes the source. An hour is merged again from its blocks only when it is not committed: after `Hours` is lost and `Rebuild` does not commit it (its marks disagree), while its blocks are still kept. If that hour had been moved, the copy could sit beside the rows the repeat merges: read twice. **The rule (chosen over moving only hours whose blocks are gone, which would pin a week database for ever behind a class-0 sensor's unreadable block), in two halves that do not depend on each other:**

- **Writing an uncommitted hour deletes everything every database of its week holds of the hour**, its moved keys included (`DeleteHourKeys`: the hour's prefix and `0xFF | hour`), in the databases it writes a part into and in every other one, by the keys themselves and not by a mark. The rows then are exactly what the repeat merges, in `ClassOf(hour)` of each sensor.
- **`CopySensorHours` always leaves the hour's mark in the database it writes into.** It copies the mark of the source database (not the record of `Hours`, whose commit time a rebuild changes) in the same synced write when the target has none; a source hour with the sensor's records and no mark, or a mark that does not decode as that hour's record, is refused with nothing written. So moved batches of an hour never exist in a database without the hour's mark, and a rebuild of `Hours` sees the same bytes in every database of the hour (`A_copied_mark_commits_the_hour_in_a_rebuild_of_the_hours_after_the_class_it_came_from_was_dropped`: the copy's mark is the only one left).

The first version cleared a database only when it held a mark of the hour, and the first moved write (`WriteMoved`) wrote none: a copy moved into a database without a mark survived the hour's repeat and was read beside the rows merged again (the review's sequence, `Writing_an_hour_clears_every_key_of_it_in_every_database_of_its_week_with_or_without_its_mark`).

What `Rebuild` and `WriteHour` do with a mark in a class the record does not name (checked in the code): `Rebuild` groups marks by hour across every database of the week and adds the class to the found set; with the same bytes as the other marks the hour is rebuilt (the extra class is not added to the record's classes), with other bytes the hour is not rebuilt. So the move must copy the record's bytes unchanged. `WriteHour` returns at once for a committed hour; for an uncommitted one its step 3 replaces whatever a database of a class the record names holds of the hour and step 4 (`RemoveStaleParts`) deletes the hour from every other database of the week that holds a key of it: both through `DeleteHourKeys`, so both clear the moved keys too, with or without a mark.

| Crash or event | On disk | A read | What follows |
|---|---|---|---|
| During the copy of hour h (target written, no switch) | copy and mark in T, source in c | `ClassOf(h) = c`: the source | the move copies again (overwriting) |
| After the switch, before the delete of the source | copy in T, source in c | `ClassOf(h) = T`: the copy | the move deletes the source |
| `Hours` lost and h not rebuilt, blocks still kept | marks of h in c and T (and other classes) | h not merged: its blocks | the merge writes h again: every database of the week is cleared of h (both regions, marked or not), the rows go to `ClassOf(h)` of each sensor; nothing is read twice |
| `Hours` lost and h rebuilt | as before | as before the loss | nothing |

**The store's primitives of the move and of the removal** (#1850 parts 4c and 4d; the move job calls them, "The move"; the removal comes next). They pin a week database only when its week is the product's pinned (newest) week, and a product's pinned week is known from its open (the newest week of a commit or a database): otherwise a quiet product's move would pin, and keep open past `MaxOpenBatchDatabases`, every database it touched until the product wrote an hour again (`After_a_reopen_the_primitives_of_a_quiet_product_pin_only_its_newest_week_...`). A copy holds its whole range in memory and writes it in one synced write under the product's lock: the job cuts a step at 64 MB of the sensor's batches (`GetSensorHourBytes`) and one week (`A_week_larger_than_a_step_is_moved_in_several_steps_...`); the rows' order is kept by the new ordinals, which a read ranks by, not by the moved keys' order (first time, then ordinal) (`A_move_returns_the_same_rows_in_the_same_order_when_batches_of_an_hour_are_not_in_time_order_by_ordinal_...`):

- `CopySensorHours(product, sensor, from, toClass, first, end)` (replaces the internal `WriteMoved`, which had no production caller): in **one synced write** into the database of the same week and class `toClass` (created when there is something to write; a dropped one refused), **a copy never touches the target for an hour the source has nothing of** (there the target's moved rows may be the sensor's only copy: a step repeated after it completed, `A_step_repeated_after_it_completed_leaves_the_targets_rows_intact_and_readable`, `A_copy_replaces_the_targets_moved_rows_of_the_hours_the_source_holds_and_leaves_the_other_hours_untouched`); with no such hour it writes nothing at all. For each hour the source holds, it first deletes every moved key of the sensor of that hour there (`WriteMoved` did not, so a repeat with fewer batches left stale ones: a copy repeated leaves exactly one copy), then puts the sensor's index records and batches of **both regions** of the source in read order (hour region before moved region, each by ordinal), numbered `0..n-1`, as bytes: an index record whose batch is missing, or a batch that does not decode, is carried as it is (the copy reads with the same failures as the source); and the hour's mark where the target has none. The source is not changed. The bytes it deleted in the target count in the target's counter. **Its refusals are `TableBatchRefusedException`** (not a `TableBatchStoreException`, not counted in `Batch write failures`: a repeat cannot cure them, so a caller that repeats store faults must not repeat these, and the disk's diagnostics must not show them), with nothing written and no generation changed: a target retention dropped; a source hour with the sensor's records and no mark, a mark that does not decode, an index key of the sensor that does not parse; and a target that holds index records of the sensor of a copied hour in its hour region: they are either the sensor's rows of the hour in the class that holds it, or a source a move left behind (a step that died between its switch and its delete, whose record was then lost or did not read), and copied beside them they would be read twice once the target holds the hour (and carried on, doubled, by a later copy out of it, which reads both regions). The store cannot tell which, so it deletes nothing: the move job, which knows from the placement that the target is not the class of those hours, deletes them first with `DeleteSensorHours` (`A_copy_into_a_class_whose_hour_region_holds_the_sensors_rows_is_refused_so_no_read_returns_them_twice`).
- `DeleteSensorHours(product, sensor, week, first, end)`: in one synced write into **one** week database (the caller loops: the move over every database of the week except the target, the removal over every one), the sensor's index records of the hour region and the batches **those records name by their ordinal** (a batch key of the hour region carries no sensor id), and every key of the sensor in the moved region; never a mark, never a key of another sensor; plus the batches' bytes added to the database's counter **in the same write**. Nothing for a database that does not exist. The caller holds the write side of the read gate (`TableHourGate`): a full read that planned the database reads it without checking the generation again. `Deleting_a_sensors_hours_leaves_every_key_of_another_sensor_byte_for_byte_keeps_the_marks_and_counts_the_bytes_also_after_a_reopen` compares every other key of the database byte for byte.
- `GetSensorHourBytes(product, sensor, week, first, end)`: batches, rows and stored bytes of the sensor in both regions, from the index records only (the stored length is in the index value; no batch fetched).
- The **deleted-bytes counter** (`GetDeletedShare(product, week)`: the counter and the folder's size) and `CompactWeek(product, week)`: LevelDB's `CompactRange` over every key of the database, holding a lease on it and **not the product's lock while it compacts**, nor the read gate (a read of the database, a write of the product and a read holding an iterator across the whole compaction go on and end complete: `A_compaction_holds_no_lock_a_read_or_a_write_of_the_product_needs_and_a_read_across_it_is_complete`), then the counter lowered by what it held before the compaction in one synced write (a crash in between leaves the counter, and the compaction is made again: the safe side). The durable compaction list (`<product>/Compact`, `GetCompactList`, `AddToCompactList`, `RemoveFromCompactList`), so a compaction decided before a crash is not forgotten. **Others wait for a compaction while they hold the product's lock**: a `DropWeek` of the same database (for its lease), the flush of the same database while it is the newest week's (LevelDB runs one manual compaction at a time), and a dispose (for the lease, without a bound).
- The move in flight (`<product>/Move`, `GetMoveInFlight`, `SetMoveInFlight(product, record or null)`): `TableMoveInFlight(sensor, week, from class, to class, first hour, end hour)`, strict.
- Every durable write of them has a crash case: a stop without a flush right after a copy or a delete keeps it, and a repeat writes nothing more (`A_crash_right_after_a_copy_or_a_delete_...`); a crash between the compaction and the counter's write (`A_crash_between_the_compaction_and_the_counters_write_...`); a file whose temporary cannot be written is a fault with nothing changed (`A_write_of_the_move_in_flight_or_of_the_compaction_list_that_fails_...`); a file that cannot be opened at the open is taken as none (`A_move_in_flight_or_a_compaction_list_that_cannot_be_opened_...`). One fault leaves memory and disk apart until the next open: in strict mode `DurableFile` renames (or deletes) first and syncs the folder after, so when that sync fails (Linux) the call throws although the disk holds the new record or list, and memory keeps the old one. Harmless: the recovery of a step takes every decision from the placement (the record only names the other class that may hold a copy), and the compaction list is a hint.

**Two moved copies of an hour and a rebuild of `Placements`.** The rebuild prefers the hour region; with no copy there and two in moved regions (a second move of an hour moved once, stopped between its copy and its delete, then `Placements` lost) it takes the first one seen, the lower class. That is safe as it is, and it is pinned rather than changed (`A_rebuild_of_lost_placements_with_two_moved_copies_of_an_hour_takes_one_of_them_and_reads_every_row`, both orders): a copy is one write and a delete of a sensor's hours one write per database, and the rows of a committed hour never change (a merge of it again deletes every key of it in every database of its week), so every database either holds all of a sensor's rows of the hour or none of them: either copy is complete. The recovery of the move then keeps `ClassOf(hour)` (one of the two classes its record names) and deletes the other; a class it does not name means it deletes nothing.

**For the move, the reader's selection of an hour** (built, #1850 part 4c, before the move itself): rows moved into a class the hour's record already names (a sensor moved from P1 to P5 in an hour whose record names both) have times within the range of the class they came from, not of the one they are in. `TableBlockService.RowTimes` answers the union of the record's class ranges for every hour (in part 4b it answered a named class's own range), and the store skips an index record out of the read's range before it fetches its batch, so the union costs no false "batch failed" ("The read", steps 3 and 4). The stored record is not widened: every mark must stay the commit's bytes. Pinned by `TableChartReadTests.Rows_moved_into_a_class_the_hours_record_names_are_read_outside_that_classs_own_range` (it fails with the own range). **And the plans around a step:** the copy and the switch of one sensor change only that sensor's generation ("What is in memory"), so a chart of another sensor never plans again for a step of the move; a chart of the moved sensor across its switch plans again once and reads the moved rows; a read that planned before the switch reads the class it planned, which still holds the rows until the source is deleted (that delete is to take the write side of the gate, which the read holds). Pinned by `TableChartReadTests.A_move_step_of_one_sensor_plans_no_chart_of_another_again_and_a_chart_of_the_moved_sensor_plans_again_once`, the copy and the switch written through the store's `CopySensorHours` and `SetPlacement`; the delete of the source and its wait for the gate come with the move.

Pinned for the store by `A_part_written_again_also_deletes_the_moved_batches_of_its_hour_in_that_database`, `Writing_an_hour_clears_every_key_of_it_in_every_database_of_its_week_with_or_without_its_mark` (the copy in the database the repeat writes into, and in one its record does not name), `Moved_batches_always_come_with_the_mark_of_their_hour_and_a_rebuild_takes_the_hour_with_its_own_classes`, and for the primitives by the tests named above; the move's own crash matrix is in "The move".

## The move (#1850, part 4c)

After a table sensor's period changed, its rows merged under the old period (the segments of its placement) are brought into the databases of its target class by the merge job, in the background, a step at a time (`TableMergeJob.Move.cs`). ADR-0021 point 12 and the owner's decisions of 2026-11-25: a lengthened period is moved too; the first version always copies (no rename of a week folder, no early drop of an emptied database); a week database is compacted when a tenth of it is deleted, by no other rule.

**The invariant.** For every sensor and committed hour, the database of the class the placement names (`ClassOf(hour)`) holds all the sensor's rows of that hour, or they have expired by the one rule. Another class may hold a copy (being made, or a source not deleted yet) that nothing reads. The placement is the only authority: for reads, for retention and for the move's own recovery. The product's in-flight record (`<product>/Move`) only says which other class may hold a copy.

**A step** is one sensor, a run of hours inside one segment and one week, at most 64 MB of its batches (`TableMergeJob.MoveStepBytes`, counted from the index records; at least one hour). It takes only hours before the product's oldest arrival hour with blocks that is not committed and before the current hour of the pass's clock, so no run of the merge can write an hour of a step: an hour left behind stops the move there until it is merged. An hour whose batches did not verify is not committed until the next start and is not due in this process (so its product does not count as lagging): every step of the product, copy and expired alike, stops before it, so hours at and after it are not moved and retention keeps their old class's databases until a restart. Its sensor-weeks at and after that hour count in `Move steps blocked`, and a warning names the hour, once an hour per product (`A_step_stops_before_an_hour_that_did_not_verify_...`). A sensor is eligible when it is in the tree, its product was reconciled in this pass, and its setting's class is its placement's target (otherwise the next reconciliation retargets first).

**A pass.** `DeleteDue -> Reconcile -> merge -> RunMoves -> RunRetention -> RunCompactions`, on the job's thread under its run lock. `RunMoves`: (1) the in-flight record of every product is recovered; (2) the removal of table sensors and root products ("The removal", #1850 part 4d), within the same budget; (3) the expired steps, store-wide, oldest week first, then product, then sensor; (4) the copy steps in the same order, of the products whose own merge has no lag (no closed hour of theirs is due and unmerged; one product whose merge keeps faulting holds off no other's) (`A_products_copy_steps_wait_while_its_own_merge_lags_and_another_products_do_not`). Recovery and expired steps do not wait for the product's lag (they free disk), but an expired step, like a copy step, never takes an hour at or after the product's oldest uncommitted hour. The store-wide `Merge lag` keeps its meaning as a gauge only.

**A copy step**, its durable writes in order, and what the next start does after a crash right after each (`A_crash_after_any_durable_write_of_a_step_...`: the store stopped without a flush and restarted over the same folders; a read then equals the rows before the move, a rerun completes the step, a second rerun writes nothing):

| # | Write | A crash right after it: a read | The next pass |
|---|---|---|---|
| | First, the sensor's leftovers in the target for those hours (the placement names the step's class there, not the target: a copy or a source a lost record left) are deleted under the gate's write side, counted (`Move leftovers cleaned`) and logged as a warning: a copy refuses a target whose hour region holds them | the step's class | |
| C1 | the in-flight record `{sensor, week, from, to, first, end}` (`SetMoveInFlight`, a file written atomically) | the step's class | recovery: every hour is in `from` by the placement, so the sensor's rows of those hours in `to` are deleted (none); the record cleared; the step runs again |
| C2 | `CopySensorHours` into the region of moved batches of the target's database of the week (one synced write, the hour's mark where missing) | the step's class (the copy is not read) | recovery deletes the copy; the step runs again |
| C3 | the switch: `SetPlacement(placement.WithoutHours(first, end))`, on the placement read again | the target | recovery: every hour is in `to`: the sensor's rows are deleted in `from` |
| C4 | `DeleteSensorHours` in every database of the week except the target (the source and any garbage of a lost record), each under the write side of `TableHourGate`, on the placement read again (it must name the target for every hour) | the target | recovery deletes in `from` again (nothing left) |
| C5 | the record deleted | the target | nothing |

A step whose source holds nothing of the sensor writes no record and no copy: the switch and C4 only. The cancellation token is checked between the writes; a step stopped there leaves its record for the recovery.

**The recovery never copies.** For every hour of the record it keeps the class the placement names now and deletes the sensor's rows of that hour in the record's other class; when the placement names neither class of the record (or the sensor has no placement) it deletes nothing, logs an Error and clears the record. A copy is made only by a step, from the class the placement names as holding the hours: a copy repeated from a class the placement does not name (the record of a step that finished, come back; a step whose source was already deleted) could replace the only copy with nothing (`A_stale_in_flight_record_of_a_finished_step_deletes_nothing_in_the_target_...`). An abort (the period changed again: the record's `to` is not the target) and a recovery that deleted something are logged as warnings. A record that is lost or does not read is taken as none by the store, and nothing depends on it: what it named is cleaned when a later step meets it, the leftovers in a target before a copy into it and the garbage in any other class by C4 (`A_crash_whose_in_flight_record_is_lost_or_unreadable_...`: every write, both cases; then the period set back, so the step into the old class meets the source left there after a switch, deletes it first, and every row is read once).

**An expired step** (the target class has passed for the week): decided right before its delete by the one rule of expiry applied to the placement the switch writes (`TableBatchRetention.IsExpired(placement.WithoutHours(first, end), hour, now, setting)`, with the setting read then, which must equal the target). E1: `DeleteSensorHours` in every database of the week, each under the gate's write side (counted in `Rows expired by the move`); E2: the switch. No record: after a crash between them the placement still names the old class, which holds nothing of those hours any more (rows that have expired may be gone), and the next pass deletes nothing and switches (the crash matrix has both). It is the only deletion that does not wait for the class that holds the hours: what the owner's decision asks for, a shortened period frees disk. A period lengthened between the selection and E1 deletes nothing (`A_period_lengthened_between_the_selection_and_the_delete_...`).

**Budgets.** `TableSensors.MoveSecondsPerPass` (10) by a stopwatch, never the pass's clock, and `TableSensors.MoveMegabytesPerPass` (256: the bytes the steps copy); at least one step a pass when there is work. The compaction runs after retention and is not bounded by them (one database a pass). A copy step needs `MinFreeDiskMb` plus its bytes free (with `MinFreeDiskMb` 0 no check): below it no copy step runs in that pass (counted in `Move steps refused`, logged once an hour per product), while expired steps, the recovery and compactions go on (`With_too_little_free_disk_...`). Test seam: `TableMergeJob.MoveStepsPerPass` stands for the time budget (0 holds the steps off: the tests of what holds while rows wait for the move); `Steps_go_oldest_week_first_then_by_product_one_a_pass_with_a_budget_of_one_step`: the order is the oldest week first, then the product's id, not a turn per product: the work goes one source database at a time, which bounds the tombstones held before its compaction, and one product's large backlog in a newer week waits for every older week of the store.

**Reads during a step.** The copy and the switch take no gate; the deletes (C4, E1, the leftovers, the recovery) take the write side of `TableHourGate`, as `DropWeek` does: a full read that planned the old class reads it under the read side for its whole run, and the source is not deleted until it ends (`A_full_read_planned_before_the_switch_and_read_after_it_is_complete_...`, the job's delete seen waiting with `TableHourGate.WaitingDeletes`). A step changes only the moved sensor's generation: a chart of another sensor never plans again for it; a chart of the moved sensor across its switch plans again once (`A_chart_of_another_sensor_never_plans_again_...`). Rows moved into a class the hour's record names are found outside that class's own range (the union, "The read") (`Rows_moved_into_a_class_the_hours_record_names_are_read_and_charted_...`). An hour moved, then `Hours` lost and the hour not rebuilt with its blocks kept: the merge writes it again into the class that holds it, every row once (`A_moved_hour_merged_again_...`).

**Retention after a move.** After the switch the source class no longer holds those hours for the sensor, so the retention guard releases the source database by itself: it is dropped at its own time once no placement holds hours there. For a lengthened sensor that is the point of the move: a P1 database is no longer kept for a year by one sensor kept for a year (`A_lengthened_period_is_moved_so_retention_drops_the_old_class_at_its_own_time_...`). A target database retention dropped while its class had not passed (only with the clock set back) refuses the copy: the step is refused and counted, the rows stay in the source and are read there (`A_copy_into_a_database_retention_dropped_...`). Any refusal of the store (`TableBatchRefusedException`: a dropped target, rows of the sensor in the target's hour region, a source hour without its mark or with a mark or key that does not read) is a decision about that step, not a fault: counted in `Move steps refused`, logged once an hour per product, the placement and the record left as they are (the next recovery clears the record, which names nothing written), the other steps go on. The step is not tried again in this process while it stays the same step (product, sensor, source week and class, target, hours): a change of the placement or of the period makes another step, and a restart tries it once more; the gauge `Move steps refused now` shows how many are held so. A dropped target is known before the record is written (`IsWeekDropped`), so such a step writes nothing at all (`A_copy_the_store_refuses_is_counted_once_...`). A store fault (`TableBatchStoreException`) is a fault: counted in `Move faults`, logged, the product's steps stop for the pass, the record stays for the recovery.

**Disk and compaction.** Deleted keys free space only at a compaction. After every delete the database's deleted share (`GetDeletedShare`) is looked at; at a tenth it goes on the product's compaction list (`<product>/Compact`). After retention, one database a pass from the lists is compacted (`CompactWeek`), on the job's thread (never beside a drop of it), whatever the move's budget left (so compactions never wait for the end of a long move). Not compacted: a database of the newest week (the week of the product's newest committed hour, or of the clock, whichever is earlier: its flush would wait for the compaction), and one due to be dropped by its own class (retention removes it whole); both keep their entry. An entry whose database is gone or dropped, or whose share is below a tenth, is removed. A database whose share is still at a tenth after its compaction (its counter not lowered: a fault after the compaction) is not compacted again in this process until a tenth more of it is deleted; its entry stays, so a restart tries once more (`A_database_a_tenth_of_which_is_deleted_is_compacted_once_...`, `A_compaction_whose_share_does_not_go_down_...`, `An_entry_of_the_compaction_list_whose_database_is_gone_is_removed`).

**A period changed again.** One step is in flight per product, each computed from the placement of the moment. A -> B, then B -> C before the step switched: recovery deletes the copy in B (the placement names A), the rows move from A to C. A -> B switched, then back to A: recovery finishes the delete of the source in A, and the hours (now a segment of B) move back to A. Weeks moved twice are written twice: cost, not loss (`A_period_changed_again_after_the_copy_...`, `A_period_changed_back_after_the_switch_...`).

**Metrics and logs.** Self-monitoring (under `Database/Tables`): `Move steps pending` and `Move steps blocked` (set at the end of every pass, whatever it did: `The_steps_of_a_product_whose_recovery_faults_every_pass_count_as_pending_and_blocked`), `Move steps refused now`, `Moved rows`, `Moved batches size`, `Rows expired by the move`, `Move faults` (Error in the sample in which it grew), `Move steps refused`, `Move leftovers cleaned`, `Batch databases compacted`. A fault of the move or of a compaction is not the pass's fault (`TableMergePassReport.Fault`, which `TableMergeService` logs as a pass that stopped): the pass did not stop. `TableMergePassReport`: `MoveSteps`, `MovedBytes`, `MoveExpiredRows`, `Compactions`, logged by `TableMergeService` with the pass. Log `TableMerge`: Info when a sensor's move starts (classes, target, sensor-weeks) and ends, per expired step with rows, per compaction (database, bytes before and after, ms); Warn on an abort, a recovery that deleted a copy (a recovery that deleted nothing is not logged), leftovers cleaned, a refused step (once an hour per product), a share that did not go down; Error on a fault, once per product and hour of the pass's clock (counted every time). A fault stops that product's steps for the pass and leaves its record.

**Not done.** The rename of a week folder when every sensor of a database moves to one class, and the early drop of a database left without owners (decided from the measurements below, a change of its own).

## The removal (#1850, part 4d)

A removed table sensor's rows are deleted at once (by the next passes, within the move's budget), as an ordinary sensor's values are, and a removed root product's batches and never-merged blocks go with it (ADR-0021 point 12, the owner's decisions of 2026-11-25). No grace period and no undo, as for an ordinary sensor. Code: `TableMergeJob.Removal.cs`, `TableBatchDatabase.Removal.cs`.

**The record.** The tree records a removal in the batch store before it removes the entity (`ITableBatchStore.MarkRemoved`, the store-wide file `Removed`, one write per call): `TreeValuesCache.RemoveSensor` for a table sensor (with its root product); `RemoveProduct` of a root product marks the product and the table sensors of its tree in one call (the folder goes whole and the sensors' marks with it; they stand alone when the product's own removal did not complete, so a sensor whose entity went is not left an orphan); `RemoveProduct` of a node marks the table sensors of its subtree in one call; the removal at start of a sensor whose parent is missing marks it with its product not known (the job finds the products that hold a placement of it). A mark that cannot be written is logged as an Error and the removal goes on (a failed record must not make a sensor come back): its rows then stay as an **orphan placement** (below). Ordinary sensors are not touched. A mark says whether it was read from the file at the store's load (`TableRemoval.Earlier`: written by an earlier run) or written in this run; a mark of this run is acted on only once the tree has confirmed that the entity left its database (`ConfirmRemoved`, in memory, after `RemoveSensorWithMetadata` or the removal of the product's subtree, and only for an entity the environment database reads as absent, `IDatabaseCore.EntityExists`: its deletes are logged and swallowed when they fail, and a read that fails counts as present): between the sensor's removal from the tree's cache and from the database a crash would bring the sensor back at the restart, and its rows must still be there (`A_mark_of_this_run_is_acted_on_only_once_the_tree_confirms_its_entity_left_the_database`). A removal whose entity is still in the database stays unconfirmed in this run; after a restart its mark is of an earlier run and the tree says whether the entity is still there.

**In the pass.** `ReadRemovals` once at the start of a pass: a root product with a mark and gone from the tree is left out of the merge from then on (a commit, even one without any class, would create its folder again; its hours are not due, so `Merge lag` does not count them). In `RunMoves`, after the recovery of the steps in flight and before the steps, under the steps' budget (each week database a sensor's keys were deleted from and each hour of a product's blocks is one unit; `MoveStepsPerPass` 0 holds them off as it holds the steps), whatever the merge's lag: root products first, then sensors. Nothing is deleted for a sensor or product that is in the tree (`TryGetProduct`; for a sensor, the table sensors of the store's products in the tree, or `GetSensor`): a mark of an earlier run (a crash between the mark and the removal of the entity, which then stayed) is cleared with a Warn; a mark of this run is a removal the tree is still making, and waits; so does a mark of this run not confirmed yet, also when its sensor or product is already out of the tree. Each decision is taken on the mark as it is then, read after the check of the tree (the tree marks before it removes; `FindRemoval`, a keyed lookup under the record's lock, #1922: before, each check copied and sorted every mark): a mark the pass read and that was replaced since (an earlier run's mark made again, not confirmed yet) deletes nothing (`A_mark_replaced_during_the_pass_by_one_not_confirmed_deletes_nothing_on_the_mark_the_pass_read`), and a removal is counted and logged as done only when its marks were cleared.

**A sensor**, in every product that holds a placement of it, its writes in order:

| # | Write | A crash right after it: the next pass |
|---|---|---|
| D1..Dn | `DeleteSensorHours` of the whole week in every week database of the product from the week of the placement's first hour on, every class (not only those the placement names: what a lost in-flight record left is found too), oldest first, one synced write per database that holds anything of it (with the deleted-bytes counter; then, for every database visited, the compaction list at a tenth, so a crash between a delete and its note loses no compaction: `A_crash_between_a_removals_delete_and_its_note_...`), each under the write side of `TableHourGate` | the databases done hold nothing of it and are not written again; the others are |
| Dn+1 | the product's move in flight, when it is the sensor's (the recovery earlier in the same pass normally cleared it: one whose recovery faulted is left) | |
| Dn+2 | `SetPlacement(sensor, null)` | |
| Dn+3 | the mark cleared (`ClearRemovals`: only the same mark, so one made again since stays), together with the marks of every other sensor whose deletes completed in the same pass: one synced write of the record at the end of the sensors' part of the pass, however many sensors it removed (#1922; `A_pass_that_completes_many_sensor_removals_writes_the_record_of_removals_once`). A write that fails is a move fault; the marks stay and the next pass, which has nothing more to delete for them, clears them | a mark without a placement anywhere is cleared only |

`DeleteSensorHours` deletes only keys that carry the sensor's id, and a batch of the hour region only by the ordinal of one of the sensor's own index records; never a mark. So a shared database keeps every other sensor's keys and values byte for byte (`A_removed_sensor_loses_its_keys_in_every_class_within_the_budget_and_another_sensors_keys_stay_byte_for_byte` dumps every key of every week database with the store closed, before and after). A new sensor registered on the path has another id: it keeps its rows and placement, also when they were merged before the pass that removes the old one (`A_removed_sensors_table_is_refused_and_a_new_sensor_registered_on_its_path_before_the_pass_keeps_its_rows_and_placement`). A sensor removed while a step of its move is in flight: the recovery deletes the copy as for any step, the removal both classes and the record (`A_sensor_removed_while_a_step_of_its_move_is_in_flight_loses_both_copies_and_the_record`, also with the recovery faulting). Never-merged blocks are not touched (they hold other sensors' rows): the merge drops the sensor's rows from them (`Rows of removed sensors dropped`) and expired-block retention judges its tables as unserved. Its feed sensor stays (table feed sensors).

**A root product**, its writes in order:

| # | Write | A crash right after it: the next pass |
|---|---|---|
| P1 | per arrival hour with blocks of the product that the merge takes as closed (its end plus `MergeGrace` has passed; an hour still open waits for a later pass): `CloseHour`, then the hour listed again (the whole hour: nothing can be appended to it after the close) and `DeleteMergedHour(hour, keep: every other product's block of the hour, no watermarks)` under the write side of the gate | the hours done hold none of its blocks |
| P2 | `RemoveProduct`: the slot marked removed (a read finds no product, as for one without a folder; a write is refused, for the rest of the process), every week database of it closed once the reads that hold it end, `Hours` and `Placements` closed, the folder renamed to `<product>.removed-<ticks>` (atomic; the store's folder synced on Linux) and deleted | the renamed folder is not listed and is deleted by the store's first listing in the next run; a product without a folder is only marked |
| P3 | its mark and every sensor mark of the product cleared, as they are then | |

A put for a removed product is refused (every table `UnknownSensor`: its sensors are gone from the tree), so nothing of it comes back after P1. P2 takes no gate: the store waits for the leases of the product's databases, and a full read of one of its sensors in flight finds the weeks after the one it holds absent (the sensor is gone). Pinned by `A_removed_products_blocks_and_folder_go_while_another_products_blocks_of_the_same_hours_stay_and_the_merge_never_writes_it_again` (one of its hours not merged yet, one still open) and the store's `A_removed_product_reads_as_absent_refuses_writes_and_its_folder_is_renamed_and_deleted_while_another_product_stays`, `A_removed_products_folder_left_by_a_crash_or_a_failed_delete_is_never_listed_and_the_next_run_deletes_it`, `A_product_removal_waits_for_a_read_that_holds_one_of_its_databases_and_the_read_completes`.

**Crashes.** Every write above is a case of `A_crash_after_any_durable_write_of_a_sensors_removal_is_completed_by_the_next_pass_which_then_writes_nothing` (after the first and the second database, after the placement, the mark's write failing, after the mark) and `A_crash_after_any_durable_write_of_a_products_removal_is_completed_by_the_next_pass_which_then_writes_nothing` (after an hour of blocks, after the rename, after P2, after P3): the store stopped without a flush and restarted over the same folders; the other sensor reads the same, the next pass completes the removal, and a pass after it writes nothing (no generation changes). The sensors' clear and the product's clear are separate points (`removal-sensors-cleared`, `removal-product-cleared`): with one name for both (`removal-cleared`, until the CI failure of 2026-11-26) a crash meant for the product's clear could land on the sensors' clear of a pass that left the product waiting. `A_crash_after_the_sensors_clear_of_a_pass_whose_product_waits_leaves_only_the_products_mark_and_the_next_pass_removes_the_product` covers that order. Every crash test checks that its pass faulted at its own crash point (`CrashedPass`): a fault before it (a file held by another process during the record's write or the folder's rename) would leave the state of an earlier point, which the test would otherwise read as its own.

**What is never deleted by itself.** A placement whose sensor is not in the tree and has no mark (a mark that could not be written, a sensor whose entity fails to build and is left out of the tree without being removed) is an orphan: kept, its rows held by its stored terms as before (`TableBatchRetention.IsExpired` with no setting), counted in the gauge `Orphan table placements` (by the marks as they are at the end of the pass: a sensor removed during the pass is not one, `A_sensor_removed_during_a_pass_is_not_counted_as_an_orphan_...`) and logged as a Warn once a day of the pass's clock with the ids (at most 50) (`A_placement_without_its_sensor_and_without_a_mark_is_kept_counted_and_still_holds_its_week_database`). A record that cannot be read (a sharing violation, an access right: `GetRemovals` throws) removes nothing: the pass counts a fault in `Move faults` (an Error once an hour), merges every product, and counts every placement whose sensor is not in the tree as an orphan until the record reads again; `MarkRemoved` fails meanwhile (it never writes over a record it has not read), so a removal made then leaves an orphan (`A_record_of_removals_that_cannot_be_read_deletes_nothing_is_counted_and_the_removal_runs_once_it_reads`). A line of the record that does not read is logged as an Error at the load and skipped: nothing is deleted for it, and the next write of the record leaves it out.

**Self-monitoring and logs.** `Removals done` (a counter) and `Orphan table placements` (a gauge, set at the end of every pass). A fault is counted in `Move faults`, logged once per product and hour of the pass's clock, stops that product's removals and steps for the pass and leaves the mark; it never sets the pass's fault. `TableMergePassReport.RemovalsDone`; its `MoveSteps` does not count the removals' writes. Log `TableMerge`: Info when a removal completes (the batches and rows, or the blocks, it deleted), Warn when a mark of something in the tree is cleared, the daily Warn of orphans.

**Compatibility.** New on disk: the file `Removed` and, for a moment, folders `<product>.removed-<ticks>`; nothing changes in a week database, `Hours` or `Placements`. A build before this one ignores both (it lists only folders whose name is a product id) and deletes no removed sensor's rows: they stay until this build's next pass deletes them.

### Blocks or batches, never both, never neither

The order of writes for one arrival hour H:

1. `CloseHour(H)`.
2. Per product with blocks in H: read the blocks, build the batches, encode, decode and compare every cell and every null with the source rows. A mismatch: nothing written for that product, the failure counted as an Error, the blocks stay.
3. `WriteHour` for the product (parts, then the commit in `Hours`).
4. Per product, only once that product has committed H, and after its delay: `DeleteMergedHour(H, keep: its unreadable blocks and every other product's blocks of H, watermarks: its watermarks)` (part 4b: before, only once every product with blocks in H was committed).

**The read rule that makes it hold:** for product P and hour H, when `IsHourMerged(P, H)` (the commit exists) the hour is read from batches only and its blocks are ignored, kept ones and those still within the delay included; otherwise from blocks only. A crash at any point leaves an hour either committed (batches) or not (blocks); the blocks are deleted only after the commit. A repeat of the merge skips committed hours and writes again every part of an hour not committed.

### What goes into the batches

- **The sensor of a table:** by its path in the product (`ITreeValuesCache.TryGetSensorByPath`), as the put does. Rows of a table refused in the envelope are skipped; rows of a table with no table sensor on its path, or of a block whose sequence is below the sensor's `FirstSequence` (a removed sensor's rows), are dropped and counted. Batches are keyed by sensor id, so a sensor created on a removed sensor's path never sees the old rows.
- **The class of an hour's batches:** the period class the sensor has at the merge (its history setting in whole weeks, rounded up: Week 1, Month 5, 3 months 14, 6 months 27, Year 53, a custom period rounded up, at least 1; Forever = `P0`). A change of the period afterwards is a move (part 4), never a second class for the same week.
- **Order:** the rows of a sensor in the hour sorted stably by time, then block sequence, then row in the block (the order `TableRowCollector` uses for blocks), cut evenly into batches of at most 4,096 rows (`ChunkCodec` cuts the same way) and written in that order: the ordinal of a batch within its hour and database is its rank.
- **Equal times across blocks and batches:** a read orders by time, then by arrival hour, then by rank within the hour. For an unmerged hour the rank is (block sequence << 24 | row); for a merged one it is the batch ordinal then the row in the batch. Since every block of an earlier arrival hour has a smaller sequence than every block of a later one, the order is the same before, during and after the merge of an hour.

### Watermarks and duplicates

- The watermark of a product and producer is the highest producer sequence merged. It is durable in the records of the merged hours (the highest per producer over all of them); in the block store it is in memory only (`RaiseWatermarks`, raised again by `DeleteMergedHour`). After a start the merge must raise it from `GetWatermarks` for every product before the first put, or a resend of a merged block would be stored again.
- A put at or below the watermark is a duplicate with `RefusalsKnown` false. `AcceptedTables` is null then (and for a duplicate whose stored envelope cannot be read): which tables were taken is not known (#1850, after the review of #1867).
- It relies on a producer delivering its blocks in order and never taking its sequence back (#1845: a collector that cannot read its producer state takes a new producer id).

### Memory and time of the merge

Measured in phase A (in memory, one busy hour of 2.4 M rows): about 1.7 s on one core (0.2–0.35 s reading and splitting the 360 blocks, 1.2–1.3 s encoding, under 0.1 s verifying) and about 200 MB of managed heap with list-based accumulators; with arrays about 40 bytes per row (3 columns). The budget idea (since weighed by the columns, see "A pass"): when an hour's rows (the sum of `TableBlockIndexEntry.RowCount` of its blocks) times 40 bytes exceed a configured budget (256 MB suggested), merge the hour's tables in several passes, each pass reading the blocks again (0.2–0.35 s a pass) and keeping only its share of the tables. One merge at a time, below normal priority, never holding the block store's append lock while it reads or encodes.

### Retention and removal (part 4)

- **Rules for the move job (the store's primitives above).** Treat `TableBatchRefusedException` of a copy as a decision to take (an expired step for a dropped target, a delete of the leftover first for hour-region rows, a damaged source reported), never as a fault to repeat. Never compact a database of the newest (pinned) week, and compact on the job's own thread after retention, never beside a `DropWeek` of the same database (both wait on each other's holds under the product's lock: "The store's primitives of the move and of the removal"). Before a copy into a class that is not the class of those hours by the placement, delete the sensor's rows of those hours there (`DeleteSensorHours`): `CopySensorHours` refuses a target whose hour region holds them. Remove an entry of the compaction list whose database is gone (`CompactWeek` does nothing for it).

- Retention drops a week database when its class's period has passed for it; every sensor in a class database has that period (the move keeps it so). Blocks never merged leave when they have expired by the rule of expiry for every table sensor with rows in them, never by age alone (part 4b; the first plan said: when their arrival hour is older than the longest period of the product's table sensors).
- A period change moves the sensor's rows into the databases of the new class (copy into the moved region of the same week, delete from the old database, one compaction of the old database at the end), with a durable record of the move in progress that the read consults; a second change during a move is queued or redirects it; a removed sensor cancels its move; a week whose new period has passed is deleted instead of copied. When every sensor with rows in a week's database moves to the same new class and that class has no database for the week yet, the move is a rename of the folder.
- Removing a sensor deletes its index records and batches; under Forever a week is compacted once the removed share passes 10% (built: "The removal", #1850 part 4d).
- The `CheckSensorHistory` skip of table sensors (`src/server/HSMServer.Core/Cache/TreeValuesCache.cs`) is where the history setting starts to apply to them; the page of a table sensor says that rows are kept by whole weeks and may stay up to a week longer.

## Known Issues / Limitations

- The choice against raw at zstd 1 was measured on synthetic quotes, where raw wins only for a few tiny batches; a column of unrelated whole numbers (sizes) is where raw should win.
- Not measured on real data: the check of the codec over the two private hours of the epic was skipped (their converted files cannot be read without the old benchmark); it stays open for the rollout step (#1849).
- The move between period classes ("The move") closes what part 4b left open: a sensor's rows no longer stay in the class they were merged under after a change of its period, and a database is no longer kept past its own period for rows owed to another class once they are moved. What remains: a product's copy steps wait while its merge lags; every step of a product (copy and expired) stops at its oldest uncommitted hour, so a batch that never verifies holds the product's move for the hours at and after it until a restart (counted in `Move steps blocked`, logged once an hour); one sensor that is a few percent of its week frees no disk by itself until a tenth of the database is deleted (the owner's rule; a source under P0 may keep such tombstones for ever); a week folder is never renamed and an emptied database never dropped early (to be decided from the measurements, "The move"); garbage a lost in-flight record left in a class no later step of the sensor touches stays until that database is dropped or the sensor removed (the removal deletes it: every class is scanned); a chart of the sensor being moved may answer 503 Retry-After during its own steps.
- The removal ("The removal", #1850 part 4d) closes what parts 4a to 4c left open: a removed table sensor's rows and placement no longer stay until their week is dropped (for ever under P0), and a removed root product's batches and never-merged blocks no longer stay. What remains: a placement whose sensor left the tree without a record of its removal is kept for ever and reported (the owner's decision: never deleted by itself); a removal made while the record cannot be read leaves such a placement; a removed product's hour still open holds its removal back until the hour closes (about an hour); the tombstones of a removal free disk only once a tenth of a database is deleted (the owner's rule), so one small sensor removed from a P0 week keeps them for ever; a removed product's slot stays refused until the process restarts (the tree never reuses a product id).
- **The union of an hour's class ranges selects hours for every class** (#1850 part 4c, "The read", steps 3 and 4). A sensor L in P1 with one stale or backfilled row about four weeks old in every arrival hour makes each hour's P1 range [now - 4 weeks, hour]; a 24-hour chart of a sensor R in P5 over a window in the past then selects every committed hour of the four weeks after it whose P5 week database exists (672 sources instead of 24, measured), each costing the gate, two generation readings, an acquire of its week database (opens beyond the handle bound when they are not cached), an iterator and two seeks, all answering nothing, and the early stop never stops before them (their earliest row is the read's `from`); a sensor kept for ever pays it over its whole history. It is conservative: never a wrong answer and no false "batch failed" (the store skips the records out of the range before their batch). Before part 4c the union was already the answer for an hour whose record does not name the sensor's class (a sensor with no rows merged in that hour); the new cost is for the hours whose record names the class with a range outside the read. What would remove it: recording which sensors have moved rows (only those need the union), so the others keep their class's own range. Measured with the move job's benchmark ("The move", Measured, case (e)) for rows with old times: such ranges reach back, so a chart of the last day selected 24 hours with or without the wide sensor, and a 24-hour chart of a window four weeks back 672 hours instead of 24 (131 ms against 59 ms cold, 5.3 ms against 0.8 ms warm). Not measured: rows with times after their arrival hour (a collector's clock ahead, rows stamped in the future), which nothing on ingest refuses (times are checked only against the format's range, `TableBlockReader`): their hours' ranges reach forward, and recent windows select them as well. Not built; for the owner to decide.
- A sensor whose period is lengthened after retention has dropped the database of its old class for a week does not get that week back, and rows of that week still to be merged then (blocks held by another sensor's longer period) are left out by the merge and counted as expired ("Not expiry, but left out all the same").
- A table sensor that inherits a dynamic preset (a month, a year) from a folder is kept for ever (see "The period class"): an open question for the owner.
- A part of an hour moved by a period change between two runs of the merge no longer stays behind: the repeat deletes it after writing its own parts and before the commit (see "Writing an hour"). A period change after the commit leaves the sensor's batches in the old class's database, where the read finds them through the placement (part 4b) until the move brings them over.
- An hour committed with no batch at all (every table of its blocks refused or dropped) has no mark in any week database: an `Hours` rebuilt from the marks loses it, and with it the watermarks of that hour if it was the newest; the hour is then merged again from its blocks while they are kept, and its producers' resends after the deletion are not recognised until the next merged hour raises them.
- A block appended to an arrival hour after the hour's parts were written and before its commit (a clock set back past `CloseHour`): if `Hours` is then lost, the rebuild commits the parts without that block's rows, and the deletion of the hour takes the block. The same clock set back past `CloseHour` lets a block land in an hour between the listing of a deletion and its `DeleteMergedHour`, whose `keep` is taken from the listing: the deletion takes it (as the whole-hour deletion before part 4b did for a block of a product that was not yet in the hour).
- (Closed by the cut-off hour of a change, part 4b: two runs of an uncommitted hour give every sensor the same class.) A lone mark of an earlier run taken as committed. R1 has A in P0 and B, C in P1 and crashes after writing only P0(A). Before R2, A's block becomes unreadable and B's period changes to P52, so R2's record names P1 and P52; R2 crashes after writing P1(C), before P52(B) and the removals. The merge keeps failing for longer than P1's period, retention drops the P1 database, and `Hours` is lost: `Rebuild` sees one mark, P0 of R1, whose other class is recorded as dropped, commits the hour, and the delayed deletion takes B's block although no batch holds B. It needs all three: a period change between two runs that did not commit, the merge failing for longer than the shorter period, and the loss of `Hours`. Without a period change a class of R1 is dropped only when its rows have expired under the period they still have, so the commit loses nothing that retention would not.
- A damaged index key of a sensor (one under its hour prefix that does not parse) is treated two ways: `CopySensorHours` refuses the whole range (`TableBatchRefusedException`), `DeleteSensorHours` deletes the key all the same (it carries the sensor's id) without the batch it may name, logs a Warn with the count, and does not count that batch's bytes. Such a batch is then orphaned: no later delete scoped to a sensor can reach it (a batch key of the hour region carries no sensor id), and it stays until its database is dropped.
- The deleted-bytes counter is lowered only by `CompactWeek`. LevelDB's own background compactions also give deleted bytes back without touching it, so the share it gives can overstate what is left to reclaim (even above 1), and a later `CompactWeek` can rewrite a database for little. The flush no longer compacts (see "Keys of a week database").
- The stale-part scan of `WriteHour` acquires the databases of the newest week pinned before it knows whether they hold a key of the hour: after a reopen, the first hour written pins every class database of the newest week, beyond `MaxOpenBatchDatabases`, until the week rolls over.
- Recorded by the review of 139327ef1 (#1850 part 4b), not fixed:
  - **A watermark whose only durable copy is forgotten.** A commit without any class (every table of its blocks refused, dropped or expired) can be the only record that holds a producer's highest sequence. Once no database of its hour's week is left and its blocks are gone, `ForgetHours` removes the record (as it removes every hour's then); after a restart the product's watermarks are loaded without it, and a block of that producer with a sequence at or below the forgotten one would be accepted again. It needs a producer that sends nothing merged afterwards and resends an old sequence after a restart.
  - **The clock set back before an hour that was never committed and whose blocks retention has deleted.** Nothing durable says that such an hour is over (its record does not exist; `CloseHour` is in memory, and only the newest committed hour is closed again after a start), so with the clock set back that far a block can be filed under it again and the hour merged from the new blocks alone, under the placements as they are then.
  - **A placement is created from the setting at the moment of the sensor's first merge** (`Resolve`), not from the setting the sensor had when its rows arrived: a period changed between the arrival of a sensor's first rows and their merge is applied to those rows too, with no cut-off (there is no earlier class to keep them in), and until then expiry of its blocks is judged by the setting of the moment.
  - **Retention and `GetHours` scan every committed hour of a product**, under its lock: `GetHoursWithoutDatabases` in every retention run, the list of `GetHours` after every commit. Measured for five years of hourly commits (43,800 hours, 261 weeks): 70 ms and 11 ms ("Measured" under "Retention"). Linear in the hours; a per-week index of the hours would remove it. Not built.
  - **`Acquire` holds the cache lock (`_cacheLock`) across the native open of a week database and the pauses of its retry** (up to 10 + 30 + 60 + 120 ms on the transient `.dbtmp` failure): one product's slow open delays every other product's acquire and release of a database already open, a cached read included.
  - **A slot is kept for every product id ever asked for** (`_products`): a call for an id without a folder leaves its empty `ProductSlot` until the store is disposed. Bounded by the ids the tree and the block store ever name; two small objects each.
