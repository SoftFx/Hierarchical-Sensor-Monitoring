# Feature: Native Collector C++ API

> Owner: integrations | Last reviewed: 2026-11-25 | Canonical: yes
> Scope: The public, developer-facing C++ RAII API over the native collector C ABI, plus its `find_package` packaging, console example, and migration story from the C++/CLI wrapper.

---

## Description

The native collector (epic #1093) is layered: a C++ core, a stable **C ABI** (`include/hsm_collector/hsm_collector.h`), and — this feature — a header-only **C++ RAII wrapper** (`include/hsm_collector/*.hpp`, `namespace hsm::collector`) that gives application code a modern, exception-based, strongly-typed surface without touching raw C handles. It is the C++ analogue of the .NET `HSMDataCollector` API.

**The legacy C++/CLI wrapper in `src/wrapper/` is now native too.** Its implementation (`hsm_wrapper::DataCollectorProxy`, `DataCollector.h` + sensor/options/alert DSL) was reimplemented over this `hsm::collector` API with the **public headers keeping every declaration** (2.0.0 added `DataCollectorProxy::UseHttpTransport()`), so it ships as a pure-native `HSMCppWrapper.dll` (no CLR). Downstream consumers (tt-aggregator2) **replace the headers, relink, and change no source of their own** — see `docs/native-collector-migration.md` (relink path) and the "Native wrapper DLL" guide below.

The wrapper is a **thin convenience layer**: it adds no wire behavior. Every registration/value payload it produces is byte-identical to the raw C ABI, pinned by the `native_wrapper_*` twin tests (wrapper sensor vs raw-ABI sensor → identical `hsm_sensor_test_wire_registration_json`). All wire/parity contracts live in `collector/` features; this feature owns only the ergonomics, lifetime management, and distribution.

**Error strategy (resolved #1100):** exceptions. Every failing call throws `hsm::collector::Error` (carrying the collector's `last_error` for collector-scoped calls, or a static message + C result-code name for sensor-scoped calls). This matches the .NET wrapper's throwing style.

**`hsm_collector_last_error` is thread-safe from 0.8.2 (#1444).** The stored message is written by whichever thread failed an operation — a host call or one of the collector's own worker threads — so the C entry point no longer returns an interior pointer into it: it copies the message (under a dedicated leaf mutex) into **thread-local** storage and returns a pointer into the caller's own copy, valid until *that thread* calls the function again. The classic C last-error contract, chosen over an additive `_ex`/caller-buffer entry point because it fixes every foreign-language wrapper (the Rust probe, the C++ wrapper, any host) **without an ABI change and without the wrapper changing a line** — a new entry point would only help callers that migrate to it, and would leave the unsafe one in place. The ABI is therefore unchanged (PATCH, not MINOR). Callers that need the text to outlive their next call must copy it, exactly as the C++ wrapper's `Collector::LastError()` already does.

**Hosted by the HSM Agent (#1167).** The standalone Windows-service product `src/agent/` consumes this API to run the collector as an always-on service. See `agent/feature.md`.

## Invariants

- **No wire distortion.** A sensor created/posted through the wrapper produces the exact same bytes as the equivalent raw C ABI call. Enforced by `native_wrapper_registration_matches_abi` / `native_wrapper_alert_builder_matches_abi`.
- **RAII ownership.** `Collector` and every `Sensor` are move-only; the destructor frees the underlying handle (`hsm_collector_destroy` / `hsm_sensor_release`). Releasing a sensor handle does NOT unregister it — the collector keeps it.
- **Callback lifetime (the trampoline rule).** `std::function` callbacks (lifecycle listener, logger, function-sensor body, metric-source factory) are heap-allocated and owned by the `Collector`; their address is passed to the C ABI as `void* user_data`, which **must outlive the collector**. The `Collector` destructor calls `hsm_collector_destroy` BEFORE the `std::function` storage is freed, and `std::unique_ptr` keeps each callable at a stable address across `Collector` moves.
- **Alerts ride the registration.** Attaching rebuilds the payload. Before Start it is what Start registers; while the collector runs (0.9.1) the attach re-records the run's registration in place and, on the HTTP transport, re-posts it — so a sensor created at runtime and given its alerts right after the create call registers once, alerts included.
- **Threading.** Drive `Start`/`Stop` from one thread (or serialize externally). Callbacks fire on the scheduler/lifecycle thread and must not call a lifecycle method (`Start`/`Stop`/`Dispose`) from within.

## Integration guide

- **Live server transport (#1165).** `Collector::UseHttpTransport()` (C ABI `hsm_collector_use_http_transport`) switches the collector from the in-memory recording sender to a real libcurl POST. Call it BEFORE `Start()`. It (a) registers every sensor on the server — a wire `AddOrUpdate` batch POSTed to `/commands` at Start — and (b) streams values to `/list` in the **.NET server wire format** (`Time` ISO-8601, bar `OpenTime`/`CloseTime`). It throws / returns `HSM_RESULT_INVALID_STATE` if the library was built without `HSM_COLLECTOR_HTTP`. The conformance corpus stays on the canonical/in-memory recorder (`send_wire_` is false there), so wire vs canonical never cross. End-to-end proven against a Dockerized HSM server by `examples/server-monitor`.
- **Collector session transport (#1668, collector 0.12.0).** `Collector::UseSessionTransport()` (C ABI `hsm_collector_use_session_transport`) is the alternative to `UseHttpTransport()`: one WebSocket to the server's session endpoint carries values and registrations, nothing goes over the HTTP routes, and there is no fallback to them. Call it BEFORE `Start()`, instead of `UseHttpTransport()`. It needs a libcurl with WebSocket (8.14.0+) and a server that has the session endpoint. File values travel in `list` frames with the other values (#1660 step 2b; refused with `HSM_RESULT_INVALID_STATE` before). Details: `aicontext/features/collector/http-client/feature.md` (Session transport).
- **What a second connection of the session needs (#1848, collector 0.14.2; internal, no ABI).** The lower half of the table connection, generic so that a later binary upload can use it too: `WebSocketConnection::SendBinary` sends one binary message as one frame (multi-megabyte frames go through libcurl in its 64 KiB pieces, bounded by one timeout for the whole frame); the receive cap is a constructor argument (default 8 MiB, the session's; the table connection asks for 1 MiB) and `Receive` stays text only; `SessionTransport::CurrentSession()` gives the hello's `sessionId` and a generation that changes at every new session, `Options()` the URL, headers and certificate check to repeat, `kSessionIdHeader` the `X-Hsm-Session` header name; the reconnect backoff (1 s to 60 s, jitter) is a shared helper, `hsm_reconnect_backoff.hpp`. The session's own behaviour is unchanged. Details and tests: `aicontext/features/collector/http-client/feature.md` (WebSocket client connection, Session transport).
- **Table sensors, build option and block writer (#1848 PR 1, collector 0.14.1).** CMake option `HSM_COLLECTOR_TABLES`, **OFF by default**: the default build, the agent, the probe and the wrapper build exactly as before, with no new dependency (the wrapper builds with it ON since wrapper 2.0.0, #1848 part 5). ON, it needs **zstd** (`find_package(zstd CONFIG)`, falling back to pkg-config `libzstd` where a distribution ships no CMake config, e.g. Debian's `libzstd-dev`) and **zlib** (`find_package(ZLIB)`, for `crc32_z`); both are private to the static core and re-found by `hsm_collectorConfig.cmake` for a consumer of an installed tables build. In a vcpkg manifest build of `src/native/collector` itself, zstd and zlib are the manifest feature `tables`, which `HSM_COLLECTOR_TABLES=ON` turns on before `project()` (a build with tables OFF resolves neither). The vcpkg overlay port has the feature `tables` (it depends on feature `http`, since the blocks will travel on the collector session, and adds `zstd` and `zlib`); the Conan recipe has the option `tables` (zstd, zlib) but a Conan build cannot deliver tables (its libcurl 8.10.1 has no session). What is there: `src/tables/` — `TableBlockWriter` (the format of `aicontext/features/api/table-block/feature.md`: 44-byte header with zlib CRC-32, directory, raw 8-byte columns column-major, null maps, one zstd level 3 frame that declares its content size through one reusable `ZSTD_CCtx`; header and directory stored byte by byte little-endian, columns copied on little-endian hosts and byte-swapped otherwise, nothing cast into the payload; null cells written as zero; a column without a null gets no flag and no map; every limit — tables, rows, columns per table, identifier length, the exact decompressed length in 64 bits, int32 ranges, time range — checked before anything is written, unique identifiers checked by sorting, in overflow-safe arithmetic, and after compression the block plus a caller-reserved frame header (at most 64 KiB) against a frame limit, refused as `FrameTooLarge` so the caller splits; errors are return values with static texts, no call throws and no failure path allocates; buffers grow geometrically; an allocation failure in `BeginTable`/`AddColumn` leaves the writer consistent and failed until `Reset`). **The refusal rule PR 3 builds on:** a refused `BeginTable`/`AddColumn` leaves the writer exactly as it was, and `Finish` never changes the writer whatever it returns (the tables stay, the last table stays open); the writer cannot remove a table, so the pipeline splits by `Reset` and packing the parts again from its own rows, cutting with `DecompressedLength()` before a limit and `TableSchema` (the managed rules and canonical bytes; id = CRC-32). The block's layout is written by hand (it is this repository's format); compression and the checksum come from the libraries. **What is NOT there yet:** no public ABI or C++ API for table sensors, no pipeline (buffers, tick, backlog), no table connection: nothing in the collector calls the writer. Those are the next PRs of #1848 (ABI and pipeline at 0.15.0; the binary WebSocket frames and the table link; the wrapper). Proof of the format: the native writer gives the header bytes and the decompressed payload of the managed golden blocks for their inputs (`native_table_golden_*`), and in CI (`http-transport` lane) the managed `TableBlockReader` reads every block the native writer wrote and compares rows and payload with the managed writer's (`NativeBlockVectorTests`).
- **Large files (#1887, collector 0.16.0; MINOR: 11 new exported functions).** A watched folder (`hsm_collector_watch_large_files`) and one file handed over (`hsm_collector_send_large_file`) upload large values of a File sensor in pieces on the file connection of the collector session, with the managed collector's rules (#1888): the settle time, the order, one upload at a time on a thread of lowered priority, zstd level 3 pieces, the speed limit on bytes sent, continue from the server's piece after a drop or a restart, the state files in the data folder (`hsm_collector_set_data_folder`), deletion of exactly the sent file after `stored`, refusals, given up, and every file not sent said and counted. They need `HSM_COLLECTOR_HTTP` and `HSM_COLLECTOR_TABLES` and, off Windows, OpenSSL's libcrypto (vcpkg feature `tables`); on Windows CNG, `shell32` and `ole32`. A collector that cannot send them gives `UNAVAILABLE` watches and files and fails no call. The agent and the probe do not switch large files on. Details, invariants and what differs from the managed collector: `aicontext/features/collector/large-files/native-collector.md`; the ABI: `docs/native-collector-c-abi.md`, "Large files". `AckedBinaryLink` gained `Request` (a text request with its ack), used by `begin`, `end` and `discard`.
- **The table connection (#1848 part 4, collector 0.15.1; no ABI change).** A collector on the session built with
  `HSM_COLLECTOR_HTTP` and `HSM_COLLECTOR_TABLES` delivers its table sensors: `SessionTableChannel` implements the
  pipeline's channel seam over the session (registrations as a `commands` request of their own) and over
  `AckedBinaryLink`, a generic second WebSocket of the session (the upgrade with the caller's subprotocol and
  `X-Hsm-Session`, the hello envelope and its heartbeat, the probe, bytes 0..15 of the frame header, the ack envelope,
  ping and pong, the protocol errors of the server's frames; the subprotocol, the rest of the header and the meaning of
  the hello's and the ack's bodies are the caller's). No thread of its own: the pipeline's delivery thread owns the
  connection, and the seam gained `ServiceDelayMs`/`Service` (the delivery thread's wake between ticks) and
  `WriteReports` (the channel's lines, written with no lock held). The session transport keeps an ack's `body`
  (`SessionResult::body`) and has a request that can be abandoned on its own (`Request(..., abandon)`, `Wake`);
  `WebSocketConnection` closes with a code (`Close(linger, code, reason)`) and, opted in, closes in order on a refused
  message (`1003`, `1009`). The agent (tables OFF, HTTP ON) links those changes and nothing of the table connection
  runs in it (agent 0.6.3). Behaviour, differences from the managed collector and known limits (a stop can wait for a
  Schannel write that ignores its timeout): `aicontext/features/collector/table-sensors/feature.md`, "Native
  collector".
- **Table sensors: C ABI, C++ API and pipeline (#1848 PR 3, collector 0.15.0).** The C ABI of table sensors (`hsm_collector_create_table_sensor`, `hsm_table_sensor_add_row`/`_add_rows`, `_get_stats`, `_state_reason`, `_path`, `hsm_collector_set_table_options`; `docs/native-collector-c-abi.md`, "Table sensors") and the C++ wrapper `include/hsm_collector/tables.hpp` (`TableColumn`, `TableSensorOptions`, `TableCell`, move-only `TableSensor`, `Collector::CreateTableSensor`/`SetTableOptions`; create throws `Error` like every factory, `AddRow`/`AddRows` return `bool`/`size_t` for a drop and throw only for a wrong shape) exist in **every** build. The pipeline under `src/tables/` (`hsm_table_pipeline.{hpp,cpp}`, `hsm_table_row_buffer.{hpp,cpp}`, the internal channel seam `hsm_table_channel.hpp`) is compiled in every build too; only packing needs `HSM_COLLECTOR_TABLES`. **What works at 0.15.0:** everything up to the channel: buffering, the bound, the tick (a second `ScheduledTask` on the collector's clock, `src/hsm_scheduled_task.hpp`), registration, packing and splitting with the PR 1 writer, the backlog, delivery and every answer, the stop drain, loss reports; proven against the tests' recording channel and the shared conformance fixture. **What does not:** there is no real channel yet, so on a real host every table sensor is `Unavailable` (reason: no session transport, no table support in the build, or "the table connection of the collector session is not implemented") and its rows are dropped and counted; the table connection is the next PR of #1848. The agent and the probe build with tables OFF and create no table sensor: nothing of this runs in them (no pipeline exists without a table sensor). Details and the differences from the managed collector: `aicontext/features/collector/table-sensors/feature.md`, "Native collector".
- **Live default-sensor values + value-source plugin (#1164).** `Collector::InstallWindowsMetricSources()` (C ABI `hsm_collector_install_windows_metric_sources`) installs a ready-made Windows PDH/Win32 factory so the value-typed default sensors (Total CPU, Free RAM, disk gauges, free disk, process, TCP connections — Established gauge + Failures/Reset deltas) read live. **DoubleBar/IntBar sensors mirror managed `BarMonitoringSensorBase` (#1428, collector 0.7.1)**: they sample every `kMetricBarSampleMs` (5 s, `BarTickPeriod`) into ONE bar of the sensor's bar period (`kDefaultBarPeriodMs`, 5 min, `BarPeriod`, aligned to wall-clock multiples) and post a **partial** snapshot of that bar every catalog post period (15 s, `PostDataPeriod`, aligned to wall-clock multiples) — same OpenTime/CloseTime for every post of the window, Count/Min/Max/Mean/Last growing; the bar rolls on the first sample tick past CloseTime (the closed bar is published once more) and Stop flushes the partial. The push-fed built-in bars (queue diagnostics, network speed) run the same schedule without sampling. Before 0.7.1 the bar window equalled the post period, so every 15 s post carried a new OpenTime and the server persisted 20× more bar records than for a managed sender (details and storage effect: [`default-sensors/feature.md`](../../collector/default-sensors/feature.md#native-metric-driven-bars-partial-posts-1428)). Double/Int sensors post one value per period. A read `ERROR` disposes + recreates the source (managed recreate-on-error) **and is logged through the deduplicated error sink**; if the factory then *declines* to rebuild, the sensor is parked (`is_periodic_` cleared) rather than looping on `NO_VALUE` forever — a wedged reader is loud, not silently dead (the `PeriodicTask` lesson). The PDH factory treats query-level priming statuses (`PDH_NO_DATA` …) as a skipped tick (keeps the primed baseline) and **declines an unparseable drive** instead of guessing `C:`. It dispatches on the **sensor name** (the last path segment), not the whole `<computer>/<module>/…/<name>` string, so a user-chosen computer/module name containing a label fragment can't mis-bind. Process sensors bind to the **PID-resolved** current-process PDH instance (`<exe>` or `<exe>#N`, matched via the `ID Process` counter so several same-named processes don't cross; falls back to the bare name if it can't resolve). Both `InstallWindowsMetricSources()` and `UseHttpTransport()` reject (`HSM_RESULT_INVALID_STATE`) unless the collector is stopped — they must be installed before `Start()` (the worker reads the transport/factory lock-free). The seam is also a **plugin point**: `SetMetricSourceFactory` + an `IMetricSource` (`Read() → std::optional<double>`) supplies any custom source — `Collector::CreateMetricSensor(path, period)` makes a Double sensor the factory drives. `examples/windows-monitor` streams live host metrics; `examples/crypto-monitor` is a libcurl BTCUSD plugin — both proven against a real server. Still follow-up: non-double default sensors (WMI/registry/EventLog/prediction/ThreadPool).

- **Live default-sensor values on Linux (#1414).** `Collector::InstallLinuxMetricSources()` (C ABI `hsm_collector_install_linux_metric_sources`) is the symmetric Linux factory: `/proc/stat` busy%-by-delta for Total CPU, `/proc/meminfo` `MemAvailable` for Free RAM, `statvfs("/")` for free disk space, and `/proc/self/{stat,task}` for process CPU / RSS / thread count. Every source reads the SAME OS truth the managed Unix sensor reads and runs the mirrored normalization (rule #10), so the two collectors cannot drift; the parsing + delta math is a portable, OS-read-free `src/proc_metrics.{hpp,cpp}` (the `tcp_connection_stats.hpp` pattern) unit-tested on every lane with the SAME fixture values as the managed `ProcParsersTests`. Like the Windows factory it dispatches on the sensor name, treats an unreadable `/proc` file as a skipped tick (not a fault, mirroring the managed swallowed `IOException`), declines the TimeSpan prediction sensor, and returns `HSM_RESULT_INVALID_STATE` off its platform / on a running collector. **Registration is also platform-correct:** built for Linux, `add_disk_monitoring_sensors` registers the letter-less Unix pair and `add_all_computer_sensors` registers system + disk only — no Windows OS-info / event-log / network nodes that could never produce a value there (Windows composition unchanged). The Linux probe registers the three TCP catalog rows itself through `hsm_collector_add_default_sensor` and feeds them from `/proc/net/snmp` (#1711); no Linux metric source binds them, so nothing else posts to them. Details and the mirrored-algorithm table: `aicontext/features/collector/default-sensors/feature.md`.
- **Version sensors mark every Start AND every Stop (#1433, collector 0.7.4).** `AddAllModuleSensors(product_version)` and `AddCollectorMonitoringSensors()` don't just register `.module/Version` (the connected app's version, registered only when `product_version` is non-empty) and `.module/Collector version` (the native collector's OWN `HSM_COLLECTOR_VERSION_STRING`, or a host override via `SetCollectorVersionOverride`; independent of the managed collector, the host and the server). Each becomes a **lifecycle marker**: its `Version.ToString()` value is posted with a `Start: dd/MM/yyyy HH:mm:ss` comment on **every** Start and a `Stop: dd/MM/yyyy HH:mm:ss` comment on **every** Stop (UTC — the managed `SensorBase.DefaultTimeFormat`, rendered with `CultureInfo.InvariantCulture` on the managed side because `/` and `:` are culture-replaced separator placeholders in a .NET custom format string, so the native hard-coded separators are correct on a localised host too), mirroring managed `ProductVersionSensor.StartAsync`/`StopAsync`, whose sensors are re-Inited on each collector start. The Start instant is stamped once when the sensor is registered and **replayed unchanged** by a restart (managed stamps `options.StartTime` at prototype creation); the Stop instant is the moment of the stop. Because the agent registers sensors while the collector is **Stopped** (where the data gate drops live values), the marker is held (`version_markers_`) and emitted from the Start transition, so it lands on the server on connect rather than being silently lost; a marker registered on an already-running collector posts its Start value at once. Emission is claimed per run (`start_epoch_`), so registering the group twice — e.g. `AddAllModuleSensors()` followed by `AddCollectorMonitoringSensors()`, or an Add racing `Start()` — still yields exactly ONE `Start:` marker per run. The Stop post rides the graceful stop flush, so it only reaches a real server thanks to the bounded HTTP stop drain (#1432). Pinned by `native_version_sensor_marks_start_and_stop` + `module_markers_contract.hsmtest`.
- **`Service alive` alert waits 5 minutes (#1666).** The `ServiceAliveTtl` catalog row gives the TTL alert its own inactivity period, `kServiceAliveInactivityMs` = 300000 (`has_inactivity` on the alert), so the registration carries `"TTLs":[3000000000]`, byte-identical with managed `ServiceAlivePrototype.InactivityPeriod`. Before, the row copied the managed wire of that time, `"TTLs":[null]` (no interval: the server resolved it from the sensor's parents, which on a product with default settings is none, so the alert never fired there). Server handling of existing sensors and the accepted behaviour change: `collector/default-sensors/feature.md`. Pinned by `native_default_sensor_wire_matches_net`, `native_default_sensors_wire_golden` and `default_sensors_contract:collector_alive_registers_ttl_alert`.
- **Collector self-monitoring emits values (#1198 follow-up).** `.module/Service alive` (heartbeat) and the `.module/Collector queue stats` bars (`Queue overflow`, `Items count in package`, `Package process time`, `Package content size`) were registered-but-empty in the native port. Handles are captured when `AddCollectorMonitoringSensors` / `AddAllQueueDiagnosticSensors` run; then a dedicated **self-monitor thread** posts the heartbeat plus the queue-overflow **delta** (only when non-zero, so the bar isn't all-zeros), and the **dispatch send path** posts per-package items/time/size from its UNLOCKED window (time = the average wait of the package's values in the send queue, in seconds, as managed `AvrTimeInQueue` — until 0.10.1 it was the HTTP send duration; see `collector/default-sensors/feature.md`, #1480) — bars only aggregate (`AccumulateBar`), so there is no `queue_mutex_` re-entrancy. The heartbeat's **very first beat is `false`** — the start marker managed `CollectorAlive` posts from its first tick — and every later beat is `true`; the flag lives on the collector, not on the self-monitor thread, because managed keeps it on the sensor instance, so a Stop/Start cycle does NOT re-arm it (#1433). **The beat runs on the SENSOR's own 15 s `PostDataPeriod` (#1437, 0.8.2)**, mirroring managed, where `CollectorAlive` is a `MonitoringSensorBase` driven by that period; the queue-overflow counter keeps its own cadence, the package-collect period, because that is the cycle that evicts values. Until 0.8.2 the beat followed the collect period: the same 15 s by default, but a different knob — a host that raised the collect period above the sensor's then-intended **1 min TTL** (the agent exposes it as config) could flip `.module/Service alive` to Timeout permanently while the collector was healthy. The self-monitor loop now sleeps to the earliest of the two deadlines and advances both before posting, so a throwing post cannot spin it. Pinned in both directions: `service_alive_beats_on_the_sensor_period` (corpus; a 300 ms collect period still gives one beat in 1.5 s) + `native_service_alive_beats_on_its_own_period`, and the cadence by `service_alive_keeps_beating_with_a_long_collect_period` (corpus, #1443; a 60 s collect period still gives the second beat 15 s after Start). Overflow is counted lock-free (an atomic incremented in `Enqueue`, and since 0.10.1 also for every retry `ReEnqueueLocked` drops at capacity; Stop folds the last partial cycle into the bar, #1480); `AddBool` (which enqueues) only ever runs on the self-monitor thread, never under `queue_mutex_`. **Registering either group AFTER `Start()` is allowed and safe (#1453, 0.8.2):** the handles are published under a dedicated LEAF mutex and every reader (the self-monitor thread, the dispatch stats path) takes a whole-struct snapshot and releases the mutex before touching a sensor, so a late registration cannot race a running reader; the two "group enabled" flags are atomics. A late registration also **arms** the loop (`EnsureSelfMonitorRunning`) — it is otherwise armed only at Start, so a group added on a running collector used to leave the heartbeat registered-but-empty for the rest of the run, which the sensor's inactivity alert turns into a Timeout alert on a healthy collector. The arm/join pair is guarded by its own `self_monitor_lifecycle_mutex_`, **deliberately not `op_mutex_`**: a lifecycle listener runs with `op_mutex_` held and is allowed to register sensors, so arming under it would self-deadlock that host. `StopSelfMonitor` takes the same mutex and `StopCore` flips the state before it, so a late arm either lands before the join (which then reaps the new thread) or sees Stopping/Stopped and does nothing. Arming is accepted in **Starting** as well as Running, so an Add racing `Start()` cannot leave the loop unarmed; the beat it queues waits in the send queue like every other pre-worker value. A handle published while the loop is already asleep sets a wake flag in the wait predicate — a bare `notify_all` would not break `wait_for(…, predicate)` — so it beats at once instead of waiting out a long collect period. Before that fix the publish was a plain `shared_ptr` assignment against an unsynchronized read — the TSan lane caught it on an unrelated PR. Guarded by `native_collector_self_monitoring_emits` + `native_service_alive_marks_the_first_beat` + `native_self_monitor_handle_published_after_start_is_synchronized` (which exists to keep the TSan lane exercising that exact ordering) + `native_self_monitoring_added_after_start_arms_the_heartbeat` + `native_self_monitoring_group_from_listener_does_not_deadlock` + `native_late_heartbeat_handle_wakes_the_sleeping_loop`, and cross-language by `module_markers_contract:service_alive_beats_when_added_after_start` — managed starts a sensor added during Starting/Running at once (`SensorsStorage`), so the arming fix is a parity contract, not a native-only detail.
- **Rate options parity (`RateSensorOptions`).** `RateOptions` carries the full registration surface (TTL / unit / display-unit / keep-history / self-destroy / statistics / aggregate / grafana / singleton / location), not just `post_period`, and lowers through the new C ABI `hsm_collector_create_rate_sensor_with_options`. The bare `hsm_collector_create_rate_sensor` (post-period only) is unchanged, so the default rate registration stays byte-identical. Pinned cross-language by `rate_options_contract.hsmtest` + `native_rate_options_parity`.
- **Description updates (#1416, collector 0.10.0).** `hsm_sensor_set_description(sensor, text)` (NULL emits null, which the server reads as "unchanged"; "" clears) rebuilds the registration exactly like an alert attach: before Start it is what Start registers, while running the run's recorded registration is replaced in place and re-posted. Pinned by `native_set_description_rebuilds_the_registration` and the HTTP re-registration test; cross-language (since the managed counterpart `IDescribableSensor.SetDescription`, #1482) by `registration_contract:set_description_*` in both drivers.
- **Previous paths (#1724, collector 0.13.0).** `hsm_sensor_set_previous_paths(sensor, paths, count)` (C++: `Sensor::SetPreviousPaths(std::vector<std::string>)`) declares the FULL product-relative paths the sensor was registered under before; the server moves (or merges) the old sensor here on registration. Strings copied; NULL and ASCII-whitespace-only entries dropped (the managed rule); `count == 0` removes the list and an empty list omits the member, keeping the wire byte-identical to 0.12.x. Re-emission as `hsm_sensor_set_description`, including the bounded retirement of replaced registration texts. Pinned by `native_wire_registration_with_previous_paths_matches_net_byte_layout` and `previous_paths_contract` in both drivers; server side in `features/server/sensor-move/feature.md`.
- **Sensors created while running are registered on the server (#1416, collector 0.9.1).** The Start batch posts every sensor that exists at Start; a sensor the host creates later through any public create path (the Linux probe's Docker source meeting a new Compose service) used to be recorded locally only — the HTTP transport never POSTed it, so the server knew it from its values alone, without metadata or alerts. `RegisterSensorLocked` now queues such a sensor; the worker posts the queue to `/commands` at its next dispatch cycle, before that cycle's values (the managed command-queue cadence), and the stop drain flushes it first. Each sensor carries a registration version: a successful post records it, so an unchanged registration is never re-sent (the built-in lazy sources that post at once are not posted twice), and an alert attached after the post bumps it and re-queues the sensor. A runtime post that got no HTTP response is retried at the next cycle; an HTTP error answer is final, as for managed commands (both logged, deduplicated). A registration text replaced by a later attach is kept alive until the collector is destroyed, so a pointer from `hsm_collector_get_registration_json` never dangles. The registration inputs are guarded by a per-sensor leaf lock, since an attach may now race the Start snapshot and the worker's post. Pinned by `alert_registration_contract:alert_on_sensor_created_while_running_registers_with_it` (both drivers), `native_http_registers_sensors_created_while_running`, `native_http_alert_after_runtime_registration_reregisters`.
- **Enum sensor with sensor options; options-anchored bars and rates (#1476, collector 0.9.0).** `hsm_collector_create_enum_sensor_with_sensor_options(collector, path, options, enum_options, count, out)` is the one C entry point that registers an enum sensor with BOTH its `EnumOptions` and the full `hsm_sensor_options_t` surface — the managed `CreateEnumSensor(path, new EnumSensorOptions { … })`, the shape of the `Service status` state sensor (EnumOptions + `AggregateData = true` + an attached "not Running for 5 min" alert). It shares `ApplySensorOptions` with `hsm_collector_create_sensor_with_options`, so the two cannot drift in how a sentinel maps to null; the enum kind keeps `DisplayUnit:null`. Unlike the managed `EnumSensorOptions` constructor, nothing defaults `AggregateData` to true — the caller sets it. Same release: the bar and rate `*_with_options` creates now resolve the path through `CalculateSystemPath`, like every instant sensor (before, `is_computer_sensor` forced `IsSingletonSensor` but the sensor still landed under `<computer>/<module>/`). First consumer: the Linux probe's Rust wrapper (`src/probe-linux`, `Collector::enum_sensor_with_options`), for the Docker source (#1416); its computer-level CPU-temperature bar needed the anchoring fix. Pinned by `options_surface_contract:enum_full_options_*`, `bar_options_contract:bar_{computer,product}_sensor_*`, `rate_options_contract:rate_{computer,product}_sensor_*` (both drivers) + `native_enum_sensor_with_sensor_options_validates_arguments`.
- **TCP connection failure rate (admin rate metric, Windows; first built-in Rate consumer).** `EnableTcpConnectionFailureRateSensor(period)` (C ABI `hsm_collector_enable_tcp_connection_failure_rate_sensor`) starts an owned thread that each period reads the cumulative failed-connection-attempt counter (`MIB_TCPSTATS.dwAttemptFails`, IPv4+IPv6 summed via `GetTcpStatisticsEx`) and pushes the interval delta into a **Rate** sensor at `.computer/Network/Connection failures rate` (OriginalUnit ValueInSecond, **DisplayUnit per-minute** → failures/min). The first sample seeds the baseline; a quiet interval pushes nothing (posted rate 0). The baseline/delta/wrap/quiet math lives in a portable, OS-free `TcpFailureRateAccumulator` (unit-tested by `tcp_failure_accumulator_*`); the read of the two families and the error report live in a portable `TcpFailureRateSampler` (family readers in, error report out; unit-tested by `tcp_failure_sampler_*`), and `WindowsTcpFailureSampler` only binds the two `GetTcpStatisticsEx` reads to it. The sensor is created **synchronously at Start** (so it is deterministically registered); the thread is joined on Stop/Dispose. Call BEFORE `Start()`; Windows-only. The HsmAgent enables it by default on Windows (60 s). It carries a threshold **alert** (rides the registration): `Value > 1` failed attempt/sec (≈ 60/min), `AndSetSensorError` + notification, 5-minute confirmation period — so a sustained failure spike pages while transient blips don't. **Parity:** managed has the same sensor since 3.8.0 (#1659 B2, `IWindowsCollection.AddNetworkConnectionFailuresRate`): the same OS source through `IPGlobalProperties`, a mirrored accumulator, and a registration held byte-identical by the conformance fixture `collector/windows/tcp_failure_rate_contract.hsmtest`. Managed keeps its older `ConnectionFailuresCountSensor` (a delta count from the performance counter) beside it. **Neither address family readable (0.13.1, #1752):** a tick on which the TCP statistics of neither IPv4 nor IPv6 can be read (the seeding one included) is reported through the collector's deduplicated error channel (`LogError`: the logger and `.module/Collector errors`), so a blackout of any length is one line per `exception_deduplicator_window_ms`; the text is the managed one (`TCP connection failure rate sampling error: the TCP statistics of neither IPv4 nor IPv6 could be read.`). The sensor goes on posting 0 meanwhile, which without the report would read as a quiet network (root rule 8). One unreadable family is not reported, as in managed. **Asked for more than once (0.13.1, #1752): the first period stays**, one rule for both collectors. A repeated enable call with the same period changes nothing and reports nothing; with another period it does not apply it and reports `The TCP connection failure rate sensor was already enabled with a period of <first> ms; the period of <asked> ms of the second request is not applied.` through the logger only: the call comes while the collector is stopped, when `.module/Collector errors` takes no values. The call still returns `HSM_RESULT_OK` (no enable call of the C ABI has a result for "already enabled with other settings", and a new failure for a call sequence that succeeded before would break hosts), so the C++ wrapper does not throw; `period_ms <= 0` is `HSM_RESULT_INVALID_ARGUMENT` on a repeat too, and a call after Start stays `HSM_RESULT_INVALID_STATE`. The first period is the collector's for good: a request between a Stop and the next Start does not replace it either (the managed monitor stays in the storage across a stop). Before 0.13.1 the last period given before Start was the one used. **Neither #1752 rule has a conformance scenario, by design:** the period is not on the wire (the registration does not carry it), and the report needs the OS read to fail, which a driver cannot cause through the public API; both are pinned per language (native `native_tcp_failure_rate_repeated_enable_keeps_the_first_period` and `tcp_failure_sampler_*`, managed `TcpFailureRateTests.Adding_the_sensor_twice_keeps_one_monitor` and `Monitor_reports_when_neither_family_can_be_read`), and the corpus pins the registration (`collector/windows/tcp_failure_rate_contract.hsmtest`).
- **Live Windows service status (named service, Windows; wrapper-parity gap).** `EnableServiceStatusMonitoring(service_name, scan_period)` (C ABI `hsm_collector_enable_service_status_monitoring`) registers the `.module/Service status` **enum** sensor (catalog id, byte-identical to managed) at Start and starts an owned thread that every `scan_period` queries the named service via the Win32 SCM (`OpenSCManager`/`OpenService`/`QueryServiceStatus`) and posts its `ServiceControllerStatus` (Stopped=1…Paused=7 — the SCM `dwCurrentState` values are identical) to the sensor **on change**. A missing/unqueryable service posts **-1 with Error** ("Service not found!") once, then backs off for an hour (mirrors the managed `WindowsServiceStatusSensor` fault-state delay). The service name is the service NAME (case-insensitive), not the display name, and drives the query only — it is not part of the registration. Call BEFORE `Start()`; the thread is joined on Stop/Dispose. Replaces the C++/CLI wrapper's `AddServiceStateMonitoring(service_name)`. Smoke-tested by `native_service_status_sensor_emits_running_for_critical_service` + `native_service_status_sensor_reports_missing_service`.
- **Runtime alert attach to a built-in sensor (agent example).** The HsmAgent raises the built-in **Total CPU** sensor to **Error** on top of its default Warning: it grabs the sensor via `hsm_collector_add_default_sensor(TOTAL_CPU)` (idempotent by path — `AddAllComputerSensors` already created it), builds an `EmaMean > 50` alert with the fluent `CreateAlert(AlertKind::Bar).If(EmaMean, GreaterThan, "50").AsSensorError().ThenNotify(…).WithIcon(Error).WithConfirmationPeriod(5min)`, and `AttachAlert`s it before Start. `AttachAlert` rebuilds the sensor's registration in place, so the extra alert rides the AddOrUpdate. **No catalog/golden/managed change** — the shared default stays Warning@50%; this agent additionally Errors@50%. (`EmaMean`=213 is the bar's smoothed-mean property.) Pinned by `native_total_cpu_error_alert_attaches`.
- **Native wrapper DLL (`src/wrapper/`, drop-in replacement for the C++/CLI wrapper).** The legacy `hsm_wrapper::DataCollectorProxy` ABI is reimplemented over `hsm::collector`: `DataCollectorImpl` holds a `Collector`, lifecycle/`Initialize*Monitoring`/`Create*`/file/service-state forward to the native API, the static `AlertsBuilder` DSL accumulates plain data converted to a native alert (`Collector::CreateAlert` + `Sensor::AttachAlert`) at sensor creation, and the former managed func-sensor delegate bridge collapses (the native `Function`/`ValuesFunctionSensor` take a `std::function` directly). `Start`/`StartAsync` call `InstallWindowsMetricSources()` (live values, Windows) before the native `Start`. **Transport (wrapper 2.0.0, #1848 part 5; ADR-0019 point 5 amended 2026-11-25):** the `DataCollectorImpl` constructor calls `UseSessionTransport()`, so the collector session is the default and everything made before `Start` (a table sensor through `Native()` included) already sees it; the one new exported method `DataCollectorProxy::UseHttpTransport()` (non-virtual, mirrored on `DataCollectorImplWrapper`, no STL type in its signature) switches to HTTP for a server without sessions, before `Start` or after `Stop`, and throws `hsm::collector::Error` (the transport unchanged) when the collector is not stopped or a `StartAsync`/`StopAsync` task has not finished: the collector's own status cannot decide alone, since after `StartAsync` it stays Stopped until the start's thread runs, so `UseHttpTransport` also looks at the two futures (`wait_for(0)`), under a small mutex that guards only reading and replacing the two handles. Start, StartAsync, Stop and StopAsync are as before 2.0.0 apart from choosing the transport; nothing is held across a native call or a wait, so a function-sensor callback (on the scheduler thread that `Stop` joins) may still call `StopAsync`/`StartAsync`. A `UseHttpTransport` concurrent with a `StartAsync` on another thread is not ordered with it. On the session a file from `SendFileAsync` must fit one server frame as JSON (about 1 MiB with the default 4 MiB `CollectorSessions.MaxFrameBytes`); a larger one is dropped, logged and counted in `Queue overflow` (`docs/native-collector-migration.md`, "Transport"). The configure fails when the libcurl found does not state WebSocket support and 8.14.0+ (`CURL_SUPPORTS_WS`/`WSS`, `CURL_VERSION` of curl's CMake package). No fallback either way. Before 2.0.0, `Start` forced `UseHttpTransport()`. In a build without the network transport the constructor's choice fails silently and `Start` throws, as it did before. Built by `src/wrapper/CMakeLists.txt` (`add_subdirectory` of the native collector with `HSM_COLLECTOR_HTTP=ON` and `HSM_COLLECTOR_TABLES=ON`; dependencies from the vcpkg manifest `src/wrapper/vcpkg.json`, pinned to the native collector's baseline: curl with `websockets`, zstd, zlib) into `HSMCppWrapper.dll`; the wrapper's own version is `project(HSMCppWrapper VERSION 2.0.0)`; `pch.h` force-defines `HSMWRAPPER_API=__declspec(dllexport)`. The public headers under `src/wrapper/include/` keep every declaration they had (2.0.0 added `UseHttpTransport` and comments to `DataCollector.h`), so a consumer replaces them and relinks with zero source edits. Behavioral residue vs the managed wrapper is in `docs/native-collector-migration.md`; smoke-driven in-process by `WrapperConsole` (`src/wrapper/WrapperConsole/WrapperSmoke.cpp`), built + run in the `hsm-wrapper-build` CI lane. **Incremental-migration escape hatch:** `DataCollectorProxy::Native()` returns the wrapper's underlying `hsm::collector::Collector&`, so new sensors can be created directly against the native API on the same collector/connection while old sensors keep using the wrapper; the DLL re-exports the `extern "C"` C ABI (a CMake-generated `.def` from the frozen `hsm_collector.h`, `_t` typedefs filtered) so a consumer links only `HSMCppWrapper` — no second copy of the collector runtime. When the last wrapper call-site is gone, the proxy is swapped for a directly-owned `Collector` and the wrapper deleted (no big-bang). **Rollout of 2.0.0:** a server without sessions (before 3.43.0) must be updated before a host with the new wrapper talks to it, or the host calls `UseHttpTransport()`; otherwise the host sends nothing. **Handoff:** the DLL is delivered to consumers as a versioned zip (both x64 configs + libcurl/zlib/zstd runtime + headers + a swap-recipe `MANIFEST.md`) attached to a `wrapper-v*` GitHub Release by the `hsm-wrapper-release` workflow — a stable cross-host download for the GitLab-hosted aggregator; layout mirrors their vendored tree so it unzips over the checkout. See `src/wrapper/packaging/` and the "Getting the native wrapper bundle" section of `docs/native-collector-migration.md`.
- **TLS / transport.** `CollectorOptions::allow_untrusted_server_certificate` and `allow_plaintext_transport` map to the C options of the same name; they take effect once `UseHttpTransport()` installs the libcurl transport (`HSM_COLLECTOR_HTTP` build). Default builds use the in-memory recording sender (no network), which is what lets the console example and tests run with no server.
- **Logging (managed-parity).** Two sinks, both fed by the single `LogMessage` path: a **callback** via `SetLogger(std::function<void(LogLevel, const std::string&)>)` (C ABI `hsm_collector_set_logger`), and a **built-in rolling file logger** via `EnableFileLogging(directory, min_level = LogLevel::Info)` (C ABI `hsm_collector_enable_file_logging`) — the parity replacement for the managed NLog default sink. The file logger writes `<dir>/DataCollector_<UTC-date>.txt` (every level ≥ `min_level`) plus `<dir>/DataCollector_error_<UTC-date>.txt` (errors only), format `yyyy-MM-dd HH:mm:ss|LEVEL| message`, rolling by UTC date, on a background thread (Enqueue never blocks the caller; the destructor drains the queue before joining so shutdown logs are not lost). Both sinks receive every message; the file applies its own min-level filter. Install before Start; a second `EnableFileLogging` swaps the sink, an empty directory clears it. **Events:** lifecycle `DataCollector -> Starting/Running/Stopping/Stopped` (Info, via `NotifyLifecycle`); `Registered N sensor(s) on connect` (Info) / `Failed to register …` (Error) at the Start `/commands` POST — on no response or a 5xx it ends `; retrying on the next send cycle.` and the landed retry logs `Registered N sensor(s) after an earlier failed attempt.` (Info; #1515, see data-pipeline "Registration retry"); `Failed to send N value(s): HTTP <code> …` (Error, **deduplicated** — the dispatcher's re-enqueue retry is itself silent, matching the queue); plus the pre-existing metric-source-read / top-CPU / stop-time-drop errors. **Errors** pass through the deduplicator (`exception_deduplicator_window_ms` / `max_deduplicated_messages`; window 0 logs every message). A throwing callback is swallowed. **Parity delta vs the managed collector:** per-sensor `New sensor added {path}` (Info) and per-value `value rejected` (Debug) are deliberately *not* emitted — they would fire the user callback under the collector lock (registration) or need sensor→collector plumbing (value path); the `Registered N sensor(s)` batch line plus the sensor's own status/telemetry cover those cases.
- **Threading expectations.** `Start`/`Stop` single-threaded; sensor `AddValue` is thread-safe; callbacks run on the scheduler thread and must not re-enter a lifecycle method. `StartAsync`/`StopAsync` wrap the sync calls in `std::async` (note `std::future`'s destructor blocks until the task completes).
- **Shutdown semantics.** `Stop` **delivers** what is still queued — the flushed partial bars, the last values, anything posted just before it — and is bounded: the drain runs on a stop budget of `clamp(RequestTimeout, 1 s, 5 s)` for a graceful `Stop` and `min(that, 1 s)` for a terminal `Dispose` (the managed `DataProcessor`/`ShutdownMode` matrix), after which the remainder is dropped rather than blocking host restart — and that drop is logged at Info, so lost data is visible at default verbosity. Delivery is **at-least-once**: a POST still in flight when the stop begins is cancelled, re-enqueued and re-sent by the drain, so a server that had already committed it sees that package twice (values are keyed by timestamp and a bar partial re-posts the same OpenTime, so a duplicate overwrites rather than accumulates). Until collector **0.7.2** the in-flight cancel that keeps the stop bounded stayed latched, so on the HTTP transport the drain (and the next `Start`'s registration) delivered nothing even against a healthy server (#1432). `Dispose` is terminal and idempotent; after it, `Status()` is `Disposed` and further lifecycle/registration calls are rejected. The rules of the drain are the managed collector's too and are pinned for both by the shared corpus (#1751): the batch cancelled in flight is sent again, on Stop and on Dispose; the first failed value send ends the drain and what is left is dropped; nothing of a failed or hung stop is sent by the next Start (`stop_drain_contract`, every build); pending registrations go before the values, on the one budget, and a failed registration post does not end the drain of the values (`stop_drain_registration_contract`, on the HTTP transport, so in the HTTP build only: the in-memory sender is never sent a registration). The list with the scenario names is in [`data-pipeline/feature.md`](../../collector/data-pipeline/feature.md#shutdown-modes--drain-order).

## Packaging & versioning

Three consumption paths, all built on the one set of CMake `install()` rules; the package version tracks the C ABI semver (`HSM_COLLECTOR_VERSION`, currently 0.4.0):

- **CMake `find_package`** (baseline). `cmake --install` emits the headers, the static core lib, and `hsm_collectorConfig.cmake` + version file + exported namespaced targets (`hsm_collector::hsm_collector_core` / `::hsm_collector_cpp`). `find_package(hsm_collector 0.4)` version checks work. Proven by the CI **install-consume** lane (build → install → standalone `find_package` build+run, Win+Linux).
- **Conan** (`conanfile.py` + `test_package/`). `conan create` builds from source with tests/examples gated off; Conan owns the CMake integration (the project's own config is dropped in `package()`, components re-declared). An optional `http` Conan option pulls `libcurl`; an optional `tables` option pulls `zstd` and `zlib` (#1848; no table delivery from a Conan build). Proven by the **conan-consume** lane (`conan create` runs the `test_package` consumer).
- **vcpkg** (overlay port `vcpkg-port/`). `portfile.cmake` + manifest build the library from the adjacent source (`SOURCE_PATH=../`), with an `http` feature for curl and a `tables` feature (zstd, zlib; depends on `http`, #1848); for registry publication the `SOURCE_PATH` line is swapped for a `vcpkg_from_github` block at a release tag. Proven by the **vcpkg-consume** lane (install the overlay port → build+run a consumer through the vcpkg toolchain, Win+Linux).

CMake gates: `HSM_COLLECTOR_INSTALL`, `HSM_COLLECTOR_BUILD_EXAMPLES`, `HSM_COLLECTOR_BUILD_TESTS` (each defaults to `PROJECT_IS_TOP_LEVEL`), `HSM_COLLECTOR_HTTP` and `HSM_COLLECTOR_TABLES` (both OFF by default). Package builds set tests/examples OFF.

**NuGet native assets** were intentionally **dropped** — there is no concrete mixed managed/native consumer to justify the `.nuspec` + native-asset layout; .NET consumers use the managed `HSMDataCollector` package, native consumers use one of the three paths above.

## Known limits

- **Table block writer on a big-endian host (#1848).** The writer byte-swaps every value there (`CopyColumnLe` with `swap`), but no CI lane builds on a big-endian host. The swap itself is unit-tested on every host (`native_table_byte_swap_writes_little_endian` calls the swap path directly); the writer's choice of path is pinned only for little-endian.

## Divergences from the C++/CLI wrapper (`DataCollector.h`)

Tracked in full in `docs/native-collector-migration.md`. Headlines:

- **Function sensors are int / int-values only** — the C ABI is int-only; the .NET wrapper's templated `T/U` function sensors are not reproduced (would require ABI growth).
- **`SendFileAsync(disk path)` → `FileSensor::SendFile(path)`** — `hsm_sensor_add_file_from_path` reads the file and derives `Name`/`Extension` from the path, overriding the creation-time defaults (mirrors managed `FileSensor.SendFile`; 10 MiB cap, content treated as UTF-8 text). The disk read itself is host I/O, not cross-language-portable, so it carries unit — not conformance — coverage; the file-value wire shape stays covered by the file conformance case. Raw-string content still goes through `FileSensor::AddContent(string)`. With a transport installed a file value leaves in the `FileSensorValue` wire format, `List<byte>` as a numeric array, in the `/list` batch or `list` frame with the other values (#1660 step 2b; before, it left in the canonical corpus format, which the server cannot read, and the HTTP batch carrying it was refused on every cycle).
- **No `RedirectAssembly` / `Initialize(config_path)`** — those are CLR-hosting concerns with no native analogue.
- **Time-in-GC sensors dropped** (#1099) — no managed GC in a native host.
