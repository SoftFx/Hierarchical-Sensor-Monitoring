## Alert schedules

**Gate decision matrix** (`ApiTokenAuthorizationServiceTests`, evaluator level — `HasOperationAtAnyVisibleBoundary`):

- A grant at a visible boundary → true, and allowed decisions record NO event; a grant at an INVISIBLE boundary (owner lost it) → false — the intersection decides; a Global grant → true only for an admin owner; no matching grant anywhere → false.
- `HasOperationAtGlobalScope` (the schedules sensor-filter short-circuit): admin owner + matching Global grant → true; non-admin owner, a grant for ANOTHER operation, or a scoped grant → false.
- An unresolvable token (absent from the index) → false, fail closed.
- The denial event is pinned to `AuthorizationDenied` — the 403 scope-denial kind, exactly ONE record; the gate must never feed the `AuthorizationNotFound` enumeration-probe signal.
- Non-matching operation grants are never probed (a `products:read` grant's boundary is never even resolved — `TryGetProduct` never called); a malformed boundary id (unreachable through canonicalization) is skipped fail-closed, not thrown.

**Controller** (`AlertSchedulesApiControllerTests`, controller level — the gate is mocked):

- Conventions reflection pin (same attribute set, route `api/v1/alertSchedules`, `ControllerBase`).
- Denied gate → 403 with the provider and the sensor cache never queried (list), and 403 for ANY id on get-by-id — no existence leak for an unentitled caller.
- **List**: pagination math and clamps (same envelope and constants as templates); ordering name-then-id; the page's sensor references resolved in ONE bulk cache call (`GetSensorsByAlertSchedules`, never the per-id lookup on the list path); sensor paths filtered per product visibility — same leak surface as get-by-id, pinned on the list path too; the visibility decision memoized per DISTINCT product (3 sensors over 2 products → exactly 2 `IsVisible` calls); the Global-grant short-circuit (admin + `alerts:read@Global` → sensors of ALL products, per-product predicate never consulted).
- **Get by id**: DTO maps the durable fields (id/name/timezone/schedule YAML); sensor references carry only the sensors whose PRODUCT boundary is visible to the caller (hidden product's sensor dropped, paths of the visible one kept); absent id → 404 for an entitled caller.

## Sensor muting (#1569)

**Controller** (`SensorMuteApiControllerTests`, controller level — the `SensorMuteMcpToolsTests` harness shape): the service is real; the `ITreeValuesCache` mock mirrors the core's own `UpdateMutedSensorStateAsync` (the State + EndOfMutingPeriod translation onto the live model, the Blocked no-op, the unchanged-period skip), so the round-trip runs the actual semantics, and every invocation (sensor id, initiator, period) is captured.

- Conventions reflection pin (same attribute set, route `api/v1/sensors/{sensorId:guid}`, `ControllerBase`).
- **Mute**: omitted body AND an explicit `endOfMuting: null` both mute indefinitely — the model stores the core's `DateTime.MaxValue` ("Forever", never swept) and the echo renders `state: Muted` + `endOfMuting: null`; a period mute echoes the stored instant and the model carries it; a LOCAL-kind instant CONVERTS to its UTC instant (not relabeled — the mute does not shift on a non-UTC server); the same period twice is an idempotent 200; the write names the token's OWNER as the InitiatorInfo (`User`/`api-owner`, the #1384 rule).
- **Unmute**: after a period mute resumes notifications (`state: Available`, model `EndOfMuting` null, the core's null period); a not-muted sensor answers 200 with its unchanged state (idempotent).
- **Blocked**: mute and unmute on a Blocked sensor → 409 `conflict` (the web flow's silent no-op surfaced as an explicit error), the sensor untouched.
- **Semantic validation**: a past `endOfMuting` → 422 field-keyed (`details.endOfMuting`), the write never dispatched.
- **Authorization mapping**: evaluator Forbidden → uniform 403 (both actions, write never dispatched — the read-only-token/Viewer arm); unknown id and the evaluator's NotFound answer the SAME 404 body (anti-enumeration); authorize-before-write pinned on the 404 path (no `UpdateMutedSensorStateAsync` call).

## Sensor deletion (#1637)

**Engine** (`SensorDeletionAdministrationServiceTests`, service level): the REAL service over a mocked cache whose `RemoveSensorAsync` mirrors the queue-thread dispatch (the sensor leaves the cache lists before the task resolves, like the core's cache-first order); `GetSensorHistoryInfo` feeds the preview's history numbers.

- **Delegation**: the write goes to the core's `RemoveSensorAsync` — the SAME entry the web UI's remove-node drives — naming the token's OWNER as the InitiatorInfo (`User`/`api-owner`, the #1384 rule).
- **Dry run**: answers the `SensorDeletePreviewDto` (kind/operation/entityId/path, product ref, state + endOfMuting with the mapper's Forever rule, lastValueTime, historyValues/historySizeBytes from the core's statistics accessor, the affected list — the sensor plus every data and TTL policy) and NOTHING is applied (no core removal call, the sensor still reads back); a MUTED sensor previews its mute state.
- **Authorization mapping**: evaluator Forbidden → 403 (the write never runs — the read-only-token/Viewer arm); unknown id and the evaluator's NotFound answer the same 404; a repeat delete after removal → 404 with the core called once.
- **State**: a BLOCKED sensor deletes (the web UI's remove-node rule — no state filter, unlike the mute engine).
- **Honest verification**: a mocked core removal that does NOT apply (the queue's swallow-only failure channel — the removal never reached the cache) → 409 `conflict`, never a ghost success. The CACHE removal is everything the read can verify: a persistence-side failure inside the core's handler (after its cache-first step) is unreachable from the engine and stays a success — the Known Issues boundary, which is why the probe can only mock the never-reached case.

**Controller** (the delete pins inside `SensorsApiControllerTests`, controller level — the same service-real harness): 204 on success with the sensor gone; the `X-HSM-Dry-Run: true` header → 200 + preview with nothing removed; unknown id → the uniform 404; a read-only owner → 403 with the sensor untouched.

**Dry-run header fail-closed** (`DryRunHeaderFilterTests`, the filter invoked directly + the `AddHsmMvc` registration pin): malformed values (`maybe`, `True1`, `yes`, `1`, `0`) → 400 `validation_failed` under the header's field key before the action; absent/empty/`true`/`TRUE`/`false`/`False` reach the action; a stray header outside `/api/v1` is not the filter's business; a READ endpoint under `/api/v1` with a stray malformed header answers the same 400 (the rule is area-wide, not write-only — a visible behaviour change for clients that send the header everywhere); `WriteOptions` accepted forms pinned; and the MVC registration itself is pinned — `AddHsmMvc` (what `Program.cs` calls) must install the filter, or dropping/moving the line fails a test instead of quietly re-enabling the irreversible delete.

## Notification chats (reads #1393, verification #1826, writes #1829)

**Writes, the engine** (`ChatAdministrationServiceTests`, `Model/ManagementApi/Chats/`): the name rule that both surfaces share — a creation without a name, a blank one and one over 100 characters are refused under `Name` with the web form's own messages; a name held by another chat is refused ignoring case; a rename to the chat's own name in another letter case passes; a partial update that omits the name is not checked; the name is stored trimmed. The rule guards changes, not history: an update (and a save of a row the `/start` flow pre-created) that KEEPS a name another chat also holds is accepted, and so is an over-long name of an old row — only its rename meets the length rule. A row stored with a padded name (from before names were held trimmed) keeps it on an unchanged save even while another chat holds that name trimmed, and is not silently renamed (`KeepingItsStoredName`: the write carries the stored name verbatim); a real rename onto another chat's padded name is refused — stored names are compared trimmed. **The loser of a lost race**: the store refuses a write whose name was taken between the engine's check and the write (`ChatsManager`, below), and a refused creation or update whose name is held by now answers the same `Invalid` under `Name` — the engine runs the same rules once more against the store as it is now (`RefusedWrite`) — never the opaque conflict, which stays for a refusal whose name is still free. `TheWebFormAndTheEngine_SayTheSameAboutTheName` keeps the form and the engine on one length and one text (the form's `StringLength` message is formatted from the same maximum, and the view model holds the name trimmed). The aggregation delay's range (0 to 86 400 seconds — a negative delay never flushes a channel's accumulator): a creation with `-1` or 86 401 is refused under `MessagesAggregationTimeSec` and stores nothing, an update with a negative delay is refused without a write, 0 and 86 400 are accepted, and `TheWebFormAndTheEngine_SayTheSameAboutTheDelay` keeps the form's `Range` attribute and the engine's message on the same bounds. The webhook URL shape and the folder-binding rules are the earlier pins of the same suite. The `/start` flow's own naming — a second Telegram group under the same title gets `title (2)`, ignoring case, and a 128-character title is cut to 100 (96 + ` (2)` when disambiguated) — is pinned in `Notifications/ChatFolderBindingTests`, together with the trim of a title's surrounding spaces. **The store's own repeat of the rule** is pinned on the real `ChatsManager` in `Notifications/ChatsManagerTests`: an add refused for a name another chat took after the caller's check never reaches the database, eight concurrent adds of one name store exactly one, a rename onto a name taken in the meantime writes nothing, a chat keeping a name another chat also holds stays editable, and nameless rows are not each other's duplicates.

**Writes, the service** (`ChatWriteServiceTests`): the REAL `ChatWriteService` on the REAL engine over `ChatWriteHarness` — an in-memory chat store and folder store wired to each other the way `NotificationsCenter` wires the real managers; the evaluator's decisions and the usage counter are its inputs (the evaluator's own matrix lives in `ApiTokenAuthorizationServiceTests`).

- **Admission**: create — an admin stores the chat with the token's owner as its author; a refused `AuthorizeChatCreate` is Forbidden with nothing stored. Update and delete — an unknown id is NotFound without the evaluator being asked; otherwise the service asks `AuthorizeChatWrite` for the chat and a snapshot of its bindings, BEFORE anything of the request is read, and answers its NotFound (outside the caller's sight) and Forbidden (visible, not changeable) as they are — a dry run included; admission precedes validation (an invalid body on a forbidden chat answers 403, never the 422 that would reveal it exists).
- **A request's rules, answered together**: a duplicate name under `name` (the wire key — the engine's `Name` is re-keyed in camelCase), a name carrying a bidi override under `name` (#1705, this surface only), a webhook that is not an absolute http(s) URL under its own field, and a folder the owner does not manage or that does not exist under `folders` (one message for both — nothing is disclosed about folders outside the owner's reach); a request with three mistakes answers all three in one body; a chat duplicated before the name rule keeps its other settings editable while it keeps its name; a chat stored with a padded name (from before names were held trimmed) keeps it on an unchanged save — while another chat holds that name trimmed — and is not renamed; a delay of `-1` or 86 401 on a creation or an update is refused under `messagesAggregationTimeSec` with nothing written, 0 and 86 400 are accepted and echoed.
- **Partial update**: only the given fields change; an empty webhook value changes nothing; the clear flags remove the channels and the echo says so; a clear flag set to false removes nothing.
- **Folders**: the listed set replaces the bindings among the folders the owner manages (a managed binding not listed goes, an unmanaged one stays, a listed one comes); a bound folder the owner does not manage may be listed back — a read-modify-write client is not refused for a binding that stays — while the same list may not add a new unmanaged one; omitted leaves the bindings alone; an empty list makes the chat global for an admin, and for a non-admin is refused under `folders` unless another binding stays (making a chat global is the admin's decision); the echo lists the bindings the caller can see — empty when the update leaves the chat bound only to folders outside the caller's sight, and then without the detail fields, judged on the chat after the write.
- **Delete**: a dry run answers the preview — kind `chat`, operation `delete`, the usage count and the "lower bound" flag when sensors were skipped, the chat (`remove`) and its visible folders (`unbind`) in `affected` — and removes nothing; applied, it goes through `IChatsManager.TryRemove` once, naming the token's owner as the initiator (the pruning of the folder bindings is that removal's own event, the entry the web list's remove runs too); a removal that never reached the store is Conflict, a chat that vanished on the way is NotFound.

**Writes, the gates** (`ApiTokenAuthorizationServiceTests`, the chat blocks): `AuthorizeChatCreate` allows an admin owner with a read-write token; a non-admin owner, an admin's read-only token and a revoked token are Forbidden; a denial is recorded ONCE as `AuthorizationDenied`, never as the enumeration-probe `AuthorizationNotFound`. `AuthorizeChatWrite` allows an admin and the manager of any bound folder (nothing recorded for an allowed write); the read surface's caller-wide gate comes first — an owner who sees no boundary answers NotFound for a global chat too, recorded as `AuthorizationNotFound`: the same answer an unknown id gets, so the two cannot be told apart; a chat bound only to folders outside the owner's sight is NotFound, recorded as `AuthorizationNotFound`; a global chat and a visible folder-bound chat are Forbidden to an owner who may not change them (a non-admin; a Viewer of the folder), and so is a read-only token — each recorded as `AuthorizationDenied`.

The response annotations of the three actions are pinned in `ManagementApiSwaggerTests`' per-action map.

**The web form** has no controller harness (none exists for `NotificationsController`), but its own validation is exercised the way MVC runs it, in `ChatAdministrationServiceTests`: `Validator.TryValidateObject` on the view model refuses a delay of `-1` and 86 401 with the engine's text under `MessagesDelay` (`TheWebForm_RefusesAnOutOfRangeDelay_WithTheEnginesText`), passes 0 and 86 400 with the name held trimmed (`TheWebForm_AcceptsADelayAtTheEdges_OfTheRange`), and the two parity tests keep the form's attributes and the engine on one bound and one text. ## Uniform JSON error contract (#1353)

**Controller side** (`ManagementApiErrorContractTests`, controllers constructed directly):

- Every error status carries the `ManagementApiErrorDto` body with the right machine code: 403 `forbidden` (message names the operation), 404 `not_found` (generic message, `details: null`), 400 `validation_failed` (`details` is the field→messages map — `folderId`, `name`, `paths`), 409 `conflict` (message carries the cache error).
- **404 indistinguishability**: unknown id and the evaluator's invisible-folder decision produce the SAME code AND message (anti-enumeration, now observable at the body level).

**Pipeline side** (`ApiJsonErrorContractTests` — where no action ever runs):

- The shared writer's wire shape: camelCase `{error, message, details}`, `application/json`, and `details` an explicit JSON `null` when absent (the three fields are always present). Since #1371 the writer is exercised through its public per-kind helpers only (the raw `WriteAsync` is private — no caller can compose a mismatched code↔status pair), including the bearer scheme's `WriteForbidden` twin; the typed details map (`Dictionary<string, object>`) serializes the unchanged wire shape (field→message arrays through the same `WriteAsJsonAsync` the pipeline uses).
- Area-guard rejection (unmatched `/api/v1` route) → 404 with the SAME generic body as the controllers' unknown id.
- Legacy bearer guard (hsm_pat_ outside the area) → 401 `unauthorized` JSON.
- Exception middleware: an exception on an `/api` path → 500 `internal_error` with `details.traceId == context.TraceIdentifier` and no exception text on the wire; a non-API path rethrows (Razor error page keeps serving the UI); a started response rethrows; a staged representation on the aborted response (Content-Encoding/ETag/Last-Modified/Content-Language/Location/Range) is reset while transaction headers (HSTS) survive (#1371); a **server-side** cancellation — OCE with `RequestAborted` NOT set, the HttpClient-timeout-inside-handler shape — renders the JSON 500 on `/api` and still rethrows on non-API paths (#1371).
- Binding-failure factory: a `[ManagementApi]` action's invalid ModelState → the uniform 400 with MVC's own field keys (`name`, `$.policies[1]`); an empty binder message gets the framework's fallback wording; the WIRED factory (`WrapBindingFailureFactory`) delegates non-management actions to the captured framework default **verbatim** (spy assertion — the sensor-data/Grafana `problem+json` shape is delegated to, never reimplemented) and never calls it for management actions; a null captured default throws `ArgumentNullException` at capture time, not per request (#1371).
- Swagger port gate: swagger paths off the SitePort (both `/swagger/*` and `/api/swagger/*`) → the uniform 404 body; on the SitePort and for non-swagger paths on any port → pass-through.

**Challenge** (`HsmApiTokenHandlerTests.Challenge_BodyIsTheUniformJsonErrorContract`): the 401 keeps `WWW-Authenticate: Bearer`, no redirect, and adds the uniform JSON body. **Forbid** (`Forbid_BodyIsTheUniformJsonErrorContract`, review round 2): the scheme's 403 twin carries the uniform body too — defense-in-depth for the `HsmApiTokenOnlyRequirement` path. The exception middleware rethrows **client aborts** (`RequestAborted` set — `ExceptionMiddleware_Cancellation_RethrowsUntouched`) untouched — an aborted request never becomes a failed 500 write; a **server-side** cancel renders the JSON error instead (`ExceptionMiddleware_ServerSideCancellation_IsUniformJson500`, #1371).

`ManagementApiSwaggerTests`:
