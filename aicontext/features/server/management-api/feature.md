# Feature: Management REST API (resource controllers)

> Owner: server | Last reviewed: 2026-11-26 | Canonical: yes
> Scope: the `/api/v1` REST resource controllers for non-interactive management clients (bearer-token authenticated); the conventions every controller in the area follows — including the uniform JSON error contract and the OpenAPI publication (#1353). Controllers: alert templates CRUD (#1351), alert schedules CRUD (#1352 read; the write path per the fixed Global-boundary direction), sensor-tree read surface (#1386): products, nodes, sensors, values, history; alert administration (#1500): data-policy and TTL-policy CRUD on sensors and products; sensor muting (#1569): mute/unmute (notification suppression) on a sensor; sensor deletion (#1637): irreversible delete with a dry-run preview; sensor move (#1721): move/merge sensors to another path and remove a moved sensor's alias; root-product creation (#1786): the first step of the agent-installation scenario; access-key reads (#1787): a product's keys, the id source for the write surface and the agent-connected signal; access-key writes (#1789): issue/re-permission/block/remove a product's keys — the credential-lifecycle half of the scenario; agent-installer download (#1788): the bundle stream + the one-time link — the hand-over half; notification chats — read-only (the id source for destination.chats), the verification pair (#1826: a test message with a delivery outcome, a Telegram invitation) and the write surface (#1829: create/update/delete with a dry-run usage preview, on the engine the web editor runs); access-grouping folders read-only (the folderId source for alert templates); the Telegram bot credential (#1830: the status and a validated one-call update — the first server-settings surface of the area).

---

## Overview

Epic #1347 gives non-interactive clients (AI agents, scripts, resident services) a machine-friendly REST management API under `/api/v1`. Authentication (the `HsmApiToken` bearer scheme), the fail-closed area guard, the security-event sink and the effective-rights evaluator are owned by the api-tokens feature; this feature owns the resource controllers built on top of them. Alert templates (#1351, full CRUD) and alert schedules (#1352, read-only) are landed; #1353 added the area's uniform JSON error contract and its OpenAPI publication: every operation of both controllers is annotated in the server's single swagger document (`/api/swagger`, `HSMSwaggerComments.xml` doc comments + `ProducesResponseType`), carries the `HsmApiToken` bearer security requirement (scoped by `ManagementApiSecuritySwaggerFilter` — the doc also contains the sensor-data API, which keeps its Key header), and documents the domain enum values of every byte field in the DTO XML remarks, so an agent that reads only the spec can authenticate and perform every operation. #1386 added the sensor-tree read surface — the AI-agent discovery path ("analyze network problems in product X"): root products, any node with its direct children, flat recursive sensor search over name/description/path, one sensor with its current value, and the newest-N history window — all GET, all through the same conventions.

## Invariants

- **Area conventions (every controller, enforced by `ManagementApiGuardMiddleware` before authentication)**: attribute-routed `ControllerBase` (never the cookie-world `BaseController`), route `api/v1/<resource>` (camelCase plural mirroring the controller resource name, e.g. `alertTemplates`), class-level `[ManagementApi]` + `[Authorize(Policy = HsmApiTokenDefaults.ManagementPolicy)]`, no `[AllowAnonymous]`. SitePort-only; a 404 (never 403/redirect) answers anything non-conforming in the area. A reflection test pins the attribute set on every controller.
- **Authorization is per request** through `IApiTokenAuthorizationService` at the resource's own boundary — since #1384 a token is a full mirror of its owner (reads follow the owner's sight; writes additionally need the owner's Manager role at the boundary and a read-write token). The evaluator's 403/404 anti-enumeration split is preserved verbatim: invisible to the owner → 404, visible but read-only token or Viewer owner on a write → 403 — returned as explicit uniform-error results (never `Forbid()`, which would engage the cookie scheme's redirect handling). **Authorization precedes body validation**, so error ordering leaks nothing about existence or rights; an unknown id is a plain 404 with no evaluator call. **List endpoints filter per item by the owner-sight half of the read decision** (`IsVisible(principal, resource)` — the same predicate as `AuthorizeRead`, minus security-event recording): an item is listed exactly when `GET {id}` would answer it; the read-only flag never narrows lists, only item writes. Never 403-per-item: out-of-sight folders are simply not listed. The decision is memoized per **distinct** folder within one list request; no snapshot API exists yet.
- **Server-assigned identity on create**: POST ignores any client-sent id (the cache Add is an upsert by id — honoring a client id would let a scoped token overwrite a template it cannot see). PUT requires the body id to equal the route id or be absent.
- **Folder moves need write on both sides**: updating a template into a different folder requires `alerts:write` on the CURRENT folder (the move destroys its per-sensor policies) and on the NEW one (the template injects policies into its sensors).
- **Uniform JSON error contract (#1353)**: every error response of every error path in the area — controller results, `[ApiController]` automatic binding failures (`WrapBindingFailureFactory` in Program.cs: management actions get the uniform body, every OTHER ApiController — sensor-data, Grafana — delegates to the **captured framework default** verbatim, so their `problem+json` wire shape is untouched; the captured default is null-guarded at capture time — a broken wiring fails fast at startup instead of NRE-ing per request, #1371), the `HsmApiToken` 401 challenge and its 403 **Forbid** twin (`HandleForbiddenAsync`; the management policy carries `HsmApiTokenOnlyRequirement`, so Forbid — not Challenge — is reachable for an authenticated-but-malformed principal; defense-in-depth, the handler this scheme produces always satisfies the requirement), `ManagementApiGuardMiddleware` rejections, `LegacyBearerGuardMiddleware`'s 401 for a misplaced token, and unhandled exceptions on ANY `/api` path (`ApiExceptionJsonMiddleware` sits between the global `/Error` handler and `LoggingExceptionMiddleware`, so non-API paths still get the Razor page and the failure is still logged; it resets the status plus every header describing the aborted response's representation — content metadata (Content-Type/Length/Encoding/Language/Location/Range) and the old body's validators (ETag/Last-Modified) — never `Response.Clear()`, so headers set by outer middleware such as HSTS survive (#1371: a staged `Content-Encoding: br` left on the rewritten body would corrupt its decoding); a **client** abort (`RequestAborted` set) rethrows untouched — an aborted request is not a 500, and writing to a dead connection would only replace the original exception in the outer logging — while a **server-side** cancellation (an `OperationCanceledException` with `RequestAborted` NOT set, e.g. an `HttpClient` timeout inside a handler) is a failure of a live request and renders the JSON error, never the Razor page (#1371); it also wins over `UseDeveloperExceptionPage` on `/api` paths in Development — JSON-only is the invariant, stack traces live in the logs) — is `application/json` with the SAME three-field body `ManagementApiErrorDto` (`ManagementApiErrors` result factory for MVC paths, `ManagementApiErrorResponses` for pipeline paths — its per-kind helpers are the ONLY public surface, the raw writer is private, #1371): `error` (stable machine code, one per status: `validation_failed`/`unauthorized`/`forbidden`/`not_found`/`conflict`/`unprocessable_entity` (422, #1500: the alert-administration surface's semantic validations — condition-vs-type, chat availability, schedule references, the TTL interval/inherit switch; field-keyed details like a 400)/`internal_error`/`service_unavailable` (#1387 r4: a capacity abort — an exhausted evaluation budget — is NOT a validation failure; the message names the caller-side remedy), append-only), `message` (human summary), `details` (field-keyed messages on 400s — **item-indexed** keys like `policies[2].conditions[0].operation`, empty binder messages get the framework's fallback wording, `{"traceId": …}` on 500s — correlated with the error/all log layouts, which carry `aspnet-TraceIdentifier`; the ASP-only layout is Debug-only — explicit `null` otherwise; the three fields are always present; typed `Dictionary<string, object>` since #1371 — the values serialize by runtime type so the wire JSON is unchanged, and `ManagementApiErrorDetailsSchemaFilter` publishes the union explicitly in the OpenAPI doc: field→message-arrays on 400/422, pointer-key→string on 500/409). All 404s of the area — unknown id, invisible folder, unmatched route, wrong port, off-SitePort swagger — render the SAME generic body (`ManagementApiErrors.NotFoundMessage`), preserving anti-enumeration at the routing layer too. Never HTML on `/api/*`; nothing throws out of an action. The contract's scope is `/api/v1` responses plus 500s anywhere under `/api`; unrouted non-v1 `/api` paths still answer the framework's bare 404.
- **JSON in, JSON out, never HTML**: manual 400s are `ManagementApiErrors.Validation` with **item-indexed** field keys (`policies[2].conditions[0].operation` — the shape `[ApiController]` itself produces for binding failures, so multi-policy payloads have locatable errors); state-dependent write failures from the cache are 409 — POST/PUT on "folder without products" and on partial per-sensor apply failure (#1394: a DB error applying the template to some product's sensors returns `(false, error)` naming the products, the same contract DELETE gives for partial removal; previously the failure was only logged and the save reported success), DELETE also on partial per-sensor policy removal. Per-policy VALIDATION rejections on a save that PERSISTED are NOT a 409 (#1401): the template create/update echo carries an additive output-only `warnings` list (`AlertTemplateDto.Warnings`, `[{sensor, reason}]` per rejected policy, ordered sensor-path-then-reason) — set only when a matching sensor refused a policy, ABSENT on clean writes and on reads (`JsonIgnoreCondition.WhenWritingNull` on the property), so a warning-free save's response and every read differ from before by nothing — the field never appears; the MCP `create/update_alert_template` tools render the SAME DTO and therefore the same strings. Since #1565 the same `warnings` list also carries one entry per PATH PATTERN that matched no sensors in the template's folder (`sensor` = the pattern itself, reason "path pattern matched no sensors in the template's folder") — a dead pattern is still a successful save (the template may precede its sensors), but the response no longer reports clean success over it. A rejected alert is never created on the warned sensor (each rejection also leaves a per-sensor journal record — see `alerts/feature.md`).
- **Create-path partial-apply 409 discloses `details.templateId` (#1394)**: POST persists the template BEFORE reconciling sensors, so a partial-apply conflict leaves a live template the caller has no id for — and a plain re-POST would trip the name-uniqueness 400. The conflict body therefore carries the server-generated id in `details` for the PUT fix-up retry. The pre-persist "folder without products" 409 fires before anything is stored and carries no details.
- **Validation parity with the web UI** (same order, same error strings): global case-sensitive name uniqueness excluding self, at-least-one-path, path/type mismatch check (#1210; AnyType templates skip it), chat availability (a destination chat must be global or bound to the template's folder — the UI dropdown rule), schedule references must resolve (`scheduleId` is validated against the schedule provider — the UI dropdown cannot produce a dangling id, and at evaluation an unknown id is silently treated as always-in-working-time). Plus API-side structural validation the UI gets for free from its widgets: enum membership of every enum-coded field (Operation/Property/Combination/TargetType/RepeateMode/SensorStatus/SensorType — `int`-typed on the wire since #1607, so out-of-range values like `sensorType: 999` or `-1` BIND and reach the validator under their field key instead of dying in argument binding with no field name; the check is byte-range + `Enum.IsDefined`, because a plain cast to the byte-backed domain enums TRUNCATES) and the path-regex GRAMMAR (#1607: `PathTemplateConverter.ApplyNewTemplate` compiles the pattern eagerly, so a malformed pattern like `HSM Server Monitoring/([` answers `paths: Invalid path template: Invalid pattern '…'` — never an unhandled `RegexParseException` escaping the write) — BEFORE the domain casts — and of the **sparse long `TimeInterval` enum** for `ttls[].interval` (an undefined value persists but throws `NotImplementedException` in the timeout-scan loop, outside the controller's try; ticks-authoritative intervals also keep `now + ticks` inside the DateTime range — `AddTicks` throws in the same loop), parallel-list length equality for TTL policies/intervals, schedule tick range, chat keys parseable as Guids, **null list elements rejected** (`"policies": [null]` is a 400 — System.Text.Json materialises it, and the structural pass runs outside the reconstruction try, so a null dereference there would be a 500), **duplicate non-empty policy ids rejected** (the id becomes the per-sensor `TemplateAlertId` — the apply-time matching key — so duplicates silently collapse two policies into one), **a path pattern of literals without `/` rejected** (#1608 — it can never match: every sensor full path has at least `Product/SensorName`, and a pattern with no `/`, no wildcard and no live regex metacharacter cannot produce that `/`; patterns that might still match through a metacharacter — `Product.cpu`'s `.` crosses `/` — or through wildcards stay accepted and ride the #1565 zero-match warning), **control characters and bidirectional overrides rejected in the icon, the message template and names** (#1705 — C0/C1 controls and U+202A–U+202E/U+2066–U+2069 never appear in a legitimate value; tab, newline and carriage return stay allowed in message templates (multi-line templates survive a Windows CRLF paste and a stored `
` round-trips; `
` is inert in both renderers), NAMES and ICONS are single-line surfaces (line-break characters are rejected there too, the Unicode line separators U+2028/U+2029 with them — browsers and Telegram break lines on them though they are not control characters; the soft direction marks U+200E/U+200F/U+061C stay allowed everywhere, they are ordinary mixed-direction text outside #1705's set), emoji stay allowed everywhere, and RAW HTML is deliberately not rejected at write time — the renderers own it: Telegram uses MarkdownV2 where HTML is inert, the web sanitizes `MarkdownHelper.ToHtml`'s plain parts and encodes the action icon. This character rule is the one deliberate break of the parity above: it runs ONLY on the API/MCP write paths — the web UI editors do not validate it, so a value they still accept, or one stored before #1705, fails an otherwise-unchanged GET→PUT until the field is corrected), **curly braces in a policy/TTL message template rejected** (#1608 — the message renders with `string.Format` over the substituted `$variables`, where braces throw at evaluation time or silently substitute another variable's value; the field docs' "curly braces are not allowed" is enforced on write, on both policy kinds), **conditions on a TTL policy rejected** (#1608 — the trigger is the inactivity interval; a structural `ttlPolicies[i].conditions` error instead of the reconstruction's leaked `NotImplementedException` on the wrong `policies` key), and explicit size bounds the widgets impose implicitly (name ≤ 200 chars, ≤ 100 paths, ≤ 100 policies regular+TTL combined — collection counts and name only; individual strings stay bounded by the request body limit, see Known Issues). `"destination": null` / `"schedule": null` mean "omitted" (the mapper substitutes the defaults), not a domain parse failure. A missing/empty `folderId` is a 400 (never routed through the evaluator's 404 — an all-zero Guid references no folder and leaks nothing); on PUT that 400 is issued only AFTER authorization, so a body-shape error cannot reveal that a template exists to a caller outside its reach. Every policy condition is validated against the per-type rule table BEFORE the domain reconstruction — SKIPPED WHOLE when `sensorType` itself is invalid (#1677: the byte-truncated cast would judge conditions against a type the caller never sent) (#1611, `AlertTemplateConditionValidator` — the sensor-policy surface's own table): a property the template's sensor type does not offer, an operation the property does not accept, or an unparsable target constant answers a field-keyed 400 (`policies[i].conditions[j].property/operation/target`, the same message catalogue the per-sensor 422s use — e.g. `The target must be a number.`; non-finite constants (`NaN`, `Infinity`) PARSE like the domain's `double.Parse` and stay accepted — the per-sensor surface rejects them only because JSON cannot express them as numbers, and templates stored with them before #1611 must keep round-tripping through GET->PUT); an AnyType template accepts only the common subset (Status/Comment/NewSensorData) and its errors name AnyType, never the Boolean stand-in; TTL policies accept no conditions at all. The acceptance set is the domain executors' own, which the rule table diverges from in four pinned places (Enum's EmaValue has no typed executor; Version's Value runs the six comparisons, not the table's text operations; String's Value also runs IsChanged; NewSensorData's executor is operation-blind — every operation code runs, but it is typed BaseValue and takes only the LastValue getter, so a Const target on a TARGETED NewSensorData operation is a field-keyed 400 whatever the constant would parse as) — a drift-guard test probes the real domain over the full type×property×operation grid. The domain reconstruction itself still runs inside a try as the last-resort net — an unpredicted `Policy.Apply`/`TTLPolicy` throw is a 400, never a 500, and since #1439 the 400 details carry the reconstruction reason (the thrown message, e.g. "Unsupported policy property Value with type Byte[]") instead of one static sensor-type wording, so the failure class is diagnosable from the API response alone. Condition targets of **target-less operations** (IsChanged, IsError, IsOk, IsChangedToError, IsChangedToOk, ReceivedNewValue — `PolicyCondition.IsTargetless`): the core evaluates whatever `target.type` is posted (or stored) as the sensor's own previous value, LastValue(self) — the only form the web editor submits and the only one those executors accept — so a `Const` target on them is accepted and coerced instead of answered with a masked reconstruction error; the stored `Target` echoes the client's value unchanged.
- **Write-side normalizations (observable in the echoed DTO)**: server-generated template id; `Guid.Empty` policy ids regenerated (empty ids would collide in per-sensor policy collections at apply time); destination chat display names overwritten with the manager's current names.
- **Writes are never client-cancellable**: `RequestAborted` is deliberately NOT forwarded into the cache. `AddAlertTemplateAsync` persists the template BEFORE reconciling sensors, and `RemoveAlertTemplateAsync` strips per-sensor template policies BEFORE removing the template — a client-triggered cancellation mid-reconcile would leave half-applied state, and a cancelled DELETE would silently leave the template alive with some sensors already disarmed (nobody to report to — the client is gone). The web UI passes no token either: a write completes once accepted.
- **Global read-only resources (alert schedules, #1352)**: schedules are not folder-scoped, and the web UI shows them to every logged-in user. The gate is therefore caller-wide, not per-resource, and lives **inside the evaluator** (`CanSeeAnyBoundary`, #1384): the caller may read schedules when the token's owner is an admin or currently holds a role on at least one product/folder — with caller resolution and token liveness inside the same decision. An unentitled caller (an owner with no roles at all) gets 403 for every id (the provider is never queried — schedule existence is not per-caller scoped, so nothing leaks), an entitled one a plain 404 for an unknown id. One denial audit record per denied request is written by the gate itself, as `AuthorizationDenied` — the plain 403 scope-denial kind, deliberately NOT the `AuthorizationNotFound` enumeration-probe signal, because the caller-wide gate discloses nothing about any concrete target. Sensor references in the DTO (full paths, the UI list page shows them as a tooltip) are filtered per sensor through the evaluator at the sensor's **product** boundary (`IsVisible` — the owner-sight predicate): a token never learns sensor paths outside its owner's sight; parentless sensors fail closed (dropped). On the list path the decision is memoized per **distinct** product within one request (sensors cluster into few products; the evaluator re-resolves caller + token on every call), and the page's sensor references are resolved in ONE bulk cache pass (`GetSensorsByAlertSchedules` — the per-id lookup scans every sensor, so per-item calls would be a full scan per schedule; the cookie UI list uses the same bulk method).
- **Sensor-tree read surface (#1386)**: five GET endpoints over the LIVE cache — `GET /api/v1/products` (visible ROOT products only; nested folders are not listed — walk them via the node endpoint or the product filter; an owner who sees nothing gets an EMPTY list, not 403: emptiness discloses nothing), `GET /api/v1/nodes/{id}` (any product or folder, metadata + DIRECT children only, no recursion; products and folders are one model — `ProductModel` in the flat `_tree` index — authorized through the Product boundary; the children lists are CAPPED at the area's list ceiling (200, ordered by name) with `totalFolders`/`totalSensors` carrying the uncapped counts — a flat product can hold thousands of direct sensors, and no `/api/v1` response is unbounded; the paginated sensor search serves the full sensor list, and the FOLDERS list paginates itself (`foldersPage`/`foldersPageSize` — direct subfolders have no other addressable surface, #1387 round 3)), `GET /api/v1/sensors` (flat recursive search: optional `product` = any node id whose whole subtree is searched — a FOLDER id works too; without it the search spans every sensor visible to the owner's sight), `GET /api/v1/sensors/{id}` and `GET /api/v1/sensors/{id}/history`. **Visibility is the owner's sight resolved per ROOT product** — exactly how the evaluator resolves a sensor resource (`sensor.Parent.Root`) — memoized per distinct root product within one request (the schedules-list pattern); parentless sensors fail closed (dropped). The `product` query parameter is a concrete target reference (any product or folder id): unknown → the plain area 404 with no evaluator call, invisible → the evaluator's 404 — indistinguishable; the visibility decision resolves the node's ROOT product (ProductsRoles holds root ids, folder roles materialize per root — authorizing the folder id itself would 404 a scoped owner whose sensors under that folder are listable via the root). The node endpoint resolves the same way. **Search**: `search` matches DisplayName + Description + Path (OR — a null field simply never matches); `searchMode=contains|regex` (default contains, OrdinalIgnoreCase substring; regex = case-insensitive .NET pattern with a 100 ms PER-MATCH timeout and a 200-char bound; a 2 s whole-scan evaluation budget applies to EVERY mode — the unfiltered full-cache listing is the most expensive request shape (a materialized snapshot, a `FullPath` allocation per ancestor level per sensor, a full sort, repeated per page), and nothing else in the server throttles it. The budget covers EVERY phase of the shape — snapshot materialization, the filter pass, and the sort after it (#1387 r4). An exhaustion (or a regex match timeout) answers **503 `service_unavailable`** with the mode-appropriate remedy in the message — a capacity abort is not a validation failure, and a 400 would tell an agent its request is malformed; an invalid pattern GRAMMAR stays a 400. Never a hang, never a 500). The area's existing `PathTemplateConverter` wildcard engine is deliberately NOT reused (path-only, template-macro semantics). **Sensor DTO is identical in list and item** — the current value (`lastValue`) is embedded, so a search hit needs no second request; list ordered by full path then id, `ApiPageDto` envelope. **Value envelope** `{time, status, comment, value}` with a typed `value` by sensor type: native scalars, TimeSpan/Version as round-trip strings, Enum `{value, label}` (label from the sensor's registered options, null when unregistered), Bar `{min, max, mean, stdDev, count}` (`stdDev` = the bar's population σ #1509, exposed here since #1620; null = unknown — never reported as 0), File **metadata only** `{name, extension, size}` — file CONTENT is never serialized anywhere in the area. **History**: `from`/`to` UTC (defaults `now−24h` / `now`), `maxPoints` default 1000 cap 10 000 (non-positive → default; File sensors additionally capped at 100 — every scanned File row deserializes a full payload while holding the per-sensor lock) — the **newest** `maxPoints` values of the window, oldest first, NO server-side decimation (#1386 decision). The database streams a window **NEWEST-FIRST** (`Database.GetValueToFrom` iterates descending keys, `to` → `from` — #1389: the endpoint originally assumed the opposite and answered with the OLDEST points in reverse order), so the newest-N read is a bounded PREFIX of the stream: the endpoint asks for `maxPoints + 1` (the page generator's own count bound), drops the surplus — the oldest of the batch, whose presence is exactly `truncated` — and reverses for the oldest-first wire order; the response cap is enforced by construction (`RemoveRange` from `maxPoints`), not by dropping exactly one element. Read cost is `maxPoints + 1` rows regardless of window density; the projection to metadata DTOs happens inside the loop, so no raw `BaseValue` (a File sensor's full byte payload) is ever retained. The cache's generator releases the per-sensor file-history lock on every exit path (try/finally, #1386 review pass 3: the count-reached exit used to skip the release and latch the lock until restart, for every caller of a bounded read). A File sensor whose history is being read by another request answers `readUnavailable=true` with no points — its reads are serialized per sensor, and an agent must distinguish "busy, retry" from "no values" (checked before and after the read; `IsFileHistoryReadInProgress` on the cache). OffTime timeout markers are included (`RequestOptions.IncludeTtl` — silence is part of the honest timeline). For `AggregateValues` sensors the cache rewinds `from` to the pre-window border value (the partially-aggregated bar), so the response may carry one point older than the requested `from` — the same border semantics the cookie UI's history reads; the echoed `from` stays the requested one. The border arrives LAST on the newest-first stream, so it is the first thing dropped when the response is full — it survives only in an under-full response, and dropping it alone never sets `truncated` (it is outside the window; otherwise a window of exactly `maxPoints` values would falsely report truncation, #1390 review). Timestamps are UTC by contract: zone-less inputs are pinned as UTC, offset-bearing ones are converted to the instant they denote. All reads are `ConcurrentDictionary` scans (`GetProducts` / `GetSensors` / subtree `GetAllSensors`) — lock-free by construction; the dictionary walk itself is single-digit ms for tens of thousands of sensors, but the FULL listing shape also materializes a snapshot, computes the recursive `FullPath` per sensor and sorts it — that is the cost the evaluation budget bounds, not something to assume cheap (#1387 round 3). Products with 5000+ sensors are a first-class sizing constraint (hence server-side search + pagination, and no tree-dump endpoint). The filter loop and the history stream both observe `RequestAborted` — a disconnected client stops the work, never a 500 (the /api exception middleware rethrows cancellations untouched).

- **Notification chats, read-only (the destination.chats id source)**: alert policies and alert templates reference chats by id and the write paths validate those references (unknown or folder-unavailable chat -> 422/400), but until this surface no `/api/v1` endpoint could LIST valid chat ids — the write endpoints were not usable end-to-end by an API-only client. `GET /api/v1/chats` + `GET /api/v1/chats/{id}` close the gap. **Visibility**: the caller-wide gate first (the schedules rule — `CanSeeAnyBoundary`; an owner who sees no boundary has no sensors to attach chats to, so global chat names must not leak either), then a chat is visible when it is GLOBAL (bound to no folder — attachable from every node's policies, the same rule the write paths validate against) or bound to at least one folder the owner can see; the folder decision is memoized per distinct folder within one request (the templates pattern), out-of-sight chats are silently absent from the list, and an invisible id answers the SAME 404 as an unknown one. Chats carry no `ApiTokenResourceKind` of their own — this composition of the folder sight IS the chat sight rule. **Secrets**: the chat row stores cleartext Slack/Mattermost webhook URLs; the DTO exposes presence booleans only (`hasSlackWebhook`/`hasMattermostWebhook`) — the URLs never leave the server through this surface (the web UI's mask exists for its round-trip editor, not for reads). **Two-tier body (the web UI's authorization model, which shows chat detail only to admins and PMs of a bound folder)**: every gated caller gets the id-discovery fields — `id`, `name`, `telegramType`, the channel flags and `folders` (the `hasSlackWebhook`/`hasMattermostWebhook` flags are DELIBERATELY discovery-tier, the one exception to the detail gate: presence says which delivery channels a chat offers when composing `destination.chats`, never the URLs — a secret never travels in a flag) — while the detail fields (`telegramChatId` — for a direct chat a personal Telegram user id, `telegramChatTitle`/`telegramChatDescription`/`telegramAuthorizationTime`, `author`, `description`, `creationDate`, `sendMessages`, `messagesAggregationTimeSec`) are NULL unless the owner is an admin or a manager of a bound folder (`CanSeeChatDetail`, the token-side twin of the UI's `TelegramRoleFilterById` EditChat gate; a GLOBAL chat has no bound folder, so its detail is admin-only). The `folders` list carries only folder ids the caller can see — an invisible folder id stays indistinguishable from an unknown one (the area's anti-enumeration rule; empty still means global). The write half is the next invariant.

- **Notification chats, written (#1829)**: `POST /api/v1/chats`, `PATCH /api/v1/chats/{id}` and `DELETE /api/v1/chats/{id}` run on the write engine the web editor runs (`ChatAdministrationService`) — no rule is re-implemented. **Gates mirror the web editor.** Create is admin-only (`AuthorizeChatCreate`: a chat created with an attacker-supplied webhook URL would exfiltrate every alert sent to it); a non-admin answers 403, never 404 — a creation has no target whose existence a 403 could disclose. Update and delete take `AuthorizeChatWrite` — the evaluator's chat-write decision: the read surface's caller-wide gate first (an owner who sees no boundary sees no chat at all, a global one included, so every chat answers them the same 404 as an unknown one), then the read surface's sight rule, then the chat's detail rule (an admin or the manager of a folder the chat is bound to, so a global chat is admin-only) — in the anti-enumeration split: an unknown and an invisible chat answer the same 404, only a visible chat the caller may not change answers 403; its denials are recorded like those of every other write. Authorization precedes body validation, so a body-shape error never reveals that a chat exists. **The write rules are the engine's — one set for both surfaces**: the name (required, at most 100 characters, unique per server ignoring case and surrounding spaces with the chat excluded against itself — `ChatNameValidator`, the same messages the web form shows inline), the aggregation delay (0 to 86 400 seconds: 0 sends every alert at once; a negative delay never flushes a channel's accumulator, so a chat holding one would drop its alerts in silence) and the webhook URL shape (absolute http or https). The name rule guards changes, not history: a row that keeps its own name breaks nothing, so chats duplicated before the rule stay editable until someone renames them — a row stored with a padded name (from before names were held trimmed) included: a save that posts the name back as it reads, trimmed, is no change. **The engine checks a name on a snapshot and the storage has the last word**: `ChatsManager` repeats the uniqueness part under one gate in front of its own write, so of two creates of one name racing through the window between the check and the write one lands and the other answers the same 422 under `name` (`Chat with the same name already exists.`); a refused write whose name is still free is the storage's own failure, the fixed-message 409. A chat the `/start` flow creates gets the first free name (`Dev team`, `Dev team (2)`…), since two groups may share a title and nobody is there to pick another; the name is picked under the storage's write gate, and a title is trimmed and one longer than 100 characters is cut to the maximum. A row that already holds an over-long name, from before the cut, is editable through this API while it keeps it — the web form's own length check asks for a shorter name first, as it always did. The API adds the two rules that have no meaning for a cookie user: #1705's character rule on the name (API/MCP paths only) and the folder scope. **Partial update**: an omitted (null) field stays unchanged; a webhook or the Telegram binding is removed only by its clear flag, and an empty webhook value changes nothing (a read never returns the URL, so there is nothing to echo back). A Telegram binding cannot be requested — it is a person's /start against an invitation (ADR `docs/adr/0002`). **Folders**: the complete list of bindings among the folders the token's owner manages — a managed binding not listed is removed, a binding to a folder the owner cannot manage stays, and a NEW binding needs an existing folder the owner manages; any other id answers 422 under `folders` with one message for an unknown and an unmanaged folder alike, and nothing is applied. A folder the chat is already bound to may be listed whatever the owner's role there is (it stays bound): a read names every bound folder the caller can see, and a client that sends that list back must not be refused for a binding that simply stays. **Making a chat global is an administrator's decision**: a non-admin's update must leave the chat bound to at least one folder, or it answers 422 under `folders` — a chat without bindings is offered from every node and only an admin can change it afterwards, so unbinding the last folder would widen the chat's audience and lock the caller out in one call. (The web form still lets a folder manager do that; the API is the stricter of the two.) A request's every problem answers in ONE 422 body. **Secrets**: a webhook URL is write-only — stored, never echoed (the echo answers `hasSlackWebhook`/`hasMattermostWebhook`). **Delete**: the same removal the web UI's list runs (`IChatsManager.TryRemove`), with the web removal's own reach: the storage's removal event prunes the chat's id from every folder bound to it, and each such folder update from the alert policies of its products. References elsewhere are left in place: a global chat's everywhere, and a chat's in the policies that referenced it while it was global and belong to folders it was never bound to. With `X-HSM-Dry-Run: true` nothing is removed and the 200 body is `ChatDeletePreviewDto` — the area's preview shape plus `sensorUsageCount`, the counter behind the web list's usage badge, and `sensorUsageIncomplete`, the badge's own "≥" caveat. A removal that never reached the store answers 409 (404 when the chat vanished on the way). **Journal**: every write leaves the `chat` records naming its initiator (the journal feature), the token's owner — who is also the author of a new row.

- **Access-grouping folders, read-only (the folderId source)**: alert templates are scoped to a Folder entity (writes validate `folderId` against `IFolderManager` — the folder must exist, be visible and contain products), but until this surface no `/api/v1` endpoint enumerated Folder entities — ids were discoverable only indirectly, from the templates that referenced them. This is NOT the "folder" of `GET /api/v1/nodes` (a nested product of the tree's flat index): it is the separate grouping entity of the web UI's Folders page. `GET /api/v1/folders` + `GET /api/v1/folders/{id}` follow the templates pattern verbatim (folders ARE the per-item boundary): no caller-wide gate — an unsighted owner gets an EMPTY page (emptiness discloses nothing); the list filters by the owner-sight half of the read decision memoized per distinct folder; an item is listed exactly when `GET {id}` would answer it; unknown and invisible ids answer the SAME 404. **Two-tier body like the chats (the web UI gates the whole folder page at the folder Manager)**: the id-discovery fields — `id`, `name`, `products` — answer every sighted caller, with `products` (id + name, name-ordered) FILTERED to the caller's own product sight through `MemoizedProductVisibility`: a folder role must NOT grant product sight (per-product narrowing edits `ProductsRoles` only — the same no-folder-fallback rule the evaluator enforces; the tree lists just `GetUserProducts`), so a product the owner was explicitly revoked from stays absent. The detail fields — `description`, `color`, `creationDate`, `author`, the bound chat ids, the default-chats routing (mode: `fromParent`/`notInitialized`/`empty`/`custom` + the selected chat ids — what FromParent-destination policies resolve to) and the retention defaults (`ttl`/`keepHistory`/`selfDestroy` in the same sparse-enum `TimeIntervalDto` shape the template TTL intervals use, mapped through the view model's own storage serialization `ToModel()` — the stored truth, not the UI display form) — are NULL unless the owner is an admin or the folder's Manager (`CanSeeFolderDetail`, the token-side twin of the UI's `FolderRoleFilterByFolderId` gate). Folder CRUD (create/rename/delete, product assignment, chat binding, retention edits) stays web-UI-only.

- **Server settings: the Telegram bot credential (#1830) — the first server-settings surface**: `GET /api/v1/telegram-bot` and `PATCH /api/v1/telegram-bot` read and change the one bot credential of the server (`TelegramConfig`: the bot name, the token, the delivery switch). No server setting had a `/api/v1` surface before. **Gate: administrators only, on both actions** (`AuthorizeServerSettingsRead` / `AuthorizeServerSettingsWrite` — the web Configuration page's `[AuthorizeIsAdmin]` in the evaluator's terms; a read-only token of an administrator reads, as everywhere). The settings are one well-known block with no id, so a non-admin answers 403 and never a 404 — there is nothing to enumerate; the read's 403 says the owner is not an administrator, the write's is the area's single write-denial text. Denials are recorded once, as `AuthorizationDenied`. **The token is write-only**: reads and echoes answer `hasBotToken`, never the value; it is journaled as a state and never logged (#1824). **The update is a partial update** — an omitted field does not change — and an update that changes nothing does nothing: no probe, no save, no journal record, no restart. An empty `botToken` or `botName` is refused under its field: empty means empty here, not "clear"; clearing the credential stays a web page action. **The order of a token change is the point.** The new token is asked of Telegram (`getMe`, through a client of its own) BEFORE anything is saved. A rejected token — Telegram's 401 or 404, or a token of the wrong shape — is the field-keyed 422 under `botToken` naming Telegram's answer, and the working bot keeps running (the web page's Restart stops the running bot first and learns of a mistyped token afterwards). No road to Telegram — a timeout, a rate limit — is the fixed-message 409: the token was not judged, and the same call may be made again. Only then is the credential saved to the settings file, journaled (the `serverSettings` records the web page's save leaves, naming the token's owner) and the bot restarted. **The name goes with the token**: invitation links are built from it, and a typo breaks them silently. A passed `botName` must be the username Telegram reports for the *effective* token — the new one when the token changes, otherwise the stored one — ignoring letter case and surrounding spaces; a mismatch is the 422 under `botName` naming the username Telegram reported. After a token change the STORED name must match too: an omitted field does not change, so a stored name of another bot is refused until the right one is passed (a first setup included — a token without a name answers the name to pass). A name check asks the running bot first: it remembers the username `GetMe` gave when it started on exactly that token, so a name-only change needs no call to Telegram while the bot runs on the stored token. A stopped bot — or one still running a token the settings have left behind (the web page saves and restarts in two steps) — means one `getMe` with the stored token; its rejection is the 422 under `botToken`, for the name is not what is wrong, and so is a name without any stored token. **Only a token change restarts the bot**; the name and the switch are read live — disabling or enabling changes the setting and nothing else, and a stopped bot stays stopped. **The echo is the resulting status** (`{botName, isEnabled, hasBotToken, isRunning}`). A restart that fails — or throws — after the save is not a failure of the request: the save has landed, and a failure would read as "not saved", whose retry would change nothing and restart nothing. The answer is 200 with `isRunning: false`, and the log names why. Route note: a single settings block, so the route is singular and kebab-cased like the area's nested resources (`test-message`, `ttl-policies`), not a plural collection.

### The AI-agent scenario ("manages alerts via key", #1347/#1353 acceptance)

The acceptance bar of the epic: an AI agent that starts from NOTHING but the OpenAPI document can manage alert templates end to end.

1. **Credential**: the agent's operator provisions a personal API token (an operator action today — a self-service issuance flow is #1356 step 4) and hands over the full credential `hsm_pat_v1_<token id>.<secret>`, disclosed once.
2. **Discovery**: the agent reads the swagger document (`/api/swagger` → `/swagger/{version}/swagger.json`). The `HsmApiToken` security scheme tells it the Authorization header shape (`Bearer hsm_pat_v1_…`) and the credential lifecycle; management operations are marked with the scheme's security requirement; the doc-level description states the error contract; every operation declares its statuses with the `ManagementApiErrorDto` schema.
3. **Act**: it calls `GET /api/v1/alertTemplates` (or `/api/v1/alertSchedules`) on the web-UI port with the bearer header. Missing/invalid token → 401 `unauthorized`; owner cannot see the target / read-only token on a write → 403 `forbidden`; both bodies machine-parseable.
4. **Write**: it creates/updates/deletes templates built purely from the DTO schemas — enum-coded integer fields carry their full value tables in the field remarks, round-trip traps (id handling, parallel TTL lists, chat availability) are documented in the DTO summary. Malformed payloads → 400 `validation_failed` with field-keyed `details` the agent can act on mechanically.
5. **Trust the errors**: every failure — down to a server 500 (`internal_error` + `details.traceId` to quote in a bug report) — is JSON with a stable `error` code; the agent never has to parse HTML or distinguish empty bodies.

### The read-analysis scenario (#1386 acceptance)

"Analyze network problems in product X" with a read-only token, no prior knowledge:

1. `GET /api/v1/products` → the visible root products; find X by name.
2. `GET /api/v1/sensors?product={X}&search=network` (or `searchMode=regex` with an alternation) → matching sensors with paths, descriptions, units AND current values in one response — the last-value envelope is typed per sensor type, so numeric comparison is direct.
3. Odd readings → `GET /api/v1/sensors/{id}/history` (defaults: last 24 h, 1000 points) → the newest points oldest-first with a `truncated` flag; narrow the window when set.
4. `GET /api/v1/nodes/{id}` only when the tree shape itself matters (folder walk).

## Data Flow

```
bearer token ──► ApiExceptionJsonMiddleware (catches what's left on /api, else rethrows
             │   to the global /Error Razor handler; LoggingExceptionMiddleware, inner,
             │   has already logged)
             ──► ManagementApiGuard (SitePort, [ManagementApi]+policy, else uniform-JSON 404)
             ──► HsmApiToken scheme (generic 401 on any failure, uniform JSON + WWW-Authenticate)
             ──► binding ([ApiController]) ── invalid → 400 uniform error via the factory
             ──► controller action
                  ──► IApiTokenAuthorizationService.Authorize(User, op, Folder(template or dto folder))
                  │     Allowed → proceed; Forbidden → 403 uniform error; NotFound → 404 uniform error
                  ├── alertSchedules (global, read-only): CanSeeAnyBoundary(User)
                  │     true → proceed (list: one bulk sensor pass + visibility memoized per
                  │             distinct product); false → 403 uniform error + one AuthorizationDenied
                  │             audit record (never the enumeration-probe kind)
                  ├── structural validation (enums, list parity, ids) ── 400 uniform error w/ details
                  ├── condition rule table (per template sensor type, #1611) ── 400 field-keyed
                  ├── entity reconstruction (try, last-resort net) ── 400 on unsupported domain input
                  ├── semantic validation (name/path/mismatch/chats) ── 400
                  ├── TreeValuesCache.Add/RemoveAlertTemplateAsync ── 409 on (false, error)
                  └── 201+Location / 200 + stored DTO / 204
```

## Storage / Persistence

None of its own — reads and writes go through `TreeValuesCache` (`AddAlertTemplateAsync` upsert-by-id, `RemoveAlertTemplateAsync`, `GetAlertTemplate(s)`); durable rows are the alert-templates feature's. The one setting this area writes is the bot credential (#1830): `PATCH /api/v1/telegram-bot` changes the three values through `IServerConfig` and its `ResaveSettings` — the settings file — and journals through `JournalAppender`, the path the web Configuration page takes.

## UI / Operator Visibility

No UI. The cookie web UI (`AlertTemplatesController`) remains the human surface; the REST API mirrors its validation rules. For the bot credential the human surface is the Configuration page's Telegram tab, which keeps Save and Restart as its two steps.

## Dependencies

- Depends on: api-tokens feature (scheme, area guard, evaluator, security events), alert templates domain (`TreeValuesCache`, `AlertTemplateModel`), alert schedules domain (`IAlertScheduleProvider`), Swashbuckle (the server's single OpenAPI doc).
- Used by: non-interactive management clients; the OpenAPI document at `/api/swagger` is their self-describing entry point. The MCP feature (`aicontext/features/server/mcp/`, #1391) renders the same sensor-tree read logic (`SensorTreeReadService`) and the alert read paths for MCP-native agents.

## Notes

- **Echo is canonical**: POST/PUT return the stored shape, not the request — normalizations (ids, chat names) and mode collapse are visible to the caller.
- **Mode collapse (documented)**: a "custom destination with zero chats" reconstructs as `NotInitialized` (the domain derives the mode from flags + chat count); echo-back of GET output is always stable because the DTO carries only the flags.

## Known Issues / Limitations

- **Apply-time rejection residuals (#1401)**: a persisting save with per-policy rejections answers 201/200 + `warnings` (never a 409), and a hard apply failure answers 409 — but the apply that runs when a NEW SENSOR is created against an existing template has no caller to warn: its rejections are journaled and logged only (nobody is waiting on a response). The `warnings` list is also unbounded in size on a save whose every matching sensor rejects (capped renderings exist on the restore path only; REST/MCP echo the full list).
- **Name uniqueness is a cross-folder existence oracle** (deliberate, parity with the web UI): the uniqueness check spans all folders, so a folder-A-scoped token can probe whether a template named X exists anywhere on the server — including folders it gets a 404 for — through the duplicate-name 400. Scoping uniqueness to reachable folders would diverge from the UI rule and allow same-name templates the UI considers invalid.
- **PUT racing a DELETE resurrects the template**: the existence check and the upsert `AddAlertTemplateAsync` are not atomic; a PUT concurrent with a successful DELETE re-creates the template under the route id. Same upsert semantics the web UI relies on.
- **Concurrent POSTs with the same name both persist**: the name-uniqueness check reads `GetAlertTemplateModels()` and the cache Add does not enforce uniqueness, so two racing creates can both land. Same race the web UI has; uniqueness is advisory, not a constraint.
- **The chat delete's dry run walks the whole sensor cache** (#1829, the `delete_sensor` precedent): the preview's `sensorUsageCount` comes from `ChatSensorUsageCalculator.Compute`, the same uncached scan the web chat list runs on every request, synchronously on the request thread. Until #1829 only admins triggered it (the list is admin-only); now any manager of a bound folder can, through `DELETE … X-HSM-Dry-Run: true` or `delete_chat(dryRun: true)`, and the tool description tells agents to dry-run first. On a large tree each call is a full scan. Accepted as is; a short-lived cache inside the calculator would cover the web list and the API alike if agent traffic makes it necessary.
- **The aggregation delay's ceiling of one day is a product choice** taken at the review's request for "a sane upper bound"; nothing in the delivery code constrains the number.
- **Chat names: what the uniqueness rule still leaves open** (#1829). The check-then-write race is closed — the storage repeats the rule under a write gate in front of `TryAdd`/`TryUpdate`, unlike the templates' two races above — but two caveats remain. The rule deliberately lets a row keep its own name, so duplicates that predate it are never repaired by it: they coexist until someone renames one of them. And for a non-admin the check is still a server-wide existence oracle: the manager of one bound folder learns through the 422 whether a name is taken by a chat anywhere, including chats they cannot see (creation itself is admin-only, so the oracle is reachable only through an update).
- **A chat's deletion leaves its references outside the folders it was bound to** (#1829 keeps the web removal's reach): the pruning runs from those folders — `FolderManager.RemoveChatHandler`, then `RemoveChatsFromPoliciesAsync` per folder — so a global chat's id stays in every alert policy that referenced it, and so does a chat's in the policies that referenced it while it was global and belong to folders it was never bound to. The senders skip a chat that no longer exists, so nothing is delivered; the policies keep a dead reference until they are edited. A tree-wide prune on a chat's removal changes the web removal's semantics and is a separate decision.
- **A stopped bot cannot be started through this surface** (#1830, the issue's rule that only a token change restarts): a bot whose credential is saved and enabled but which is not running — a failed start, a server start during a Telegram outage, a token saved from the web page without a Restart — stays stopped for an update that changes nothing, and re-sending the saved credential changes nothing. The web Configuration page's Restart button starts it. An explicit restart endpoint (or flag) is the follow-up if an agent workflow proves it necessary.
- **The probe of a token change waits as long as the Telegram client does** (#1830): its `getMe` runs on the real client with the five-minute timeout the web page's Restart has always had. A refused token answers in one round trip; a blackholed network holds the request until the client gives up.
- **A Telegram client is never disposed** (the pre-existing shape of `TelegramBot.CreateClient`, which #1830's probe now reaches once per token change): the `HttpClient` behind a client is dropped, not disposed — on a restart as on a probe. Its connection idles out on its own, so nothing accumulates but the handler object until it is collected.
- **Per-item string sizes are unbounded**: the guard rails bound collection counts and the name only; path strings, message templates, icons, condition target values and per-policy condition counts are limited by the request body limit alone. A multi-megabyte template would be copied onto every matching sensor and re-serialized on every sensor write. Tighter per-item bounds are a deliberate open decision (the web UI has none either).
- **`sensors` in the schedules LIST response is unbounded** (deliberate, parity with the UI list tooltip): a schedule referenced by tens of thousands of sensors emits every visible full path, for up to `MaxPageSize` schedules in one response. The per-product visibility memoization bounds the CPU cost, not the response size; a count-plus-item-fetch split is a possible follow-up if machine clients prove it necessary.
- ~~A future schedule WRITE must not reuse the caller-wide gate~~ — RESOLVED by the schedule write path: `AlertScheduleAdministrationService` (the schedules' twin of `PolicyAdministrationService`, #1500 pattern — transport-agnostic, scoped, shared with the later MCP write tools) authorizes every write through `AuthorizeWrite(User, ApiTokenResource.GlobalScope)`, the direction this entry fixed. **Write semantics**: POST generates the id server-side (the provider's Save is an upsert by id — the templates id-handling rule); PUT takes the id from the route only (`AlertScheduleUpsertDto` carries no id); validation is field-keyed 422 — global exact-case name uniqueness excluding self (`name` — the check-then-save pair runs under one process-wide static gate, so concurrent same-name creates cannot both pass, and the update-path existence check and the delete's final remove take the SAME gate: an update racing a delete cannot resurrect the deleted schedule), the schedule parser's YAML/semantic errors (`schedule` — the `daySchedules` key must be present, #1598: an explicit empty list is valid, but a missing key is a 422 because the model's `new()` list initializer made it indistinguishable from `daySchedules: []` and silently stored a no-working-time schedule; the check (`AlertScheduleParser.HasDaySchedulesKey`) lives on the WRITE path only — rows stored before the rule may omit the key and keep loading; windows >= 1 min, non-overlapping, start < end, dates 2000..2100); #1599 made the texts deterministic and field-specific: every message names the offending value and the expected format where one exists (a shape mismatch answers `The schedule structure is invalid: ...`) (`Invalid time '24:00' (expected HH:mm, ...)`, `Unknown day 'Funday' ...`, `Invalid date '...' (expected yyyy-MM-dd)`, an empty document answers `The schedule is empty: ...`), a day-schedule entry is named by its client-sent `id` or, without one, by its position (`daySchedules[0]`) — never by a parser-generated Guid — and a reversed window reports only the start >= end error, and a NEW server-side system timezone check through `TimeZoneInfo.FindSystemTimeZoneById` (`timezone` — IANA and Windows ids both resolve, the same lookup `AlertSchedule` uses at evaluation; the web UI relies on its dropdown and never validated server-side); the name is bounded at 200 chars (the area's MaxNameLength convention; since #1597 the cookie UI form enforces the SAME bound — `AlertScheduleViewModel.Name` references the writer's constant, so the two surfaces cannot drift). DELETE detaches the id from every referencing policy FIRST — on an incomplete detach the schedule SURVIVES and the answer is 409 (retry re-runs the idempotent detach over the survivors — the #1409 rationale carried into the API); an unknown id answers 404 for an entitled caller, and the web Remove's unconditional-detach variant (cleaning rows the loader skipped) stays a cookie-UI capability. **Known limitation (accepted, round-2 review)**: nothing serializes a schedule DELETE against a policy/template write that is mid-flight — a policy write can pass its scheduleId existence check while the delete detaches current references, then persist pointing at the now-deleted schedule; the evaluator treats a missing schedule as working time (#1409 throttled error log is the only trace), and the delete-retry cannot help (the id is gone, the API answers 404). The web UI has the same gap between its own endpoints; the API surface does not widen the per-write semantics, it only makes scripted concurrency more likely. Closing it would mean serializing validation with delete inside the core write paths (TreeValuesCache) — out of scope for the management API. The success echo renders through `AlertReadService.RenderSchedule` — sensor paths visibility-filtered exactly as GET answers. A non-admin owner answers 404 (Global sight is admin-only — nothing about the write surface leaks); a read-only token is rejected by the method backstop before the action and answers 403 through the evaluator's Forbidden arm.
- List re-resolves the caller per **distinct** folder within a request (memoized); templates sharing a folder cannot straddle a mid-request role change, but two folders in one page still can. A snapshot API in the evaluator is a possible follow-up.
- ~~The ported `TryApplyPathTemplates` semantic check is effectively unreachable through string input (the converter builds the pattern lazily; a malformed pattern surfaces at match time, not registration)~~ — RESOLVED by #1607: `PathTemplateConverter.ApplyNewTemplate` compiles the pattern eagerly, so a malformed path regex fails the semantic check (`paths: Invalid path template: …`) instead of throwing `RegexParseException` at match time.
- **Enum tables in the OpenAPI spec are XML remarks, not generated schemas** (deliberate: typing the DTO enum-coded fields as the DOMAIN ENUMS would move their membership check into model binding — BEFORE the in-action folder authorization — and break the authorization-precedes-validation invariant, leaking existence through a 400; since #1607 the fields are plain `int`, which keeps the check where it was while letting out-of-byte-range values bind and be REJECTED by the validator under their field key instead of dying in binding). The tables CAN drift — and did once on day one: `sensorStatus` was published with the values of `HSMSensorDataObjects.SensorStatus` (OffTime=0…Error=3) while the controller validates `HSMCommon.Model.SensorStatus` (`Ok=0, Error=1, OffTime=255`), silently inverting Ok/OffTime for spec-driven agents. Since then `ManagementApiSwaggerTests.DocumentedEnumTables_MatchTheDomainEnums` parses every `N=Name` pair out of the DTO XML remarks and pins the full tables (values AND names) against the domain enums the controllers validate with — including the deliberate extra `100=AnyType` on SensorType.
- **The OpenAPI document is anonymous on the SitePort — considered and accepted**: the port gate restricts WHERE the doc is served (SitePort only), not WHO reads it. The doc publishes the management route map, schemas and credential FORMAT, but no data and no credential material; the SitePort is the web-UI port, whose routes are equally anonymous, and hiding the shape behind authentication would break the discoverability the epic is about (and the operator browsing the doc). If the threat model changes (SitePort exposure widens), an authorization gate on the swagger endpoints is the follow-up.
- **The reserved cookie-only family (`/api/v1/api-tokens`, #1356 step 4) is outside the uniform contract until it lands**: it authorizes through the cookie scheme, whose 401 challenge redirects to the login page — a bearer-shaped JSON 401 there needs that PR's own decision (the guard 404s every unmatched route in the family today, with the uniform body).
- **HSMSwaggerComments.xml is build output that is tracked in git** (pre-existing repo policy, predating #1353): every PR that adds XML doc comments carries a regenerated diff. Changing that policy (gitignore + untrack) is a separate housekeeping decision.
- **File-sensor history reads are serialized per sensor** (pre-existing `TreeValuesCache` file-history lock, #1386 inherits it): a file sensor's history endpoint invoked while another read of the same sensor's history is in flight returns `readUnavailable=true` with no points instead of blocking (#1387 round 3) — the cookie UI's file history sees the raw empty stream, as before. The acquire is now ATOMIC (`TryAdd`/`TryUpdate` — the previous read-then-set could interleave two readers through the same gap), and since the release moved into a `finally` (#1386 review pass 3), an abandoned mid-stream enumeration releases it too (`await foreach` disposal runs the iterator's `finally`); the only surviving latch is a caller that manually takes the enumerator and never disposes it.
- **The `lastValue` of the list item is a read-time snapshot**: list and item both read the live `Storage.LastValue`; a value arriving between the search and the item read makes the two differ — no consistency guarantee between calls is offered (the same as the web UI).
- **A sensor deleted mid-history-read can still 500** (pre-existing cache-level landmine, narrowed in #1386): the endpoint re-checks the sensor between authorization and the stream (the page read would dereference a null deep in the cache), but a deletion landing AFTER that re-check escapes as a 500 with `details.traceId` — the uniform error contract still answers, and the race window is milliseconds wide. Fixing it properly (null-safe page reads in `TreeValuesCache`) belongs to the cache, not this surface.
- **A mute write does not surface a persistence failure** (#1569, accepted): the service delegates to the core's `UpdateMutedSensorStateAsync`, which discards the update queue's `TaskResult` — a LevelDB write failure after the in-memory apply still answers 200 with the (in-memory) resulting state, the exact visibility the web UI's own mute flow has. The policies write engine builds its own `SensorUpdate` through `UpdateSensorAsync` and reports that failure as 409; a mute write is a single-field update, and routing it the same way would mean re-implementing the core's State/period translation the issue explicitly forbids. The residual risk is identical to the web modal's.
- **A delete answers 204 on the cache removal alone** (#1637, accepted — the web UI's own visibility): the engine's post-write read verifies the sensor left the CACHE; `RemoveSensorAsync` performs the journal record, the DB history wipe and the change-set purge inside its own swallow-only handler, so a failure THERE is logged by the core and the 204 already stands. Unlike the mute twin, the observable honest-failure channel exists (a removal that never reached the cache answers 409), and re-deleting is harmless (the SEQUENTIAL retry answers 404 for a cache-clean sensor; two concurrent deletes of the same id can both answer 204 — the second write no-ops on the already-gone sensor, so the not-found repeat is a sequential property); the residual is orphaned DB rows the core's logs name — the same residual the web UI's remove-node has always had.
- **A move request is not atomic and runs its sensors sequentially** (#1721, by design — owner decision 1 of #1718): every sensor goes through its product's queue, and a merge copies the absorbed sensor's history inside that queue, so a large merge holds that product's ingestion for the copy (see `sensor-move/feature.md`). A cancelled request stops before the next sensor; a merge already started is completed. The dry run predicts each sensor against the live tree independently: a sensor whose destination another requested sensor would vacate earlier in the same batch is predicted as `conflict` but moves.
- **The delete's dry-run preview reads history stats through the core's scan** (#1637, accepted at #1639 review): `historyValues`/`historySizeBytes` come from `GetSensorHistoryInfo` (the same LevelDB scan the web UI's node info runs), so a preview against a sensor with millions of stored values pays that scan — bounded by the values DB's iteration, not by the response. The scan is synchronous on the request thread, no `CancellationToken` reaches the core accessor, and a read-write token can repeat the dry run without limit; bounding the scan or making the stats opt-in is the follow-up if machine clients prove it necessary. The numbers are computed at preview time and the real delete may remove slightly more (values arriving between preview and delete).
- **A Blocked sensor racing the mute write still answers 200** (#1569, inherent): Blocked is checked before the write; a sensor blocked between the check and the core call is silently no-opped by the core, and the echo honestly renders `state: Blocked` in the 200 body — the caller can self-correct from the echo.
