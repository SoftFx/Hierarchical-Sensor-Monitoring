# Feature: Journal (unified configuration journal with rollback)

> Owner: server | Last reviewed: 2026-11-25 | Canonical: yes
> Scope: the single journal of every monitoring-tree configuration change (#1588) — the global Journal page, the per-node Journal tabs, the `/api/v1/journal` surface, the `list/get/rollback_journal_record` MCP tools, the entity-kind/product/undo-group tags on journal records, the admin-only rollback by record, and the journal-visible-only records of chats and server settings (#1828). The undo mechanics of #1570 (before/after images, compensating writes, conflict detection) live on as internal machinery of this feature, addressed through journal records. Decision record: ADR-0013 (supersedes the surface decisions of ADR-0010).

---

## Overview

Every monitoring-tree configuration change — from the web editor, the REST management API and the MCP tools alike — lands in ONE journal with an entity kind, the root product and, for the rollbackable kinds, a link to its request's undo group. One HTTP request / MCP call / form post journals under exactly one server-minted undo group, so one rollback undoes the whole request. The web editor rides the same administration services as REST/MCP (the single write path); the cache layer keeps journaling settings and tree mutations it always did, now kind-tagged. Rollback is ADMIN-ONLY on every transport.

## Invariants

- **Single write path** — sensor data/TTL policy lists, alert templates and alert schedules from the web editor go through the administration services (per-node gates, authorization seam with the cookie twin, undo journaling), exactly like REST/MCP writes. Node settings and tree CRUD remain cache-layer writes (journal-visible, not rollbackable).
- **Per-request undo groups (#1588)** — group ids are SERVER-minted (minted once per HTTP request and cached in `HttpContext.Items`; one per MCP call; one per form post). There is no client-supplied id, no `X-HSM-Change-Set` header, no `changeSetId` MCP argument, and the #1570 fork rule is gone: an append always lands in the id it was given. `X-HSM-Dry-Run` stays as the write-preview switch.
- **Kinds** — every record carries one: `sensorDataPolicies`, `sensorTtlPolicies`, `productTtlPolicies`, `alertTemplate`, `alertSchedule` (rollbackable); `nodeSettings` (node general info/settings), `treeCrud` (product/sensor/folder create/delete/move), `folder` (folder edits), `chat` (chat create, update and delete), `serverSettings` (the Telegram bot settings). The list is public contract (`JournalKinds.All`, pinned by a test): the web kind filter renders from it, while the journal API's `kind` documentation and the MCP tool descriptions enumerate it by hand and must name every kind. Legacy and non-configuration rows have null kind STORED, filter as "other", and RENDER as `"other"` on the wire with the root product backfilled from the live-tree resolution the product filter uses (#1679 — the payload answers what the filters matched, so a client grouping by `kind`/`productId` does not lose the legacy rows; `productId` stays null where no root product is derivable — global and folder-scoped records, legacy rows of deleted entities).
- **Rollbackable kinds stay the #1570 five, from all sources** — sensor data/TTL policies, product TTL, alert templates, alert schedules. The web editor's writes journal like REST/MCP writes. Tree CRUD and node settings are journal-visible only: sensor/product deletion irreversibly purges data, rollback is impossible by design. Chats and server settings are journal-visible only for another reason (#1828): they hold secrets (webhooks, the bot token), and a secret cannot sit in a before/after image.
- **Chat and server-settings records carry no secret (#1828)** — `ChatsManager` is the single write path of chats (the web flows' engine, the delete action, the Telegram `/start` binding, the bot's own cleanup), so it journals: an add leaves `Create chat` — the chat, then one record per channel the chat is created with; an update leaves `Chat update` with one record per setting whose value actually changed (name, description, enable switch, messages delay — the old and the new value); a removal leaves `Remove chat`. A webhook never reaches a record: its record reads as the state of its channel (`not set → set`, `set → changed`, `set → removed`), the Telegram binding as `not bound → bound (direct | group)` or `→ removed` — the Telegram chat id is never written (for a direct chat it is a person's Telegram user id). The bot's title/description sync and the supergroup move change no journaled setting and leave nothing. The initiator is the write's (`ChatUpdate.Initiator`: the engine stamps the signed-in user, or the token's owner for a write of the management surface (#1829), and the `/start` binding names the user who issued the invitation), the row's author for a creation, `System` for the bot's own removal of a chat. The Telegram bot settings save leaves `Telegram bot settings update` records (`serverSettings`) for the bot name, the on/off switch (old → new) and the token (`not set → set`, `set → changed`, `set → removed` — never the value) under a fixed entity id (`TelegramSettingsChanges.JournalEntityId`); the same list of changes is the save's log line. Records of both kinds resolve to the admin-only Global scope: a manager of a folder the chat is bound to can edit the chat but does not see its records. No two records of one entity share a storage key — `JournalAppender` reserves a block of successive ticks per write — and they are best-effort, as the durability rule above requires: a journal failure is logged and never fails the applied write. Records appear for changes made after deployment; there is no backfill.
- **Record-to-group links** — policy writes link through the write initiator (stamped with the group id; the cache-layer records copy it); templates and schedules have no cache journal hook, so the recorder IS their journal writer; every rollback entry leaves its own record (the redo handle is visible in the journal). A template write's fan-out policy records copy the same stamp (#1610): the fan-out initiator keeps the AlertTemplate type (the change-table owner that guards template-owned policies) but carries the write's group id, so one rollback undoes the template row and its whole fan-out together.
- **Rollback by record, admin-only everywhere** — the record's undo group replays through the internal engine. Web: admin-only (`[AuthorizeIsAdmin]`). REST/MCP: the token's OWNER must be `IsAdmin` (breaking change — Manager tokens are denied); per-resource write pre-flight stays as the second line of defense. A record without a group answers Conflict ("journal-visible only"). A rollback is itself journaled — its own journal record (same entity) is the redo handle; a group that was rolled back renders non-rollbackable on the global surface, and a mid-request write whose group went terminal forks into a fresh group with its own journal record.
- **Conflict rule is content, never timestamps** (inherited from #1570) — unchanged, internal.
- **Rollback restores configuration only** — notifications already sent, alerts already fired and sensor history are untouched.
- **Durability trade-off (ADR-0010)** — journal appends run AFTER the primary write succeeds; storage failures are logged loudly and never fail an applied write.
- **No backfill** — records written before #1588 deserialize with null tags and show as "other"; pre-unification change sets are unreachable inert history in the internal store.
- **Count-limited reads pick by time across shards and record types** — the journal is stored in weekly shards, and inside a shard each record type (Actions, Changes) is its own key range. `GetJournalValuesPage` walks the shards newest week first for a negative count (oldest first for a positive one) and merges the record types of a shard by time, so a page of N holds the N records nearest its starting edge in time order (newest first for a negative count) whatever their week or type. Records with equal ticks come back Actions-then-Changes oldest first and Changes-then-Actions newest first, so the two directions mirror each other. A type filter cannot exclude Actions (`RecordType.Actions` is 0, so `HasFlag` always matches it; pinned by `JournalBorderTests`). The per-node Journal tab relies on this read: it asks for the newest 100 records of each node over the last year (`Count = -100`) and keeps them oldest first in its per-node queue, because a live record evicts from the queue head. Before the fix a negative count read the OLDEST week first and all Actions before any Changes, so a node with more records than the limit showed old ones instead of the latest. Pinned by `JournalPageOrderTests`.
- **Operation tag (#1638)** — every row names what kind of write it is — `create` / `update` / `delete` / `rollback` — in the table's Operation column and on the wire (`operation` field of the record DTO, additive; `property` keeps its format). A rollback row (the redo handle) is tagged `rollback`, never the compensating operation its property carries. A record whose undo group went terminal additionally renders `rolledBack: true` (and keeps its non-rollbackable list rendering). The tag is DERIVED at read time (`JournalOperations`), never stored: the rollback rows by their enviroment marker, template/schedule rows by the operation part of their property, policy rows by their undo-group entry, tree-CRUD and node-settings rows by the legacy enviroment wording; rows where nothing says render without a badge and with `operation: null`. Since #1828 the chat and server-settings rows derive theirs from their enviroment wording too: `Create chat` is a create, `Remove chat` a delete, `Chat update` and `Telegram bot settings update` an update.

## Surfaces

- **Web** (`/Journal`, Configuration menu): the global page with author/time/kind/product filters, an Operation column (Create / Update / Delete / Rollback badges plus the "rolled back" marker on undone writes), details modal (the record plus its undo group's before/after images), admin-only Rollback with the dry-run-backed confirmation dialog; the per-node Journal tabs show the same records for the node with the same operation badge on record-local derivations (see Known Limitations), and a Rollback button on rollbackable rows for admins.
- **REST**: `GET /api/v1/journal` (author/fromUtc/toUtc/kind/productId/entityId filters, limit ≤ 200 + offset), `GET /api/v1/journal/{recordId}` (record + undo-group details), `POST /api/v1/journal/{recordId}/rollback?force=&dryRun=` (admin owner only). The details' per-entry fan-out (the per-sensor images of a template write) is a PAGE (#1688): `fanoutOffset`/`fanoutLimit` query parameters select it (default the first 10, limit capped at 200 — every image grows the response linearly), `fanoutTotal` carries the honest count; the web details modal rides the ceiling with prev/next paging (200 images per fetch, both links stepping by the page limit — every fan-out node stays reachable before the admin-only Rollback; one offset pages every entry of the undo group at once, and an entry shorter than the current offset says "none on this page" instead of rendering an empty list). BEHAVIOUR CHANGE (#1688): a caller that sends no paging parameters now gets the first 10 images, not the whole fan-out — `fanoutTotal` names the full count; scripts that treated the default list as complete must page or raise the limit. `rollback` with `dryRun` stays compact regardless (a per-entity conflict list).
- **MCP**: `list_journal_records` (paged envelope), `get_journal_record` (the fan-out page rides `fanoutOffset`/`fanoutLimit` arguments, default bounded — #1688), `rollback_journal_record` (force/dryRun, admin owner only).
- **Internal (no external surface)**: the change-set store (`Databases/ChangeSets` LevelDB folder), `ChangeSetJournal`, `ChangeSetRecorder`, the rollback engine — reachable only through journal records.

## Primary Workflows

| # | Workflow | Initiator |
|---|---|---|
| 1 | Change configuration from any source; audit it in one journal | Operator/agent |
| 2 | Filter the global journal by author, time, kind or product | Operator/Viewer |
| 3 | Inspect a record: the change plus its undo group's before/after images | Operator (UI/API/MCP) |
| 4 | Roll back a record (refuses on conflicts with a diff; force overrides) | Admin (UI/API/MCP) |
| 5 | Redo a mistaken rollback by rolling back the rollback's own journal record (same entity, kind-tagged) | Admin |
| 6 | Audit what an agent/script did (author, time, kind filters) | Operator/Viewer |

## Known Limitations

- The global list scans the Changes-type records of the overlapping time shards and filters in memory (limit ≤ 200); the default window is 30 days.
- Records keyed by deleted entities resolve to the admin-only Global scope for sight filtering.
- The product filter narrows product-scoped records to the selected root product — the stamp narrows whether or not the product is still alive (a deleted product’s records never leak into another product’s filter); records with no root product of their own (global entities such as alert schedules, folder-scoped alert templates and folders, unscoped legacy rows) stay visible under any product filter (#1601) — a selected product must never make the page look empty while the journal holds non-product records.
- The MCP list tool pages exactly through the service (limit ≤ 200 per call, offset unlimited); there is no total count over the shard-walking scan — a short or empty page is the end of the stream.
- The product TTL POLICY list is authored through the API/MCP only — the web product form edits the inactivity-period SETTING (nodeSettings), not the policy list.
- Schedule-delete rollback semantics are the #1570 ones (per-node full lists plus the touched template rows), now reached through the journal record.
- The per-node Journal tab derives the operation badge from the record's own data only (rollback marker, property format, legacy enviroment wording) — the tab streams records without undo-group access, so policy rows, whose operation lives on the group entry, render no operation badge there, and no "rolled back" marker exists on the tab; the global page (one group read per distinct group of the page) names both.
- Operation tags are derived, not backfilled: rows written before #1638 render whatever their stored data says. Template/schedule ROLLBACK rows written before the marker (their enviroment read "Alert template"/"Alert schedule", their property the compensating operation) render as that compensating operation — an update/delete, not a rollback; and the pre-#1638 recorder stamped forked policy rows with the same "Rollback" enviroment as true rollback rows, so those render as rollbacks. Both populations stop growing with #1638; the rows themselves are indistinguishable after the fact.
- A storage key is (entity id, ticks, record type) and the append is a plain put. The chat and server-settings writer (`JournalAppender`, #1828) reserves a block of successive ticks per write — at the wall clock, or right after the previous block when the clock has not moved that far — because on Windows the wall clock keeps one value for about a millisecond (18 distinct values over 20,000 consecutive reads on a development machine); a dozen records of one write are then stamped up to a few microseconds ahead of the clock. The older writers still stamp with the raw wall clock: two of their records of ONE entity written inside the clock's resolution share a key and only the last survives. #1828 does not change them.
- The change list of a chat update is the diff of two snapshots taken without a lock, like the update itself: two writers racing on one chat can both record the field the other changed.
- `serverSettings` names a kind, not a writer: today only the Telegram bot settings leave records of it (#1828). The other sections of the Configuration page — server port and certificate, agent, backup, self-monitoring — still leave no journal record, whatever the kind filter offers.
