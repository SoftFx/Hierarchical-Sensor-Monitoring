# Feature: Alerts

> Owner: server | Last reviewed: 2026-09-24 | Canonical: yes
> Scope: Server-side alert ownership, creation paths, and the boundary between global (template) and per-sensor alerts.

---

## Overview

HSM alerts are server-side rules that evaluate sensor state and produce notifications or icon changes. There are two ways an alert ends up attached to a sensor:

1. **Global alerts (AlertTemplate)** — wildcard-path + folder-scoped templates that auto-apply policies to every matching sensor. This is the canonical mechanism for non-leaf alerting. Managed from `Views/AlertTemplates/Index.cshtml` and `AlertTemplatesController`.
2. **Per-sensor editor** — the `_Alerts.cshtml` partial rendered inside `_MetaInfo.cshtml` for a selected sensor. Managed through `HomeController.UpdateSensorInfo` and the `AddDataPolicy` / `AddAlertCondition` / `AddAlertAction` partial builders.

Per-node (Folder/Product) alert creation is **removed** as of issue #1142. Templates are the only supported path for alerting scenarios that previously used per-node alerts. The per-sensor editor remains in place because sensors own their runtime state and templates materialize onto sensors.

As of issue #1159 the editor exposes a single "Add" entry point: Inactivity Period is selectable as a condition property (`AlertProperty.TimeToLive`) inside the regular alert editor and the Alert Templates editor. The dedicated "Add Inactivity Period" link and TTL section are removed. Storage semantics are unchanged — the form collection JS routes each row to `DataAlerts[255]` when its main condition is TTL, and the controller's existing split persists it as `TTLPolicy`.

## Invariants

- **TTL evaluation is schedule-aware at EVALUATION TIME (#1404)**:
  - A TTL policy with an alert schedule gates its expiry decision on `IsWorkingTime(ScheduleId, DateTime.UtcNow)` — never on the stale value's timestamp (the restart incident: a value in-session at session end, no OffTime because the server was down, fired on the first sweep after boot).
  - The gate also RESOLVES the sensor on the first out-of-window sweep (`SetExpiredSnapshot` fires on the transition), so a session close without OffTime ends the alert instead of firing into the night; at window open a still-stale value fires a fresh alert.
  - Schedule-less policies have no gate (unchanged), and in a mixed sensor the sensor-level state follows ANY timing policy — a scheduled policy merely stops contributing out-of-window.
  - The transition arm (`SetExpiredSnapshot`'s notification loop) carries the same gate on the FIRE side: when a schedule-less sibling flips a mixed sensor while the scheduled policy is out-of-window, that policy's alert is CANCELLED silently (state reset, no send) instead of leaking out-of-window — so the mixed-sensor silence holds on the transition path, not only on the repeat path.
- **The WINDOW PREDICATE is evaluated ONCE, at one captured instant (#1404)** — both sweep halves participate:
  - `SensorTimeout` computes the per-policy in-window decisions from a single `DateTime.UtcNow` captured at the start of the pass and passes that instant (together with the value it judged) through `SensorExpired` to `SetExpiredSnapshot`, whose notification gate reuses it via `TTLPolicy.IsOutsideSchedule(provider, evaluationTime)` instead of recomputing. `SetExpiredSnapshot` additionally MATERIALIZES the per-policy (outside, stale) decisions in one pass before both consumers — the sensor-global cause and the per-policy gate — so a `SaveSchedule` landing mid-transition cannot make them read different schedule definitions for the same instant, and the provider's process-wide lock is taken once per policy per transition instead of twice.
  - The resend half participates too: `RunSensorTimeoutStep` captures one instant for the whole resend pass; its window predicate and the repeat-interval comparison inside `TTLPolicy.ShouldResend` read it instead of fresh `UtcNow`s.
  - SCOPE of the invariant — the window predicate only. STALENESS is not pinned to the captured instant: `TTLPolicy.IsStale` delegates to `TimeIntervalModel.TimeIsUp`, which reads `DateTime.UtcNow` internally; threading the evaluation instant into it would ripple through a shared model used everywhere for no known gain. The drift between two staleness reads is microseconds and only affects comparisons between different policies; no concrete misbehaviour is known.
  - A sweep straddling a minute boundary that is also a window boundary must not split the decision from its notification (an alert message with no UI entry, or a UI entry that never sends).
  - The same reasoning forbids "unifying" the TTL gates with the regular data-policy gate in `SensorPolicyCollection`: the data-policy gate is deliberately VALUE-TIME (the value IS the event there — an old value arriving out-of-window is judged by its own timestamp), while the TTL gates are EVALUATION-time (a stale in-session value must not fire when "now" is outside the window). Either unification re-breaks #1404.
- **TTL repeats are CANCELLED per-policy outside the schedule window (#1405)**:
  - The sweep's resend step is an explicit per-policy state machine with NO hidden writes: `RunSensorTimeoutStep` cancels an out-of-window timed-out policy itself (`CancelNotification` — clock and counter reset, so a window open with a still-stale value fires a FRESH send at once instead of resuming yesterday's cadence) and consults the PURE `TTLPolicy.ShouldResend` (never-sent bypass, then the repeat cadence) only for policies already established as timed-out and in-window. A second caller of `ShouldResend` can never silently reset an operator-visible clock.
  - The fresh send at window open holds for EVERY repeat mode, the DEFAULT `Immediately` included: for SCHEDULED policies the never-sent branch (null repeat clock) answers BEFORE the repeat-mode gate (`Schedule.IsActive` is false for `Immediately`), because on a mixed sensor flipped out-of-window by a schedule-less sibling there is no second sensor transition at window open — the resend arm is the only delivery path left, and gating it on the repeat mode lost the alert forever while the UI kept showing it active (#1405).
  - The bypass is scoped to scheduled policies because a null clock on them is produced only by the cancellation and resolution paths (both leave the sensor unexpired, so the next expiry re-arms the clock through the transition before the resend loop runs); SCHEDULE-LESS policies keep the master order — the repeat-mode gate answers first, so `Immediately` never delivers from the resend loop for them.
  - Cancellation is per-policy because the schedule is per-ALERT while OffTime is sensor-wide (never fabricated here); a scheduled policy goes silent in a mixed sensor while its schedule-less siblings keep their cadence, and a per-policy window close sends NO farewell — resolution notifications come only from the sensor-level transition.
  - The two gates are inseparable: the #1404 gate resolves the sensor out-of-window, the resolution resets the repeat clock, and without the #1405 window arm the "never sent" branch would send on EVERY sweep tick outside the window (the zombie).
  - Tolerated race, unchanged: the notification state pair (`_lastTTLNotificationTime`, `_notifyCount`) is written from two threads (the sweep via `SetExpiredSnapshot`, the API thread via `TryAddValue -> SensorTimeout`) without a lock — worst case one duplicate notification; the unsynchronized read-modify-write is the established trade-off (cf. the #1296 notes in `BaseSensorModelT`).
- **Window-caused resolutions are SILENT; genuine recoveries still send the Ok (#1404/#1405)**:
  - RULE: a resolution with NO new data since the sensor expired suppresses EVERY policy's Ok (cancel, no send); a resolution WITH new data sends the Ok for every policy that passes its own fire-arm gate, out-of-window included. The discriminator — `windowCaused = !timeout && !newDataArrived && ttlSnapshot.Any(t => t.ScheduleId.HasValue)` — is computed ONCE, before the notification loop, SENSOR-GLOBALLY.
  - The witness for "new data arrived" is SERVER-SIDE on QUEUE ORDER (#1452), immune to the client clock skew of value `Time` (batched/bar sends arriving minutes "behind" the wall clock): every update-queue item receives a monotone dispatch sequence when its processing starts, the expiry transition stamps `BaseSensorModel.LastExpirySequence` with it, the item that delivers a value stamps the value's `DeliverySequence` (`BaseValue`, in-memory only — never persisted, never on the wire), and `newDataArrived` compares the evaluated value's sequence against the expiry's. The value item and the expiry's sweep item travel the SAME single-reader product queue, so "the value was delivered after the expiry decision" is exact. The pre-#1452 form compared the value's `ReceivingTime` against `LastExpiryAt` — two SERVER stamps taken at DIFFERENT pipeline stages (a value's `ReceivingTime` is stamped when the API thread converts it, before enqueue; `LastExpiryAt` when the sweep item runs, at dequeue), so a value that arrived and was enqueued BEHIND the sweep still carried an earlier stamp and its genuine recovery Ok was cancelled — a window of one sweep iteration plus queue backlog, centred exactly on the TTL boundary. `LastExpiryAt` survives as the "expiry with a judgeable value on record" gate (`null` -> genuine, below) and is ATOMIC (#1452): backed by a `long` ticks field (0 = none) published through `Volatile`, not `Nullable<DateTime>` — that is a 16-byte has-flag + ticks pair whose unsynchronized cross-thread write can tear into `HasValue == false` over a written instant (the discriminator reads GENUINE -> a false recovery Ok) or `HasValue == true` over a stale one (a wrong boundary). The cold-load path that restores `IsExpired` without a transition still seeds `LastExpiryAt` from the restored marker row's `ReceivingTime`; `LastExpirySequence` needs no seed — rows deserialized from history carry `DeliverySequence == 0`, which never reads as newer, and the first post-restart value arrives through a real queue item (sequence >= 1). Deliberately NOT the timeout marker's `ReceivingTime`: the marker-rewrite guard compares that server stamp against the CLIENT-stamped `sensor.LastUpdate`, so a lagging clock suppresses the rewrite and leaves the marker naming an EARLIER expiry — a discriminator keyed on the marker then read a value received after the first expiry (but before the second, whose marker was suppressed) as "new data" and re-delivered the schedule-less guard's false "recovered" Ok at session close. The round-4 discriminator before it ("is some out-of-window policy still stale for the evaluated value") had the mirror defect: it let the SHORTEST out-of-window TTL decide for the whole sensor and suppressed a longer schedule-less guard's genuine recovery Ok — an alert vanishing with no farewell.
  - No recorded expiry instant (expired with an empty cache — no transition with data ever ran) reads as GENUINE: the value in force at expiry is not observable then, and a false recovery Ok beats a lost one. The suppressed marker rewrite is NOT such a case anymore: the instant is recorded on the transition regardless of whether the marker write underneath went through.
  - Why "no new data" means window-caused — but only where a window EXISTS: a scheduled policy dropping out of its window is what flipped `anyTimeout` — the sensor did NOT recover, so no policy may claim it did. A schedule-less sibling is never out-of-window and would otherwise deliver a false "recovered" Ok at every session close on a mixed sensor whose guard TTL outlives the silence (scheduled TTL 5 min + schedule-less TTL 8 h: the session closes at 4 h of silence). The sibling still fires on its own later — when its own TTL elapses (schedule-less policies are never gated) or at the next window open. A TTL edited longer while the sensor is expired resolves through the same silent arm — equally "did not recover" — but ONLY on a sensor that owns at least one SCHEDULED TTL policy: on a sensor with no schedule at all a window cannot have caused a resolution, so its non-data resolutions (TTL edited longer past the silence, alert disabled or removed) keep their resolution Ok through the ordinary per-policy gate, as before #1404/#1405 — the chat alert closes.
  - The ordinary session close on a single-scheduled-TTL sensor, and the restart whose restored `IsExpired = true` resolves on the first out-of-window sweep, are both window-caused: the cancelled state fires a FRESH alert at the next window open.
  - Staleness is read INDEPENDENTLY of enablement (`TTLPolicy.IsStale`: "time since the last value exceeds the interval", regardless of `IsDisabled`; a policy with no interval resolving anywhere — TTL-from-parent with no parent — reads not stale, but one WITH a parent interval reads the parent's value and can be stale): a disabled scheduled policy can still be stale for its own gate, so disabling a fired TTL alert on an expired sensor does not turn the recovery arm into a false Ok. The FIRE gates (`HasTimeout` in `SensorTimeout` and the resend step) keep honoring `IsDisabled` — a disabled alert neither expires the sensor nor repeats.
  - The discriminator uses the EVALUATED value, not `sensor.LastValue`: on the data path the event fires before the value reaches Storage, so `LastValue` is still the previous value there.
  - Per-policy gate at the transition (the cause is NOT window-caused), one row per (timeout, outside, stale) triple — `outside` = out-of-window at the shared evaluation instant, `stale` = the EVALUATED value is stale for THIS policy:

    | timeout | outside | stale | action |
    |---|---|---|---|
    | true | true | any | CANCEL silently — no alert leaks out-of-window; fires FRESH at the next window open |
    | true | false | any | send the TTL alert (the expiry transition) |
    | false | true | true | CANCEL silently — this policy's own terms still say dead |
    | false | true | false | send the recovery Ok — genuine, out-of-window included |
    | false | false | any | send the recovery Ok |

  - Accepted residual, stated plainly: the window-caused resolve still clears `IsExpired`, so the TREE shows the sensor healthy overnight while it is silent — the fresh alert at window open is the operator's signal; keeping the sensor visibly expired out-of-window would require gating the state flip itself, which is not taken here.
- **The policy-id index's read-modify-write is serialized, and the boot self-heals what the lock cannot cover (#1407)**: the global policy-id index (one LevelDB key, read-modify-write) is mutated only under a process-wide lock in `EnvironmentDatabaseWorker` — template applies run concurrently on per-product queue threads, and an unlocked interleaving used to lose one side's id forever (the row landed under its own key; the boot path `GetAllPolicies` walks the INDEX, so the load silently skipped the sensor's reference: a template alert that lived in memory until the next restart and vanished with no journal trace). Under the same lock sits an in-memory membership mirror with a strict discipline: it is seeded only from a read that can FAIL LOUDLY (a read error leaves it unseeded and retried on the next mutation — never seeded with a guess), and mutated only AFTER the durable index write it mirrors succeeds — in `RemovePolicy` deliberately ahead of the row delete, so a failed row delete leaves a stray, heal-absorbed row rather than a mirror still holding an id the index just lost — so a failed index write cannot desynchronize the mirror from the index; the write payload is built FROM the mirror, which also collapses any duplicate entries the index accumulated historically (a removal drops EVERY copy) and spares the per-add index re-read — each NEW id still pays one full-list serialize, so a bulk template apply remains O(N²) bytes through the single lock, a deliberate correctness-over-latency trade (a batched add is follow-up material). The lock guarantees the INDEX LIST is never lost-updated — no more, no less: policy ROW writes (`AddPolicy`/`UpdatePolicy`) stay outside it, so an add or update racing a removal of the SAME id can still resurrect a row with no index entry; the narrow window (per-product queue serialization makes same-id add-vs-remove rare) is deliberately left to the heal. The boot HEALS both pre-lock orphans and that residual: `PolicyIndexHealer` walks the sensor entities' policy-id references (keyed by the RAW reference string — the same key `ApplyPolicies` looks up; a non-canonical reference whose row is already indexed under the normalized key gains a raw-key alias without counting as a heal) and pulls rows the index missed directly by id (`IDatabaseCore.TryGetPolicy(Guid)`, the index-bypassing fetch that tells "absent" from "unreadable") — existing orphaned rows recover on the first boot after the fix, with no repair tooling and no boot-path writes (the index is left as-is; every boot heals again). A reference that resolves to NO row anywhere is a true orphan: the load still skips it, but logs a Warn with the (distinct, capped) ids — the difference between "alert vanished without a trace" and a diagnosable boot line; a row that cannot be READ is NOT an orphan — it is Error-logged as unread and retried on the next boot. KNOWN RESIDUAL: the sibling id-lists in `EnvironmentDatabaseWorker` (sensor ids via `UpdateSensorIdsList`, the product list, the access-key list) still use the same unlocked read-modify-write pattern — a lost sensor-id update would make a whole sensor (and its alerts) vanish at restart with no heal; #1407 deliberately scoped the fix to the policy index where the incident was diagnosed.

- **Journal coverage of TTL-alert removals (#1394)**: every path that removes a TTL policy leaves the same journal record a regular-policy removal does — `RemoveTTLPolicy` (template delete and stale-prune, initiator `AlertTemplate`) and the manual editor's full-list drop in `UpdateTTLs` both write the "Alert" removal record (old value → empty). One exception: a drop that the SAME `UpdateTTLs` call re-creates with identical content (`TTLPolicy.ToString()` comparison, id-free) journals NOTHING — the collector registers its TTL alerts with empty ids on every reconnect, which reads as drop + re-create, and journaling that pair would blame every collector restart for removing an alert that never went away (and double the journal volume on that path). Previously a TTL alert could vanish with NO journal trace at all — the exact mechanism behind "alert disappeared, journal shows only the creation".
- **Template apply failures surface, not swallow (#1394)**: `AddAlertTemplateAsync` returns `(false, error naming the products)` when a per-sensor apply fails to PERSIST — the sensor missing or the DB write throwing (`ApplyTemplateRequest.Error` carries the failure off the queue thread), or the reconcile itself throws. Per-policy VALIDATION noise with a successful persist (e.g. an AnyType template's Value condition on a bar sensor) stays a log line — it must not turn into a permanent 409 over a save that worked; a rejected policy is never created at all, and surfacing that without failing the persisted save is tracked by #1401. The REST POST/PUT answers 409; the template itself stays persisted and editable for retry — retry means PUT with the id, not a re-POST (a re-POST is rejected by the name-uniqueness check, and a create-path 409 discloses the server-generated id in `details.templateId` so the caller has it) — and a failed orphan-persist leaves memory UNTOUCHED so the retry still sees the orphans (the #1127 lesson, applied to the apply path).
- **The apply's add/update arm is report-only, not persist-first**: only the orphan arm reorders persistence ahead of memory. `TryUpdateSensor` still mutates the in-memory sensor first and persists the row after, so when that row write fails the new alert is live in memory (fires notifications, visible in the UI) but absent from the stored entity — gone after the next restart; the 409 reports it, and the retry (PUT re-apply) or any later successful persist heals it. This residual divergence is deliberate for now: `TryUpdateSensor` is the shared path of EVERY sensor update, and reordering it persist-first is a separate, higher-risk change — do not assume symmetry with the orphan arm.
- **Orphan-only TTL removals persist (#1394)**: when a template edit removes TTL entries such that the orphan removal is the ONLY delta, the sensor is still persisted — through the orphan branch's own persist-first write (entity stripped of orphans → `UpdateSensor` → only then memory + journal + `Revalidate` + view), NOT through the regular apply-update condition, which is unchanged and still skips a zero-delta update (previously the removal lived in memory and the alert RESURRECTED after a restart).
- **Schedule deletion detaches policy references (#1409)**: deleting a schedule nulls the `ScheduleId` on every policy that references it, so no dangling id survives (dangling ids fail open at evaluation, #1405, and log a missing-id error). Sub-rules:
  - *Entry and access*: schedule VIEWING is open to every authenticated user (page, table and editor partials, and the "Alert Schedules" nav entry — matching the schedule dropdowns in the alert editors, which product managers already read); schedule MUTATION is admin-only (`[AuthorizeIsAdmin]` on `SavePartial` and `Remove` individually — creating, editing and deleting global schedules is the same class of tree-wide/global mutation), and the UI matches the gate: the Add Schedule button and the per-row Edit/Remove actions (the whole Actions column) render ONLY for admins (`Context.User is User user && user.IsAdmin`, the Dashboards pattern), so a Manager sees the read-only page instead of buttons that answer a bare 401. `Remove` runs the detach unconditionally — there is deliberately NO existence guard (a guard made a retry after a partial detach a silent no-op, and an unparseable stored schedule — a row the loader SKIPS, i.e. a guaranteed dangling-id population — never enters the in-memory cache such a guard reads): when nothing references the id the walk dispatches no work at all, and the idempotent `DeleteSchedule` then purges the row, so an unparseable row is purged by a normal Remove after the detach pass cleared whatever in-memory references existed (policies carry the raw id regardless of the schedule's parseability). The `CancellationToken` from `HttpContext.RequestAborted` is threaded through the detach (product walk, sensor walk, template loop, chunk dispatch): a browser-side timeout stops the dispatch of further detach work (already-queued chunks still complete), and ONE cancellation event produces exactly ONE error entry — the first walk to observe the token returns immediately instead of every follow-up walk appending its own "cancelled during ..." line.
  - *Owners and per-arm mechanics*: every sensor policy (regular and TTL), every product TTL policy, and every alert template policy (regular `Policies` and `TtlEntries`) bound to the deleted schedule gets its `ScheduleId` nulled; the policy itself survives and degrades to schedule-less semantics (always in working time). Product entities build their full-list update ON the queue thread (`DetachAlertScheduleFromProductRequest` reads the live `product.Policies` there, so a TTL policy added between the pre-scan walk and execution is not silently dropped) and are routed to the product's ROOT product's queue (mirroring `RemoveChatsFromPoliciesAsync`). Sensors are batched per ROOT product in chunks of ~100 (`DetachSensorsChunkSize`): one queue round-trip per chunk instead of one per sensor, and the chunks of one root are dispatched SEQUENTIALLY — each chunk is awaited before the next is enqueued, because the bounded queue channel accepts writes synchronously while capacity is free, so eagerly created chunk tasks filled the queue back-to-back and a concurrent ingestion item landed behind every chunk anyway; sequential per-root dispatch is what actually lets `AddSensorValueAsync` (the same queue) slot in between chunks, while different roots still drain in parallel and a chunk's hold time stays bounded by its size. When the pre-scan finds no matching sensor, product or template, no queue item is built at all. Templates are detached PERSIST-FIRST through the failure-propagating `UpdateAlertTemplate` (the detached entity is built WITHOUT touching the live model; only on a successful write are the in-memory ids nulled — a surviving template would otherwise re-mint the dangling id on every new matching sensor and re-attach it on the next template save). TTL intervals are re-asserted explicitly on the detach update (a null `TTL` in full-list semantics is an explicit FromParent reset, so without this every TTL policy on an affected entity would silently lose its interval; an explicit Never/`long.MaxValue` interval degrades to FromParent — the same mapping `TTLPolicy.FullUpdate` applies everywhere; NOT reachable through the web editors, but the management API accepts `ttls[i].interval = 0` (`TimeInterval.None` → `long.MaxValue` ticks), where the degrade applies equally, including at template-apply time).
  - *Ordering and completion contract*: the detach runs BEFORE `DeleteSchedule` and reports completion through a `TaskResult` (`DetachAlertScheduleFromPoliciesAsync` never throws): `Ok` only when every referenced entity was detached. On ANY incomplete detach — a request abort, a per-entity queue failure, a HARD sensor or template persist failure, or the caller-thread walk blowing up — `DeleteSchedule` is SKIPPED: deleting the schedule would strand the surviving references permanently (nothing left to Remove), while the live schedule keeps the retry meaningful — `Remove` again re-runs the idempotent detach over the survivors, and a process crash between the two calls leaves the same recoverable state. Per-sensor failures are SPLIT by the `TryUpdateSensor` return value: a HARD failure (the sensor gone, the update throwing, or the DB write failing — the failures the queue handler would otherwise swallow travel out through the chunk request's error bag) marks the detach incomplete; a SOFT failure (`TryUpdateSensor == true` with a non-empty error — the update was applied and persisted but a per-policy rebuild failed, validation noise of the "AnyType Value condition re-asserted on a bar sensor" class) is Warn-logged with sensor and schedule context and does NOT block the deletion, because a deterministic noise policy would otherwise make the schedule permanently undeletable with no override — whatever reference the noisy policy keeps degrades to the fail-open lookup (#1405) plus the throttled missing-id report. Per-template persist failures always block (they leave that template's memory untouched so the retry re-runs it). The failure is flashed on the schedules page (cookie `TempData` error, the same pattern as `AlertTemplatesController.Remove`) as a FLAT, two-way-capped aggregate: per-root chunk errors fold into ONE wrapping level (no nested "did not complete (...)" per root), and the final string is capped by item count (first five errors + "and N more") AND by a hard character budget of 1500 (`MaxDetachErrorCharacters` — a cookie is ~4 KB and `CookieTempDataProvider` silently DROPS an oversized flash, which would read as a clean page while the schedule was not deleted); everything beyond both caps points at the per-entity detail, which is Error-logged inside the detach with schedule/product/sensor context. Residual: the sensor arm is memory-first (the `TryUpdateSensor` shape, see the apply arm above) — a failed sensor persist clears the id in memory while storage keeps it, so an in-process retry walk sees nothing until a restart reloads the stored row; keeping the schedule alive preserves exactly that recovery path, and until then the throttled report and fail-open below backstop the stored id.
  - *Ownership and journal*: the detach writes NO journal record, by design of the change journal: it compares each policy's rendered content (`Policy.ToString()`, which does not include `ScheduleId`), and a detach changes no rendered field. Ownership follows the same rule through an explicit opt-out, NOT a rendered-content compare on the shared path: the detach's updates carry `PolicyUpdate.PreserveChangeOwnership`, and `BaseNodeModel.Update` skips re-stamping the change-table owner only for updates carrying that flag — every other full-list update (UI saves, collector re-registration, template applies) stamps its targeted policies unconditionally, exactly as before #1409, so edits the change journal does not render (e.g. a chat-only `Destination` edit on a template-cleared TTL alert) still transfer ownership. A hand-edited User-owned TTL policy on an affected entity keeps its owner across a detach, and a later template apply stays blocked by the `CanChange` gate instead of silently overwriting it. The acting operator is also not recorded — the mutation runs under the system-force initiator `DetachAlertSchedule`, which is REQUIRED to reach template-owned policies (a plain user initiator is limited to enable/disable on those).
  - *Residuals, deliberate*: ids that already dangle from BEFORE this change (in policies or stored templates) are not retroactively cleaned — `AlertScheduleProvider.IsWorkingTime` still fails open on a missing id (#1405) and reports it at most once per id per HOUR (`MissingScheduleReportInterval`; a re-saved schedule re-arms the report immediately) instead of one ERROR per scheduled policy per sweep. The throttle timestamp is `Environment.TickCount64` (monotonic — a backwards wall-clock jump must not mute the report) and the entry is pruned by the provider's cleanup timer once older than twice the current interval. An operator's template save can still interleave with the template detach (`AddAlertTemplateAsync` REPLACES the dictionary entry rather than mutating the live model): the detach re-reads the dictionary entry immediately before each write and SKIPS the persist when the reference changed (the save's own persist is authoritative), so the interleaving window is collapsed to the single `Put` itself — not atomic, and a save landing inside that window can still restore the dangling id; the time-throttled report surfaces it and re-running the schedule delete re-runs the detach. The template walk also mutates LIVE template models on the HTTP request thread (deliberately NOT queue-dispatched — templates are not per-product entities): a sensor created DURING the walk can read a template via `ApplyTemplateToSensor` and mint a policy carrying a not-yet-nulled `ScheduleId` that the sensor arm's pre-scan already passed or has not reached; the `ReferenceEquals` re-read guard covers template SAVES, not reads, so the window stands (the detach then reports `Ok`, the schedule is deleted, and the minted reference dangles — same recovery as any post-delete dangling id: re-save the affected template/policy, see Known Issues) — backstopped by the same fail-open lookup and throttled report.
- The `_Alerts.cshtml` editor partial renders only when the selected node is a `SensorInfoViewModel`. `FolderInfoViewModel` and `ProductInfoViewModel` no longer render it.
- `HomeController.AddDataPolicy` and `HomeController.AddAlertAction` return `_emptyResult` for any entity id that is not in `_treeViewModel.Sensors`. Stale JS or direct POSTs against a product/folder id cannot create per-node policies.
- `HomeController.UpdateProductInfo` no longer parses `DataAlerts`; only TTL, description, history, self-destroy, and default-chats propagate from the form.
- The multi-edit TTL modal (`_MultiEditModal` / `HomeController.EditAlerts`) remains the supported way to bulk-set TTL across selected items.
- `AlertsController` (export/import) is preserved as-is.
- `ProductEntity.Policies` (the non-TTL persisted policy-id list on a product) is **dead at runtime**: `ProductModel(ProductEntity)` only loads `entity.TTLPolicies`, never `entity.Policies`. The field exists for backward-compatible deserialization only; a startup migration prunes it.
- A single "Add" entry point is exposed in both `_Alerts.cshtml` and `_AlertTemplate.cshtml`. "Inactivity Period" is one of the options in the regular condition property dropdown (added to every condition view model's `Properties` list). When a new alert is appended from `AddDataPolicy`, the property select is client-side flipped to `TimeToLive` and `.trigger('change')` runs the promote handler in `_ConditionBlock.cshtml` — so the default newly-added alert is TTL, with the interval picker shown and the action schedule restricted to repeat mode. The user can switch the property back to a regular value to demote the row.
- Each `dataAlertRow` carries a `data-alert-type` attribute (`255` for TTL, sensor type byte otherwise). The form collection JS (`_AlertsFormCollection.cshtml` partial, inlined into `_MetaInfo.cshtml` and `AlertTemplate.cshtml`) reads this attribute per row and routes field names to `DataAlerts[255][i]...` or `DataAlerts[sensorType][i]...` accordingly, with per-type counters keeping indices contiguous for the model binder. The attribute is read via jQuery `.attr()`, never `.data()` — `_ConditionBlock.cshtml` updates the attribute via `.attr()` on promote/demote, and jQuery's `.data()` cache is not invalidated by `.attr()`, so a `.data()` read after a `.attr()` write returns the stale pre-toggle value and routes the row to the wrong dictionary key.
- TTL alerts are single-condition: when the main condition's property is `AlertProperty.TimeToLive`, the `_ConditionBlock.cshtml` change handler removes any non-main conditions and hides the "add condition" button.
- The TTL demote path in `_ConditionBlock.cshtml` is a no-op inside an Any-template TTL container (`containerType == ttlKey`). Any templates only allow TTL alerts, so there is no concrete sensor type to demote to — the dropdown reverts to `TimeToLive` and the operation-refetch ajax is skipped, keeping the row routed as `TTLPolicy`. Without this guard the demote would set `data-alert-type` back to the container's key (which is also `ttlKey` for Any) but flip the visual state to regular, producing a row with a non-TTL property persisted as a malformed `TTLPolicy`.
- `ConditionViewModel.Property` defaults to `PropertiesItems.First()`. `AlertProperty.TimeToLive` is the last entry in every condition view model's `Properties` list (asserted by `ConditionViewModelPropertiesTests.DefaultProperty_IsNotTimeToLive`), so a freshly-created alert never defaults to TTL — the user must explicitly pick Inactivity Period.
- Alert Templates with a concrete sensor type validate at save time that no path template matches an existing sensor whose type differs from the template's selected type (#1210). `AlertTemplatesController.GetPathTypeMismatchErrors` queries `_cache.GetSensors(path, null, folderId)` without a type filter and surfaces a per-path field error on `PathTemplates` when a matched sensor's type differs. The check mirrors the type filter in `AlertTemplateModel.IsMatch` so anything flagged here would otherwise be silently skipped at apply time. AnyType templates skip the check (they match every type by design); path templates with no current matches stay allowed (future sensors). Applies to TTL-only templates with a concrete type too — `IsMatch` filters by type uniformly regardless of alert kind.
- As of #1207, a TTL alert reloaded from storage exposes the underlying sensor type's full regular property list in its main-condition dropdown (`TimeToLiveConditionViewModel(sensorType)` switches on `SensorType` and reuses the matching `*ConditionViewModel.SupportedProperties`). `null`, `SensorType.Boolean`, and Any-template (`Type == AnyType`) fall back to the Common subset (`Status`/`Comment`/`New data`/`Inactivity Period`). The sensor type is threaded from `SensorNodeViewModel.Type` at `BuildAlert(TTLPolicy, NodeViewModel)` time, and from `DataAlertTemplateViewModel.Type` for template TTL alerts. The dropdown is therefore never single-option, and the user can demote a saved TTL alert back to a regular condition. The `_ConditionBlock.cshtml` AJAX that refetches the operation partial after a property change uses `containerType` (the real sensor type from the parent container id) rather than `data-type` (which is `SensorType.Boolean` for TTL alerts), so demote fetches the correct typed operation list.

## Storage / Persistence

- `PolicyEntity` rows live in a single LevelDB table keyed by `byte[] Id` (Guid). The `"NewPolicyIds"` index lists all known ids.
- `PolicyDestinationEntity` (nested in `PolicyEntity.cs`) keeps a legacy `string Kind` field for read-tolerant deserialization of pre-refactor rows, but the field is no longer written or consulted (the heterogeneous-destinations refactor dropped the top-level discriminator). `PolicyDestination.Chats` is a heterogeneous `Dictionary<Guid, string>` — one action can target both Telegram chats and Slack destinations simultaneously; each id resolves to its channel via manager lookup at delivery time. Notification delivery lives behind the `INotificationChannel` seam — see `features/server/notifications/feature.md`.
- The destination picker in `_ActionBlock.cshtml` is folder-scoped: a single heterogeneous `ActionViewModel.AvailableChats` (`HashSet<Guid>`) holds both Telegram chat ids and Slack destination ids bound to the folder of the sensor, **plus** all global chats (chats/destinations with zero folder bindings). It is derived from `folder.Chats ∪ {chats with Folders.Count == 0}` via `NodeExtensions.TryGetChats`. Global chats appear in every folder's picker; explicit bindings narrow delivery to only those folders. Existing alert policies with ids that are no longer folder-bound still **deliver** (delivery resolves through the manager directly, not via `AvailableChats`), but those ids won't render as selected options in the UI until re-bound. See `features/server/notifications/feature.md` for the folder-binding wiring.
- Default destinations (`DefaultChats`) on folders/products/nodes are heterogeneous: one mode + one heterogeneous id list per node. A single `FromParent` walk resolves Telegram chats and Slack destinations simultaneously through the unified `Settings.DefaultChats.CurValue`. The picker label reads "Chat(s)". See `features/server/notifications/feature.md` for the heterogeneous default-chats plumbing.
- `BaseNodeEntity.Policies` (a `List<string>` of stringified Guids) exists on every Product and Sensor entity. At runtime, only `SensorEntity.Policies` is loaded into the in-memory `SensorPolicyCollection`. `ProductEntity.Policies` is **never read** into `ProductModel` — only `TTLPolicies` is.
- Template-derived policies carry non-null `TemplateId` / `TemplateAlertId`; user-added policies have `TemplateId == null`.
- `TreeValuesCache.CleanupProductOwnedPolicies` runs once at startup (`Initialize()`, after `ApplyProducts`) and deletes any `PolicyEntity` referenced by `ProductEntity.Policies` whose `TemplateId == null`, then prunes the dangling references from the list. The migration is idempotent: a second run finds an empty list and writes nothing.

## Tests

Coverage for the schedule-window semantics (#1404 + #1405) lives in two suites. `src/tests/HSMServer.Core.Tests/Model/Policies/TtlScheduleWindowTests.cs` (next to the other policy unit tests — it touches no cache) pins the DECISION layer (`SensorPolicyCollection` / `TTLPolicy`) with a mocked schedule provider that DISCRIMINATES on the timestamp — the stale in-session value always reads in-window, so a value-time gate passes where the evaluation-time gate must not; the incident's exact shape:

- Expiry: out-of-window-now does not expire / in-window-now expires / no schedule expires regardless / mixed sensor — scheduled silent (asserted on `PolicyResult.Alerts` too: the scheduled id is absent, the schedule-less id present), schedule-less fires.
- Staleness vs enablement: a DISABLED policy with an elapsed interval is still STALE (`IsStale` ignores `IsDisabled` — the resolution discriminator's read) while `HasTimeout` keeps honoring it (a disabled alert neither fires nor repeats); a TTL-less (`IsTTLFromParent`) policy is never stale.
- Repeats (against the SPLIT state-machine seams: the sweep's cancel arm + the pure `ShouldResend`): the cancellation is REAL (window open fires fresh despite the 1-minute-old send — a pause would still be inside the 5-minute interval); the same fresh-at-open hold for the DEFAULT `Immediately` mode (the never-sent bypass outranks the repeat-mode gate for scheduled policies); in-window interval held; schedule-less policies are never out-of-window (the cancel arm is unreachable) and schedule-less `Immediately` NEVER delivers from the resend loop even with a nulled clock (the bypass is scheduled-only); a FRESH value skips the step at its first arm, `HasTimeout` (the data decides); mixed resend — the scheduled policy hits the cancel arm while the schedule-less sibling keeps its cadence. The interval comparison reads the CALLER'S captured instant (the sweep threads it in — one evaluation instant per pass).
- The zombie pin: after the sensor resolves out-of-window (`GetNotification(false)` nulls the repeat clock), the null clock WOULD fire in-window (the bypass) — which is exactly why the sweep's window arm must answer first; the out-of-window silence itself is structural (cancel-and-continue) and pinned end-to-end by the integration suite.

`TtlScheduleWindowIntegrationTests.cs` pins the TRANSITION layer on the real cache wiring (real `TreeValuesCache` with `SensorExpired -> SetExpiredSnapshot`, real `AlertScheduleProvider` whose window flips through `SaveSchedule`); sweep steps run through the cache's `RunSensorTimeoutStep` — the same internal method the production sweep calls, not a test copy:

- Window closed, mixed sensor: the schedule-less policy's timeout flips the sensor, the timeout marker is written, the scheduled policy NEVER notifies (cancelled at the transition — the mixed-sensor silence holds on the fire arm), the schedule-less sibling fires exactly once.
- Window closed then OPEN, mixed sensor with the DEFAULT `Immediately` repeat: the cancelled scheduled policy FIRES at the window-open sweep (`RetryCount == 0` via the sweep's resend step on the real cache wiring) — the first delivery does not live behind the repeat-mode gate.
- Window open then CLOSED with data resumed: the transition fired the alert in-window; the fresh value resolves the sensor on the data path, resets the repeat clock, and the recovery Ok IS sent out-of-window (the genuine-recovery negative control — only window-caused resolutions are silent). Async ingestion is awaited by POLLING, never by fixed sleeps.
- Window close on a mixed sensor, data resuming with a SKEWED CLOCK (the value's `Time` is 30 s behind the wall clock; the sensor is seeded 60 s stale so the resumed value is 30 s NEWER than the one in storage and actually LANDS — asserted by an explicit `LastValue.Time` precondition, the earlier 10 s seed let storage's newest-wins guard silently discard the resumed value and the assertions inspect the original one): the resolution is a GENUINE recovery — the guard's Ok IS sent, the scheduled policy is cancelled on its OWN terms (outside and stale) — pinning the expiry-instant discriminator against the shortest-scheduled-TTL misclassification.
- Window close ALONE on a scheduled policy (the ordinary session close, no fresh data): the first out-of-window sweep resolves the sensor SILENTLY — no recovery Ok message for the still-silent sensor (asserted on the cache's `NewAlertMessageEvent`, the pipeline observable that distinguishes a sent Ok from a suppressed one — both leave `RetryCount` at -1) — and the next window open fires a FRESH alert.
- Window close on a mixed sensor with UNEQUAL guards (scheduled TTL shorter than a schedule-less sibling's, the session closing before the sibling's TTL is up): the window-caused resolution sends NO Ok for EITHER policy — the sibling does not claim a recovery for a still-silent sensor — the sibling still fires when its own guard elapses (out-of-window: schedule-less policies are never gated), and the scheduled one fires FRESH at the next window open. Second-scale TTLs keep the run short (initial staleness 10 s, scheduled 8 s, guard 25 s — ~15 s of headroom for the async ingestion + sweeps + the `SaveSchedule` LevelDB write before the resolve, and ~15 s of wait for the guard; the earlier 14 s guard left only ~4 s and flaked on a loaded agent, the 90/120 shape before it cost ~30 s); the sweep is polled through the shipped step.
- Window close on a mixed sensor whose value `Time` LAGS its `ReceivingTime` ACROSS TWO EXPIRIES (the lagging-clock scenario: value 30 s behind the wall clock; after the first expiry a lagging resume resolves genuinely, the collector stops, the scheduled TTL is edited shorter to force the re-expiry, whose marker rewrite the marker guard SUPPRESSES — asserted: `LastTimeout` still names the first marker): the window close resolves the sensor with NO data after the second expiry, and the schedule-less guard stays SILENT — the transition-recorded `LastExpiryAt` witness is what keeps the marker's stale identity from re-opening the false "recovered" Ok.
- A recovery value INGESTED BEFORE THE SWEEP but DELIVERED AFTER IT (the #1452 stamp-stage asymmetry, made deterministic: the value's `ReceivingTime` predates the expiry's `LastExpiryAt` — as it does for any value enqueued behind the sweep — while its `DeliverySequence` names an item ordered after the sweep's; the public entry stamps `ReceivingTime` inside the same call that enqueues, so the value is constructed directly and the sequence is stamped exactly as the queue dispatch would): the queue-order discriminator reads the resolution as a GENUINE recovery and the Ok IS SENT — red under the pre-#1452 wall-clock comparison.
- TTL edited longer on an EXPIRED SCHEDULE-LESS sensor (the default shape — a single TTL alert, no schedule anywhere): the longer interval makes the last value fresh, `BaseNodeModel.Update`'s `CheckTimeout` resolves the sensor, and the resolution Ok IS SENT — a window cannot have caused a resolution where no schedule exists, so the silent arm does not apply and the chat alert closes.

## Known Issues / Limitations

- `ProductInfoViewModel.DataAlerts` is still populated but never posted from the form; cleanup deferred to avoid rippling into import/export.
- Switching a template's sensor type after adding alerts empties the unified alerts container (existing behavior for regular alerts; as of #1159 this also clears any TTL rows mixed in). Type changes are rare in practice; preserving TTL across type changes would require splitting the container.
- Demoting a TTL alert (loaded from storage) to a regular alert via the property dropdown does not restore the schedule's "starting at" / "instant send" fields. Those fields are gated server-side by `Model.IsTtl` in `_ActionBlock.cshtml` and never render for TTL rows, so the client cannot show them after demote. Regular-to-TTL-to-regular works correctly because the fields exist in the DOM and are only hidden+disabled by the `.ttlAction` class on `.fullAction`. Workaround: save and reopen the editor.
- Dangling schedule ids created BEFORE #1409 (deletions that predate the detach) persist in stored policies and stored alert templates until the operator re-saves the affected entity; between hourly reports they are silent and evaluate as always-in-working-time.
