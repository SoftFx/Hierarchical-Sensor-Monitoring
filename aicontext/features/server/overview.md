# HSMServer Overview

> Owner: server | Last reviewed: 2026-05-26 | Canonical: yes

## Purpose

HSMServer is the central ASP.NET Core 8.0 MVC application that receives sensor data from DataCollector instances, stores history in LevelDB, and provides a web dashboard for visualization, alerting, and management.

## Architecture

```
Browser                DataCollector
    |                                    |
    v                                    v
HSMServer (ASP.NET Core MVC)     API Controllers (/api/sensors/*)
    |                                    |
    +-- Views (Razor + TS/Webpack)       +-- TreeValuesCache
    +-- Controllers (MVC + API)          +-- UpdatesQueue (Channel-based)
    +-- BackgroundServices               +-- BaseSensorModel<T>
    +-- ConcurrentStorage<T>             +-- Policies (TTL, alerts)
    |                                    |
    +------------ LevelDB ---------------+
```

## Key Components

### TreeValuesCache
In-memory tree of Products -> Nodes -> Sensors. Source of truth for current sensor state. Backed by LevelDB for persistence across restarts.

A sensor's path is not stored: it is the chain of node names from the root product down (`BaseNodeModel.Path`, root-relative), built from each entity's parent id and `DisplayName`. Ingestion finds a sensor through an index from that path to the sensor, one per root product (`CachedValue.Sensors`, keyed by the root's id), filled when the tree is loaded and kept by sensor creation, removal and move. A name that is a path segment therefore changes only together with the index: a sensor is renamed by a sensor move, and a node below the root is never renamed (`UpdateProductAsync` refuses it, see `sensor-move/feature.md`). A root product's name is no part of a root-relative path, so a root rename leaves the index as it is. The full path does change, for every sensor of the product at once, so the rename re-evaluates their alert templates and offers them to the dashboard subscriptions (a root's change of folder, the other thing templates and subscriptions match, does the same), and the by-name index of root products (`_productsByName`) follows the name the model took; the self-monitoring product, which the server finds by its name, is not renamed (see the same doc).

### UpdatesQueue
`System.Threading.Channels`-based async queue for processing incoming sensor value updates. Decouples HTTP request handling from sensor model updates.

A request the queue or its handler fails on with an exception comes back to the caller as an error result, not as an exception. For a sensor registration the cache sorts that result into a fault and a refusal (`TreeValuesCache.AddOrUpdateSensorAsync`, `TaskResult.IsFault`, #1756): an exception of the queue and a failed write of the sensor's row to the store are faults, which the Sensor API answers `500` so that a collector sends the registration again; the other callers of the cache do not read the mark. What the handler finds wrong once it runs (a product or a sensor that is not there, an exception while the settings are applied in memory) is logged and answered as applied, as before. A write the LevelDB layer fails on is caught and logged there and not thrown; the registration path alone asks the store for the outcome (`IDatabaseCore.AddSensorChecked` / `UpdateSensorChecked`) and takes a reported failure as a fault, every other caller writes with the void methods and is not told. A registration forwarded through an alias to another root product's queue is sorted by the same rule: its outcome there is awaited outside any queue (`ForwardedRegistration`), never by the handler that forwards. The rule in full: `aicontext/features/api/wire-contract/feature.md` § Statuses of the registration routes.

### BaseSensorModel<T>
Typed sensor model. Manages:
- Last value and history
- TTL (time-to-live) expiration
- Alert policies and conditions
- Status computation

Initialization is expected before values are accepted. `Initialize()` loads history from LevelDB under a per-sensor lock and publishes its `_isInitialized` flag only once that load has **finished or failed** (#1296), so the three value-ingress gates — `TryAddValue`, `TryUpdateLastValue`, `CheckTimeout` — park on the lock instead of racing past on an empty `Storage`. Two limits the contract does not cover: a failed load latches as well and leaves an empty `Storage` (deliberate — one logged error beats a per-value retry storm against a broken database), and only those three gates wait; direct readers such as `LastValue`, `HasData`, or `Revalidate()` are unguarded and may observe a mid-load sensor.

**Invariant — nothing reached from inside a sensor's initialization lock may block.** This is the canonical statement; the code carries one-line pointers here rather than four copies of the reasoning.

Policy evaluation runs inside that lock and fans out well past a database read: `Policies.TryValidate` → `CalculateStorageResult` → `SensorTimeout` → `SensorExpired` → `TreeValuesCache.SetExpiredSnapshot`, and from there both `SensorUpdateView` → every `ChangeSensorEvent` subscriber (view-model updates in `TreeViewModel`, panel bookkeeping in `Dashboard`) and `SendNotification` → `ConfirmationManager` → alert dispatch. So the lock is held across up to three LevelDB reads plus all of that. None of those paths takes a blocking lock today, and none may start — in particular nothing there may wait on the `UpdatesQueue`, a `SingleReader` channel (`MaxQueueSize` 1000, `FullMode.Wait`) whose reader, parked on a sensor lock, back-pressures all the way to the HTTP ingest threads.

Why startup is nonetheless not serialized: **the lock is per-sensor**, so a waiter only ever blocks behind that one sensor's load. `Initialize()` is driven from several places at once — `FillSensorsData`, `CheckSensorsTimeout` → `CheckTimeout()` on each product's queue reader, `ProductModel.CheckTimeout()` from `BaseNodeModel.TryUpdate`, and the ingest path — so several sensors can be mid-load on several threads, and more than one reader can be parked at a time.

Worst case worth knowing (not new — `master` does the same loads): a product-settings save during startup runs `TryUpdate` → `ProductModel.CheckTimeout()` → a serial history load for every sensor in the product, on the caller's thread, and now also stalls that product's queue reader behind each in turn. Bounded, but it is the latency ceiling this change makes visible.

Direct `Storage` readers stay unguarded, with one now-guarded exception: `ShouldDestroy()` (#1328).

- **What changed:** `ShouldDestroy()` defers the decision (returns `false`) unless `IsHistoryLoaded` is true — meaning "history actually loaded", not "a load was attempted" (a failed load latches `_isInitialized` but never publishes; for such sensors self-destroy is disabled between the bounded retries below, logged at `Warn` by the sweep). The decision takes the **newest** of the signals available, never a priority chain:
    - with a cached value, the newest of `LastUpdate` and `Storage.To` — where `To` is the newest of the last real value's time (`Clear()` does not reset it) and the floor a history-load retry restored. `LastUpdate` alone was the hazard: on a sensor whose cache is empty — a retention purge, a full history clear, or a retried load, which restores the floor but never the cache — `AddValueBase` accepts the next value whatever its timestamp (its newest-wins guard has no `_lastValue` to compare against), so one out-of-order value from a reconnecting collector flipped `HasData` and hid the freshly restored floor behind its own old `LastUpdate`;
    - with an empty cache, the newest of the timeout marker's `.Time` and `Storage.To` — `_lastTimeout` is not advanced once a newer real value arrives (a later re-expiry writes no marker, because `SetExpiredSnapshot` requires `HasData`), so a stale marker must not shadow a fresher `To`;
    - `CreationDate` only when the sensor never received a value.

  `IsHistoryLoaded` therefore means "a load completed", not "Storage mirrors history" — for a retry-restored sensor it holds only the activity floor. Check `HistoryRestoredByRetry` before keying anything else (TTL revalidation, history reads, snapshot persistence) on it.
  The marker stays confined to the empty-cache case deliberately: `GetTimeoutValue` stamps `Time = UtcNow` when the **server observes** the silence, not when the sensor fell quiet, so after a maintenance window it carries the restart instant. As the last remaining signal that over-estimate is worth taking; as a floor under a sensor that still has a cached value it would postpone every quiet sensor's cleanup by the server's downtime. Pinned by `ShouldDestroy_CachedValueAndNewerMarker_JudgesOnTheValue`. The marker path is deliberately conservative: the marker's time over-estimates last activity by up to one TTL. `ShouldDestroy()` stays a pure predicate: no history load, no policy fan-out, no notifications. The sweep itself is self-sufficient for never-attempted sensors: it calls `Initialize()` on any self-destroy-enabled sensor that `CheckSensorsHistoryAsync` never reached (e.g. sensors lost to a product-name or sensor-path collision), with per-sensor exception isolation.
- **What it relies on:** `ClearDatabaseService.ServiceActionAsync` awaits `CheckSensorsHistoryAsync` (which initializes every sensor reachable through the cache, with per-sensor error isolation) before the self-destroy sweeps — pinned by `ClearDatabaseServiceTests`. The sweep logs deferred/failed-load/not-removed counts at `Warn` with id samples, and `CheckSensorsHistoryAsync` logs per-product `TaskResult` failures instead of discarding them.
- **Still open:** sensors registered after the history check in the same tick are deferred for one sweep; `HasData` remains a cache-occupancy signal used as "sensor ever had data". A failed load is retried only by the bounded seam below, and only for self-destroy-enabled sensors — a sensor with self-destroy off still needs a process restart to recover its in-memory history. And the `LastTimeout`/`Storage.To` fallbacks are in-memory only: after a restart they survive only if the backing rows still exist in the database — a sensor whose rows were purged falls back to `CreationDate` again (same data, different outcome depending on process lifetime). Residuals are tracked in #1344 (item 2 — the non-monotonic `LastTimeout`/`Storage.To` fallback — is carried by #1345).
- **Failed-load retry (#1344):** the `Initialize()` failure latch (anti-retry-storm, #1296) is rerun by `BaseSensorModel<T>.RetryFailedHistoryLoad(utcNow)`, called only from the self-destroy sweep and never from the per-value paths.
  - *Timing.* Both gates run on the caller-supplied clock (`utcNow` also stamps the attempt clock inside `LoadHistoryUnderLock`, so the two never compute across different timelines). The sweep reads that clock **per sensor**, not once for the pass: a sensor whose lazy `Initialize()` fails while the sweep is running stamps its attempt clock from the real clock, and an earlier snapshot would read as "overdue" and retry back-to-back against the database that just failed it. A stamp in the future is therefore suppressed, not treated as elapsed — and the gate re-anchors to the caller's clock, so a backwards system-clock step cannot park a sensor until the wall clock catches up. The **first** retry must clear `HistoryLoadFirstRetryDelay` (1h) measured from the **failure itself**, which is what keeps the sweep that just observed it — including the eager `Initialize()` of `CheckSensorsHistoryAsync` one await earlier in the same maintenance tick — from hitting the database back-to-back; the delay only has to exceed that pass's duration, so `ClearDatabaseService.Delay` being 1h too is a coincidence, not a coupling. Later retries back off from the previous retry: 2h, 4h, 8h, 16h, then a 24h cap, so a longer outage degrades gradually instead of jumping straight to a full day of disabled self-destroy, and a permanently broken database still settles at one attempt per sensor per day. A failure mid-interval waits up to 2h for its first retry.
  - *Per-sweep budget.* At most `MaxHistoryLoadRetriesPerSweep` charged retries per sweep: a whole-database outage latches many sensors at once, and the cap keeps the serial sweep from becoming a synchronized burst of throwing reads. Only retries that reached the database **and failed again** are charged — `RetryFailedHistoryLoad` returns a `HistoryLoadRetryResult` (`Suppressed` / `Failed` / `Loaded`) precisely so the sweep can tell them apart. Charging suppressed calls would let the sensors early in the (stable) enumeration order exhaust the cap sweep after sweep and permanently starve every sensor past it; charging successful ones would make a large latched set drain at 100 sensors per hour, though each of those retries is an ordinary read pair costing milliseconds. Capped-out sensors are picked up next sweep with no per-sensor budget consumed, and the sensors served this sweep are backed off for hours, so successive sweeps work through the whole latched set. What is deliberately **not** bounded is the post-recovery drain: the first sweep after the database returns does two synchronous LevelDB reads per latched sensor inline in the serial loop, which on a large tree stretches that one maintenance tick. Accepted — rationing cheap successful reads would leave self-destroy disabled for hours after everything is healthy.
  - *What a retry may write.* The mode is explicit (`LoadHistoryUnderLock(isRetry, utcNow)`), not inferred from `Storage`: a live sensor can have a null `LastValue` (timeout-only traffic, rejected values, retention purge), so "Storage looks empty" does not mean "no live ingestion". A retry leaves `_isInitialized` set, so ingestion keeps running lock-free against a `ValuesStorage` that is not safe for concurrent writes — it therefore writes only `Storage.SetLastActivity` (the `To` activity floor: its own field, single-writer under the sensor lock, merged into `To` at read time so live ingestion can outgrow it but never overwrite it) and `Cut(From)`. It never replays history into the cache and never runs the policy fan-out, which would reach `SensorExpired` → `SetExpiredSnapshot` → `TryAddValue` from the maintenance sweep. The floor takes a marker row's `.Time` and a real row's `.LastUpdateTime`, mirroring what `ShouldDestroy()` judges a cached value on (an aggregated row's `LastReceivingTime` can be days newer than its `Time`). Restoring it is not optional: a successful retry latches `_historyLoaded`, so a retry that restored nothing would let `ShouldDestroy()` fall through to `CreationDate` and delete an established sensor whose newest value is minutes old.
  - *Observability.* A successful retry drops the sensor out of the failed-load `Warn` line while its cache is still empty. `BaseSensorModel.HistoryRestoredByRetry` (retry-loaded **and** still no cached data) keeps it in a `Warn` line of its own. It is set only when the retry left the cache empty — a sensor that kept reporting through the outage is not degraded — and cleared by the first value ingestion **stores** — at the write, not by whoever reads the flag while the cache happens to be full — so a later retention pass or history clear cannot resurrect the warning for a sensor that recovered long ago. A timeout marker does not clear it: it leaves the cache empty. The sweep also spells out when `MaxHistoryLoadRetriesPerSweep` bound the pass instead of leaving an operator to infer it from the constant — otherwise a quiet sensor with a long self-destroy interval would sit degraded and unnamed for weeks.
  - *Residual limits.* A retried sensor's value cache, `LastTimeout`, `IsExpired` and TTL clocks are **not** restored (`_lastTimeout` belongs to lock-free ingestion; a second writer there could lose an update and regress the signal). Retry only fires for self-destroy-enabled sensors. For the rest a process restart is still needed, and the cost is more than an unrecovered cache: a latched sensor keeps `From == DateTime.MinValue`, so `CheckSensorHistory`'s `KeepHistory.TimeIsUp(From)` fires a redundant `ClearSensorHistory` on every hourly tick until restart (benign — the delete range comes from the policy, not from `From` — but after a mass outage it is thousands of no-op clears per hour). `Cut(first.Time)` on the retry path is exactly what repairs it, so widening the retry beyond self-destroy-enabled sensors is the natural follow-up; deliberately out of scope for #1344 item 1. A marker's `.Time` over-estimates last activity by up to one TTL, and the floor is stamped without validating the row, unlike the cold load, which skips a policy-rejected newest row. Every divergence points the same way: a retried sensor destroys later, never earlier, than a cleanly-loaded twin.
- **Verdict on the remaining unguarded readers** (`LastValue`, `LastDbValue`, `HasData` elsewhere, `LastUpdate`, `From`/`To`, `Result`, `Revalidate()`, `Cut()`, `Clear()`, #1325 inventory): none destroys data — they at worst show an empty/stale view during the startup window or act on it (e.g. a TTL revalidation against no last value is a no-op).

Changes around `TryAddValue`, `TryUpdateLastValue`, TTL, or policy loading should include tests for first-value initialization and timeout behavior.

**Aggregated values (`AggregateValues`).** A value equal to the cached last value (same value, status and comment; bars and files never compare equal) is folded into it instead of becoming a row: `BaseValue.TryAggregateValue` raises the last value's `LastReceivingTime` and `AggregatedValuesCount`, and the cache saves that row again under its own key time (the run's first value). A run ends at a different value, at a timeout marker, and at the **storage-week boundary** (Monday 00:00 UTC, `StorageWeek` in `HSMDatabase.AccessManager`, the same week that picks the history shard): `ValuesStorage.TryAggregateValue` folds only when the cached value and the incoming one fall in the same week, so the re-save never reaches a week that has ended. The first equal value of a new week is stored as a new row, as a differing value would be; alerts, TTL and `LastUpdate` see no difference, because policies are evaluated against the previous last value before the value is stored, and `LastUpdateTime` of the new row is that value's time. The rule also applies to an older equal value (the out-of-order fold): it folds into the cached value only from the same week, otherwise it is an out-of-order value of its own week. Rows written before this rule can span many weeks, so every reader that looks back for the start of a run (`IsBorderedValue` in clear history and retention, the page-read rewind, the out-of-order span probe) keeps doing so. Tests: `AggregateWeekBoundaryTests`.

### ConcurrentStorage<T>
Thread-safe in-memory storage pattern that syncs writes to LevelDB. Used for products, users, access keys, sensor configs.

### Background Services
- Data collection (self-monitoring)
- Database snapshots
- Data cleanup/retention (hourly `ClearDatabaseService`: history older than `KeepHistory`, sensors idle for longer than `SelfDestroy`, old empty nodes). A new root product and a new folder get `KeepHistory` and `SelfDestroy` = 3 months (`TreeValuesCache.DefaultRetention`, 1 month before 2026-11-25); the value is stored with them, so the default never changes an existing product or folder. A stored folder with no period still reads as 1 month.
  - **A calendar preset inherited from a folder (#1864).** A product whose `KeepHistory`, `SelfDestroy` or `TTL` is "from folder" holds a `TimeInterval.FromFolder` model. A period in ticks is inherited as its ticks; a calendar preset (1, 3, 6 months, 1 year, and 5 years since #1945) has no length in ticks and is inherited as itself, `TimeIntervalModel.FolderPreset` (stored as `FolderPreset` in the product's `TimeIntervalEntity`, omitted when null). Every reader evaluates `AppliedInterval` (the preset when there is one): `TimeIsUp` and `GetShiftedTime` use calendar arithmetic (`AddMonths`/`AddYears`) exactly as for the preset set on the node, so does the out-of-order history floor, `SelfDestroyIsActive` and the alias expiry; `TablePeriodClass` counts it by nominal length (5, 14, 27, 53, 261 weeks). Both ways a product comes to inherit build the preset: a change of the folder (`FolderManager.GetCoreUpdate` → `ToFromFolderModel`) and saving the product with "from folder" (`TimeIntervalViewModel.ToModel`). Before #1864 the first gave `FromFolder` with 0 ticks, which never expires (history kept for ever, idle sensors never removed, a table sensor kept for ever), and the second the preset's nominal length in ticks (31, 93, 186, 365 days instead of the calendar period). A product stored that way is re-derived from its folder's present setting by `FolderManager.Initialize` (`ResolveInheritedCalendarPresets`, as a `ServerMigration` update, one Info line per product) and stored with the preset; until then a `FromFolder` with 0 ticks is still "never". The same start also re-derives every product that holds a preset, whatever the folder says now (a folder change cut off before it reached the product, or a product the folder does not list, would otherwise keep clearing by a preset the folder no longer has); a product holding a preset whose folder is not found, or that is in no folder, has the preset dropped (`FromFolder` with 0 ticks, never expires, one Warn line). A model without a preset under a folder without one is left as it is, so a second start changes nothing. Whether a folder says a calendar preset is read from its model (`TimeIntervalViewModel.ToModel`, the value it stores), never from the view's interval: a custom period of exactly a preset's nominal length (31, 93, 186, 365 days) is stored as ticks, and `TimeIntervalViewModel.FromModel` reads such ticks as a custom period, not as the preset (it used to show them as "1 month" and the next save of the folder or node stored the calendar preset instead). Other effects of an applied inherited preset: a moved sensor's alias expires by it (`AliasExpired`; the alias-removal Info line names the interval, `FromFolder(Month)`), an inherited TTL preset raises TTL alerts, and an empty sub-node is removed after the calendar period rather than at once (`ClearEmptyNodesAsync` shifted by 0 ticks before). A product-level TTL alert "from parent" shows the inherited preset (`TimeToLiveAlertViewModel`). The first retention pass in a process that clears history, and the first self-destroy sweep that removes sensors, because of an inherited preset log one Info line per product with the sensor count (`TreeValuesCache.InheritedPresetCleared`). The product page always showed the folder's preset ("From parent (1 month)", resolved from the folder view); the journal now shows `FromFolder(Month)` instead of `FromFolder(00:00:00)`. Tests: `Folders/FolderCalendarPresetTests`.
  - **The 5-year preset (#1945).** "5 years" (offered for "Keep sensor history" only) is a calendar preset like the four above: `TimeInterval.FiveYears` in the core (1,577,664,000,000,000, the web enum's value: 1826 days, its nominal length), stored as itself, evaluated as `AddYears(5)` (`GetShiftedTime`, so the retention pass, the out-of-order history floor and the large-file floor), inherited from a folder as `FolderPreset` and re-derived at start like the others, and a table sensor's class is 261 weeks. Before #1945 it was neither static nor dynamic in `TimeIntervalViewModel.ToModel` and fell through to the inheritance branch: a folder, a product in no folder and a sensor set to 5 years stored `FromParent` with 0 ticks, a product in a folder stored "from folder" with the folder's value. So on a folder and a product it never applied (never expires, or the folder's period), and on a sensor it took the product's period, which could clear history younger than five years. A custom period of 1826 days (the collectors' `KeepHistory` of their version sensors, 365 * 5 + 1 days) stays ticks and is shown as a custom period: before #1945 it was shown as "5 years" and the next save of the sensor's page stored `FromParent`. **Stored values are not converted (a known limitation):** a 5-year choice saved by a server before #1945 is stored as exactly the bytes of a real "from parent" (`{"Interval":-10,"Ticks":0}`) or "from folder"; nothing tells them apart (the journal recorded the change as "From Parent" too), and a guessed conversion would delete history that may have been meant to be kept for ever, which cannot be undone. Such a node keeps what it does today (a folder: its products inherit `FromFolder` with 0 ticks, never expires; a product in no folder: never expires; a sensor: its product's period) until its owner sets "5 years" again. Pinned in `Folders/FolderCalendarPresetTests` (`FiveYears_*`, `StoredFromParent_*`, `FromParentWithZeroTicks_*`, `TicksOf1826Days_*`). **A setting with nothing to inherit from, stored as `FromParent`** (a folder's, or a product's in no folder: an old 5-year choice, or any other value left as `FromParent`) never expires. Its select has no "from parent" item (the view removes it when there is no parent), so up to 3.46.0 no option matched the stored value, the browser showed the first one ("1 week" for Keep sensor history, "Never" for the others) and an unchanged save of the folder or product form stored it: a week of history, the rest deleted at the next cleanup. Since #1945 such a setting is read by `TimeIntervalViewModel.FromNodeSetting` (the folder's load, `NodeViewModel.Update`): shown as the item that behaves the same (Forever where the list has it, otherwise Never), and while that item stays selected the stored model is what is saved (`ToModel` returns it; `FolderModel.UpdateSetting` keeps the folder's stored view, `KeepsStoredFromParent`): an unchanged form changes nothing, pushes nothing new to the folder's products and records nothing in the journal. Choosing another item applies it as usual; the journal then names the old value "Forever" / "Never". Plain `FromModel` (alert templates, TTL alerts) is unchanged, so a template's "from parent" TTL stays "from parent". Verified by tests through the view models and the update paths of `HomeController.UpdateFolderInfo` / `UpdateProductInfo` (the browser's choice of the first option is emulated), not in a browser (`Folders/FolderCalendarPresetTests`, `UnchangedSaveOf*StoredAsFromParent_*`, `FolderStoredAsFromParent_ChangedOnItsForm_*`). **Rollback after someone chose 5 years:** a server up to 3.46.0 does not know `TimeInterval.FiveYears` (1577664000000000). Read from the 3.46.0 code, not run: a folder storing it fails to load (`TimeIntervalViewModel.FromModel` → `ToDynamicServer` throws `NotImplementedException`; `FolderManager.Initialize` does not catch it, so the server is not expected to start); a product or sensor storing it throws in the same place when the web tree builds its view, and in the core `GetShiftedTime` throws for it: the hourly retention pass logs an error for each such sensor and clears nothing (it catches per sensor), and an out-of-order value or a large file of such a sensor fails on the history floor (`HistoryFloor` → `RetentionCutoff`). A product that only inherits five years from its folder (`FolderPreset`) is read by 3.46.0 as `FromFolder` with 0 ticks, never expires, but its folder still stores the value. `TablePeriodClass` and the journal's text tolerate it (kept for ever; the number as text). Before a rollback, set every 5-year setting to another value on the newer server.

## Authentication

- Cookie-based authentication
- Optional SSO sign-in through an OpenID Connect provider (off by default; password login stays): `sso-login/feature.md` (#1782)
- Custom `UserManager` with roles: Viewer (read-only), Manager (read-write)
- Hiding a button is not authorization: a mutating MVC action must check the role server-side and
  be POST (+ antiforgery for a destructive one), because the auth cookie is `SameSite=Lax` and rides
  a top-level cross-site GET. Removing a product or node (`ProductController.RemoveProduct`,
  `HomeController.RemoveNode`) requires Manager of the node's ROOT product or admin — the removal is
  recursive and irreversible (#1512; `ProductControllerTests`).
- The tree page and the history routes resolve every sensor, node or folder id from the client through `UserTreeAccess`: an entity of a product the user has no role on is answered like an unknown id. Names, paths and file content from collectors and users are output as text. Both rules: `web-ui-access/feature.md`.
- Product roles are held per ROOT product (`User.ProductsRoles`); a node below the root has no roles
  of its own. Six writes of `ProductController` go through one gate (`DenyUnlessManager`): the
  caller must be an admin or a Manager of the root product of the posted id; an id that is not in
  the tree is answered 404, everyone else 403, and a role entry on a nested node's own id counts for
  nothing. The six are the product edit form (`EditProduct` POST: name, description, default
  chats), the Members table (`AddUserRight`, `EditUserRole`, `RemoveUserRole`), the move between
  folders (`MoveProduct`) and the removal. `UpdateSensorGroups` is guarded separately, by
  `ProductRoleFilterBySensorGroups`, which compares the posted id with the caller's roles as it
  is, without resolving the root. Past the gate the role actions answer 400 for a JSON body that
  cannot be read and 404 for an unknown user (an empty user id on `AddUserRight` is answered 200
  after a validation message is put into `TempData`), and they look the user up only after the
  caller has passed, so a refused caller cannot probe user ids. `MoveProduct` is POST only: a move
  changes roles (the users of the folder the product leaves lose the folder role they hold on it;
  the users of the folder it enters who hold no role on the product yet receive theirs).
  Antiforgery is validated on `EditProduct`, `MoveProduct` and `RemoveProduct`, whose callers send
  the token; the role actions take a JSON body, which a cross-site form cannot send, and their
  callers send none. `ProductControllerTests` covers admin, Manager, Viewer, a user with no role, a
  Manager of another product, an unknown id, and a node one and two levels below the root.
- A folder's Chats tab (`FoldersController.UpdateChats`) requires Manager of that folder or admin,
  like the other writes of the folder edit page; an unknown folder id is answered 404
  (`FoldersControllerUpdateChatsTests`). It validates no antiforgery token: the page replaces the
  form's content with the saved partial, which drops the token the form was rendered with.
- Access keys authenticate DataCollector instances (no user session needed)
- A role is checked on the entity that is written, not on an id the form carries next to it. The
  access key dialog posts the key's id and a product id; `AccessKeysController.ModifyAccessKey`
  (POST) looks the STORED key up by its id and requires admin or Manager of the root product of the
  node that key was issued for. A master key belongs to no product and a key whose product is gone
  has no Manager: both are the admins' alone. An unknown key id is answered 404 and a caller who
  may not change the key 403, both before the form's validity is looked at; the posted product id is
  replaced with the stored key's, so the answer (the key list of a product, or the dialog again) is
  built for the key's own product (`AccessKeysControllerModifyTests`).
- A folder's product list is a list of role grants: every user of a folder receives their folder
  role on a product that enters it (unless they already hold a role on that product) and loses it
  when the product leaves (`FolderManager.AddProductToFolder`, `RemoveProductFromFolder`). So the
  save of the folder page's General tab (`FoldersController.EditFolder` POST) requires more than
  Manager of the folder (or admin; an unknown folder id is 404): each product that enters or leaves
  must be one the caller manages, as an admin or as a Manager of that product, and a product may
  enter only as a root product that sits in no other folder. A request that names a product the
  caller does not manage is answered 403, one with a product that cannot enter 400, and in both
  cases nothing of the request is applied, the rename and the other products included; an id that
  is not in the tree is left out, as before. The page follows the same rule: it offers to add only
  the folderless products the caller manages and shows "Exclude from folder" only for the products
  they manage. Creating a folder (`AddFolder`) is for admins only, 403 for everyone else, with the
  same rule for the products it starts with (`FoldersControllerProductsTests`). These two test
  classes run the role filter attributes declared on an action before the action
  (`Infrastructure/DeclaredFilters`): a direct call of the method would skip them.

## Feature Folders To Add Here

- `ingestion/` - receiving and validating collector data.
- `alerts/` - alert conditions, templates, schedules, notification triggers. See `alerts/feature.md` for the canonical model: global alerts via `AlertTemplate` plus per-sensor editor; node-level alerting on Folders/Products was removed in #1142.
- `notifications/` - Telegram/email delivery, retries, failure handling.
- `dashboards/` - server-owned dashboard behavior and data shaping; today it documents the panel subscriptions: how a path template adds sources by a scan and for a new or moved sensor, and when the dashboard is stored.
- `bar-stddev/` - per-bar standard deviation (#1509): storage (MemoryPack, appended field), exact compression of σ, Sensor API / Grafana / CSV output, the sensor page's Candlestick / Mean ± σ view and the dashboard `StdDev (σ)` property; also why the server builds against the in-repo DTO (`src/Directory.Build.targets`).
- `authentication/` - authentication surfaces: the persisted Data Protection key ring behind cookie sessions and antiforgery tokens (#1633); bearer tokens live in `api-tokens/`.
- `sso-login/` - the optional OpenID Connect sign-in of the web UI (#1782): `Oidc` settings with an environment-only client secret, provider username = HSM login, auto-created users without roles, `IsAdmin` from an optional provider group, absolute cookie lifetime, local logout.
- `management-api/` - the `/api/v1` REST resource controllers for non-interactive (bearer-token) clients; alert templates CRUD first (#1351).
- `mcp/` - the read-only Model Context Protocol endpoint at `/mcp` (#1391): nine tools rendering the same read surface for MCP-native AI agents, same HsmApiToken credential.
- `file-sensor-page/` - the Files tab of a File sensor: the list of its values page by page, the description of the last value without its bytes, the states, downloads and download log of large file values, the uploads in progress, the dump password notice; the file actions of `HomeController` and their access check (#1886, ADR-0022 point 18).
- `table-sensors-ui/` - what the web UI shows of a table sensor's rows: the chart reduced on the server to a minimum and a maximum per bucket of time, its scan limit and the hour gate held per source; the routes `POST /TableSensors/Chart` and `GET /TableSensors/Download` (CSV, paged), their access check and limits (#1847, ADR-0021 point 14).
- `table-sensors/` - the table sensor kind: a sensor whose data is rows with a schema fixed at registration; what it refuses (values, alerts, moves) and how a server that does not know it loads the tree (#1844, ADR-0021).
- `table-feed-sensors/` - the ordinary sensors under `.tables` of a table sensor's product that users alert on (rows, stored MB, delivery lag, refused tables, blocks the merge could not read; rows per table sensor), posted by the server per period through a keyless internal value path (#1847).
- `sensor-move/` - moving a sensor to another path, same or another product, keeping its id, history, settings and policies; the old path becomes an alias that keeps routing values to it (#1718, ADR-0018).
- `collector-session/` - the WebSocket session a collector may hold with the server (#1664): `GET /api/sensors/session`, acks with the HTTP route's status, the server-wide session cap, the session registry and the `Open sessions` self-monitoring sensor. Meant to replace the HTTP routes for collectors after a transition period. No collector uses it yet.
- `database-backup-monitoring/` - self-monitoring of the server's own database backup (#1525): per-run `Backup result` (status + TTL so a missed run turns Timeout), backup file sizes, duration, and per-database sizes.
- `token-usage-monitoring/` - per-token self-monitoring of `/api/v1` + `/mcp` access (#1402): request rate and duration per API token, plus the aggregate auth-failure counter.
- `agent-download/` - admin-only per-product HSM Agent (Windows) bundle download and its `agent-release.txt` staging; also the admin **Downloads** page (#1550, Configuration menu) that offers both bundles for a chosen product.
- `linux-probe-download/` - its Linux sibling (#1424): per-product probe `.tar.gz` with `install.sh`, staged from `probe-release.txt`.
- `large-file-download/` - how a large file value leaves the server (#1885, ADR-0022): the AES-256 zip built once and re-encrypted per password version, the web and `/api/v1` download with its order of checks, the hand-over to the bundled Caddy, the download log and their self-monitoring.
- `dump-password/` - the password of a root product under which its large file values are given out (#1885): set and seen by a Manager of the product or an admin on the settings page, generated or typed, versioned, never in an API answer, a log or a journal value.
- `web-ui-access/` - which sensors, nodes and folders a web user can address by id in the tree page, the history routes and the per-node journal (`UserTreeAccess`), and how collector- and user-supplied text is put into pages (encoding rules for views and scripts, file previews).
- `background-services/` - hosted services, queue workers, startup/shutdown.
