# Feature: MCP server (AI-agent tools)

> Owner: server | Last reviewed: 2026-11-04 | Canonical: yes
> Scope: the Model Context Protocol surface at `/mcp` (#1391) — snake_case tools rendering the landed management-API surface for MCP-native agents (Claude, Cursor, …): the sensor tree, alert templates/schedules, notification chats, access-grouping folders and sensor policies (reads), plus the phase-2 WRITE tools for sensor policies, alert templates, alert schedules and sensor muting (#1569). REST stays the canonical surface; MCP is an adapter over the same implementations.

---

## Overview

Issue #1391 exposes the sensor-tree + alert read surface (merged via #1387/#1390, epic #1347) through the Model Context Protocol, so an MCP-native agent discovers the same capabilities a REST client has without hand-writing HTTP. The server is hosted by HSMServer itself via the official `ModelContextProtocol` C# SDK (NuGet `ModelContextProtocol.AspNetCore` 2.2.0), Streamable HTTP transport, **stateless** sessions (the tools are pure reads; no session affinity needed). The tools are snake_case, camelCase parameters; item tools return the REST DTOs verbatim (same types and camelCase keys on both transports; the SDK's serializer omits null members where REST writes explicit nulls — absent ≡ null for JSON consumers, pinned by a registration test), list tools carry a `limit` (default 20, cap 200) + `totalFound` envelope plus the **effective paging echo** (`limit`, the `page` actually served, `totalPages`) — the clamps rewrite the caller's `limit` silently, so the agent must divide by the limit the server applied, never the one it asked for — and **no pagination cursors** by design: an agent narrows instead of chasing pages. Every list tool also takes a `page` (clamp semantics as REST — a page past the end serves the LAST page, and the Skip arithmetic is ClampPage-bounded so a huge page number can never wrap int into "page 1 labeled as page N"): narrowing is preferred, but not guaranteed (get_node's sensors list caps at 200 unpaged; uniformly-named sensors cannot be partitioned by search), so `page` is the guaranteed reachability past the cap.

The sensor-tree tools are a thin rendering of `SensorTreeReadService` — the same implementation the REST controllers run on since #1391 (their suites are the regression net). The alert tools render `AlertReadService` the same way since #1393, the chat tools render `ChatsReadService` and the folder tools render `FoldersReadService` the same way — the visibility rules exist in one place, shared with the REST controllers. Expected failures surface as tool errors (`isError=true` with a text message — `McpException`), never as protocol-level crashes, so the calling agent can self-correct; on the write tools the same channel carries what the REST twins answer as HTTP 400/404/409/422 — there is no status code on the MCP surface, the field-keyed validation detail flattens into the message text (#1609). The SDK also logs each such `McpException` at ERROR; since #1613 that log entry is kept out of the operator error log (see the invariant below).

## Invariants

- **Same credential, same sight, no second credential kind**: the endpoint requires the SAME `HsmApiToken` bearer scheme and `HsmApiTokenDefaults.ManagementPolicy` as `/api/v1` (`RequireAuthorization` on `app.MapMcp("/mcp")`). No anonymous access. READ-ONLY TOKENS CANNOT REACH `/mcp` AT ALL: every MCP message (initialize included) is a POST, and the policy's method backstop (`HsmApiTokenOnlyAuthorizationHandler`) rejects a read-only token on unsafe methods — pinned by a wire test. Visibility and write-authorization follow the token owner through the exact REST decision paths (per-root-product sensor sight, per-folder template sight incl. the both-folders move rule, caller-wide schedule read gate, admin-only Global boundary for schedule writes) — the tools delegate to the shared services rather than re-implementing any rule.
- **Outside the area guard, inside the credential family**: `/mcp` is NOT under `ManagementApiGuardMiddleware` (no `[ManagementApi]` marker; the SDK owns the route and errors follow MCP's JSON-RPC semantics, not the uniform JSON contract). `LegacyBearerGuardMiddleware` exempts it (`IsTokenRoutePath`) — the hsm_pat_ credential is expected there, not misplaced. The one carry-over from the JSON world: whatever ESCAPES the SDK handler (a transport-level failure, a serialization error) is caught by `ApiExceptionJsonMiddleware` and answers a **JSON-RPC error envelope** (`-32603 Internal error` with `data.traceId`) — machine-parseable, never the Razor HTML page (#1392 review, round 3).
- **SitePort-only, probing-blind, fail-closed over the endpoint family**: `McpSitePortOnlyMiddleware` (before authentication, with the other guards) answers `/mcp` off the SitePort with the area's uniform 404 — an unauthenticated probe on the sensor port never gets a 401 that confirms the endpoint exists. It also carries the area guard's rule over `/mcp`'s endpoints: a matched endpoint under `/mcp` must require `ManagementPolicy` and never be anonymous, so a future route mapped there is unreachable without the credential, exactly like an unmarked route under `/api/v1`.
- **Always on, no config toggle**: like `/api/v1`, the endpoint ships enabled behind its auth; there is no feature flag to drift.
- **Tool metadata reflects the operation**: reads declare `ReadOnly=true, Idempotent=true`; writes declare `ReadOnly=false` with `Idempotent=true` only for retry-safe writes — the full-replace updates (`update_*`) and the state-setting mute/unmute pair (#1569: re-sending converges on the same state) — never for creates/deletes; clients can surface the safety hints. The flags are METADATA: the enforcement is the credential policy plus the services' per-call authorization.
- **Compactness rule**: only `get_sensor` embeds the current value (`lastValue`); `find_sensors` returns compact summaries (id, path, type, status, unit), mapped straight from the cache models so the rule holds in the WORK, not only on the wire (#1392 r5 — mapping the full DTO first would materialize current-value payloads just to discard them). No tool serializes file content (the REST File-value metadata rule holds).
- **Field-value documentation travels in the schemas** (#1545, output side #1553): every record and property of the DTOs the MCP tools bind carries a `[Description]` — the schema exporter (Microsoft.Extensions.AI `AIJsonUtilities`) surfaces only those attributes into `tools/list` schemas, never the XML doc comments. The enum tables (SensorType/PolicyProperty/PolicyOperation byte codes on the template DTOs, enum names on the policy DTOs), the round-trip rules, and the schedule YAML grammar (see `AlertScheduleYamlDocs`) are therefore machine-readable on the wire. Since #1553 every tool opts into structured content (`UseStructuredContent` on `[McpServerTool]`), so the SDK also emits the tool **output schemas**: the READ-DTO documentation (sensor tree, chats, folders, list envelopes — the null-semantics, value tables, visibility rules) reaches agents the input schemas could never carry. A new DTO field of an MCP-bound type gets its `[Description]` in the same change, or the agent is back to guessing values; wire tests pin the presence of the tables on BOTH sides so SDK drift or a DTO refactor that drops them fails loudly. The wire escapes non-ASCII conservatively (apostrophes travel as `\u0027`) — assertions about schema text must decode the JSON first.
- **The two blind-guess surfaces are documented exhaustively** (#1556): the message-template fields of BOTH write surfaces carry the FULL alert-template variable table (`AlertVariablesDocs.Variables` — every registered `$variable` with its `[AlertVariable]` description; variables substitute as substrings, the message renders with string.Format so braces are not allowed, and the template splits on spaces, dropping whitespace that touches a space (whitespace with no space in it is kept) — only other plain text ships as-is), and the condition `property` fields carry the property x sensor-type availability matrix (`AlertPropertyMatrixDocs.Matrix` — the exhaustive table with negatives: no `Value` on Boolean/File/bars, `Length` String-only, `OriginalSize` File-only, bar statistics on no single-value type; the Enum `EmaValue` pair passes validation but currently fails at apply time), mirroring `AlertPolicyConditionRules` — the table behind the 422 validation. The template write does not consult the rule table but enforces the same matrix through the domain reconstruction of its policies (#1609): every policy is rebuilt with the template's sensor type (a Boolean stand-in for AnyType, so an AnyType template accepts only the common set), and a property the type does not offer — or one whose typed executor the domain cannot build, Enum's `EmaValue` — fails the whole write with a parse error naming the reason; nothing non-offered is stored by a write. Since #1608 the template write also enforces the three documented field contracts structurally: a `paths` entry of literals without `/` (can never match — every sensor path has at least `Product/SensorName`), curly braces in a policy/TTL message template (the field-keyed `policies[i].template` / `ttlPolicies[i].template` error instead of a `string.Format` failure at evaluation time) and conditions on a TTL policy (`ttlPolicies[i].conditions` — the trigger is the inactivity interval; previously the condition reached the domain reconstruction and failed with the leaked `NotImplementedException` text on the wrong `policies` key). Both texts are shared consts referenced from the `[Description]s` of the policy and template DTOs alike; `AlertSchemaDocsTests` re-derives the expected sets from `AlertState.VariablesHelp` and the rule table, so the prose cannot drift from the code in either direction.
- **Anti-enumeration carried into MCP**: unknown and invisible ids answer the SAME tool-error text (`"The requested resource was not found."`); out-of-sight items are silently absent from lists; the schedule gate denies before the provider is queried.
- **Expected tool failures are not operator errors** (#1613, ADR-0016): the tools signal validation/not-found/conflict outcomes by throwing `McpException`, which the SDK relays to the caller as `isError=true` — and ALSO logs at ERROR (`"\"{tool}\" threw an unhandled exception"`) from its `ModelContextProtocol.Server.McpServer` logger; the SDK's argument binder adds a second arm, rejecting unbindable caller arguments with an `ArgumentException` logged the same way. A retrying agent would flood `HSM-error-log.txt` with entries needing no operator attention (one test session produced 39 + 5, all client mistakes), so a `when`-filter on the errorfile rule in `src/server/HSMServer/nlog.config` skips exactly those entries — `McpException` or any `System.Argument*` type, from that one logger — while they still reach `HSM-all-log.txt` (the Warn+ rule); genuinely unexpected exceptions (any other type, or from any other logger) still reach the error log. Pinned end-to-end by `NlogConfigTests.ExpectedMcpToolFailuresStayOutOfTheErrorLog` (the real rules drive real events with the file targets swapped for in-memory capture).

## Primary Workflows

| # | Workflow | Initiator |
|---|---|---|
| 1 | MCP client initializes a session (HTTP POST `initialize` at `/mcp`) | MCP client (bearer token) |
| 2 | `tools/list` → the tool set with generated schemas | MCP client |
| 3 | The read-analysis scenario: `list_products` → `find_sensors` → `get_sensor_history` | AI agent |
| 4 | Alert review: `list_alert_templates` / `get_alert_template`, `list_alert_schedules` / `get_alert_schedule` | AI agent |
| 5 | Chat discovery for alert routing: `list_chats` / `get_chat` (the valid `destination.chats` ids) | AI agent |
| 6 | Folder discovery for template scoping: `list_folders` / `get_folder` (the valid `folderId` values — the access-grouping entity, not the tree's nested products) | AI agent |
| 7 | The noisy-sensor flow: `mute_sensor` / `unmute_sensor` after a diagnosis | AI agent |
| 8 | The policy lifecycle: `list_sensor_policies` / `list_sensor_ttl_policies` → the matching `update_*` / `delete_*` tool (#1615) | AI agent |

### The read-analysis scenario (#1391 acceptance)

"Analyze network problems in product X" with an MCP client and a read-only token:

1. `list_products` → the visible root products; find X by name.
2. `find_sensors(search="network", productId={X})` → compact matching summaries + `totalFound`.
3. `get_sensor(sensorId)` when the current value matters (the only tool embedding it).
4. `get_sensor_history(sensorId, from, to)` → the newest points oldest-first with `truncated`/`readUnavailable` (the #1389/#1390 contract unchanged).

### The alert-management scenario (phase-2 acceptance)

"Create an alert on sensor S routed to chat C, working nights only" with a read-write token:

1. `find_sensors` → pick S by path; `get_chat` / `list_chats` → resolve C's id (and its folders, for availability).
2. `list_alert_schedules` → an existing night window, or `create_alert_schedule` (admin owner; the id is server-generated).
3. `create_sensor_policy` on S with `destination.chats: [C]` and the `scheduleId` — 422-class tool errors flatten field-keyed ("destination: Chat ... is not available ..."), so the agent self-corrects.
4. For many sensors at once: `list_folders` → `create_alert_template` with path patterns (folder-scoped, applies tree-wide).
5. To rework or remove an existing policy later: `list_sensor_policies(S)` / `list_sensor_ttl_policies(S)` — the listed ids are the handles `update_*` / `delete_*` take, so policies created earlier (via REST, the Web UI, a template apply or a previous session) stay reachable (#1615 — before the list tools an id existed only inside the create response of the session that created it, making the write tools one-shot).

### The noisy-sensor scenario (#1569 acceptance)

"The diagnosed sensor keeps paging overnight; silence it until the morning" with a read-write token:

1. `find_sensors` / `get_sensor` → the diagnosis names the sensor id (and `state`/`endOfMuting` show it is not muted yet).
2. `mute_sensor(sensorId, endOfMuting=<tomorrow 09:00Z>)` → the echo renders `state: Muted` + the lift instant; omit `endOfMuting` to mute indefinitely.
3. The server's system-initiated sweep auto-unmutes at expiry — no second tool call needed; `unmute_sensor(sensorId)` lifts it early, and the unknown/invisible id answers the same tool-error text as every item tool.

## Data Flow

```
bearer token ──► McpSitePortOnlyMiddleware (SitePort check, uniform 404 otherwise)
             ──► UseAuthentication/UseAuthorization: RequireAuthorization(ManagementPolicy)
             │   → HsmApiToken challenge = plain 401 (no redirect)
             ──► SDK StreamableHttpHandler (JSON-RPC validate, stateless session)
                  ──► tools/call ──► tool class (DI, scoped)
                       ├── SensorTreeMcpTools → SensorTreeReadService → ITreeValuesCache
                       │     failures → McpException → isError result (text message)
                       ├── AlertsMcpTools → AlertReadService → IAlertScheduleProvider / ITreeValuesCache
                       │     (folder sight / caller-wide gate, as REST)
                       ├── ChatsMcpTools → ChatsReadService → IChatsManager
                       │     (caller-wide gate + global-or-visible-folder chat sight, as REST)
                       ├── FoldersMcpTools → FoldersReadService → IFolderManager
                       │     (owner-sight folder filter, as REST)
                       └── PoliciesMcpTools / SensorMuteMcpTools → PolicyAdministrationService /
                             SensorMuteAdministrationService → ITreeValuesCache
                             (the write engines, as REST; errors → McpException);
                             PoliciesMcpTools' list reads go through AlertReadService
                             (the sensor-boundary sight, as REST)
```

The tools resolve the caller through `IHttpContextAccessor` — the stateless transport executes a `tools/call` inline within its POST, so the ambient context flows; the principal is the one `RequireAuthorization` already admitted. Cancellations flow to the service where it takes a `CancellationToken` (same abort semantics as REST `RequestAborted`); the policy lists (#1615) are synchronous snapshots over the live model and take no token — like their REST twins.

## Storage / Persistence

The read tools persist nothing. The write tools persist through the shared services exactly as the REST surface does: policy writes through the atomic full-list `SensorUpdate` (LevelDB via the cache), template writes through `AddAlertTemplateAsync`/`RemoveAlertTemplateAsync` (persisted before reconciling, never client-cancellable), schedule writes through the provider's Save/Delete (LevelDB rows).

## UI / Operator Visibility

No dedicated UI. Operators provision the same personal API tokens as for REST (Profile page, cookie flow); an agent config entry needs the server URL + the credential. Since #1463 the token-creation dialog's one-time-secret modal carries a "How to use this token" block that points MCP clients at `https://<site-host>/mcp` with the same-token note and a link to the wiki `MCP` client-setup page — for a read-only token the MCP line is swapped for the read/write requirement note (a read-only credential cannot reach `/mcp` at all), so the dialog never points a credential at an endpoint it would reject.

## Notes

- Wire casing is camelCase on both transports: MVC JSON options vs the SDK's `McpJsonUtilities.DefaultOptions` (Web defaults); a registration test pins the camelCase rendering of the tool result records AND the exact property-key sets of a null-valued `SensorDto` under both option sets, so an SDK default change cannot silently diverge the surfaces. One pinned shape nuance (#1392 r5): the SDK options carry `DefaultIgnoreCondition = WhenWritingNull`, MVC's do not — a null DTO member (`lastValue`, `unit`, `status`, …) is ABSENT on MCP and written as `null` on REST; absent ≡ null for any JSON consumer, and aligning them would mean mutating the SDK-owned options the JSON-RPC envelope itself serializes through or changing the shipped REST wire.
- Structured content (#1553) is a DELIBERATE wire-behavior change over the pre-#1553 surface: every `tools/call` success now carries `structuredContent` (the tool result as a JSON object, serialized through the same `McpJsonUtilities.DefaultOptions` — the WhenWritingNull nuance above applies to it identically) ALONGSIDE the single JSON text block that was the whole result before. The text fallback is kept by the SDK, so a client that never reads `structuredContent` loses nothing; the one behavior an old client could notice is the new member on every result. Every tool return type is a non-nullable record/class (the write tools answer the `McpWriteResult<T>` envelope, #1605), so each output schema is a plain `type:"object"` document — the SDK's legacy-wire `{"result": …}` wrapping for pre-2026-07-28 clients never applies.
- The write-tool result envelope (#1605) is a DELIBERATE MCP wire-behavior change over the #1570 shape: the twelve journaled write tools used to return `Task<object>` (the DTO echo or the dry-run `WritePreviewDto`, one runtime type per call), whose permissive `true` output schema the SDK's legacy-wire compatibility wrapped into `{"type":"object","properties":{"result":true},"required":["result"]}` for pre-2026-07-28 clients — valid JSON Schema, but Claude Code accepts only object sub-schemas and discarded the whole `tools/list` (0 tools, the connection still reporting "connected"; every `tools/call` result was also wrapped as `{"result": …}` unlike the read tools). Since #1605 each write tool returns the concrete `McpWriteResult<T>` envelope — `{value: <stored DTO>}` after an applied write, `{preview: <WritePreviewDto>}` after a dry run, exactly one arm per call (the null arm is absent, WhenWritingNull; `WritePreviewDto` and its affected-entity entry now carry `[Description]s` like every other MCP-bound DTO) — so the exported schema is object-shaped on every protocol version. The REST arm is unchanged: it keeps answering the bare DTO/preview body (the envelope is the MCP-only price of one static output schema per tool). The registration test and a legacy-protocol wire test (`2025-06-18`, the Claude Code negotiation) pin that every tool's wire schema root AND every property schema inside it is a JSON object — no boolean sub-schemas.
- Server identity: `Implementation { Name="HSMServer", Version=ServerConfig.Version }`; stateless sessions set explicitly (`WithHttpTransport(options => options.Stateless = true)` — the 2.2.0 default since the 2026-07-28 protocol revision) and pinned by a registration test: the tools resolve the caller through the ambient HTTP context, which only flows in stateless mode, so an SDK default change must fail a test rather than silently degrade every `tools/call`.
