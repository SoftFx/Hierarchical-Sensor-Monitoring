# Feature: API tokens (authentication foundation)

> Owner: server | Last reviewed: 2026-09-08 | Canonical: yes
> Scope: durable personal API tokens (hsm_pat_v1_*) — material, verifier, grants, store, the authoritative in-memory index with token lifecycle semantics, the ASP.NET authentication/authorization surface that consumes them (`HsmApiToken` scheme, `/api/v1` area convention, effective-rights evaluator, security-event sink), the cookie-only personal token management UI (`ProfileController`, the profile page), and the IsAdmin emergency revoke-user/revoke-all surface (`ApiTokensAdminController`).

---

## Overview

Personal API tokens are opaque bearer credentials for non-interactive management clients (AI agents, scheduled scripts, resident services). A user creates a token through the cookie-authenticated profile page (`ProfileController`, step 4); the server generates the entire credential, persists only an irreversible verifier, and discloses the full token exactly once.

Status: steps 1–3 of the initiative (`docs/initiatives/fine-grained-api-token-authentication.md`, issue #1356) delivered the persistence/domain foundation and the HTTP surface that consumes it (the `HsmApiToken` handler, scheme isolation, the fail-closed `/api/v1` area convention, the legacy-route bearer guard, the effective-rights/resource evaluator, last-used coalescing, the security-event sink, retention and invalid-attempt throttling). **Step 4, PR A** adds the personal token management UI: the header user menu (avatar + name dropdown with Profile/Logout), the profile page (read-only user card + the API tokens section), and the cookie-only lifecycle endpoints (create/list/restrict/rotate/revoke) with the issuance-side `ApiTokens.*` knobs — `Enabled` (kill switch, default false: the handler rejects every `hsm_pat_` bearer before any lookup while it is off; cookie list/revoke stay available for cleanup), `MaxTokensPerUser` (10), `AllowNoExpiration` (false), `DefaultLifetime` (90d — the expiry preset preselected by the create form, not a cap), `MaxLifetime` (365d — the hard lifetime cap the create endpoint enforces, so switching `AllowNoExpiration` off cannot be sidestepped with a year-9999 custom date). Still later in step 4: **PR B** adds the IsAdmin emergency revoke surface (`ApiTokensAdminController`) — the Users-page row action and the Configuration kill-switch companion, both advancing a durable revocation generation. The `/api/v1` resource controllers are landed (alert templates #1351, alert schedules #1352 — see the `management-api` feature).

## Invariants

- Only the verifier `SHA-256(ASCII("HSM-API-TOKEN") || 0x00 || versionByte || tokenId[16] || secret[32])` is persisted; never a plaintext secret, pepper, or reversible material. The dummy verifier used on the unknown-TokenId path is drawn from the CSPRNG per process, so no presentable credential hashes to it — callers must still fail when no record was found, never treat the compare result alone as the decision.
- Token format is strict: `hsm_pat_v1_` + exactly 22 canonical unpadded Base64URL chars (128-bit TokenId) + `.` + exactly 43 canonical chars (256-bit secret). Padding, wrong lengths, foreign alphabet, and non-canonical aliases are rejected before any database access; the canonicality check inspects the trailing bits of the final character directly, so parsing allocates no strings that could hold an uncleared copy of the secret.
- Persist-first publication: every mutation writes durably before it enters the in-memory authentication index. A failed write leaves **neither durable nor live state**; token creation never goes through the generic `ConcurrentStorage.TryAdd`. "Durable" here means process-crash durable (LevelDB write-ahead log, default async write options, consistent with the rest of the database layer): a host power loss can still drop the most recent revocation or generation advance. A synced-write option for the revocation paths is a deliberate open decision for the configuration PR, not a silent claim.
- Thread safety: the manager is a singleton reached from request threads. Every lifecycle mutation and generation advance runs its whole read → persist → publish sequence under one state lock, so a restrict/rotate derived from a pre-revocation snapshot can never durably overwrite a revocation, and in-memory generation values never regress below the durable counters. Read paths are lock-free and walk snapshot-safe concurrent structures only.
- `TryInsertApiToken`/`TryRotateApiToken` serialize the TokenId existence check with the write inside the database worker; a collision (false) retries with a **completely new** id/secret pair and never overwrites.
- Rotation is one atomic LevelDB batch: the source token is revoked and the replacement inserted together, or neither happens. Rotation copies the source grants verbatim (narrowing a token is what restriction is for) and never turns a finite expiry into an unlimited one, and the resulting expiry (requested or inherited) must not already be in the past — no one-time secret is disclosed for a dead credential. A dead source — revoked, already expired, or invalidated by a revocation generation — is refused: rotating an emergency-revoked token must not mint a live replacement that silently undoes the revoke. The replacement keeps the original `CreatedBy` and records the rotating actor in its own `RotatedBy` field, so the audit trail survives later removal of the source row.
- Restriction can only remove grant pairs or shorten expiry (unlimited → finite is allowed); any expansion attempt fails, and dead records are terminal — restriction of a revoked or generation-invalidated token is rejected. Null `remainingGrants` keeps the current grants (symmetric with null expiry); an explicit empty list strips every grant. A no-op request (grants unchanged, expiry unchanged) succeeds without a rewrite or an audit stamp.
- Revocation is immediate and idempotent — for any token visible in the index. While `IsGenerationStateHealthy` is false (e.g. after a failed boot scan, when the in-memory index is empty but the durable rows survive), per-token revoke reports false for every token; the operator's lever in that state is the emergency revoke — a generation advance, which bypasses the index and acts durably. The management layer distinguishes "unhealthy index, use emergency revoke" (false + unhealthy) from "no such token" (false + healthy) on the health flag.
- Grants are explicit operation + boundary pairs (Global / Product id / Folder id), canonicalized before persistence; unknown operations, boundary kinds, empty-guid resource ids, or operation/boundary combinations the catalog does not allow (v1: `system-health:read` is Global-only) fail closed, and duplicate operation+boundary pairs are **rejected** (not silently deduplicated) — the management layer must surface a distinguishable error for them. Pairs are never recombinable. Grant lists are bounded (`ApiTokenGrants.MaxGrants` = 1024) — canonicalization allocates per grant and the row is rescanned into memory at every boot, so the grant list must not be an unbounded caller-supplied input. Rows are re-canonicalized at load, so the in-memory grant shape always matches the persisted contract.
- Revocation generations: every token captures the global and per-owner generation at issue. Emergency advances persist the new generation before publishing it; missing-as-zero is the fresh-install baseline, corrupt or regressed generation state makes the whole index fail closed (`IsGenerationStateHealthy = false`). A failed token-row scan at boot fails the index closed the same way — an empty scan result must mean a fresh install, never a silent outage. An owner absent from the in-memory generation cache (no loadable records, e.g. after retention removed them) has the durable value read once on the next create/rotate and cached, so a post-cleanup token never carries a generation the durable state would invalidate after restart.
- Minting fails closed: `TryCreateToken`/`TryRotateToken` return `false` — never throw — while `IsGenerationStateHealthy` is false and when a generation row is unreadable at capture time. No credential is stamped with unproven generation values, which would work only until the rows are repaired and the server restarts and then be silently invalidated forever.
- Quota counting (`CountQuotaEligibleTokens`) counts only unexpired, unrevoked tokens issued at current generations — generation-invalidated tokens stop counting immediately, before any per-record reconciliation. Both generations are snapshotted once per count. `CountQuotaEligibleTokensGlobally` applies the same IsLive rule across every owner at once — the advisory affected-count an emergency revoke-all reports (computed before the advance; a token created between the count and the revoke is missed by the number while still being invalidated by the revoke itself).
- Records with a future `EntityVersion`, a foreign version byte, invalid TokenId shape, malformed verifier, an empty `EntityId`/owner, invalid grants, or a **key that disagrees with the payload TokenId** are skipped at load and can never authenticate (fail closed). A key/payload mismatch is the resurrection case: lifecycle writes target `ApiToken_<payload id>` while the stale `ApiToken_<key>` row would be rescanned and re-published at every restart, silently undoing each revocation — such a row is rejected with its key logged so retention can clear it. A row whose `EntityId` duplicates an already-loaded record is skipped too: a shadowed record would make revoke-by-entity-id report success while the shadowed token keeps authenticating. Grant-skip warnings name the offending operation/boundary, not just the entity id.
- The operation catalog is append-only once releases ship real tokens; renames/removals require a store migration (ADR-0002, `docs/decisions/0002-api-token-operation-catalog-append-only.md`). Unknown-operation grants fail the whole record at load — loudly, with the operation named — rather than silently narrowing the credential.
- Every public manager result is a verifier-free projection (`ApiTokenInfo`): the stored verifier never crosses `IApiTokenManager`, so a management controller cannot serialize credential material through a careless response. The projection also carries no `TokenId` — it is the public half of the credential and the authentication lookup key; lifecycle and list responses expose `EntityId` only (a caller holding the credential derives it with `ApiTokenMaterial.TokenIdOf`). Grant lists are `ImmutableArray<ApiTokenGrantEntity>` end to end (entity, projection, canonicalizer output): `IReadOnlyList` over a `List` is not a defensive boundary — a cast back would let a consumer expand a live token's grants in place, with no durable write and no canonicalization.
- All `DateTime` inputs are UTC by contract: `Kind.Local` converts, `Kind.Unspecified` (an offset-less form/JSON value) is interpreted as UTC — never converted from the server's local zone, so stored expiries do not shift with the deployment timezone.
- Free text is bounded and control-character-sanitized before persistence, so records cannot forge log lines: name ≤ 256, description ≤ 1024, revocation reason and the actor fields (created/restricted/rotated/revoked-by) ≤ 256 chars each. Over-long name/description is **rejected** at create time (an operator's token must not be named something other than what they typed); actor fields and revocation reasons truncate instead — a revocation must never be blocked by an over-long reason. Unpaired surrogates are replaced with U+FFFD (System.Text.Json would substitute them in the row anyway), truncation never splits a UTF-16 surrogate pair and never ends in the space of a replaced control character, and input that sanitizes to nothing normalizes to null — keeping the live entity byte-identical to the JSON row it round-trips through.
- Retention removal is `TryRemoveToken`: the durable delete and the in-memory unpublish happen under one state-lock hold, so a concurrent revoke/rotate cannot rewrite a row the removal just deleted and resurrect it after restart. A TokenId absent from the live index still gets its durable row deleted — rows rejected at load are exactly the orphans retention exists to clear. A failed durable removal (`RemoveApiToken` false — the row may still exist) unpublishes nothing. There is deliberately no unpublish-only escape hatch around this ordering.
- The full token string is returned by create/rotate exactly once and is never logged or persisted.

### HTTP surface (step 3)

- **Scheme isolation.** Cookie remains `DefaultAuthenticateScheme`/`DefaultChallengeScheme`, and the `DefaultPolicy` behind bare `[Authorize]` is explicitly pinned to the cookie scheme — an API-token identity can never satisfy a legacy MVC/Razor authorization. `HsmApiToken` is never a default or forwarded scheme; it runs only from the management policy (`HsmApiTokenDefaults.ManagementPolicy`), which authenticates through `HsmApiToken` only (a cookie session alone produces no principal and challenges as a plain 401, never a login redirect) and requires exactly one authenticated identity of the HsmApiToken scheme carrying the owner/token claims — mixed or multiple identities fail closed as a denial.
- **Handler contract.** `HsmApiTokenHandler` reads only the `Authorization: Bearer` header; tokens in URLs, query, cookies, or bodies are never credentials. A non-`Bearer` header, a bearer without the `hsm_pat_` prefix, an absent header, or duplicated `Authorization` values (the joined string is not a parseable credential) is `NoResult` (another scheme's business, no token lookup); a credential claiming the prefix but failing the cheap shape check fails before any index lookup; otherwise the single decision is `IApiTokenManager.TryAuthenticate` plus the owner-existence check. Every rejection is one indistinguishable generic failure; its security event carries a TokenId only when the id is canonical (`IsValidTokenId`) — the cheap shape check passes attacker-chosen alphabets, and no unauthenticated input is persisted into the append-only store as an identifier. The principal carries exactly two claims (owner user id, public token id) — `Identity.Name` is never set to a login. On success the handler calls `MarkUsed` (coalesced, never blocks the request).
- **`/api/v1` area convention (fail-closed).** `ManagementApiGuardMiddleware` (after `UseRouting`, before authentication) serves the area only on the SitePort listener — `HsmListenerBindings` is the one immutable registry that both drives `Listen` and answers `IsSitePort`, so the guard cannot disagree with the listeners and config changes apply only on restart. Within the area an endpoint is reachable only when it matched a route, carries `[ManagementApi]`, and requires its family's authorization: the management policy outside the reserved cookie-only `/api/v1/api-tokens` family, a cookie `[Authorize]` (the default policy — without a named policy and without explicit schemes, so a scheme-bearing attribute cannot union the token scheme into the cookie policy) inside it — never anonymous (there is no fallback policy, so absence of `[Authorize]` is as anonymous as `[AllowAnonymous]`, and the guard 404s both). A failed authorization inside the reserved family answers a plain non-redirecting 401 too (`MyCookieAuthenticationEvents.RedirectToLogin` override for the area) — the whole `/api/v1` area never sees the cookie LoginPath redirect. Anything else under `/api/v1` is a plain **404 before controller execution** — a newly added route without the metadata is unreachable by default, and 404 (not 403) on SensorPort never confirms a management route exists.
- **Legacy-route bearer guard.** `LegacyBearerGuardMiddleware` rejects an `hsm_pat_` bearer sent to any non-`/api/v1` path with a generic non-redirecting 401 before MVC/Razor execution, performing **no** token lookup — the credential material is none of the legacy pipeline's business, and a `BaseController` cast can never turn it into a 500. The guard matches the version-independent `hsm_pat_` family prefix (a future `hsm_pat_v2_` credential cannot slip past it into the legacy pipeline) and inspects each duplicated `Authorization` value on its own — a `", "`-joined multi-value header would otherwise parse as its first value's scheme and hide the credential.
- **Principal-replacement skip.** `UserProcessorMiddleware` (which replaces `HttpContext.User` with the stored HSM user by `Identity.Name` on SitePort) passes a token principal through untouched — replacing it would restore unrestricted owner rights behind the token's grants. The short-circuit checks **any** identity of the HsmApiToken scheme, not just the primary one, so it does not depend on how a merged principal ordered the identities.
- **Effective-rights evaluator.** `ApiTokenAuthorizationService.Authorize` recomputes both sides of `allowed(operation, resource) = ownerCurrentlyAllows AND tokenGrantAllows(currentBoundary(resource))` from the authoritative stores on **every** call: owner downgrade/deletion, role removal, resource moves, and token revocation take effect immediately — the caller re-checks token liveness through `IApiTokenManager.IsTokenLive` (the manager's sanctioned IsLive predicate), so a token revoked between authentication and authorization fails closed within the same request. Sensors resolve through their product's current boundary; **token-side** folder grants follow the folder's current membership, while the **owner side** mirrors the app's own checks exactly (`IsProductAvailable`/`IsManager` semantics, no folder fallback): HSM materialises folder roles into per-product `ProductsRoles` entries at grant time and at move time, so a per-product narrowing (`RemoveUserRole`/`EditUserRole`) always wins over the folder role — the token can never exceed what the owner's own session can do. A Global grant never acts as a wildcard over scoped resources ("all boundaries" expands to concrete ids at creation and is never persisted). Decision mapping: target absent, invisible to the owner, or outside every grant of the token → `NotFound` (anti-enumeration); boundary covered and visible but operation not granted or owner cannot perform it → `Forbidden`. Writes need the Manager role at the boundary (or IsAdmin) — derived from the catalog's naming discipline via `ApiTokenOperations.IsWrite`; global operations are admin-only. `IsVisible(principal, operation, resource)` (the list-filtering predicate) applies the same conjunction as `Authorize` — owner sight, the **operation's** grant at the current boundary, owner capability — minus security-event recording: a list that returns full bodies must not disclose items whose item endpoint would 403, and list filtering is not a probe signal. For GLOBAL resources (alert schedules, #1352) the evaluator also owns the caller-wide gate `HasOperationAtAnyVisibleBoundary(principal, operation)`: candidate boundaries are enumerated from the token's own grants inside the evaluator and decided by the same list predicate, with ONE `AuthorizationDenied` (the 403 scope-denial kind — never the enumeration-probe kind) recorded per denied call. Its companion `HasOperationAtGlobalScope(principal, operation)` answers the token-side "everywhere" shape (admin owner + matching Global grant) for callers that already passed the gate — the schedules sensor filter short-circuits on it, since the per-product predicate deliberately never treats a Global grant as a wildcard. The first listing consumer (the `GET /api/v1/alertTemplates` page, #1351) memoizes the decision per distinct folder within a request; a future snapshot API would give a whole-list owner+grants consistency guarantee instead.
- **Last-used coalescing.** `MarkUsed(tokenId)` records the latest observed use in memory; a background flush (30 s) writes the durable `LastUsedAtUtc` under the manager's state lock — copy, persist, publish, never mutate in place — so a flushed timestamp can never clobber a concurrent revocation, values are monotonic, and a failed write retries on the next tick. Bounded staleness is the documented trade for keeping this off the request path.
- **Security-event sink.** `ApiTokenSecurityEventSink` records authentication success/failure and authorization denial into the append-only `ApiTokenSecurityEvent_<ticks>_<eventId>` LevelDB table — separate from the entity-keyed lifecycle journal by design. The request path only enqueues (bounded channel, 1024, `FullMode.Wait` so a full queue makes `TryWrite` return false rather than silently evicting a queued event); one background writer drains to storage. Volume control: successes are sampled 1-of-16; denials are always recorded; failures are recorded within the per-source invalid-attempt budget (`ApiTokenInvalidAttemptLimiter`: up to `ApiTokens.InvalidAttemptRateLimit` events per remote IP address per aligned minute, dropped beyond it — counted and logged by the limiter, never blocking or changing the authentication decision, and never consuming another source's budget; the connection's **port is not part of the budget identity** — it is ephemeral, so an ip:port key would hand every TCP connection a fresh budget and let one host fill the per-window registry with connection-scoped buckets, suppressing other sources' events; the full `ip:port` stays in the event payload as forensic context; a null/absent remote endpoint shares one `?` bucket so it cannot bypass the bound; the per-window source registry is itself bounded at 1024 entries, and when it is full only untracked NEWCOMERS are dropped — a source already in the window keeps its budget). The attempts themselves are never delayed or rejected — every invalid bearer keeps answering the same generic 401 (the bound is on the audit-event volume, not on the response); request-level rate limiting of invalid attempts is deliberately out of scope for v1 and can be layered on later without touching this contract. A full queue or a failed write drops the event (counted in `DroppedCount`; the first drop and every 1024th are logged) — a security event must never block or fail the request. Authorization denials preserve the decision: out-of-reach/invisible targets are `AuthorizationNotFound` (the enumeration-probe signal), scope denials are `AuthorizationDenied`. Event payloads carry only safe identifiers (public TokenId, owner id, operation, safe target id, request correlation id, remote endpoint) — never a secret or verifier. The handler fills correlation/source from the HTTP context; denial events gain them when the first `/api/v1` controllers pass their context through.
- **Retention + abuse bounds (landed).** `ApiTokenRetentionCleaner` (driven hourly by `ApiTokenRetentionService`; the first pass runs at the **next whole-hour boundary after boot** — `BaseDelayedBackgroundService` computes the initial delay as `(now + StartDelay).Ceil(Delay) - now`, which rounds up to a `Delay` multiple, so the 5-minute `StartDelay` only decides which hour boundary when boot falls within the last minutes of one) makes four bounded, idempotent, failure-isolated passes per run: (0) reconciliation of emergency-revoked rows — generation-invalidated records (no per-row `RevokedAtUtc`) are stamped through `IApiTokenManager.StampGenerationInvalidatedTokens` with `RevokedBy = "emergency"` and the pass's observation clock, bounded by the same 100-row batch limit, so a later pass can reap them (see "Emergency revoke" below; the initiator and reason live in the journal's audit record, not on every row); (1) dead token rows whose `RevokedAtUtc` or `ExpiresAtUtc` is at or before `utcNow - ApiTokens.TokenRecordRetention` are removed row-by-row through `TryRemoveToken` (atomic over the durable row and the live index; a failed removal logs and stays for the next pass) — live records are never eligible, and a generation-invalidated row without a per-row `RevokedAtUtc` is not eligible until pass 0 stamps it; (2) orphan rows (rejected at load, listed by the manager's `GetOrphanTokenIds` registry keyed by the storage key, pruned by `TryRemoveToken`, bounded at 10 000 keys — **duplicate-EntityId rows are deliberately not orphans**: which of the two rows is the legitimate one is unknowable, and auto-deleting a possibly-newer credential row is riskier than leaking it; an operator clears those by hand, and if the loaded twin is ever removed a restart rescans and loads the skipped one) are removed after one window counted from the cleaner's first observation — a damaged row carries no trustworthy clock, and a restart re-observes and therefore re-waits the window; (3) security events strictly older than `utcNow - ApiTokens.SecurityEventRetention` are removed through the database's bounded chronological prefix-range delete (`RemoveApiTokenSecurityEventsBefore`, oldest first, events exactly at the cutoff survive). Batches: ≤100 token/orphan rows per pass; the event delete repeats its ≤1000-row batch **within a pass** until a batch comes back short (a full batch means more eligible rows remain — a fixed one-batch drain of 1000 rows/hour would be slower than plausible ingest), capped at 50 batches (50 000 events) per pass so one sweep stays bounded. Storage failures are isolated per pass and per step — a failed scan/removal never wedges the sweep.
- **Credential redaction.** `ApiTokenMaterial.Redact` replaces every `hsm_pat_v1_<id>.<secret>` occurrence in free text with the public id plus a redaction marker (a lone/truncated prefix is consumed together with its credential-alphabet tail). Redaction is applied at the **NLog sink**: every target in `nlog.config` wraps message, exception and URL text in the `${hsm-redacted}` layout renderer (`HSMServer.Logging.TokenRedactionLayoutRenderer`, a thin wrapper over `Redact`) — the credential is password-class material and never reaches a log, whatever carried it: the per-request catch logger's record, an inner exception (a wrapped exception's `ToString()` would render it), or the outer ASP.NET Core exception handlers (`UseExceptionHandler`/`UseDeveloperExceptionPage` log the raw exception themselves, outside any call site that could rewrite it).

### Personal token management UI (step 4, PR A)

- **Cookie-only by construction.** `ProfileController` inherits `BaseController`'s bare `[Authorize]`, which the cookie-pinned `DefaultPolicy` answers — an API-token principal can never call token-management endpoints (the initiative's "no API token may manage tokens" rule), and the `LegacyBearerGuardMiddleware` keeps an `hsm_pat_` bearer out of the legacy pipeline before MVC runs.
- **One JSON answer shape.** Every mutation (`CreateToken`/`RestrictToken`/`RotateToken`/`RevokeToken`, all `[HttpPost]` + `[ValidateAntiForgeryToken]`, JSON in/out for the page's `fetch` calls) answers `ProfileMutationResponse { ok, error, message, token, entityId }`; `error` is a stable machine code (`disabled`, `unhealthy`, `quota`, `no_grants`, `duplicate_grant`, `grant_not_allowed`, `invalid_name`, `invalid_description`, `past_expiry`, `max_lifetime`, `no_expiration_not_allowed`, `not_found`, `create_failed`/`restrict_failed`/`rotate_failed`/`revoke_failed`, `invalid_request`, `invalid_grant`), `token` is present exactly on create/rotate success. This is the management-API error contract's cookie-MVC sibling: display text for humans, codes for the script.
- **Issuance-side owner filter.** `IApiTokenGrantOptionsService` computes what the signed-in owner may anchor grants at **right now** — boundaries (Global for admins only, products from the materialised `ProductsRoles`, folders from `FoldersRoles`; stale roles for deleted resources anchor nothing; a **Product boundary means a root product** — the set `GetProducts()` returns and the picker offers, never a sub-product node `TryGetProduct` would also resolve, which would anchor a grant at a boundary nothing resolves to) each with the catalog operations the owner can perform there (reads need any role, writes the Manager role, `system-health:read` Global-and-admin-only). `GET /Profile/GrantOptions` feeds the boundary-first picker; `IsGrantableByOwner` is the server-side guard the controller runs on **every** requested grant — the picker's hiding is a UX aid, never the enforcement. The rules deliberately mirror `ApiTokenAuthorizationService` (`IsProductAvailable`/`IsManager` semantics, no folder fallback), so a token can never exceed what its owner's own session can do.
- **Create validation.** Name 1–200 chars (trimmed), description ≤1000, **at least one grant**, no duplicate operation+boundary pairs (BoundaryIds are canonicalized to lowercase Guid text before comparison — an uppercase Guid is the same boundary), expiry strictly in the future and (boundary-inclusive) within `ApiTokens.MaxLifetime` of the create instant (`max_lifetime` — the cap that makes `AllowNoExpiration = false` a real policy bound rather than a hidden UI option), `No expiration` only when `ApiTokens.AllowNoExpiration` is on, quota pre-checked for a friendly error — but the **hard quota bound is the manager's**: `TryCreateToken` takes `maxTokensPerUser` and enforces it inside the same `_stateLock` hold that mints, so two concurrent creates cannot both pass a caller-side pre-check and exceed the cap. `Kind.Unspecified` expiry values are normalized to UTC exactly as the manager contract states (never re-interpreted as the host's local zone). The form mirrors the cap: custom-date picks beyond it are clamped to the cap instant (day-granular input), and one-click presets above it are not offered. Preset instants, the clamp and the date-input min/max are all derived from a server-rendered clock (`ServerNowUnixMs` plus client-measured elapsed time), never from the browser clock — a client running ahead of the server must not turn the largest preset into a `max_lifetime` error.
- **Rotation is exempt from the owner filter by design.** `RotateToken` re-mints the token's already-issued grant set without re-running `IsGrantableByOwner`: grants never expand through rotation, and effective rights are intersected with the owner's CURRENT roles on every request anyway — re-checking would only block rotation (never the token itself) after a role loss, taking away the secret-change lever exactly when it is needed.
- **Degraded modes.** `Enabled = false` → create/restrict/rotate answer `disabled` (and the page hides them), revoke keeps working (the documented cleanup path of the kill switch); `IsGenerationStateHealthy = false` → **every** lifecycle mutation answers `unhealthy` (per-token results are untrustworthy then; the operator lever is the emergency revoke — PR B), the page hides all actions and shows a warning banner; the handler additionally rejects every `hsm_pat_` bearer before any lookup while `Enabled` is off, so the banner's "existing tokens no longer authenticate" is literally true. `Enabled` is also togglable from the web UI: Settings → Server → "Enable API tokens" (`SaveServerSettings` mutates the live `ApiTokensConfig` singleton and persists it via `ResaveSettings` — the toggle takes effect **immediately**, no restart, in both directions, unlike the port/certificate settings on the same page).
- **Foreign ids are indistinguishable.** Restrict/rotate/revoke resolve the entity id, check ownership (`OwnerUserId == current user`) and liveness (not revoked, not expired); a foreign, unknown, revoked or expired id all answer the same `not_found` — the endpoints cannot be used to enumerate other users' tokens.
- **One-time secret.** The full credential appears exactly once, in the create/rotate response and the modal that shows it (Copy button, "shown once" warning); it is never in a list/detail payload (`ApiTokenInfo` carries no `TokenId` by construction), never logged, never persisted. The disclosure modal is deliberately non-dismissible by accident — static backdrop, Escape disabled, no header close button — so a stray keypress or background click cannot destroy the unrecoverable credential; the only exits are the explicit Copy/Close buttons, and the page reloads after the modal closes.
- **Restrict preloads from structured data.** The restrict modal preselects the token's current grants from `GrantsByTokenId` (structured JSON injected once per page), not by scraping rendered badges. The badge `×` works in both modes, so a grant the owner can no longer mint (its boundary may have vanished from the picker entirely) stays removable; the picker in restrict mode hides operations the token does not currently hold — checking one would be an expansion the server rejects.
- **List projection.** `GET /Profile` renders metadata only: name, description, grant badges (`operation @ boundaryName`, all rendered with "+N more" collapsing past the third), created/expires ("never" for unlimited)/last-used (Unix-millisecond timestamps converted from the entity's .NET ticks), status — active / expired / revoked / **invalidated** (an emergency-revoke generation advance happened after issuance; such rows are dead, agreeing with the quota counter that already excludes them) — newest first, dead rows dimmed with no actions. The header menu and the profile card share one deterministic avatar colour (`AvatarHelper`, hashed from the user id — `String.GetHashCode` is per-process randomised and would change the colour on every restart), as does the Users page.

### Emergency revoke (step 4, PR B)

- **Surface.** `ApiTokensAdminController : BaseController` with class-level `[AuthorizeIsAdmin]` — cookie session + admin role, exactly the `AccountController.Users` gate; an API-token principal can never reach it (cookie-pinned `[Authorize]` + the legacy bearer guard, like the profile endpoints). Three actions: `GET UserTokenSummary` (live count for the confirmation modal) and `POST RevokeUserTokens` / `POST RevokeAllTokens` (`[ValidateAntiForgeryToken]`, JSON in/out, the `EmergencyRevokeResponse { ok, error, message, correlationId, newGeneration, affectedTokens }` shape — the profile mutation contract's admin sibling). Buttons live where the levers' mental model is: revoke-user as a row action on the Users page (key icon, next to Edit/Remove), revoke-all on Configuration → Server next to the `ApiTokens.Enabled` kill switch; both open a modal with a typed confirmation and a required reason. The emergency routes deviate from the initiative's `/api/v1/api-tokens/emergency/...` REST shape deliberately — see the deviations section appended to the initiative document.
- **Typed confirmation.** Revoke-user requires typing the target's exact username (trimmed, case-insensitive on purpose — the deliberation is in the typing, not the casing) and is validated server-side, not only in the modal; revoke-all requires the literal phrase `revoke-all` (ordinal — the modal shows the exact phrase). A wrong confirmation answers `invalid_confirmation` without advancing anything.
- **Reason.** Required free text, 1–256 chars after trimming; control characters are normalized to spaces before the value reaches the audit record (log-forging hygiene), and empty/control-only/over-long input answers `invalid_reason`. The bound matches the manager's free-text backstop so the surface rejects friendly instead of silently truncating.
- **Semantics.** Every successful call advances the target durable generation (persist-first, published to authentication before the response) — idempotent by effect, not by no-op: repeated calls each advance, and "after this call the target set has no live pre-call tokens" holds after the first. A valid target with zero live tokens still succeeds and still advances. An unknown `userId` (missing from `IUserManager`, the same resolution the authentication handler uses) answers `not_found` — unreachable from the UI but part of the server-side contract; a removed user's tokens are already dead at the handler's owner-existence check. An admin may emergency-revoke their own user (the cookie session is a separate channel). The affected count (`CountQuotaEligibleTokens` / `CountQuotaEligibleTokensGlobally`, computed before the advance) and the new generation are reported in the response and the audit.
- **No degraded-mode gating — the whole point.** The endpoints take no `ApiTokens.Enabled` dependency and never consult `IsGenerationStateHealthy`: cleanup during kill-switch and after storage damage is exactly what the lever exists for. The `Advance*` operations go straight to the durable counters under the manager's state lock; the only failure is a storage throw, which means the revoke did **not** happen (neither durable nor in-memory state moved) and must surface.
- **Failure contract.** The controller catches the manager's throw (it must not escape to the global HTML error page) and answers `{ ok: false, error: "revoke_failed", correlationId }` — retryable, with `HttpContext.TraceIdentifier` as the correlation id, the same key that locates the NLog error record; the exception's text never crosses the wire.
- **Audit-of-record.** A journal record through `IJournalService` (the same durable store the tree changes use), anchored per scope — the target user's id for revoke-user, a fixed `DeploymentRevocationAnchorId` for revoke-all — carrying initiator, scope path, old/new generation, affected count, sanitized reason; a failed advance writes a "(failed)" record with the correlation id instead of a new generation. Best-effort **after** the advance by contract: the revoke has already happened, so a journaling failure is logged (with the correlation id) and never fails or retracts the response.
- **Reconciliation.** Generation-invalidated rows keep `RevokedAtUtc` null (the advance never touches rows), so the retention sweep now stamps them (see the retention invariant above): `StampGenerationInvalidatedTokens` marks up to the token-row batch limit per hourly pass with `RevokedBy = "emergency"` (`ApiTokenManager.EmergencyRevokedBy`) and the pass's observation clock — the initiator, reason and exact revoke instant live in the audit record, not on every row. Stamping never touches live or already-revoked rows (a fresh under-lock read per row), a failed write stays unstamped for the next pass, and a freshly stamped row is never removed by the pass that stamped it (the retention window counts from the stamp). Before this, unstamped invalidated rows were unbounded residue — no expiration, no revocation stamp, never reaped.

## Storage / Persistence

- LevelDB `EnvironmentData`, rows keyed `ApiToken_<TokenId>` (UTF-8); JSON serialized, records with `init`-only properties, UTC-tick dates.
- Security events: `ApiTokenSecurityEvent_<ticks:d19>_<eventId>` — zero-padded ticks keep the prefix scan chronological, the event id keeps it collision-free; append-only (no update path).
- Generation state: `ApiTokenGeneration_Global` and `ApiTokenGeneration_Owner_<ownerUserId>` hold plain long values in the invariant culture; unparsable or negative values are corrupt (the counter is monotonic from 0) and fail the index closed.
- Restoring an old environment backup rolls back token rows and generation rows together, so an emergency revoke performed after the backup point is undone consistently — and therefore invisibly. After any environment restore, re-run the emergency revoke.
- The `ApiToken_` / `ApiTokenGeneration_` prefixes differ at the separator position (`'_'` vs `'G'`), so the full scan (`ReadAllApiTokens`) never picks up generation rows.
- Retention cleanup is implemented (see the "Retention + abuse bounds" invariant above): dead rows and orphan rows after `ApiTokens.TokenRecordRetention`, security events after the independent `ApiTokens.SecurityEventRetention`, invalid-attempt events throttled per source by `ApiTokens.InvalidAttemptRateLimit`. **The sequencing constraint on the epic — retention and invalid-attempt throttling land with or before the first routable `/api/v1` endpoint — is satisfied; step 4 (the management UI/API) is unblocked.** The reason it existed: step 4 makes rotation routine, and without retention every rotation permanently adds a durable row and a live index entry — a deployment rotating weekly across ~200 tokens would accumulate ~21k dead index entries in two years, and any party reaching SitePort could drive unbounded security-event growth with invalid bearers.
- The issuance-side configuration landed with step 4 PR A: `ApiTokens.Enabled` (emergency kill switch, default false — upgrades opt in), `ApiTokens.MaxTokensPerUser` (10), `ApiTokens.AllowNoExpiration` (false), `ApiTokens.DefaultLifetime` (90d; the create form's preselected preset, not a cap), `ApiTokens.MaxLifetime` (365d; hard lifetime cap enforced at create, `DefaultLifetime` must not exceed it). All are startup-validated with key-named errors.

## UI / Operator Visibility

The profile page (`/Profile`, from the header user menu) is the operator surface of this feature: a read-only card about the signed-in user plus the API tokens section — token list (metadata only), create with the boundary-first grant picker and one-time secret modal, restrict/rotate/revoke with confirmations. Degraded modes are visible as banners (disabled / unhealthy generations) and the quota counter "used / max" beside the Create button. The admin's emergency levers are visible as the key-icon row action on the Users page (revoke one user's tokens, with the live count loaded into the confirmation modal) and the "Revoke all API tokens" button on Configuration → Server next to the enable/kill switch — both always present for admins, never hidden by the degraded modes they exist to fix. Security events remain queryable through `IDatabaseCore.ReadApiTokenSecurityEvents` (ops surface later).
