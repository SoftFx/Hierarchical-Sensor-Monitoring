# Feature: API tokens (authentication foundation)

> Owner: server | Last reviewed: 2026-09-10 | Canonical: yes
> Scope: durable personal API tokens (hsm_pat_v1_*) — material, verifier, the owner-mirrored power profile, store, the authoritative in-memory index with token lifecycle semantics, the ASP.NET authentication/authorization surface that consumes them (`HsmApiToken` scheme, `/api/v1` area convention, the owner-mirror evaluator, security-event sink), the cookie-only personal token management UI (`ProfileController`, the profile page), and the IsAdmin emergency revoke-user/revoke-all surface (`ApiTokensAdminController`).

---

## Overview

Personal API tokens are opaque bearer credentials for non-interactive management clients (AI agents, scheduled scripts, resident services). A user creates a token through the cookie-authenticated profile page (`ProfileController`); the server generates the entire credential, persists only an irreversible verifier, and discloses the full token exactly once.

Since **#1384** a token is a simple personal access token: an **eternal, full mirror of its owner's rights** on the whole `/api/v1` surface, optionally **read-only**. The fine-granted model of the original initiative (explicit operation + boundary grant pairs, per-token expiry) was removed before anything shipped — its evaluator never exceeded the owner's rights anyway (the owner side was recomputed per request), so the grants layer added complexity without adding a security boundary the owner did not already control, and it kept producing bugs rooted in the model itself (#1382: Global-boundary grants never matched scoped resources).

- **Full mirroring**: a token can do everything its owner can, across `/api/v1`, including admin-only resources when the owner is an admin. Owner rights are recomputed per request: a demoted/deleted owner, a removed role, a moved resource take effect on the very next evaluation. Token management endpoints stay cookie-only — a token can never mint or revoke tokens.
- **Read-only flag**: binary, fixed at creation, default read-write. A read-only token reads everything the owner can read; every write operation is denied (403 on an otherwise reachable target). Changing a token's power = revoke + create a new one.
- **Eternal**: no expiry anywhere. The remedies for a leaked credential are manual revoke, rotation (pure credential swap: fresh id/secret, same name and flag) and the admin emergency revokes, supported by last-used tracking and per-user quotas.

Status: the initiative's steps 1–4 are delivered (see `docs/initiatives/fine-grained-api-token-authentication.md` for the original design and its #1384 supersession note); the `/api/v1` resource controllers are landed (alert templates #1351, alert schedules #1352 — see the `management-api` feature).

## Invariants

- Only the verifier `SHA-256(ASCII("HSM-API-TOKEN") || 0x00 || versionByte || tokenId[16] || secret[32])` is persisted; never a plaintext secret, pepper, or reversible material. The dummy verifier used on the unknown-TokenId path is drawn from the CSPRNG per process, so no presentable credential hashes to it — callers must still fail when no record was found, never treat the compare result alone as the decision.
- Token format is strict: `hsm_pat_v1_` + exactly 22 canonical unpadded Base64URL chars (128-bit TokenId) + `.` + exactly 43 canonical chars (256-bit secret). Padding, wrong lengths, foreign alphabet, and non-canonical aliases are rejected before any database access; the canonicality check inspects the trailing bits of the final character directly, so parsing allocates no strings that could hold an uncleared copy of the secret.
- Persist-first publication: every mutation writes durably before it enters the in-memory authentication index. A failed write leaves **neither durable nor live state**; token creation never goes through the generic `ConcurrentStorage.TryAdd`. "Durable" here means process-crash durable (LevelDB write-ahead log, default async write options, consistent with the rest of the database layer): a host power loss can still drop the most recent revocation or generation advance.
- Thread safety: the manager is a singleton reached from request threads. Every lifecycle mutation and generation advance runs its whole read → persist → publish sequence under one state lock, so a rename/rotate derived from a pre-revocation snapshot can never durably overwrite a revocation, and in-memory generation values never regress below the durable counters. Read paths are lock-free and walk snapshot-safe concurrent structures only.
- `TryInsertApiToken`/`TryRotateApiToken` serialize the TokenId existence check with the write inside the database worker; a collision (false) retries with a **completely new** id/secret pair and never overwrites.
- Rotation is one atomic LevelDB batch: the source token is revoked and the replacement inserted together, or neither happens. Rotation is a **pure credential swap** (#1384): fresh EntityId/TokenId/secret, the same name and the same read-only flag, `ExpiresAtUtc` never set, `Grants` written empty. A dead source — revoked, or invalidated by a revocation generation — is refused: rotating an emergency-revoked token must not mint a live replacement that silently undoes the revoke. The replacement keeps the original `CreatedBy` and records the rotating actor in its own `RotatedBy` field, so the audit trail survives later removal of the source row.
- Rename is the only mutable field of the simplified model (`TryRenameToken`): the read-only flag is fixed at creation, and changing a token's power is what revoke + create is for. Dead records are terminal — renaming a revoked or generation-invalidated token is rejected, and a no-op rename (same sanitized name) succeeds without a rewrite.
- Revocation is immediate and idempotent — for any token visible in the index. While `IsGenerationStateHealthy` is false (e.g. after a failed boot scan, when the in-memory index is empty but the durable rows survive), per-token revoke reports false for every token; the operator's lever in that state is the emergency revoke — a generation advance, which bypasses the index and acts durably. The management layer distinguishes "unhealthy index, use emergency revoke" (false + unhealthy) from "no such token" (false + healthy) on the health flag.
- Revocation generations: every token captures the global and per-owner generation at issue. Emergency advances persist the new generation before publishing it; missing-as-zero is the fresh-install baseline, corrupt or regressed generation state makes the whole index fail closed (`IsGenerationStateHealthy = false`). A failed token-row scan at boot fails the index closed the same way — an empty scan result must mean a fresh install, never a silent outage. An owner absent from the in-memory generation cache (no loadable records, e.g. after retention removed them) has the durable value read once on the next create/rotate and cached, so a post-cleanup token never carries a generation the durable state would invalidate after restart.
- Minting fails closed: `TryCreateToken`/`TryRotateToken` return `false` — never throw — while `IsGenerationStateHealthy` is false and when a generation row is unreadable at capture time. No credential is stamped with unproven generation values, which would work only until the rows are repaired and the server restarts and then be silently invalidated forever.
- Quota counting (`CountQuotaEligibleTokens`) counts only unrevoked tokens issued at current generations — generation-invalidated tokens stop counting immediately, before any per-record reconciliation. Both generations are snapshotted once per count. `CountQuotaEligibleTokensGlobally` applies the same IsLive rule across every owner at once — the advisory affected-count an emergency revoke-all reports (computed before the advance; a token created between the count and the revoke is missed by the number while still being invalidated by the revoke itself).
- Records with a future `EntityVersion`, a foreign version byte, invalid TokenId shape, malformed verifier, an empty `EntityId`/owner, a default (unset) `Grants` array, or a **key that disagrees with the payload TokenId** are skipped at load and can never authenticate (fail closed). A key/payload mismatch is the resurrection case: lifecycle writes target `ApiToken_<payload id>` while the stale `ApiToken_<key>` row would be rescanned and re-published at every restart, silently undoing each revocation — such a row is rejected with its key logged so retention can clear it. A row whose `EntityId` duplicates an already-loaded record is skipped too: a shadowed record would make revoke-by-entity-id report success while the shadowed token keeps authenticating.
- **Pre-simplification rows fail closed at load (#1384).** The durable schema keeps the `Grants`/`Description`/`ExpiresAtUtc`/restriction fields of the fine-granted model, but they are always written empty/null now, and the loader treats a row with a **non-empty grant list, a set expiry, or a restriction stamp** as invalid: loading it as a full owner mirror would silently *widen* a deliberately narrow credential (a token minted with narrow grants would become read-write over everything its owner sees). Such rows are skipped as orphans (retention clears them); their holders re-mint under the simplified model. Nothing shipped with the fine-grained model (the last release v3.41.4 predates it), so only internal dogfood tokens are affected. Records written before the `ReadOnly` field existed deserialize it as `false` — and never load, because every such row carries grants. The only operator-visible signal for a killed row is a `LogWarning` at boot — the profile page shows nothing, and the row is unrevokable from the UI until retention clears it (acceptable for dogfood-only tokens).
- Every public manager result is a verifier-free projection (`ApiTokenInfo`): the stored verifier never crosses `IApiTokenManager`, so a management controller cannot serialize credential material through a careless response. The projection also carries no `TokenId` — it is the public half of the credential and the authentication lookup key; lifecycle and list responses expose `EntityId` only (a caller holding the credential derives it with `ApiTokenMaterial.TokenIdOf`).
- Free text is bounded and control-character-sanitized before persistence, so records cannot forge log lines: name ≤ 256, revocation reason and the actor fields (created/rotated/revoked-by) ≤ 256 chars each. An over-long name is **rejected** at create/rename time (an operator's token must not be named something other than what they typed); actor fields and revocation reasons truncate instead — a revocation must never be blocked by an over-long reason. Unpaired surrogates are replaced with U+FFFD (System.Text.Json would substitute them in the row anyway), truncation never splits a UTF-16 surrogate pair and never ends in the space of a replaced control character, and input that sanitizes to nothing normalizes to null — keeping the live entity byte-identical to the JSON row it round-trips through.
- Retention removal is `TryRemoveToken`: the durable delete and the in-memory unpublish happen under one state-lock hold, so a concurrent revoke/rotate cannot rewrite a row the removal just deleted and resurrect it after restart. A TokenId absent from the live index still gets its durable row deleted — rows rejected at load are exactly the orphans retention exists to clear (including the pre-simplification rows above). A failed durable removal (`RemoveApiToken` false — the row may still exist) unpublishes nothing. There is deliberately no unpublish-only escape hatch around this ordering.
- The full token string is returned by create/rotate exactly once and is never logged or persisted.

### HTTP surface

- **Scheme isolation.** Cookie remains `DefaultAuthenticateScheme`/`DefaultChallengeScheme`, and the `DefaultPolicy` behind bare `[Authorize]` is explicitly pinned to the cookie scheme — an API-token identity can never satisfy a legacy MVC/Razor authorization. `HsmApiToken` is never a default or forwarded scheme; it runs only from the management policy (`HsmApiTokenDefaults.ManagementPolicy`), which authenticates through `HsmApiToken` only (a cookie session alone produces no principal and challenges as a plain 401, never a login redirect) and requires exactly one authenticated identity of the HsmApiToken scheme carrying the owner/token claims — mixed or multiple identities fail closed as a denial. The policy's requirement is also the **method-shaped backstop of the read-only flag**: `HsmApiTokenOnlyAuthorizationHandler` denies unsafe HTTP methods (POST/PUT/PATCH/DELETE) for a read-only credential at the policy level, so a future mutating action that forgets the evaluator cannot hand a read-only token write access. Method-shaped on purpose — the denial is uniform across all targets and carries no per-target information, so it cannot disagree with the evaluator's 403/404 split.
- **Handler contract.** `HsmApiTokenHandler` reads only the `Authorization: Bearer` header; tokens in URLs, query, cookies, or bodies are never credentials. A non-`Bearer` header, a bearer without the `hsm_pat_` prefix, an absent header, or duplicated `Authorization` values (the joined string is not a parseable credential) is `NoResult` (another scheme's business, no token lookup); a credential claiming the prefix but failing the cheap shape check fails before any index lookup; otherwise the single decision is `IApiTokenManager.TryAuthenticate` plus the owner-existence check. Every rejection is one indistinguishable generic failure; its security event carries a TokenId only when the id is canonical (`IsValidTokenId`) — the cheap shape check passes attacker-chosen alphabets, and no unauthenticated input is persisted into the append-only store as an identifier. The principal carries exactly two claims (owner user id, public token id) — `Identity.Name` is never set to a login. On success the handler calls `MarkUsed` (coalesced, never blocks the request).
- **`/api/v1` area convention (fail-closed).** `ManagementApiGuardMiddleware` (after `UseRouting`, before authentication) serves the area only on the SitePort listener — `HsmListenerBindings` is the one immutable registry that both drives `Listen` and answers `IsSitePort`, so the guard cannot disagree with the listeners and config changes apply only on restart. Within the area an endpoint is reachable only when it matched a route, carries `[ManagementApi]`, and requires its family's authorization: the management policy outside the reserved cookie-only `/api/v1/api-tokens` family, a cookie `[Authorize]` (the default policy — without a named policy and without explicit schemes, so a scheme-bearing attribute cannot union the token scheme into the cookie policy) inside it — never anonymous (there is no fallback policy, so absence of `[Authorize]` is as anonymous as `[AllowAnonymous]`, and the guard 404s both). A failed authorization inside the reserved family answers a plain non-redirecting 401 too (`MyCookieAuthenticationEvents.RedirectToLogin` override for the area) — the whole `/api/v1` area never sees the cookie LoginPath redirect. Anything else under `/api/v1` is a plain **404 before controller execution** — a newly added route without the metadata is unreachable by default, and 404 (not 403) on SensorPort never confirms a management route exists.
- **Legacy-route bearer guard.** `LegacyBearerGuardMiddleware` rejects an `hsm_pat_` bearer sent to any non-`/api/v1` path with a generic non-redirecting 401 before MVC/Razor execution, performing **no** token lookup — the credential material is none of the legacy pipeline's business, and a `BaseController` cast can never turn it into a 500. The guard matches the version-independent `hsm_pat_` family prefix (a future `hsm_pat_v2_` credential cannot slip past it into the legacy pipeline) and inspects each duplicated `Authorization` value on its own — a `", "`-joined multi-value header would otherwise parse as its first value's scheme and hide the credential.
- **Principal-replacement skip.** `UserProcessorMiddleware` (which replaces `HttpContext.User` with the stored HSM user by `Identity.Name` on SitePort) passes a token principal through untouched. With the owner-mirror model the stored user IS the token's authority — but the middleware runs on the cookie pipeline's identity and must never touch a token principal regardless.
- **Owner-mirror evaluator (#1384).** `ApiTokenAuthorizationService` recomputes from the authoritative stores on **every** call:
  - `read allowed(resource) = ownerCurrentlySees(resource)`
  - `write allowed(resource) = ownerCurrentlySees(resource) AND ownerCanWriteAt(resource) AND !token.ReadOnly`

  Owner downgrade/deletion, role removal, resource moves, and token revocation take effect immediately — the caller re-checks token liveness through `IApiTokenManager.IsTokenLive` (the manager's sanctioned IsLive predicate), so a token revoked between authentication and authorization fails closed within the same request. Sensors resolve through their product's current boundary; the owner side mirrors the app's own checks exactly (`IsProductAvailable`/`IsManager` semantics, no folder fallback): HSM materialises folder roles into per-product `ProductsRoles` entries at grant time and at move time, so a per-product narrowing (`RemoveUserRole`/`EditUserRole`) always wins over the folder role — the token can never exceed what the owner's own session can do. Writes need the Manager role at the boundary (or IsAdmin); global resources are admin-only. Decision mapping: target absent or invisible to the owner → `NotFound` (anti-enumeration — a read-only token probing a target outside the owner's sight gets the same 404, never a confirming 403); target visible but the token is read-only or the owner cannot write there → `Forbidden`. `IsVisible(principal, resource)` (the list-filtering predicate) is the owner-sight half of the read decision minus security-event recording — the read-only flag never narrows lists, only item writes. For GLOBAL resources (alert schedules, #1352) the evaluator also owns the caller-wide gate `CanSeeAnyBoundary(principal)`: the owner is an admin or holds a role that currently **resolves** — a stale role entry pointing at a deleted product/folder counts for nothing, exactly like `TryResolveBoundary` fails closed on deleted ids — with ONE `AuthorizationDenied` (the 403 scope-denial kind — never the enumeration-probe kind) recorded per denied call. The first listing consumer (the `GET /api/v1/alertTemplates` page, #1351) memoizes the decision per distinct folder within a request.
- **Last-used coalescing.** `MarkUsed(tokenId)` records the latest observed use in memory; a background flush (30 s) writes the durable `LastUsedAtUtc` under the manager's state lock — copy, persist, publish, never mutate in place — so a flushed timestamp can never clobber a concurrent revocation, values are monotonic, and a failed write retries on the next tick. Bounded staleness is the documented trade for keeping this off the request path.
- **Security-event sink.** `ApiTokenSecurityEventSink` records authentication success/failure and authorization denial into the append-only `ApiTokenSecurityEvent_<ticks>_<eventId>` LevelDB table — separate from the entity-keyed lifecycle journal by design. The request path only enqueues (bounded channel, 1024, `FullMode.Wait` so a full queue makes `TryWrite` return false rather than silently evicting a queued event); one background writer drains to storage. Volume control: successes are sampled 1-of-16; denials are always recorded; failures are recorded within the per-source invalid-attempt budget (`ApiTokenInvalidAttemptLimiter`: up to `ApiTokens.InvalidAttemptRateLimit` events per remote IP address per aligned minute, dropped beyond it — counted and logged by the limiter, never blocking or changing the authentication decision, and never consuming another source's budget; the connection's port is not part of the budget identity; the full `ip:port` stays in the event payload as forensic context; a null/absent remote endpoint shares one `?` bucket; the per-window source registry is itself bounded at 1024 entries). The attempts themselves are never delayed or rejected. A full queue or a failed write drops the event (counted in `DroppedCount`). Authorization denials preserve the decision: invisible targets are `AuthorizationNotFound` (the enumeration-probe signal), write denials are `AuthorizationDenied`. Event payloads carry only safe identifiers (public TokenId, owner id, the access mode — the literal `read`/`write` labels since #1384 — safe target id, request correlation id, remote endpoint) — never a secret or verifier.
- **Retention + abuse bounds.** `ApiTokenRetentionCleaner` (driven hourly by `ApiTokenRetentionService`; the first pass runs at the **next whole-hour boundary after boot**) makes four bounded, idempotent, failure-isolated passes per run: (0) reconciliation of emergency-revoked rows — generation-invalidated records (no per-row `RevokedAtUtc`) are stamped through `IApiTokenManager.StampGenerationInvalidatedTokens` with `RevokedBy = "emergency"` and the pass's observation clock, bounded by the same 100-row batch limit, so a later pass can reap them; (1) dead token rows whose death stamp (`RevokedAtUtc`, and for pre-simplification rows also `ExpiresAtUtc` — the earliest of the two; nothing new can carry an expiry, the legacy half exists so those rows reap by their own old death stamp instead of waiting the orphan pass's first-observation window) is at or before `utcNow - ApiTokens.TokenRecordRetention` are removed row-by-row through `TryRemoveToken` (atomic over the durable row and the live index; a failed removal logs and stays for the next pass) — live records are never eligible, and a generation-invalidated row without a per-row `RevokedAtUtc` is not eligible until pass 0 stamps it; (2) orphan rows (rejected at load — shape failures, key/payload mismatches and the pre-simplification grant/expiry rows — listed by the manager's `GetOrphanTokenIds` registry keyed by the storage key, pruned by `TryRemoveToken`, bounded at 10 000 keys; **duplicate-EntityId rows are deliberately not orphans**: which of the two rows is the legitimate one is unknowable, and auto-deleting a possibly-newer credential row is riskier than leaking it) are removed after one window counted from the cleaner's first observation — a damaged row carries no trustworthy clock, and a restart re-observes and therefore re-waits the window; (3) security events strictly older than `utcNow - ApiTokens.SecurityEventRetention` are removed through the database's bounded chronological prefix-range delete (`RemoveApiTokenSecurityEventsBefore`, oldest first, events exactly at the cutoff survive). Batches: ≤100 token/orphan rows per pass; the event delete repeats its ≤1000-row batch **within a pass** until a batch comes back short, capped at 50 batches per pass. Storage failures are isolated per pass and per step — a failed scan/removal never wedges the sweep.
- **Credential redaction.** `ApiTokenMaterial.Redact` replaces every `hsm_pat_v1_<id>.<secret>` occurrence in free text with the public id plus a redaction marker. Redaction is applied at the **NLog sink**: every target in `nlog.config` wraps message, exception and URL text in the `${hsm-redacted}` layout renderer (`HSMServer.Logging.TokenRedactionLayoutRenderer`) — the credential is password-class material and never reaches a log.

### Personal token management UI

- **Cookie-only by construction.** `ProfileController` inherits `BaseController`'s bare `[Authorize]`, which the cookie-pinned `DefaultPolicy` answers — an API-token principal can never call token-management endpoints, and the `LegacyBearerGuardMiddleware` keeps an `hsm_pat_` bearer out of the legacy pipeline before MVC runs.
- **One JSON answer shape.** Every mutation (`CreateToken`/`RenameToken`/`RotateToken`/`RevokeToken`, all `[HttpPost]` + `[ValidateAntiForgeryToken]`, JSON in/out for the page's `fetch` calls) answers `ProfileMutationResponse { ok, error, message, token, entityId }`; `error` is a stable machine code (`disabled`, `unhealthy`, `quota`, `invalid_name`, `not_found`, `create_failed`/`rename_failed`/`rotate_failed`/`revoke_failed`, `invalid_request`), `token` is present exactly on create/rotate success.
- **Create validation.** Name 1–200 chars (trimmed, control characters neutralized before the empty-name check), the read-only flag passed through untouched, quota pre-checked for a friendly error — but the **hard quota bound is the manager's**: `TryCreateToken` enforces it inside the same `_stateLock` hold that mints, so two concurrent creates cannot both pass a caller-side pre-check and exceed the cap.
- **Rename.** The edit surface of the simplified model: a new name on a live own token; a no-op rename succeeds without a rewrite.
- **Degraded modes.** `Enabled = false` → create/rename/rotate answer `disabled` (and the page hides them), revoke keeps working (the documented cleanup path of the kill switch); `IsGenerationStateHealthy = false` → **every** lifecycle mutation answers `unhealthy` (per-token results are untrustworthy then; the operator lever is the emergency revoke), the page hides all actions and shows a warning banner; the handler additionally rejects every `hsm_pat_` bearer before any lookup while `Enabled` is off. `Enabled` is also togglable from the web UI: Settings → Server → "Enable API tokens" (immediate, no restart, in both directions).
- **Foreign ids are indistinguishable.** Rename/rotate/revoke resolve the entity id, check ownership (`OwnerUserId == current user`) and liveness (not revoked, current generations); a foreign, unknown, revoked or generation-invalidated id all answer the same `not_found` — the endpoints cannot be used to enumerate other users' tokens.
- **One-time secret.** The full credential appears exactly once, in the create/rotate response and the modal that shows it (Copy button, "shown once" warning); it is never in a list/detail payload, never logged, never persisted. The disclosure modal is deliberately non-dismissible by accident — static backdrop, Escape disabled, no header close button — so a stray keypress or background click cannot destroy the unrecoverable credential; the only exits are the explicit Copy/Close buttons, and the page reloads after the modal closes.
- **List projection.** `GET /Profile` renders metadata only: name, the access badge (Read/write or Read-only, from the token's `ReadOnly` flag), created/last-used (Unix-millisecond timestamps converted from the entity's .NET ticks), status — active / revoked / **invalidated** (an emergency-revoke generation advance happened after issuance; such rows are dead, agreeing with the quota counter that already excludes them) — newest first, dead rows dimmed with no actions. The header menu and the profile card share one deterministic avatar colour (`AvatarHelper`, hashed from the user id), as does the Users page.

### Emergency revoke

- **Surface.** `ApiTokensAdminController : BaseController` with class-level `[AuthorizeIsAdmin]` — cookie session + admin role; an API-token principal can never reach it. Three actions: `GET UserTokenSummary` (live count for the confirmation modal) and `POST RevokeUserTokens` / `POST RevokeAllTokens` (`[ValidateAntiForgeryToken]`, JSON in/out, the `EmergencyRevokeResponse { ok, error, message, correlationId, newGeneration, affectedTokens }` shape). Buttons: revoke-user as a row action on the Users page, revoke-all on Configuration → Server next to the `ApiTokens.Enabled` kill switch; both open a modal with a typed confirmation and a required reason.
- **Typed confirmation.** Revoke-user requires typing the target's exact username (trimmed, case-insensitive) and is validated server-side; revoke-all requires the literal phrase `revoke-all` (ordinal). A wrong confirmation answers `invalid_confirmation` without advancing anything.
- **Reason.** Required free text, 1–256 chars after trimming; control characters are normalized to spaces before the value reaches the audit record, and empty/control-only/over-long input answers `invalid_reason`.
- **Semantics.** Every successful call advances the target durable generation (persist-first, published to authentication before the response) — idempotent by effect, not by no-op. A valid target with zero live tokens still succeeds and still advances. An unknown `userId` answers `not_found`. An admin may emergency-revoke their own user (the cookie session is a separate channel). The affected count (computed before the advance) and the new generation are reported in the response and the audit.
- **No degraded-mode gating — the whole point.** The endpoints take no `ApiTokens.Enabled` dependency and never consult `IsGenerationStateHealthy`: cleanup during kill-switch and after storage damage is exactly what the lever exists for. The `Advance*` operations go straight to the durable counters under the manager's state lock; the only failure is a storage throw, which means the revoke did **not** happen and must surface.
- **Failure contract.** The controller catches the manager's throw and answers `{ ok: false, error: "revoke_failed", correlationId }` — retryable, with `HttpContext.TraceIdentifier` as the correlation id; the exception's text never crosses the wire.
- **Audit-of-record.** A journal record through `IJournalService`, anchored per scope (the target user's id for revoke-user, a fixed `DeploymentRevocationAnchorId` for revoke-all), carrying initiator, scope path, old/new generation, affected count, sanitized reason; best-effort **after** the advance by contract. No web-UI surface browses these records yet; the operator-visible trail today is the NLog record.
- **Reconciliation.** Generation-invalidated rows keep `RevokedAtUtc` null (the advance never touches rows), so the retention sweep stamps them (see the retention invariant above). **Stamping refuses while `IsGenerationStateHealthy` is false** — the same rule that makes minting refuse: the stamp is an irreversible durable revocation derived from the generation values, and an unhealthy state is exactly the unproven input that must not produce one. User-visible consequence of a stamp: the profile row's status flips `invalidated` → `revoked`.

## Primary Workflows

| # | Workflow | Initiator |
|---|---|---|
| 1 | Boot: rebuild authentication index from LevelDB (pre-simplification rows fail closed), load generations, mark health | server startup (`InitStorages`) |
| 2 | Create token: generate pair → persist-first insert → one-time disclosure | `ProfileController.CreateToken` (cookie flow) |
| 3 | Rename / rotate / revoke token | `ProfileController.Rename/Rotate/RevokeToken` (cookie flow) |
| 4 | Emergency revoke-all / revoke-user: advance durable generation → publish → audit | `ApiTokensAdminController.RevokeUserTokens/RevokeAllTokens` (IsAdmin cookie flow) |
| 5 | Authenticate a management request: area guard → bearer handler → principal → last-used + sampled security event | `/api/v1` client with `Authorization: Bearer hsm_pat_…` |
| 6 | Authorize a read/write on a target: owner-mirror decision, denial security event | `/api/v1` controller (per action) |

## Data Flow

```
create:  Generate() ──► TryInsertApiToken (worker lock: exists? ──► Put; grants written EMPTY, no expiry)
                          │ collision ──► new pair, retry (≤3)
                          └ persisted ──► publish to _tokensByTokenId/_tokenIdByEntityId/_tokenIdsByOwner

request: Authorization: Bearer hsm_pat_v1_…
           └─ /api/v1 path? ──► ManagementApiGuardMiddleware: SitePort? endpoint has [ManagementApi]+policy, not anonymous? ──► else 404
           └─ other path?   ──► LegacyBearerGuardMiddleware: hsm_pat_ bearer ──► generic 401, no lookup
           └─ ManagementPolicy ──► HsmApiTokenHandler: Bearer? shape? ──► TryAuthenticate (parse ──► stored-or-dummy verifier ──► IsLive ──► boot health) ──► owner exists? ──► single-identity principal ──► MarkUsed (coalesced) + sampled security event
           └─ controller ──► ApiTokenAuthorizationService.AuthorizeRead/Write(resource): resolve current boundary ──► owner sees? (else 404) ──► write? token read-only or owner not Manager (else 403) ──► allowed; denials ──► security-event sink (always)
```

## Storage / Persistence

- LevelDB `EnvironmentData`, rows keyed `ApiToken_<TokenId>` (UTF-8); JSON serialized, records with `init`-only properties, UTC-tick dates.
- Security events: `ApiTokenSecurityEvent_<ticks:d19>_<eventId>` — zero-padded ticks keep the prefix scan chronological, the event id keeps it collision-free; append-only (no update path).
- Generation state: `ApiTokenGeneration_Global` and `ApiTokenGeneration_Owner_<ownerUserId>` hold plain long values in the invariant culture; unparsable or negative values are corrupt (the counter is monotonic from 0) and fail the index closed.
- Restoring an old environment backup rolls back token rows and generation rows together, so an emergency revoke performed after the backup point is undone consistently — and therefore invisibly. After any environment restore, re-run the emergency revoke.
- The `ApiToken_` / `ApiTokenGeneration_` prefixes differ at the separator position (`'_'` vs `'G'`), so the full scan (`ReadAllApiTokens`) never picks up generation rows.
- Configuration: `ApiTokens.Enabled` (emergency kill switch, default false — upgrades opt in), `ApiTokens.MaxTokensPerUser` (10), retention windows (`TokenRecordRetention` 30d, `SecurityEventRetention` 30d) and `InvalidAttemptRateLimit` (60) — all startup-validated with key-named errors. The expiry knobs of the fine-granted model (`AllowNoExpiration`/`DefaultLifetime`/`MaxLifetime`, #1373) are gone with expiry itself.

## UI / Operator Visibility

The profile page (`/Profile`, from the header user menu) is the operator surface of this feature: a read-only card about the signed-in user plus the API tokens section — token list (metadata only: name, access badge, created, last used, status), create (name + a "Read-only" checkbox; the page states the model in one sentence: a token acts with your own rights, read-only tokens only read, tokens never expire), rename, rotate, revoke with confirmations, and the one-time secret modal. Degraded modes are visible as banners (disabled / unhealthy generations) and the quota counter "used / max" beside the Create button. The admin's emergency levers are visible as the key-icon row action on the Users page and the "Revoke all API tokens" button on Configuration → Server. Security events remain queryable through `IDatabaseCore.ReadApiTokenSecurityEvents` (ops surface later).
